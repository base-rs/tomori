# Security

This describes who may connect to the server and what each connection may do: roles, authentication, encryption, pairing and admission. It replaces the deferral of authentication in `server.md`. The long-term direction at the end is not yet required.

## Requirement

**Roles.** At any moment a connection has exactly one role, which decides what it may do:

- **Owner**: everything a collaborator can do, and also creating spaces, listing an agent's existing sessions, giving or changing a space's own instructions to its agent (see `spaces.md`), changing a space's environment (see `environments.md`), and deleting the space they are in, and its agent session with it (see `spaces.md`). An owner is an owner on the whole server.
- **Collaborator**: joining and leaving spaces, push-to-talk to the agent, live voice, presence, deciding approvals, answering questions, cancelling queued input, changing the session's mode (see `agent-backends.md`), setting attribution and the space's speech setting, reporting engagement, and hearing replies again (see `speech.md`). A collaborator is a collaborator only in the spaces they were admitted to (see knocking, below); in the lobby and in any other space, they are a visitor.
- **Pairing**: only pairing (below). A connection is admitted to pair, and nothing else, on a server that refuses visitors.
- **Visitor**: listing spaces, joining a space to watch it, leaving it, pairing, knocking and changing their own display name (see display names, below). A visitor receives what a participant receives in that space: its state, including the instructions its agent is given, presence, agent speech and participants' audio. A visitor sends no audio and no presence, including engagement, which the server ignores from a visitor rather than refusing, as a client may report it before it learns its role; a visitor hears agent speech live, is never played a catch-up, and cannot ask to hear a reply again. A visitor admitted to take part without joining again, as by knocking, joins the space's kept speech as having heard everything said while they watched. A visitor appears neither in a space's participants nor in a space's or the server's participant count. No reduced view is required for visitors yet.

Owners and collaborators in a space are its participants (see `spaces.md`); visitors are not. The server checks every client message against the connection's current role in one place before acting on it, and refuses a message the role does not permit with a short error that has no effect. It never branches on hardware (see `clients.md`). The server tells a client its role when it says Hello and whenever the role changes, such as on joining or leaving a space or on being admitted. Only an owner's `Welcome` lists the workspace roots and backends, since only owners create spaces. A client hides the actions its role does not permit, and reads a role it does not know as unknown, permitting nothing beyond a visitor's actions. The spectator client is a client like any other: it watches as a visitor, or connects with a token where visitors are refused.

**Modes.** What a connection without credentials becomes is the server's mode:

- By default it is a visitor. Credentials are needed only to do more than watch.
- With `tomori-server --no-visitors` it is refused, unless it asks to pair, with the request field `Tomori-Pairing: 1`; it is then admitted only to pair.
- With `tomori-server --auth open` it is an owner, as before authentication existed. The server then accepts no credentials, and prints and logs at startup that anyone who can reach it can create spaces and approve tool use. `--auth open` cannot be combined with `--no-visitors`.

At most 64 visitors are connected at once by default, configurable with `tomori-server --max-visitors COUNT`, so that visitors cannot take every one of the server's connection slots from participants. A visitor beyond the limit is refused with HTTP 503 before the connection reaches the hub.

**Authentication at the door.** Credentials are carried on the HTTP request that opens a connection (`POST /connect`), as an `Authorization: Bearer` header or a cookie, and are checked before the connection reaches the hub. No client presents credentials in a protocol message; the reserved `credentials` field of Hello is removed. The server issues a token in one, over TLS, when pairing or knocking admits a device. A connection that presents a credential the server does not accept, whether unknown, revoked or malformed, is refused with HTTP 401 and the same short reply in every case, never silently downgraded to a visitor; the reason is logged on the server. The client then forgets that credential, connects again without it, and shows that it is no longer admitted.

**The security crate.** Authenticators, the token store, pairing and the server's certificate live in their own workspace crate, `crates/security`. It depends on neither the server nor any client crate, so the server and clients share it, as clients derive the pairing code too. The server's hub and connection handling stay in the server crate.

**Pluggable authenticators.** Authentication is performed by a chain of authenticators in the security crate. Each inspects the request head and reports a principal, an opaque identifier namespaced by the authenticator that verified it, or passes to the next, or refuses. Authenticators report who a connection is, never what it may do: the server keeps roles against principal identifiers, so adding an authenticator changes no role check. The first authenticator is `token`, below.

**Tokens.** The `token` authenticator accepts random bearer tokens of at least 256 bits that the server issued. The server stores only a hash of each token, with the principal it identifies and the role it grants, together with the space for a collaborator, in a file readable only by the server's user; tokens survive a server restart. The token store and the server's certificate are kept in the server's state directory, `$XDG_STATE_HOME/tomori` or `~/.local/state/tomori` by default, configurable with `tomori-server --state-directory PATH`. `tomori-server auth mint --owner --name NAME` issues an owner token and prints it once; it is how the first owner is made before any device has paired, and remains a way to recover when no owner device is left. `tomori-server auth list` lists the issued tokens by name, role and space without revealing them, `tomori-server auth rename ID NAME` renames one, and `tomori-server auth revoke` revokes one. These commands act on the state directory, so they need the server's user on the server's machine, and a running server applies them within a few seconds. A revoked token is refused from then on, and every connection that presented it, or was admitted with it, is ended.

A client is given a token with `--token TOKEN` on the desktop, or the intent extra `tomori.token` on the headset. It presents it only to the server given at startup (`--server`, `tomori.server`) or over the USB connection, never to a discovered server, whose advertisement anyone on the network could make, and stores it for that server, with that server's certificate, as it stores a token from pairing or knocking.

**Display names.** A participant's display name belongs to their identity on the server, not to their device. A token holder's is the name of their token, kept with it in the token store, so it survives reconnecting, reinstalling and a server restart, and is the same on every device that presents the token. The server uses it for attribution in prompts (see `spaces.md`), in a space's participants, in knocks and on the status page, whatever name a device suggests in Hello. A token is first named by what issued it: the device's suggested name when it pairs, the visitor's when a knock admits them, and `--name` when minted. A token issued before names could change keeps its name, such as "Quest 3", and one without a name the server would show takes the name its device next suggests. A connection without a token, a visitor's or anyone's in `--auth open` mode, is called by the name its client suggests, kept only while the server keeps the participant (see `spaces.md`) and never written down. Every name follows the same rules, applied by the server wherever it accepts or keeps one: in Hello, in a rename, for a minted or renamed token and for the name kept with a token (`tomori_protocol::text`, which clients use too, so that they suggest and check names as the server does). A name is cleaned first: into Unicode's composed form (NFC), with control characters and every kind of line break or other space, such as CR, LF, NEL, U+2028 and U+2029, made spaces, format characters, such as bidirectional overrides and isolates, zero-width characters, the byte order mark and tags, removed, since they reorder or hide text, and each run of spaces made one, with none at either end. Then one is required, it does not start with `/`, it contains no `:`, `[` or `]`, and it is at most 32 characters and 64 bytes. So a name is on one line, ends at the first colon in `Name: words`, and can pass neither for another speaker's line nor for a context block such as `[Pointing at …]` in what the agent reads, and `/clear` hidden behind an invisible character is still refused. A device's suggestion in Hello over 64 bytes is refused, as clients cut it to that, but one over 32 characters is cut rather than refused, since nobody chose it to fit. A name kept with a token that the rules refuse, such as one written before they were tightened, is not shown: the token takes the name its device next suggests, as one without a name does.

The server says in `Welcome` the name it knows the participant by. A client offers renaming only to a server whose `Welcome` gives a name; an older server takes the name Hello gives, as before. Each participant renames only themselves, with `set_name`, or by saying the name with push-to-talk marked as naming, whose transcript, without a closing full stop, is the name rather than input to queue (see `hand-menu.md`). A token holder's rename applies to their token, so to every device using it, and is written to the token store before it takes effect: one that cannot be written changes nothing, and says why. A visitor's renames only them, and the server does not keep it; their client suggests it again whenever it connects to that server for the rest of its run, so it survives reconnecting, though not restarting the app. A participant cannot choose a name someone else has: one that, cleaned and with its case folded, is the name of anyone else in the space they are in, visitors included, or of a token other than theirs, is refused, saying "That name is taken", and a token holder's is checked against the other tokens again as it is written, under the store's lock, so that two renames cannot both take it. Their own other devices, holding their token, and people in other spaces do not count, and nor does a change of case to their own name. Names that only look alike, such as with a Cyrillic letter, are not detected yet. A name a device suggests, or a token is issued with, is not compared. Everyone in a space a renamed participant is in sees the new name, as do the participants of a space they are knocking on; their input already queued keeps the name it was spoken under. The server sends `Name` to each of the renamed participant's connections whose Hello said, with `names`, that it reads it, since an older client would refuse a message it does not know. An owner renames others only on the server's machine, with `tomori-server auth rename`, which a running server applies within a few seconds, as it does a revocation, telling everyone holding the token. Pairing issues a new token, so a second device a person pairs is a new identity with a name of its own, which they can change to match; a device given an existing token with `--token` or `tomori.token` shares that token's name. A visitor's name, and everyone's in `--auth open` mode, is unverified: no token vouches for it. Visitors take part in no space, so their name appears only on their knock, where clients mark it as a visitor's, as in "Let Ada (visitor) in", in the hand menu, the desktop window's title and the console, the mark kept whole however the name is cut; it never reaches the agent, since visitors cannot address it. These are additions that older clients and servers ignore, so the protocol version does not change.

**Web pages.** The server serves a few web pages on its port, over TLS like everything else, written as plain HTML by the server, without scripts or a web framework. A sign-in page takes a token and stores it in a cookie that is `Secure`, `HttpOnly` and `SameSite=Strict`; signing out clears it. A status page, shown only to owners, lists the spaces, the participants in each with their roles, how many visitors are watching, pending pairings with their codes, what spaces' agents recently did with pairings, and the issued tokens, and lets an owner confirm or decline a pairing and revoke a token. Every action that changes something is a form `POST`. Anyone else asking for the status page is sent to sign in, or told that it is for owners. Browsers warn about the self-signed certificate the first time; that is accepted. In `--auth open` mode, everyone is an owner, so the status page is shown to anyone.

**Encryption.** Whenever it accepts credentials, the server serves only TLS, and a TLS handshake that has not completed counts against the request timeout (`server.md`). It uses a self-signed certificate that persists across restarts, and advertises its SHA-256 fingerprint in its Bonjour TXT record. A client remembers a server's certificate the first time it connects, or when it pairs. It never sends a credential to that server over plain HTTP or over a connection presenting a different certificate; it connects as a visitor instead, and shows that the server's identity has changed. In `--auth open` mode, plain HTTP remains allowed.

**Participant identity.** The identity a client says in Hello is a secret of that device. The server never sends a client's identity to another client: shared state, including space participants and queue entries, names participants by a public handle the server assigns, which stays the same for as long as the server keeps that participant (see `spaces.md`). A client learns its own handle in `Welcome`. The server keeps an authenticated participant under its principal and identity together, so the same identity on a connection without that principal is a different participant and cannot take over the first one's connection, space or audio source.

**Pairing.** A device becomes an owner by pairing. Pairing runs over TLS and derives a 6-digit code from three things: the server certificate's fingerprint, as each side sees it, a random value from the device and a random value from the server. The device first sends only a commitment to its value, a hash of it. The server then sends its value, and only then does the device reveal its own. So neither side, nor anyone relaying between them, can choose a value after seeing the other's, and a relay presenting a different certificate shows the two ends different codes, except by a one-in-a-million chance. The device shows the code in the world, on the pairing object beside the connected server (see `arrival.md`), and the server shows it only on the status page, to owners. The server never writes a pairing's code, nor any digit of it, nor either side's value, to its log, at any level, or its console, nor in an error or panic message, and its debugging output of a pairing, a pending pairing's view and a confirmation leaves them out. Instead, the console says that a pairing request began from the named device, at what time, in UTC as the log gives times, when it is withdrawn unless confirmed, and how to confirm it: type the 6-digit code the device shows, or "decline". The log says that the pairing waits to be confirmed with the code its device shows, and the console and the log tell, without codes, that a pairing began, was paused, confirmed, declined, withdrawn or given a code that did not match. The operator confirms on the console by typing the code the device shows, with or without its space, which the server checks: it confirms only if it matches, and six other digits decline the pairing, telling the device, so that a code typed there has one try for each pairing, as one given to the agent does; text that is not six digits changes nothing. An owner confirms or declines on the status page, comparing the two codes. The pairing completes only once one of them confirms. So a visitor, or anyone who can reach the server, can only begin a pairing, which always needs an owner's confirmation on the status page, or the operator's on the console with the matching code, and a space's agent can confirm one only with a code a person supplies (see pairing through the agent, below), since nothing it reads through Tomori holds the code. The device then receives an owner token, stores it for that server with the certificate the pairing connection presented, replacing a certificate it distrusted, and connects with it silently from then on. Pairing is offered on any connection over TLS that is not an owner's; a server in `--auth open` mode, where everyone is an owner, does not pair. At most one pairing is pending at a time; another request while one is pending is refused, including from the same connection, which cannot begin again to get another value from the server. At most 3 pairings begin in any 10 minutes, and the console shows each one as it begins, so that a relay cannot keep trying values until the two codes happen to match: each try has a one-in-a-million chance. When pairing is paused this way, such as by someone using up the attempts, the operator on the console or an owner on the status page can allow it again. The device gives up on a pairing that is not confirmed within the server's timeout, and cancels it, so each time the participant starts pairing gives a relay at most one try. A device that does not reveal its value within 10 seconds of the server's, or a pairing not confirmed within 2 minutes, or whose device disconnects, is withdrawn, and the device is told. A pending pairing, revealed or not, is shown on the console and the status page, where it can be declined. Confirming or declining on the status page names the code shown, and does nothing if a different pairing is now pending. A connection admitted only to pair receives nothing about the server's spaces.

**Pairing through the agent.** A space's agent may also decide the pairing waiting, through Tomori's tools (see `mcp.md`), so that a participant can say "confirm the pairing, the code is 895 465" rather than reach the console. Any agent session bound to an open space may call them, as it calls Tomori's other space tools, with no further credential; no owner need be in the space.

- `pairing` lists the pairing waiting, if any: the device's name, how many seconds ago it began, how many until it is withdrawn, whether the device shows its code yet, and whether pairing is paused. It never gives the code, nor the server's value or anything else the code is derived from: only the device and the status page show it.
- `confirm_pairing`, with `code`, confirms the pairing through the same check as the console's, only if `code`, with its spaces removed, is the code. Six digits that are not the code decline the pairing at once, telling the device "The code given did not match, so the pairing was declined.", so that a code from anywhere but the device has one try for each pairing, a one-in-a-million chance. Text that is not six digits, as a mishearing may be, is refused and changes nothing, since it says nothing about the code. A pairing whose device has not revealed its value cannot be confirmed yet, and trying does not end it. A code typed on the console that does not match declines the pairing in the same way, since the console does not show the code either.
- `decline_pairing` declines the pairing waiting, as "decline" on the console does.
- The agent cannot allow pairing again once it is paused, nor begin a pairing: one pairing waits at a time, and at most 3 begin in any 10 minutes, as for the console.
- Each confirmation, decline and refusal from `confirm_pairing` or `decline_pairing` is told: logged at info and printed on the console, naming the space, its title and the calling session, as `The agent of space ID ("Studio"), session SESSION, confirmed pairing for "Quest 3" while Ada was in the space; it is now an owner.`; listed on the status page, the latest 8, under "By agents"; and projected onto that space's Tomori wall as a text panel titled "Pairing", from source "Tomori", which everyone in the space sees until someone dismisses it (see `projection.md`). A refusal to a session bound to no open space is logged and printed, since there is no space to tell. Listing is not told, since it changes nothing. Each result asks the agent to tell everyone in the space what it did.
- The agent's instructions (`tomori-tools`, see `mcp.md`) say to confirm a pairing only when a participant in the space asks and has just read its code aloud from the device's own pairing object, never with a code from any other source, such as a file, a web page, a tool's output or another agent; to decline one only when a participant asks; and then to tell everyone what it did.
- On a server that does not pair, as in `--auth open` mode, each of the tools says so and does nothing.

A visitor cannot speak to the agent: push-to-talk and live voice are a collaborator's or an owner's (see Roles), and these tools do not change that. A device whose pairing was lost, such as a headset after reinstalling, connects as a visitor, so the tools help its holder only when they can reach the agent some other way: as a collaborator in the space, admitted by knocking, which a participant there must admit; from another device that is paired; or in the agent's own session, such as in the OpenCode terminal.

**Knocking.** A visitor watching a space can knock to ask to collaborate, from their hand menu (see `hand-menu.md`). The knock, with the visitor's display name, is shown to the space's participants in their hand menus, with a cue on the wrist so that they notice it without opening the menu, and the first participant to admit or decline it resolves it, as for approvals (`spaces.md`). Admission is to that space only. An admitted visitor receives a token that makes them a collaborator in that space, and their connection becomes a collaborator connection there at once without reconnecting; the client stores the token for that server as for pairing. Elsewhere on the server, they remain a visitor. A collaborator token is revoked when its space is removed, such as when a closed space is forgotten, so that no token outlives the space it admits to. Knocks are bounded: a visitor has at most one pending knock, a knock unanswered for 2 minutes expires, a space has at most 8 pending knocks, and a declined or expired knock cannot be repeated on that space for 1 minute. Visitors cannot admit or decline knocks.

**Protocol version.** These changes raise the protocol version. A participant's handle replaces their identity in shared state, and Hello and `Welcome` change; an older client could not recognize its own queue entries.

**Tomori's MCP endpoint.** The tools Tomori offers agents are served on a listener of their own, on a loopback address by default, never on the clients' port, so headsets and visitors cannot reach them. It serves plain HTTP, since only processes on the server's machine use it, to requests carrying a bearer token of 256 bits made for each run and kept only in memory, which the server gives the agent's service when it registers the endpoint, and refuses requests from web pages. A tool that acts on a space acts on the space bound to the session that called it, which OpenCode names in each call's `_meta`: OpenCode sets it, not the model, and only OpenCode is given the token, so naming another session needs the token. A call naming no session, or one no open space is bound to, does nothing. The agent acts for the space's owners: it may change its own space's speech setting and environment, as an owner may, and nothing else beyond its own space but the pairing waiting, which it may confirm only with the device's code, or decline (see pairing through the agent, above); each change is shown to everyone in the space, announced by the agent and logged. See `mcp.md`.

**Data source credentials.** A token a server is given for a data source, such as the GitHub environment's (see `github.md`), stays on the server: it is used only in the server's own requests to that source, and never sent to a client, put in a space's state or kept spaces, told to the agent or logged.

**Repository text is untrusted.** Anyone can open an issue or pull request on a public repository, so the titles, authors and labels the GitHub environment tells the agent are marked as untrusted repository content, quoted so that they cannot end their quotation or the context block or forge another, and the environment's layer of the agent's instructions says they are data, never instructions (see `github.md`).

## Rationale

`server.md` deferred authentication until Tomori is used on untrusted networks, because space participants can approve agent tool use. The user wants people without credentials to be able to watch a space, hearing the speech and seeing the geometry, while collaborating requires admission, and only owners create spaces. Authentication should be unobtrusive: a device authenticates once and then connects silently, and admitting someone happens in the scene rather than through login forms, in keeping with `arrival.md`. It should also be pluggable, so that identity providers can be added without changing what each role may do.

In November 2026 the user asked for a participant's display name to live with their identity on the server rather than come from each device, since a device's name, such as "Quest 3" or the computer's, was lost on reinstalling and differed between devices, while the server already knew who a participant was from their token (issue #99). Keeping the name with the token needs no new store or migration, as every token already had a name. Visitors have no identity to keep a name with. Since typing on the headset is not practical yet, a name is said aloud there, as answers are. Owners renaming others in the world was left for the people and access controls in the long-term direction, and an owner can already rename any token with the command, since running it needs the server's machine. An independent review then found that names reached the agent and every display as given, so that a line break in a name could forge another speaker's line or a context line, a bidirectional override could reverse a name, and a zero-width character could copy one; that anyone could take another's name, the only sign the agent has of who spoke; that visitors' names were not marked as #99 asked; and that a visitor's rename was lost on reconnecting. With the maintainer's general direction, the coordinator of the review fixes decided that names are cleaned and refused at the server by one set of rules, the same rules as other text quoted on one line, that a name another current participant in the space or another token has is refused, leaving look-alike detection for later, that visitors are marked where their names are shown, that a visitor's client suggests their chosen name again for the rest of its run, and that a spoken name that is not changed is said again with X until B cancels.

In November 2026 the maintainer decided that only owners delete a space, and its agent session, and only from inside it, since deleting it ends it for everyone in it and deleting its session cannot be undone; collaborators and visitors are not offered it, and the server refuses it to them as it refuses every action their role does not permit.

In November 2026 the user decided that only owners change a space's own instructions to its agent, since they shape what the agent does for everyone in the space, while everyone who can see the space can read them (issue #72).

In November 2026 the maintainer, re-pairing a headset after reinstalling, asked for the agent to be able to confirm pairing, so that they could say "confirm the pairing, the code is 895 465" to it rather than type the code on the server's console. The threat considered is prompt injection: the agent reads text that others write, such as files, web pages, repository text, tool output, other agents' words and a pairing device's own name, and an injection could tell it to confirm a pairing with a code an attacker chose. An attacker who begins pairing from a device of their own knows that pairing's code, so making the agent confirm it would give them an owner token. The mitigations are these. Tomori never tells the agent the code, so an injection must bring it, and only someone who began the pairing, or can see the device or the status page, knows it. Confirming needs the exact code, and a wrong one declines the pairing, so that guessing gets one try in a million for each pairing, and only 3 begin in 10 minutes, a limit the agent cannot lift. One pairing waits at a time, so an attacker's pairing must be the one waiting, and a participant's own device asking to pair meanwhile is refused, which shows that something else is pairing. Every decision is told on the console, the status page and the space's wall, so that a confirmation nobody asked for is seen at once and its token can be revoked. And the agent's instructions say to confirm only a code a participant has just read aloud from the device's own pairing object, never one from any other source. What remains is an attacker on a network that reaches the server, who begins pairing and puts their own device's code before an agent that follows it while their pairing waits: the instructions and the agent's judgment are then the only barrier, and visibility makes the result seen and revocable rather than impossible. The server's log and console held each pairing's code when these tools were added, which the next paragraph ended; an agent that can write the server's state directory, such as through a shell as the server's user, still needs no pairing at all, so these tools keep pairing from an agent only where its other tools cannot already reach the server's state. Declining on any wrong six digits, rather than after a few attempts, was chosen as the safest rule: a participant who misreads the code begins pairing again, at the cost of one of the 3 attempts, while text that is not six digits costs nothing. Requiring an owner to be in the space, so that an unattended agent could not confirm, was considered and rejected by the maintainer, since the case this exists for is a maintainer whose only headset has just lost its pairing, so that no owner may be present at all. A notice in the space needed no new protocol message: a text panel on the Tomori wall is seen by everyone in the space, participants and visitors alike, on every client that shows projection, and stays until dismissed. Visitors still cannot send input; making a lost device's holder able to speak to the agent was left out of this change.

In November 2026, after the review of #219 found that the server logged each pairing code where a local agent could read it, the maintainer chose to stop logging codes. On the maintainer's machine, the server's console output is its log file, so any agent with a shell could read the code and confirm the pairing, whether asked to or by an injection, which needs no one to bring it the code. The server now writes no code to its log or console, but says that a pairing began, from which device, when and until when, and how to confirm it. Logging the code's first digit was considered and rejected: the operator does not need the server's code to confirm, since they type the code the device shows and the server checks it, and each digit written would cut a guesser's search tenfold. With the code no longer shown on the console, a wrong code typed there declines the pairing, as one given to the agent does, since whatever can type on the console, such as a process writing to the pipe it reads, could otherwise try every code within a pairing's 2 minutes; a misread code then costs the operator one of the 3 attempts in 10 minutes. The status page still shows the code to owners for comparison, since it is shown only to a request with an owner's token and never cached (`Cache-Control: no-store`). What remains is that the console and the log name the device as it named itself, so a device that puts a code in its name, such as its own, puts it where a local agent can read it; as for any injected code, the agent's instructions and the telling of every decision are then the barrier.

Checking credentials on the HTTP request means a refused or unauthenticated client never receives a participant record with privileges, or the workspace roots, and works with reverse proxies that set headers or cookies. Refusing an invalid credential rather than downgrading it lets a device learn that it was revoked. Bearer tokens are only safe encrypted, so accepting them requires TLS. Pairing by comparing a code shown on both ends needs no keyboard on the headset and also proves to the device that it reached the intended server; the commitment, as in Bluetooth numeric comparison, stops a relay from searching for values that make the codes match. The participant identity was sent to every client in a space, which let anyone in it reconnect as another participant and take over their connection; with visitors receiving the same state without credentials, that had to stop. The limits on visitors and knocks keep the server's resources bounded, as `server.md` requires of everything a client can cause. Agreed with the user in the November 2026 authentication discussion. The user then decided that visitors send no presence for now, that admitting a knock admits to that space only, and accepted the default limits. They chose a minted owner token as the way to make the first owner, so that owners exist before pairing does and remain recoverable; running the command needs the same access to the server's machine as confirming a pairing on its console. They chose web pages on the server's own port, signed in with a token over TLS, for login and for showing the server's state, kept to plain HTML because `base-rs` has no web framework yet, and the hand menu as the place for people and security in the world.

## Scope

The server's HTTP handling of `/connect` and its web pages, its MCP endpoint's authentication and how a tool call is scoped to the calling session's space (see `mcp.md`), the pairing tools a space's agent may use (`hub/agent_pairing.rs`), its role checks, token store, display names, state directory and command-line options; `crates/security`; the protocol's Hello, `Welcome`, role, knock, participant handle and display name; the Bonjour TXT record; and how clients store credentials, pin certificates, pair and knock.

## Validation

- Test each role against every client message: each permitted message takes effect and every other message is refused with no effect. A visitor's audio frames are neither relayed nor transcribed, a visitor's presence is not relayed, and a visitor's engagement is ignored.
- Test that a visitor joining a space receives its state, presence, agent speech and participants' audio, that it appears neither in the space's participants nor in any participant count, and that it is told its role. Test that only an owner's `Welcome` lists roots and backends.
- Test the modes: without credentials a connection is a visitor by default, is refused with `--no-visitors` and is an owner with `--auth open`, which prints its warning. Test that `--auth open --no-visitors` is refused, and that visitors beyond `--max-visitors` are refused with 503 without reaching the hub.
- Test that an unknown, revoked and malformed credential each receive the same 401 reply without reaching the hub, and that a client then forgets the credential and reconnects as a visitor.
- Inspect the security crate's dependencies: it depends on neither the server nor any client crate. Check that role decisions are made only in the server against principal identifiers. Inspect the protocol: no message carries credentials.
- Test that the token store holds no token in the clear and survives a restart, that a minted owner token is printed once and admits its holder as an owner, that `auth list` reveals no token, and that revoking a token refuses it and ends both a connection that presented it and one admitted with it, including when it is revoked by the command while the server runs.
- Test that a client given a token with `--token` or `tomori.token` connects with it to the server given at startup or over USB, stores it for that server, and does not present it to a discovered server.
- Test the web pages: signing in with a token sets a `Secure`, `HttpOnly`, `SameSite=Strict` cookie; the status page is shown to an owner and to nobody else; it lists spaces, participants, visitor counts, pending pairings and tokens without revealing any token; and confirming a pairing or revoking a token works only by `POST` from an owner.
- Test that a server accepting credentials serves only TLS, that a stalled handshake is closed after the request timeout, and that its fingerprint is in its TXT record. Test that a client sends no credential to a remembered server over plain HTTP or over a different certificate.
- Test that no client's identity appears in any message sent to another client, that a participant's handle survives their reconnecting, and that a Hello repeating an authenticated participant's identity without their credential neither supersedes their connection nor joins their space.
- Test pairing: the codes match through a direct connection, and with a relay holding a different certificate they differ, whatever values the relay chooses. A revealed value that does not match its commitment fails the pairing. Nothing is issued until the operator types the matching code, with or without its space, or an owner on the status page confirms; a wrong code typed declines the pairing, telling the device, after which the right code is no use; text that is not six digits changes nothing; and declining tells the device. Through beginning, waiting, a wrong code, confirming, declining, being withdrawn, expiring and pausing, the log, recorded at every level, and what the console is told hold neither the code, together or with spaces or dashes between its digits, nor either side's value, and the console says when the pairing began, when it is withdrawn and how to confirm it; a pending pairing's view, a confirmation and a device's pairing are debugged without the code or the device's value. A second request while one is pending is refused, including from the same connection; a fourth pairing within 10 minutes is refused; a pending pairing is withdrawn when its device does not reveal within 10 seconds, after 2 minutes, or when its device disconnects; and the status page confirms only the pairing whose code it showed. Afterwards the device connects with its token without further steps, including to a server whose certificate it had distrusted. On a server with `--no-visitors`, a device asking to pair is admitted only to pair, and receives no space listing. Pairing is refused on a connection without TLS.
- Test pairing through the agent: `pairing` lists the pairing waiting, before and after its device reveals its value, with its device, ages and whether it is paused, and its result contains neither the code, in either form, nor the server's value; confirming with the code read from the device, in two groups, pairs the device as an owner; six wrong digits decline the pairing and tell the device, and the right code is no use afterwards; text that is not six digits, and a confirmation before the device reveals, leave the pairing waiting; declining tells the device; with nothing waiting, confirming and declining say so; a call naming no session, or a session bound to no open space, is refused and logged; a session bound to a space confirms with nobody in it; a space deleted while a pairing waits leaves it waiting, its session refused, and another space's session decides the server's one pairing, after which neither has one to decide; after 3 pairings in 10 minutes another is refused, `pairing` says it is paused, and no tool allows it again; each decision and refusal is logged and printed with the space and session, listed on the status page and projected on the space's Tomori wall; a token that cannot be issued is said; and on a server in `--auth open` mode every tool says it does not pair.
- Test knocking: the first decision resolves a knock; an admitted visitor becomes a collaborator on the same connection and is told so; the pending, expiry, per-space and repeat limits hold; a visitor cannot decide a knock; and a space's collaborator tokens are revoked when the space is removed.
- Test display names: a token holder is called by their token's name, not the one their device suggests, after reconnecting, after a server restart with the same state directory and on a second device presenting the same token; a rename from either device is kept in the token store and renames both, is seen by everyone in their space and is used for attribution of their next words; renaming to the same name tells nobody; a rename that cannot be written, or whose token was revoked, changes nothing and says so; a spoken name renames without being queued, with its full stop removed, and one the rules refuse fails as the utterance; a token store written before renaming loads with its names; a token without a usable name takes its device's suggestion; `auth rename` renames a token, refusing a name the rules refuse, and a running server applies it to its participants' connections; a visitor's rename changes their knock and nothing in the token store, a token their knock earns takes the name, and a rename on the same connection once admitted is kept with that token; `Name` is sent only to a client that said `names`, and `set_name` is refused only to a connection admitted only to pair. Test the rules with hostile names: line breaks of every kind, bidirectional overrides and isolates, zero-width and other format characters and tags are cleaned away before a name is kept, shown or attributed, so that the agent reads one line; a name with `:`, `[` or `]`, or `/` behind an invisible character, is refused; names are bounded in characters and bytes, and a device's long suggestion is cut. Test that a name kept with a token that the rules refuse is replaced by the device's suggestion without telling it its name again; that a name someone else in the space has, or another token has, in another case or with invisible characters, is refused, by `set_name`, spoken and with `auth rename`, also when another process renamed the other token meanwhile, while someone in another space, the participant's own other device and a change of case do not count; that a running server applies an `auth rename` made in another process within a sweep, telling the holder and showing everyone; that a client suggests the name the server last gave it when it connects again; and that knocks mark their visitor.
- Test that an admitted collaborator is a visitor in the lobby and in another space, is told of each change of role, and is a collaborator again on returning to the space they were admitted to, including after reconnecting with their token.

Long-term direction, not yet requirements:

- People and access in the hand menu (see `hand-menu.md`). Participants can see how many visitors are watching a space. An owner can remove a visitor, promote a participant or visitor to collaborator and demote them, change other access, and confirm a pending pairing in the world as well as on the console and status page.
- Linking a newly paired device to an identity that already exists, such as by an owner choosing on the status page whose device it is, so that a person's devices share one name and admission. Pairing then issues a token for an existing principal, which needs principals kept apart from tokens, as the store keeps them one to one now.
- Invitations: an owner creates a link or code that grants a role, with a limited number of uses and an expiry.
- Further authenticators, such as one that trusts an identity header from a reverse proxy or Tailscale at configured addresses, and OAuth or OpenID Connect sign-in: through the web pages for browsers, and through the device flow for headsets, where the hand menu shows a code and an address to approve on a phone. Each ends in a token the server issues.
- A reduced view for visitors, if visitors arrive from outside a trusted network.
- Refusing names that only look like another's, such as by Unicode's confusable skeletons, and a limit on how often a participant renames.
