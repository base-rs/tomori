# Environments

This describes how a space's environment relates to the space. The first part is a current requirement; the rest is long-term direction, and the initial design must not prevent it.

## Requirement

Each space is bound to exactly one environment at a time. The environment is chosen when the space is created, is part of the space's shared state, and is the same for everyone in it, participants and visitors alike. A participant does not switch a space's environment on their own device; the per-device environment choice, such as squeezing the grip to switch between Sky and Minimal, does not apply inside a space.

**Changing it.** An owner may change a space's environment after it is created, to another the server offers, from the hand menu's Space section (see `hand-menu.md`), with `set_environment`. The change applies to the whole space at once: the server checks that the requester is an owner and that it offers the environment to the requester's client (see below), keeps the new environment in the space's record, so that a restart keeps it (see `spaces.md`), and sends the space's state to everyone in it, participants and visitors alike, who switch to it, the new scenery growing out of the space as it does on joining, or, if their client cannot present it, the grid with a warning saying what it lacks. Someone joining later arrives in it, and the lobby lists the space in it. A collaborator or visitor is refused, and their menu does not offer the change; an environment the server does not offer that client is refused, naming those it does; and a closed space keeps the environment it had. The conversation, queue, workers and settings are unaffected, except that the agent is given its instructions again, since the environment's layer changes with it. A server says in the space state that it changes environments, and a client offers the change only to such a server, so older servers and clients work as before; an older client sees the new environment only when it next joins. The server offers the environments a space can use, as it offers backends and directories: those its program registers (see Registering environments, below). Tomori's own server, `tomori-server`, offers Sky (`crates/environment-sky`), first, so that it is the default for a space whose creator names none, the Minimal grid, labelled Grid, and the farmyard (`crates/environment-farmyard`, see `farmyard.md`); and, only when it is started with `--github-repository`, the GitHub environment's prototype, whose spaces show a repository's open issues and pull requests as cards (see `github.md`). A server another project builds offers those it registers through `tomori-server`'s builder, in the order it registers them, a later one with the same identifier in place of the earlier, by the same rule as an option that changes one on the configured server with `Server::with_environment` (see `builders.md`). A space kept across a restart in an environment the server no longer offers stays in it. A client that cannot present a space's environment shows the Minimal grid and says which environment, and which version, it lacks, rather than substituting another environment silently (see below).

**Agreeing on the environment.** Client and server agree on each environment through its protocol version, an integer, 1 unless the environment is registered with another (see `builders.md`). A change to what the server and a client side exchange that an older client side can ignore, such as a new optional field with a default or a new variant read as unknown, keeps the version; any other change raises it.

**Registering environments.** The core, the framework crates that the server and clients are built from, knows no environment but the Minimal grid, which every client draws built in, as its waiting area and its fallback, at the identifier and version in `tomori-protocol`, `GRID` and `GRID_VERSION`. Every other environment, Tomori's own included, is registered by an application, Tomori's own programs or another project's, through the same builder calls: `tomori-server`'s builder and `tomori-client-quest`'s start with no environments and register nothing by default. Tomori's own server program, `tomori-server` in the `tomori-server-app` package, registers Sky, the grid and the farmyard, and the GitHub prototype's `--github-repository` option from its server crate; Tomori's own app, the `tomori` executable and APK, behind `tomori-client-quest`'s default `app` feature, and Tomori's own spectator, `tomori-spectator`, behind `tomori-client-spectator`'s, register Sky's, the farmyard's and the GitHub prototype's client halves. The core keeps what an environment's crates build on: the server's card board, which the GitHub prototype's server half fills through a `CardSource` and offers with `Server::with_cards`, and the scene's cards, which a client presents over the grid for any environment whose spaces show them, as the protocol's card messages do, until the state channel (below) replaces them. So no core crate depends on an environment's crate, and an environment's crates may build on the core, and on each other, without a cycle.

**An environment owns its identity.** Each environment's identifier and protocol version are defined once, in its own common crate, such as `tomori-environment-sky`'s `ID` and `VERSION`, which its server half registers it with and its client half presents it at, so the two cannot disagree. To bump one, raise its version there, change its server and client halves together, and add a `releases.md` entry, since clients of the earlier version then show the grid in its spaces. The GitHub prototype's is `tomori-environment-github`'s. A test in the apps keeps the two sides agreeing: `tomori-server-app`'s runs the `tomori-server` executable, offering the GitHub prototype too, and requires that Tomori's own app and spectator are each offered exactly what a client listing nothing is, and present exactly that, at the same identifiers and versions.

**Making an environment.** An environment is up to three crates, named for it after `tomori-environment-`:

- **Common**, `tomori-environment-NAME`: what both halves share, its identity, `ID`, `VERSION` and `LABEL`, and, as it grows, its message formats and shared simulation. It builds no renderer or GPU stack, such as `tomori-render` or wgpu, so that a server builds it.
- **Server**, `tomori-environment-NAME-server`: what runs only in the server, such as its server side (`tomori-environment`'s `ServerSide`), its data sources and its credentials, which never reach a client or the common crate, and the command-line options that configure it, which it adds to a server's builder. It builds no renderer either. The GitHub prototype's server crate holds its GitHub client and token and adds `--github-repository`.
- **Client**, `tomori-environment-NAME-client`: how a client presents it, such as its scenery (`tomori-render`'s `Scenery`), with a `register` function that registers it on a client's `Sceneries` at the common crate's identity. It may depend on the renderer.

An environment with nothing for one half has no crate for it: Sky has no server half, so a server offers it by registering its common crate's identity with `tomori_server::Environment`. An application registers each environment it offers or presents, the server's with `Builder::environment` and a client's with `tomori::Builder::register` or `Sceneries`, as Tomori's own programs register Sky. A test in the `tomori-bake` package reads `cargo metadata` and `cargo tree` and fails when an environment's common or server crate builds the renderer or GPU stack; when its common or client crate builds an environment's server crate, which holds what stays in the server, or its common crate a client crate; when a core crate depends on an environment's crate other than through its `app` feature, which is Tomori's own app in the package that also builds it, or on Tomori's server program, in any kind of dependency; or when a core crate builds an environment's crate at all with every feature but its `app`, as through another core crate's `app`.

- **A client says what it presents.** A client lists in `Hello` the environments it can present, each with its version: the grid, the environments it registers sceneries for, at the versions it registers them with, and those it presents over the grid, as the GitHub prototype's cards are presented by the shared scene (see `github.md` and `builders.md`). Tomori's own headset, desktop window, console and spectator list the Minimal grid, Sky and the farmyard, at version 1, and the GitHub environment's prototype, at version 1; a build that registers nothing lists the grid alone. A client that lists nothing, as one from before versions, is offered every environment, as before.
- **The server offers each client what it presents.** The server offers each environment in `Welcome` with its version, and offers a client that lists environments only those it lists with the same identifier and version, in the server's order. The first of those is what a `CreateSpace` from that client naming no environment is bound to; a `CreateSpace` naming none from a client offered nothing is refused, saying that the server offers no environment it can present. A `CreateSpace` or `set_environment` from it naming an environment the server offers, but not to it, is refused, saying that this client cannot present that environment at the server's version and naming those offered to it, or saying there are none; one the server does not offer at all is refused as unknown, naming those offered to it. A refusal names only the server's own identifiers and versions, never the request's text. The server skips an entry of a client's list that it cannot read, or whose identifier is empty or longer than the server takes (1024 bytes), keeps at most the first 64 of the rest, and reads a list that is not a list as none at all; an older server sends no versions, and a client reads each environment it offers as version 1.
- **A change reaches everyone.** An owner's change of a space's environment, to one offered to the owner's client, applies to the whole space at once, and is never refused because someone else in it, participant, visitor or spectator, cannot present the new environment: their client falls back to the Minimal grid and says what it lacks, as when joining such a space (below), as soon as the space's state reaches it. Only the requester's own list decides what they may choose.
- **The lobby lists every space.** The lobby lists each space whatever environment it is bound to, whether or not the client can present it, and anyone may join one in an environment they cannot present.
- **A client that cannot present it falls back.** A space's state names its environment's version when the server offers the environment, and names none from an older server or when the server no longer offers it. A client joining a space whose environment it lacks, or presents at another version than the state names, shows the Minimal grid and the space's state, and names the environment and the version the space needs; it never draws its own, other version of the environment instead. A state that names no version, as from an older server, is drawn by identifier, as before, and a client that lacks the environment then names it alone. On the headset, the hand menu's Space section names what it lacks in place of the environment's name. The Minimal grid is built in, at its own version, whatever version a scenery drawn with it is registered at (see `builders.md`).

**A server side.** An environment may have a server side: a program in the server process, registered with the environment through `tomori-server`'s builder (see `builders.md`), that can reach whatever the server can, such as data sources and APIs, and whose credentials, endpoints and configuration stay in the server. It is trusted like the rest of the server, since it is compiled in. An environment without one, such as Sky and the Minimal grid, behaves as it always has. An environment's server side is in its server crate, if it has one (see Making an environment, above); one that holds nothing that must stay in the server, such as the farmyard's, which runs a simulation its clients replay, may be in its common crate, which builds `tomori-environment` but not `tomori-server`.

- **It runs while a space is bound to its environment.** The server starts it for a space when the space is bound to the environment, whether it is created in it, an owner changes it to it, or it is bound to its session again after a restart in it, and stops it when the space is bound to another environment, when the space's session closes, and when the server stops. It is started once for each binding, so that a space restored after a restart is started as one just created, whichever order the server offers its environments and lists its kept spaces in. A space restored after a restart runs none until it is bound to its session again, which resolves its directory within the workspace roots again (see `spaces.md`), so a side is never given a directory the server no longer allows; one that cannot be bound again never runs one. A space whose environment the server no longer offers has no server side running, and a space that is closed has none.
- **It is given its space.** Starting it gives it the space's identifier, title and directory, and a cancellation that is cancelled when it is to stop; it has no other access to the space, the hub or the conversation. What it returns as an error is a `tomori-environment` `Error`, a message for the space, rather than a bare string, so that the interface can grow without breaking sides. Its own state, intents and anything it presents are described when they are introduced (see the long-term direction below).
- **It never harms the space.** It runs on a thread of its own, as a blocking program that may use whatever it needs, and never blocks the hub, other spaces or the conversation. When it returns an error, panics or cannot be started, the space shows the error in its error line, beside its other errors, and keeps its environment and its conversation; the failure raises no attention in the lobby, which only the problems `spaces.md` lists do. The side is not started again for that binding, and the error ends when the space is bound to another environment. What a side returns as its error is shown to everyone in the space, visitors included, cut to the bound on error text, so it must hold nothing that should stay in the server. Stopping is bounded: the server cancels the side and does not wait for it, except when it stops itself, when once the spaces have closed it waits for the sides it has cancelled for at most the time it allows connections to drain (see `server.md`), and then stops regardless. A side that ignores its cancellation is abandoned. A side is run only once the server is serving, and an environment offered again with another side, or none, stops the side it ran and runs the new one.
- **The environment's instructions are unchanged.** The layer a server side's environment contributes to the agent's instructions is given as for any environment, whether or not a side runs or has failed.

**The state channel.** A server side shares what its environment presents with the clients in its space through a channel of envelopes, each naming the environment and its version around a payload that only the environment's own crates read: any JSON value, which the server carries without reading it. It is the first, small step of state synchronization (#76).

- **State, for whoever joins.** A side keeps a state for its space with `Space::share`, at most 64 KiB of JSON (`tomori_environment::STATE_LIMIT`, equal to `tomori_protocol::STATE_LIMIT`), which replaces the one kept before and is sent at once, as `EnvironmentState`, to everyone in the space whom the channel reaches (below), and to whoever joins later, after the space's own state. A state still waiting to be sent on a slow connection is replaced by the newer one, sent after the events queued meanwhile, so that nothing is applied twice.
- **Events, for whoever is there.** A side sends an event with `Space::announce`, at most 4 KiB (`tomori_environment::EVENT_LIMIT`, equal to `tomori_protocol::MESSAGE_LIMIT`), as `EnvironmentEvent`, to everyone the channel reaches in the space now, together with the state it leaves, which is kept for whoever joins later, at once, so that nobody misses an event or sees it twice. A client ignores an event until it has a state, so a binding's first update, if it is an event, is sent to those in the space as the state it leaves instead. A client forgets what it kept when the space moves to another environment or version, so that it waits for the new binding's state.
- **Intents, validated by the side.** A participant's client asks the side for something with `EnvironmentIntent`, at most 4 KiB, only once the server has sent it the environment's state in the space, so that it never asks a server that runs no side or an older one. The server checks that the sender takes part in the space, refusing a visitor as for any action, and drops an intent quietly, since intents are ambient, when the space is not in the environment and version it names, when it is too large, or when the participant has sent more than 8 at once or 4 a second after that, across their connections, so that reconnecting does not refill the burst. It hands the rest on to the side, at most 64 waiting, with the number the server gives the participant, which everyone in the space knows them by; the side validates them against its own state and acts on those it takes. **A choice of a row** of a list panel the side published, which a participant makes with A or the trigger, reaches the side in the same inbox as an intent only the server makes, `Intent::choice`, whose `Intent::chosen` names the side's own panel and the row by their ids, and whose payload is empty; a client's intent is never one, whatever its payload says (see `panel-actions.md`).
- **Who it reaches.** The state and events are sent to everyone in the space, participants and visitors alike, whose `Hello` set `environment_state`, saying it reads them, and listed the environment at the version the side runs for, so that a client from before the channel, which would refuse a message it does not know, and one that presents another version are never sent them. Tomori's own clients set it, and keep the joined space's state and events until the environment's client side takes them; a client without one ignores them.
- **It belongs to a binding.** What a side keeps belongs to the binding it runs for: when the space is bound to another environment, closes or is bound again, what it kept is forgotten, and a side of an earlier binding keeps and sends nothing more. A side's state, events and descriptions that the server refuses, as text that is not JSON or too large, are refused with a message the side may show as its error.
- **What participants point at.** A side may describe what a participant can point at in its environment, with `Space::describe`: up to 32 objects (`tomori_environment::OBJECT_LIMIT`), each an identity of at most 128 bytes (`IDENTITY_LIMIT`) and a description the server cleans onto one line, as it cleans everything in the context block, and cuts to 200 characters (`DESCRIPTION_LIMIT`). A client attends to one as `{"kind": "object", "object": "…"}` (`Resource::object`), and the server resolves it as the words begin, from what the side last described, only while the space is in that environment, telling the agent its description, as `Ada: [Pointing at a lantern glowing by the gate] why is it lit?` (see `spaces.md`). One the side has not described, or an identity longer than any it takes, is dropped and the words kept.
- **Ids for the agent to inspect.** An object a side describes may carry a **reference**, `Object::with_reference`: a short, stable name for it, opaque to Tomori, unique among the objects the side describes and the same for as long as the object is, such as `hen/marigold` or `panel/checkout-error-rate`; it is separate from the object's identity, which clients name it by and the agent is not told. The server keeps a reference only of 1 to 64 bytes (`tomori_environment::REFERENCE_BYTES`) of ASCII letters, digits, `-`, `_`, `.` and `/` (`tomori_environment::valid_reference`), so that it can neither end the context block nor read as anything but a name, and only the first object's of two with the same; it describes an object whose reference it refuses without one. The agent is told the object's **id**, its reference after the identifier of the environment it belongs to, so that ids of different environments never collide, in parentheses after its description, as `Ada: [Pointing at Marigold, a hen in the farmyard, wandering by the coop (id farmyard:hen/marigold)] what's she up to?`; an object without a reference is described as before, with nothing added. The environment's identifier is cleaned and cut to 64 characters, and a reference has no `:`, so the last `:` of an id ends the environment's identifier; the block's bound, 1,000 characters, is unchanged, and a description and id together, at most 200 and about 130 characters, always leave room for more.
- **Inspecting an id.** A side may answer the agent's questions about what it describes with a reference, by giving its space an `Inspector`, with `Space::inspect_with`: a hook that takes a reference and answers with JSON of the environment's own choosing, such as a hen's name, activity, position, what she wears and where she roosts, or, for an object backed by a metric, its query, the range it shows, its source's name, its labels and its latest value (`tomori-prometheus`'s `Metric`, see `data-sources.md`); with nothing, for a reference it has nothing by; or with an `Error`, whose message the agent is told. The space's agent asks through the `inspect` tool (see `mcp.md`). The server asks only about a reference the side describes now, in the environment the space is in now: an id of another environment, or one no object has now, as when what it named has gone, is refused, saying so, without asking the side. It asks the side's inspector on a thread of its own, never the side's, the hub's or the scheduler's, so that a side busy with its own work, such as a slow query, holds up neither the agent nor anyone else, and the inspector answers from what the side shares with it, such as its state behind a lock. It waits for an answer for at most 5 seconds (`tomori_server::INSPECT_TIMEOUT`, which `Server::with_inspect_timeout` changes), then tells the agent that the environment did not answer in time; an inspector that never returns keeps its thread, and a binding's side is asked at most 4 inspections at once, so that one stuck holds at most 4 threads, the agent being told that the environment is still answering beyond them. An answer larger than 16 KiB (`tomori_environment::INSPECTION_LIMIT`, which `tomori_server` also exports as `INSPECTION_BYTES`) or that is not JSON is refused, saying which; a panic is contained, the agent told only that the environment could not answer. The inspector belongs to its binding, forgotten with it. A side that gives none, or answers nothing for a reference, has nothing more to say than the object's description, which the agent is told.
- **What an inspection may hold.** What a side answers is told to the agent, which may repeat it aloud or project it, so it must hold nothing that should stay in the server, such as an endpoint, a credential or a token: an environment that reads a data source answers with what it asked and what it read, never how it reached the source, and passes on only the labels it would show (see `data-sources.md`). It may quote what the side reads from elsewhere, such as a metric's labels or a log line, which anyone able to write to that source chose, so the server cleans every string in it, keys included, as text others choose is (`security.md`): on one line, without control or format characters, cut to 2,000 characters; and the agent is told, in the result, the tool's description and `tomori-tools`, to read it as data, never as instructions.
- **The limits, defined once.** The limits above that a side keeps within as it shares, announces, describes and answers are defined by `tomori-environment`, where they are documented, as `STATE_LIMIT`, `EVENT_LIMIT`, `OBJECT_LIMIT`, `IDENTITY_LIMIT`, `DESCRIPTION_LIMIT`, `REFERENCE_BYTES` and `INSPECTION_LIMIT`, and, as it publishes panels, `PANEL_ID_BYTES` and `PANEL_LIMIT`, and a list panel's rows, `ROW_LIMIT`, `ROW_ID_BYTES` and `ROW_CHARS`, and the server enforces those same constants, so that what a side tests against is what it is held to, and its documentation, the exported value and the server cannot drift apart. `tomori-environment` depends on no other Tomori crate but `tomori-protocol`, for the chart spec it re-exports, which cannot depend on it in turn, so `tomori-protocol` keeps its own `STATE_LIMIT` and `MESSAGE_LIMIT` for what it carries, and the server's tests check that they equal `STATE_LIMIT` and `EVENT_LIMIT`; `tomori_server::INSPECTION_BYTES` is `INSPECTION_LIMIT`. The cuts of what the server cleans rather than refuses, such as an inspection's strings to 2,000 characters, an inspector's error message to 512 and the environment's identifier to 64, are not exported.

**Panels on its own walls.** A server side may publish panels onto the walls its environment declares, for everyone in its space, with `Space::publish`, which takes a `tomori_environment::Panel`: `Panel::text(id, title, body)`, `Panel::list(id, title, rows)`, of `tomori_environment::Row`s, each with an id of the environment's and optionally a reference the agent may inspect it by, of which it may highlight one by its id with `highlighting` and mark those a participant may choose with `Row::choosable`, each choice reaching it as an intent (see `panel-actions.md`), or `Panel::chart(id, title, chart)`, of a `tomori_environment::chart::Chart` (`tomori-protocol`'s), `on_wall(wall, slot)`, the wall by its place in the order the environment declares them, from 0, and the slot it prefers, and `with_reference`, a reference the agent may inspect it by, as an object's. Its id, chosen by the environment, is 1 to 32 ASCII letters, digits, `-` and `_` (`valid_panel_id`); publishing it again updates that panel in place, and `Space::retract(id)` takes it away. Every client draws it as it draws the agent's panels, and participants and the agent move, point at and dismiss it as any panel, as `projection.md` requires, which also gives what it may not do: write another environment's walls, the Tomori wall or an added wall, exceed a wall's slots, or more than 32 panels in a space (`PANEL_LIMIT`), or change anything once its binding has ended. A chart panel's points, badge and status line are its live data, which only its side writes: a change of them changes no version a participant's or the agent's edit is checked against, and reaches a client that applies data ops as the points it gained, a `chart_append`, where its series only moved along, as a chart polled on a fixed step does, or else its data whole, a `chart_replace`, rather than the panel whole, as `projection.md` describes; a side therefore publishes a live chart as the whole window it shows each time, and gains the smaller update by moving its points along rather than by saying what it appended. Its changes are limited to about one a second for each panel, and 16 changes and 128 KiB a second in a space after a burst of 32 and 512 KiB, enough to put up or update every panel it may show together, counting only what the stage changes, and 80 calls a second whatever they change, so that publishing every one each second is never refused, and what it changed is told to the space's clients at most four times a second, the first change at once; a side may publish more often than that, as on its own timer, and the latest wins: an update that comes too soon waits and is made as soon as it may be, so that what it published last always arrives; one that could never be made, onto a wall it does not declare or a slot it has not, or past the 32 counting those waiting, is refused at once. Updates waiting that are due are made first, the oldest first, then a fresh one, at once while the space has changes left, so that every panel's latest arrives in turn. A panel a participant dismissed stays away through its side failing; what a run published rests when it ends, holding no slot, until the next run publishes it again, for as long as 3 runs that publish others; and a side that has failed or finished, its `run` returning, changes no panels from then on, any thread it left running included, until it runs again, since an environment's panels are shown only while it runs. What it publishes is cleaned and bounded as the agent's panels are, never HTML, and shown only while its side runs. An `Outlet` made before panels takes none: `Outlet::publish` and `Outlet::retract` default to keeping nothing, so that an outlet of a side's own tests still builds. The farmyard and Tomori's other environments publish none yet.

**A client side.** What a client presents of an environment beyond its scenery, from what its server side shares, is the environment's client side, a `tomori-scene` `ClientSide` that the environment's own crate implements and a client registers beside its scenery, with `Sceneries::set_client_side` (see `builders.md`); `tomori-render`'s sceneries hand the registrations to the conversation, and only the environment's crate knows what any of it means. The frame step makes one for the joined space, once the space's scenery has grown in and only while the environment drawn is the one it is registered for, at the version drawn, and drops it on leaving, on a change of environment and in another space, so that each space's begins anew. Each frame it is given the updates the conversation kept for the space, in order, what the participant points at in it and where their head is, and what they do with the trigger, B and the sticks (below), and returns:

- **What it shows**, which the frame carries to the renderer, and the renderer to the environment's scenery through `Scenery::animate`, once a frame before the eyes are drawn, as a value only the environment's scenery reads, such as where its animated models stand.
- **Its intents**, which the conversation sends only as `environment_intent` allows (above).
- **Its sounds**, each at a place in the scene, which play as ambient sounds (see `feedback.md` and `spatial-audio.md`).

The ray points at what the environment shows through the client side's `pick`, which names what it meets first with its identity, a short label and its distance: in a space, where the scenery has grown in and no card is carried, it is pointed at when nothing else the ray meets, a card, a worker or a projected panel, is nearer, ticking as a new target does, and the ray ends on it. While it is pointed at, the participant attends to it as `Resource::object`, and the recording indicator names it by its label, as it names a worker or card. **What the participant does with it.** A client side may mark what it picks as selectable, with `Picked::selectable`. Nothing is selectable unless it says so, and the trigger, A, B and the sticks reach a client side only as below, each after every rung of Tomori's own in the order `interaction.md` gives the control, and so only while the ray is on something of the environment's or on nothing of Tomori's, so an environment that marks nothing and reads none of them, as the farmyard, behaves as before. Each frame it is told, in its `Input`:

- **Select**, `Input::select`: a pull of the trigger, the right controller's or the desktop's left mouse button, that begins while the ray points at a selectable object of its, as the frame before found it, is the environment's until the trigger is let go, and does not attract the swarm. The client side is told `Select::Pressed` with the object's identity once the trigger is pulled as far as choosing an arrival object takes, if the ray is still on that object, and `Select::Released` with the same identity once the trigger is let go after that, wherever the ray is then, or stops acting, as on losing focus, so that each press is let go once. A pull that slides off the object before it is pressed selects nothing and attracts nothing, and a pull that was a client side's when it went, as the space or its environment changes, is nobody's until it is let go, attracting nothing and selecting nothing in the next. Since the object is the one the frame before found, a press can name an object that has since gone, as a mouse click, which pulls the trigger fully in one frame, does at once: a client side must tolerate a select for an object that has gone, ignoring identities it does not know. A pull that begins anywhere else attracts the swarm as before, even across a selectable object, and one on an object that is not selectable attracts as before and selects nothing. The thresholds are those that choose an arrival object (see `arrival.md`). **A selects too,** in the same stream, so that a client side written for the trigger works with A unchanged: a press of A, Enter on the desktop, while the ray points at a selectable object of its, as the frame before found it, is the environment's when nothing before it in A's order takes the press (see `interaction.md`), and the client side is told `Select::Pressed` with the object's identity as A goes down, at once, since a press of a button has no half-way, and `Select::Released` with the same identity once A is let go, wherever the ray is then, or stops acting, as on losing focus; a press let go in the frame it began in is pressed in that frame and let go in the next, and a press waits for the next frame that is drawn, as when the headset reads its buttons on frames it does not draw, so that it is told once. A press in the frame the hand menu or the transcript appears is theirs, as a pull of the trigger is. How this maps onto #76's plan: the kept state is #76's snapshot on join, here the whole state rather than its collections, values and series, which an environment encodes in its own payload; events are its transient events; intents are its intents, refused quietly for now rather than answered with a reason, since the first environment's are ambient; a newer state replacing an unsent one is its coalescing, without a lane of its own yet. Not yet: deltas with revisions and repair by snapshot, interest, a shared clock estimated from keepalive (an environment that needs one carries its own clock in its payload), per-space limits on the rate of a side's updates, and persistence across restarts. Each can be added beside these messages, as further optional fields and variants, without changing them. - **One facing convention.** Every anchor faces along its pose's +Z, the way it looks: the participants arriving look along it, the agent's eye looks along it, the Tomori wall's and every wall's face looks along it, and the workers' arrangement faces along it, towards whoever watches it, as the agent does. `tomori_protocol::Pose::at(spot).facing_towards(target)` makes such a pose, so that an environment never turns one backwards: `Pose::at(balcony).facing_towards(arrival)` faces the arrival, and `Pose::at(arrival).facing_towards(balcony)` arrives looking at the balcony. - **The status wall's home: beneath the agent, by default.** Where the environment names no status wall, the space's own, the Tomori wall, stands beneath the agent's home, by one rule the server and every client share, `tomori_protocol::entourage`: the middle of its row 0.88 m (`entourage::BENEATH`) directly below the swarm's middle, facing the way the agent faces, towards the arrival, and curving about the point 2.3 m before it, so that the swarm stands above it with a clear gap of 0.23 m between the swarm's lowest reach and the top of its row; and never lower than 0.52 m above the floor where participants arrive, its row's bottom edge then 0.39 m above it (`entourage::wall_beneath`). - **The agent's home.** The agent's home is the environment's `agent` carried into the space, or else the default. The agent, the swarm or whatever avatar shows it (see `avatars.md`), appears there as the space opens, and again, at the new environment's home, when the space changes environment: it is carried there at once, in the shape it has, rather than gliding across the scene, as the scenery grows in about it. - **Following the speaker.** In a space whose owner chose **Follow the speaker** (below), the agent comes to whoever it is talking with, its partner, as a person would, and the server decides where, from what it already has, sending everyone where it stands as `SpaceState::summoned`. As a participant presses X for words to the agent, not an answer, a name or a title, it turns to face them at once, sent as `SpaceState::facing`, a yaw and not a move; a press let go within 0.4 s, a tap, moves nothing more, even once its words are given. Held 0.4 s, it commits, from what was captured as the words began: their head, and what they pointed at with the right controller, else what they looked at, a wall, a panel or a person, else 2 m along the way their head faces. It stays where it is, only turning, when it already stands within 3 m of their eyes, within 50° of the way their head faces, seen from their eyes past the environment's solids and the walls shown, and out of their way (below). Otherwise it goes to their **conversation spot**: 1.5 m from their eyes horizontally, then 1.8 and 1.2 m, at 45° to their left of the line from their eyes to what they attend to, then 45° right, 70° left and right, and 25° left and right, its middle 0.1 m above their eyes, never lower than 1.1 m nor higher than 2.4 m above the floor, facing them (`tomori-server`'s `follow.rs`). A spot is refused where the swarm's reach (half of `entourage::SWARM` each way) comes within 12° of the line to what they attend to, seen from their eyes, or where its box, 0.1 m larger on every side, meets the environment's solids, a wall shown, its slots 5 cm thicker, or a panel floating within 3 m of them, or comes within 0.8 m of anyone's head, or where anything of those stands between their eyes and its middle; with every one refused, the same bearings are tried at 2.3 m, and with none clear it only turns. Once it arrives somewhere it stays at least 10 s before going for another partner, only turning, unless the new one stands more than 6 m from it or cannot see it. Two or more who spoke to it within the last minute, standing within 4 m of the speaker, are a **huddle**, served from one spot: on the side of the group most of them face, about 1.5 m from the nearest of them, at their eyes' height on average, facing the middle of their heads, clear of each of their lines of sight and seen by each; else from the speaker's own spot. Visitors never turn or move it. Words that come to nothing, cancelled, with no speech in them or failing to transcribe, stop a move begun for them where it has reached, or where it was, if it had barely begun. Every move is logged at info with whom it followed and why.
- **How it goes.** Clients glide the agent's place, its rings, halo, ring on the floor and voice with it, to where the space's state stands it, easing in over 0.4 s, cruising at up to 0.85 m/s and settling over 0.5 s, and turning round smoothly when sent back on the way (`tomori-scene`'s `glide.rs`); the swarm's agents fly a quarter faster than it moves, so that they keep up. The participant is never moved, so this is an object moving in the scene, not travel, and `locomotion.md`'s rules for moving the rig do not apply. The server checks the straight way against everyone's heads, kept 0.8 m from it, and the solids and walls shown; where it is blocked, it gives one waypoint, `SpaceState::via`, raised a metre above the tallest head along the way or a metre to either side, which clients glide through; with none clear, or beyond 5 m, the agent **streams**, `SpaceState::stream`, at up to 6 m/s, as a worker's flock flies, its agents regathering at the spot.
- **Going home.** A following agent goes home once the conversation has been quiet for the space's delay, 90 s by default: nobody recording or transcribed for it, nothing queued, no question or approval waiting, its session idle, and no agent speech playing, held or caught up on for anyone, checked each second while it is away or turned. Any words begun, and the agent's own speech, as from a worker's report, start the quiet again; a running worker does not hold it. Once its partner has left the space or gone away, the delay is 15 s at most. It goes home as it went, silently, its pin and turn ended, facing as its home faces.
- **Calling it and pinning it.** The trigger no longer summons the agent: a participant calls it by voice, "come here", which following answers, or, without speech, with **Call Tomori here** in the hand menu, `ClientMessage::CallAgent` (see `hand-menu.md`), which stands it at their conversation spot, in either mode, or, with nowhere clear there, 2.3 m in front of them as the summons did, and **pins** it there, for everyone, `SpaceState::pinned`. The agent pins itself with `move_agent stay` (see `mcp.md`). Pinned, it follows nobody and does not go home on its own, though it still turns to whoever speaks, and glances at them while busy, whether it follows the speaker or moves only when asked; unpinned where it moves only when asked, a press neither turns nor moves it; the pin ends when it is sent home, by the agent's `move_agent home` or a participant's **Send Tomori home**, `ClientMessage::PlaceAgent` without a place, as the space changes environment, as the server restarts, or after 30 minutes with nobody in the space. Visitors call and send home nothing.
- **How the agent moves, a space setting.** An owner chooses, in the hand menu's Space section, how the agent moves, kept with the space, `SpaceState::movement`: **Follow the speaker**, all of the above; **Only when asked**, the default, in which it moves only when someone asks, by voice through `move_agent` or with **Call Tomori here**, and stays where it goes until sent home; or **Stay home**, in which it never leaves home, refusing `move_agent` but for home and **Call Tomori here**, and goes home as it is chosen. - **Where workers stand is the client's.** An environment's client crate may register how its workers are placed, a `tomori-scene` `WorkerPlacement`, beside its scenery, with `Sceneries::set_worker_placement` (see `builders.md`). Where another sign is already near that place, as for workers placed together, it stands at the place nearest its own that is clear of every other sign, rising in rows 0.55 m apart above it, at most ten, before moving a column aside, along the arc about whoever it faces, a sign's width apart, and only within 30° of the worker's bearing from them, so that a sign moved aside stays near its worker rather than over another cluster, and signs stack sooner; where every such place is taken, as for very many workers at one spot, it stands above its worker, overlapping another, rather than further off. Wherever the sign stands, its leader runs from the middle of its plate's bottom edge to its worker's middle, ending in a dot there (see `interaction.md`). The default arc's signs, whose rows and columns are further apart, each stand above their own worker, and none reaches another worker or sign, even with the longest title.
- **Workers and signs at the distances an environment implies.** A worker the environment stands further from the participant than 3 m is as easy to point at as one 3 m away: the sphere about it that the ray must meet grows with its distance from the ray's origin, from 0.3 m within 3 m, so that it keeps the same angle (see `interaction.md`). A worker's sign further from whoever it faces than the default arc's 3.2 m is drawn larger in proportion, the same image at the same sharpness, so that it reads from home as one on the arc does (see `text.md`); its rows, columns, rise and the room it keeps from other signs grow with it. So workers about an agent's home across a yard or on a balcony are pointed at and read as those on the default arc are, and no environment need keep its workers within 3 m of the arrival.
- **Anchors and placements are the operator's code.** Anchors, like an environment's walls and its placement, come from the code an operator compiles into their server and clients, trusted as the rest of it is, and are bounded as above; nothing keeps the swarm, a worker or a sign clear of a participant's head (see `security.md`), which moves with travel and differs for each participant, so an environment that stands them where people stand puts them in someone's face, an accepted limit. Where the server stands the agent for someone keeps 0.8 m from every head, but an anchor is not checked.

An environment may contribute a layer of the instructions Tomori gives a space's agent, about what it presents and which tools and data sources to use (see `spaces.md`), given with the environment when it is offered. Sky and the Minimal grid contribute none yet; an environment the server no longer offers contributes none. A space keeps only its environment's identifier, not its layer: the server looks the layer up in the environments it offers whenever it shows the space's instructions or gives them to the agent, so that a space restored after a restart is given the same layer as one just created or changed to that environment, whatever order the server was configured in.

**Notice boards and consoles: an environment's own walls.** An environment's own projection walls, which its registration declares with `Environment::with_walls`, each a pose or a `tomori_server::EnvironmentWall` with its grid, the size and shape of its slots, whether it curves and tilts and what it is called, such as `Details`, which the agent puts panels on it by, as `place: wall Details slot 4` (see `projection.md`), are part of the place, and its scenery is expected to draw what each stands on, so that it reads as belonging there: a notice board on posts in a yard, a console on a bridge, a pinboard by a door. People walk up to one and put content on it, the agent's panels and their own, organising it as they like, and an environment may have several, each where its kind of work is done. They are locked until a space's owner unlocks them, so that they stay where the place puts them, while what is on them is the space's; an owner may unlock one to move or reshape it for the space, and put it back where and as the environment has it (see `projection.md`). The farmyard's notice board, two slots wide and one high on a board against its fence, is the first (see `farmyard.md`); its wall and the board it is drawn on are laid out from the same constants in its common crate, so that the two cannot drift apart, and an environment whose wall moves where its scenery no longer draws a board under it raises its version, as the farmyard did to 3.

Long-term direction, not yet requirements:

- An environment is much more than scenery. It can be dynamic and data-backed, with its own interaction, such as Fantail Observe, a separate project that shows a running system's topology and telemetry spatially. Environments are expected to be built on the server-owned scene graph and modules in `scene-modules.md`.
- The space's agent is aware of its environment: the information and data it presents, and what each participant is pointing at or has selected in it. Pointing and selection identify concrete resources, with their identity and context such as the time window, not only positions or pixels.
- A participant can refer to what they are pointing at in speech, such as "Tomori, can you investigate why this server is overloaded?". The agent receives the identified resource with the request, and uses the tools available in that space, such as its MCP servers, to investigate and answer.

## Rationale

The user intends to build specific environments for different kinds of work, so a space represents much more than a cosmetic place: it pulls in the information and interaction that work needs. Tying the environment to the space keeps every participant looking at the same thing, which shared pointing and the agent's awareness of the environment depend on. Stated by the user, speaking from the headset, in November 2026, with Fantail Observe as the example to connect eventually.

In November 2026 the user decided, from the headset, that a space's environment can be changed after it is created, from the Space section of the hand menu: by owners only, for everyone in the space, and kept in the space's record (issue #74). Since the space moves as a whole, everyone keeps looking at the same thing. In November 2026, as environments came to agree versions with clients (issue #75), the user decided that a change is never refused because someone in the space cannot present the new environment: a participant or visitor who cannot present it falls back to the grid with a warning, as when joining such a space. So nobody's client, and no visitor, can keep owners from changing their space.

In November 2026 the user decided that environments are compiled into both the server and the clients, and that client and server agree on each environment through a protocol version (issue #75, the environment framework proposal in #90, section 1). Offering a client only the environments it presents keeps whoever creates a space, or moves one, from choosing an environment they would see only as the grid themselves, and keeps a client side from reading state it does not understand; the fallback remains for spaces someone else created, and for servers that no longer offer an environment. Clients and servers from before versions keep working with each other and with newer ones, since every addition is optional. The GitHub environment's prototype is listed by every client built on `tomori-scene`, because its cards are drawn by the shared scene rather than by a scenery, so that agreeing on versions does not take it from Tomori's own headset. Bounding the list a client sends keeps what the server holds for a connection small.

In November 2026 the maintainer agreed that the core is a clean slate that environments register themselves against: the builders register nothing by default, Tomori's own programs register Tomori's own environments as another project's would, and each environment's crates own its identity, in a common crate, with server and client crates beside it. Before, the core knew Sky and the GitHub prototype, and their identities were in `tomori-protocol`, so an environment offered by the core made the server library depend on it while its client half depended on rendering crates whose tests depend on the server, a package cycle; keeping environments out of the core removes it, and lets an environment be added without changing the core.

In November 2026 the user decided that an environment's server side is a full program in the server, not only a producer of scenery: it runs where the server's reach and credentials are, and clients never hold them (issue #75, the environment framework proposal in #90). It runs on a thread of its own, as the GitHub environment's source already reads GitHub, so that a failing or slow side cannot harm the hub or another space, and each binding runs it once so that a restored space is treated as a new one. A downstream project's environment, such as one that shows a running system's telemetry, is built on it. The state it shares with clients, its intents and its client side are separate steps of the same framework (#75, #76).

In November 2026, to give a new environment's animated objects a home whose server side owns them, the maintainer asked for a first generic state channel rather than messages for one environment's objects: an envelope naming the environment and its version around an opaque, bounded payload that the environment's own crate encodes, with intents that the server side validates, additive and gated, as a deliberately small first step towards #76. The payload is JSON, as the control messages are, which answers #76's question of encoding for now. A kept state and announced events rather than deltas keep the first step small: a state is replaced whole, so a gap is repaired by the next one. Only clients that say they read the channel and present the environment at its version are sent it, since an older client would refuse a message it does not know. Objects are described by the side and kept by the server, rather than asked of the side as an utterance begins, so that resolving attention never waits for a side's thread or runs its code under the hub's lock.

In November 2026, speaking from the headset, the maintainer asked for things pointed at to carry an id the agent can inspect for more, such as the exact query and time range behind a Prometheus metric, so that the agent of a space showing a running system's telemetry can say precisely what a chart shows, or ask Prometheus the same, rather than guess from a sentence. The id is a reference the side chooses, rather than the identity clients pick by, so that an environment can keep the identity its clients already use, as the farmyard's `chicken-2`, while the agent sees a name that says what it is and stays the same, `hen/marigold`; it is optional, so that the note stays as short as before for an environment with nothing more to say, and namespaced by the environment, so that a space moved to another environment never resolves an old id against the new one. The inspector is a hook a side gives its space, called on a thread of its own, rather than a request queued for the side's own loop, as intents are, so that a side blocked on its own query still answers, and a side that never answers costs a bounded number of threads; only references the side describes now are asked about, so that the agent inspects what the space shows rather than fishing for anything a side might answer. Inspections are bounded in time and size and cleaned, since a telemetry environment may answer with what anyone could write into the system it reads.

In November 2026 a downstream environment's server side found these limits stated only in `Space`'s documentation, and repeated them as constants of its own, reading the state's from `tomori-protocol`; since a state past its limit is refused and ends its loop, it keeps within them itself and tests against them, so `tomori-environment` exports them, and the server enforces what it exports; they are defined there rather than taken from `tomori-protocol`, so that `tomori-environment` keeps no dependency on another Tomori crate and can be published on its own.

Open questions, not yet decided:

- Whether an environment is a scene module, a set of modules, or something that hosts them.
- How participant pointing and selection are delivered to the agent, and how that relaxes `scene-modules.md`'s current separation of the scene graph from agent interactions.
- How an environment's data sources, such as a telemetry service, relate to the tools available to the space's agent.
- Whether the trigger pulled while pointing at nothing an environment shows, which in a space no longer draws the swarm, should reach its client side, what the freed trigger selects beyond objects marked selectable, such as workers and list items, and how a hand-tracking pinch, which does not act as the trigger yet, selects; and whether selecting, by the trigger or by A, should tick as choosing does (see `feedback.md`), which it does not yet, so that an environment can decide what a selection means first.
- Which object a worker is working on: the protocol's workers carry no resource, so a placement cannot yet float a worker near what it investigates; associating one, and how it reaches the client, is a later step.
- How a space's edits to the Tomori wall's pose, once wall editing keeps them, are shown against its home, and whether a participant can send the wall home as they send the agent home.
- Whether a pin should be kept across a restart, and whether the agent may go to an object it investigates, as #79's coordinator turning towards a resource suggests, which `move_agent object ID` would do (stage 5 of the proposal).
- Whether the workers anchor becomes a volume, as #79 proposes, and whether a placement moves to the environment's server side, so that a participant whose client cannot draw the environment sees workers where the others do.
- How far a client side's interface grows beyond what the farmyard needed, presenting replicated state, picking, intents and ambient sounds (above): for instance, whether a client side contributes panels, tools or locomotion of its own, and whether it should run anywhere but on the headset, as in the spectator.
