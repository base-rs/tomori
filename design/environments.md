# Environments

This describes how a space's environment relates to the space. The first part is a current requirement; the rest is long-term direction, and the initial design must not prevent it.

## Requirement

Each space is bound to exactly one environment at a time. The environment is chosen when the space is created, is part of the space's shared state, and is the same for everyone in it, participants and visitors alike. A participant does not switch a space's environment on their own device; the per-device environment choice, such as squeezing the grip to switch between Sky and Minimal, does not apply inside a space.

**Changing it.** An owner may change a space's environment after it is created, to another the server offers, from the hand menu's Space section (see `hand-menu.md`), with `set_environment`. The change applies to the whole space at once: the server checks that the requester is an owner and that it offers the environment to the requester's client (see below), keeps the new environment in the space's record, so that a restart keeps it (see `spaces.md`), and sends the space's state to everyone in it, participants and visitors alike, who switch to it, the new scenery growing out of the space as it does on joining, or, if their client cannot present it, the grid with a warning saying what it lacks. Someone joining later arrives in it, and the lobby lists the space in it. A collaborator or visitor is refused, and their menu does not offer the change; an environment the server does not offer that client is refused, naming those it does; and a closed space keeps the environment it had. The conversation, queue, workers and settings are unaffected, except that the agent is given its instructions again, since the environment's layer changes with it. A server says in the space state that it changes environments, and a client offers the change only to such a server, so older servers and clients work as before; an older client sees the new environment only when it next joins. The server offers the environments a space can use, as it offers backends and directories: those its program registers (see Registering environments, below). Tomori's own server, `tomori-server`, offers Sky (`crates/environment-sky`), first, so that it is the default for a space whose creator names none, the Minimal grid, labelled Grid, and the farmyard (`crates/environment-farmyard`, see `farmyard.md`); and, only when it is started with `--github-repository`, the GitHub environment's prototype, whose spaces show a repository's open issues and pull requests as cards (see `github.md`). A server another project builds offers those it registers through `tomori-server`'s builder, in the order it registers them, a later one with the same identifier in place of the earlier (see `builders.md`). A space kept across a restart in an environment the server no longer offers stays in it. A client that cannot present a space's environment shows the Minimal grid and says which environment, and which version, it lacks, rather than substituting another environment silently (see below).

**Agreeing on the environment.** Client and server agree on each environment through its protocol version, an integer, 1 unless the environment is registered with another (see `builders.md`). A change to what the server and a client side exchange that an older client side can ignore, such as a new optional field with a default or a new variant read as unknown, keeps the version; any other change raises it.

**Registering environments.** The core, the framework crates that the server and clients are built from, knows no environment but the Minimal grid, which every client draws built in, as its waiting area and its fallback, at the identifier and version in `tomori-protocol`, `GRID` and `GRID_VERSION`. Every other environment, Tomori's own included, is registered by an application, Tomori's own programs or another project's, through the same builder calls: `tomori-server`'s builder and `tomori-client-quest`'s start with no environments and register nothing by default. Tomori's own server program, `tomori-server` in the `tomori-server-app` package, registers Sky, the grid and the farmyard, and the GitHub prototype's `--github-repository` option from its server crate; Tomori's own app, the `tomori` executable and APK, behind `tomori-client-quest`'s default `app` feature, and Tomori's own spectator, `tomori-spectator`, behind `tomori-client-spectator`'s, register Sky's, the farmyard's and the GitHub prototype's client halves. The core keeps what an environment's crates build on: the server's card board, which the GitHub prototype's server half fills through a `CardSource` and offers with `Server::with_cards`, and the scene's cards, which a client presents over the grid for any environment whose spaces show them, as the protocol's card messages do, until the state channel (below) replaces them. So no core crate depends on an environment's crate, and an environment's crates may build on the core, and on each other, without a cycle.

**An environment owns its identity.** Each environment's identifier and protocol version are defined once, in its own common crate, such as `tomori-environment-sky`'s `ID` and `VERSION`, which its server half registers it with and its client half presents it at, so the two cannot disagree. To bump one, raise its version there, change its server and client halves together, and add a `releases.md` entry, since clients of the earlier version then show the grid in its spaces. The GitHub prototype's is `tomori-environment-github`'s. A test in the apps keeps the two sides agreeing: `tomori-server-app`'s runs the `tomori-server` executable, offering the GitHub prototype too, and requires that Tomori's own app and spectator are each offered exactly what a client listing nothing is, and present exactly that, at the same identifiers and versions.

**Making an environment.** An environment is up to three crates, named for it after `tomori-environment-`:

- **Common**, `tomori-environment-NAME`: what both halves share, its identity, `ID`, `VERSION` and `LABEL`, and, as it grows, its message formats and shared simulation. It builds no renderer or GPU stack, such as `tomori-render` or wgpu, so that a server builds it.
- **Server**, `tomori-environment-NAME-server`: what runs only in the server, such as its server side (`tomori-environment`'s `ServerSide`), its data sources and its credentials, which never reach a client or the common crate, and the command-line options that configure it, which it adds to a server's builder. It builds no renderer either. The GitHub prototype's server crate holds its GitHub client and token and adds `--github-repository`.
- **Client**, `tomori-environment-NAME-client`: how a client presents it, such as its scenery (`tomori-render`'s `Scenery`), with a `register` function that registers it on a client's `Sceneries` at the common crate's identity. It may depend on the renderer.

An environment with nothing for one half has no crate for it: Sky has no server half, so a server offers it by registering its common crate's identity with `tomori_server::Environment`. An application registers each environment it offers or presents, the server's with `Builder::environment` and a client's with `tomori::Builder::register` or `Sceneries`, as Tomori's own programs register Sky. A test in the `tomori-bake` package reads `cargo metadata` and `cargo tree` and fails when an environment's common or server crate builds the renderer or GPU stack; when its common or client crate builds an environment's server crate, which holds what stays in the server, or its common crate a client crate; when a core crate depends on an environment's crate other than through its `app` feature, which is Tomori's own app in the package that also builds it, or on Tomori's server program, in any kind of dependency; or when a core crate builds an environment's crate at all with every feature but its `app`, as through another core crate's `app`.

- **A client says what it presents.** A client lists in `Hello` the environments it can present, each with its version: the grid, the environments it registers sceneries for, at the versions it registers them with, and those it presents over the grid, as the GitHub prototype's cards are presented by the shared scene (see `github.md` and `builders.md`). Tomori's own headset, desktop window, console and spectator list the Minimal grid, Sky and the farmyard, at version 1, and the GitHub environment's prototype, at version 1; a build that registers nothing lists the grid alone. A client that lists nothing, as one from before versions, is offered every environment, as before.
- **The server offers each client what it presents.** The server offers each environment in `Welcome` with its version, and offers a client that lists environments only those it lists with the same identifier and version, in the server's order. The first of those is what a `CreateSpace` from that client naming no environment is bound to; a `CreateSpace` naming none from a client offered nothing is refused, saying that the server offers no environment it can present. A `CreateSpace` or `set_environment` from it naming an environment the server offers, but not to it, is refused, saying that this client cannot present that environment at the server's version and naming those offered to it, or saying there are none; one the server does not offer at all is refused as unknown, naming those offered to it. A refusal names only the server's own identifiers and versions, never the request's text. The server skips an entry of a client's list that it cannot read, or whose identifier is empty or longer than the server takes (1024 bytes), keeps at most the first 64 of the rest, and reads a list that is not a list as none at all; an older server sends no versions, and a client reads each environment it offers as version 1.
- **A change reaches everyone.** An owner's change of a space's environment, to one offered to the owner's client, applies to the whole space at once, and is never refused because someone else in it, participant, visitor or spectator, cannot present the new environment: their client falls back to the Minimal grid and says what it lacks, as when joining such a space (below), as soon as the space's state reaches it. Only the requester's own list decides what they may choose.
- **The lobby lists every space.** The lobby lists each space whatever environment it is bound to, whether or not the client can present it, and anyone may join one in an environment they cannot present.
- **A client that cannot present it falls back.** A space's state names its environment's version when the server offers the environment, and names none from an older server or when the server no longer offers it. A client joining a space whose environment it lacks, or presents at another version than the state names, shows the Minimal grid and the space's state, and names the environment and the version the space needs; it never draws its own, other version of the environment instead. A state that names no version, as from an older server, is drawn by identifier, as before, and a client that lacks the environment then names it alone. On the headset, the hand menu's Space section names what it lacks in place of the environment's name. The Minimal grid is built in, at its own version, whatever version a scenery drawn with it is registered at (see `builders.md`).

**A server side.** An environment may have a server side: a program in the server process, registered with the environment through `tomori-server`'s builder (see `builders.md`), that can reach whatever the server can, such as data sources and APIs, and whose credentials, endpoints and configuration stay in the server. It is trusted like the rest of the server, since it is compiled in. An environment without one, such as Sky and the Minimal grid, behaves as it always has. An environment's server side is in its server crate, if it has one (see Making an environment, above); one that holds nothing that must stay in the server, such as the farmyard's, which runs a simulation its clients replay, may be in its common crate, which builds `tomori-environment` but not `tomori-server`.

- **It runs while a space is bound to its environment.** The server starts it for a space when the space is bound to the environment, whether it is created in it, an owner changes it to it, or it is bound to its session again after a restart in it, and stops it when the space is bound to another environment, when the space's session closes, and when the server stops. It is started once for each binding, so that a space restored after a restart is started as one just created, whichever order the server offers its environments and lists its kept spaces in. A space restored after a restart runs none until it is bound to its session again, which resolves its directory within the workspace roots again (see `spaces.md`), so a side is never given a directory the server no longer allows; one that cannot be bound again never runs one. A space whose environment the server no longer offers has no server side running, and a space that is closed has none.
- **It is given its space.** Starting it gives it the space's identifier, title and directory, and a cancellation that is cancelled when it is to stop; it has no other access to the space, the hub or the conversation. What it returns as an error is a `tomori-environment` `Error`, a message for the space, rather than a bare string, so that the interface can grow without breaking sides. Its own state, intents and anything it presents are described when they are introduced (see the long-term direction below).
- **It never harms the space.** It runs on a thread of its own, as a blocking program that may use whatever it needs, and never blocks the hub, other spaces or the conversation. When it returns an error, panics or cannot be started, the space shows the error in its error line, beside its other errors, and keeps its environment and its conversation; the failure raises no attention in the lobby, which only the problems `spaces.md` lists do. The side is not started again for that binding, and the error ends when the space is bound to another environment. What a side returns as its error is shown to everyone in the space, visitors included, cut to the bound on error text, so it must hold nothing that should stay in the server. Stopping is bounded: the server cancels the side and does not wait for it, except when it stops itself, when once the spaces have closed it waits for the sides it has cancelled for at most the time it allows connections to drain (see `server.md`), and then stops regardless. A side that ignores its cancellation is abandoned. A side is run only once the server is serving, and an environment offered again with another side, or none, stops the side it ran and runs the new one.
- **The environment's instructions are unchanged.** The layer a server side's environment contributes to the agent's instructions is given as for any environment, whether or not a side runs or has failed.

**The state channel.** A server side shares what its environment presents with the clients in its space through a channel of envelopes, each naming the environment and its version around a payload that only the environment's own crates read: any JSON value, which the server carries without reading it. It is the first, small step of state synchronization (#76).

- **State, for whoever joins.** A side keeps a state for its space with `Space::share`, at most 64 KiB of JSON (`tomori_protocol::STATE_LIMIT`), which replaces the one kept before and is sent at once, as `EnvironmentState`, to everyone in the space whom the channel reaches (below), and to whoever joins later, after the space's own state. A state still waiting to be sent on a slow connection is replaced by the newer one, sent after the events queued meanwhile, so that nothing is applied twice.
- **Events, for whoever is there.** A side sends an event with `Space::announce`, at most 4 KiB (`tomori_protocol::MESSAGE_LIMIT`), as `EnvironmentEvent`, to everyone the channel reaches in the space now, together with the state it leaves, which is kept for whoever joins later, at once, so that nobody misses an event or sees it twice. A client ignores an event until it has a state, so a binding's first update, if it is an event, is sent to those in the space as the state it leaves instead. A client forgets what it kept when the space moves to another environment or version, so that it waits for the new binding's state.
- **Intents, validated by the side.** A participant's client asks the side for something with `EnvironmentIntent`, at most 4 KiB, only once the server has sent it the environment's state in the space, so that it never asks a server that runs no side or an older one. The server checks that the sender takes part in the space, refusing a visitor as for any action, and drops an intent quietly, since intents are ambient, when the space is not in the environment and version it names, when it is too large, or when the participant has sent more than 8 at once or 4 a second after that, across their connections, so that reconnecting does not refill the burst. It hands the rest on to the side, at most 64 waiting, with the number the server gives the participant, which everyone in the space knows them by; the side validates them against its own state and acts on those it takes.
- **Who it reaches.** The state and events are sent to everyone in the space, participants and visitors alike, whose `Hello` set `environment_state`, saying it reads them, and listed the environment at the version the side runs for, so that a client from before the channel, which would refuse a message it does not know, and one that presents another version are never sent them. Tomori's own clients set it, and keep the joined space's state and events until the environment's client side takes them; a client without one ignores them.
- **It belongs to a binding.** What a side keeps belongs to the binding it runs for: when the space is bound to another environment, closes or is bound again, what it kept is forgotten, and a side of an earlier binding keeps and sends nothing more. A side's state, events and descriptions that the server refuses, as text that is not JSON or too large, are refused with a message the side may show as its error.
- **What participants point at.** A side may describe what a participant can point at in its environment, with `Space::describe`: up to 32 objects, each an identity of at most 128 bytes and a description the server cleans onto one line, as it cleans everything in the context block, and cuts to 200 characters. A client attends to one as `{"kind": "object", "object": "…"}` (`Resource::object`), and the server resolves it as the words begin, from what the side last described, only while the space is in that environment, telling the agent its description, as `Ada: [Pointing at a lantern glowing by the gate] why is it lit?` (see `spaces.md`). One the side has not described, or an identity longer than any it takes, is dropped and the words kept.

**A client side.** What a client presents of an environment beyond its scenery, from what its server side shares, is the environment's client side, a `tomori-scene` `ClientSide` that the environment's own crate implements and a client registers beside its scenery, with `Sceneries::set_client_side` (see `builders.md`); `tomori-render`'s sceneries hand the registrations to the conversation, and only the environment's crate knows what any of it means. The frame step makes one for the joined space, once the space's scenery has grown in and only while the environment drawn is the one it is registered for, at the version drawn, and drops it on leaving, on a change of environment and in another space, so that each space's begins anew. Each frame it is given the updates the conversation kept for the space, in order, what the participant points at in it and where their head is, and what they do with the trigger, B and the sticks (below), and returns:

- **What it shows**, which the frame carries to the renderer, and the renderer to the environment's scenery through `Scenery::animate`, once a frame before the eyes are drawn, as a value only the environment's scenery reads, such as where its animated models stand.
- **Its intents**, which the conversation sends only as `environment_intent` allows (above).
- **Its sounds**, each at a place in the scene, which play as ambient sounds (see `feedback.md` and `spatial-audio.md`).

The ray points at what the environment shows through the client side's `pick`, which names what it meets first with its identity, a short label and its distance: in a space, where the scenery has grown in and no card is carried, it is pointed at when nothing else the ray meets, a card, a worker or a projected panel, is nearer, ticking as a new target does, and the ray ends on it. While it is pointed at, the participant attends to it as `Resource::object`, and the recording indicator names it by its label, as it names a worker or card. **What the participant does with it.** A client side may mark what it picks as selectable, with `Picked::selectable`. Nothing is selectable unless it says so, and the trigger, B and the sticks reach a client side only as below, each after every rung of Tomori's own in the order `interaction.md` gives the control, and so only while the ray is on something of the environment's or on nothing of Tomori's, so an environment that marks nothing and reads none of them, as the farmyard, behaves as before. Each frame it is told, in its `Input`:

- **Select**, `Input::select`: a pull of the trigger, the right controller's or the desktop's left mouse button, that begins while the ray points at a selectable object of its, as the frame before found it, is the environment's until the trigger is let go, and does not attract the swarm. The client side is told `Select::Pressed` with the object's identity once the trigger is pulled as far as choosing an arrival object takes, if the ray is still on that object, and `Select::Released` with the same identity once the trigger is let go after that, wherever the ray is then, or stops acting, as on losing focus, so that each press is let go once. A pull that slides off the object before it is pressed selects nothing and attracts nothing, and a pull that was a client side's when it went, as the space or its environment changes, is nobody's until it is let go, attracting nothing and selecting nothing in the next. Since the object is the one the frame before found, a press can name an object that has since gone, as a mouse click, which pulls the trigger fully in one frame, does at once: a client side must tolerate a select for an object that has gone, ignoring identities it does not know. A pull that begins anywhere else attracts the swarm as before, even across a selectable object, and one on an object that is not selectable attracts as before and selects nothing. The thresholds are those that choose an arrival object (see `arrival.md`).
- **Back**, `Input::back`: a press of B, the desktop's Backspace, while the ray points at a selectable object of its, as the frame before found it, when nothing else takes it, as `interaction.md` orders; the space then shows no notice that holding B leaves. The press still starts holding to leave, which leaves after a second as ever.
- **Sticks**, `Input::left_stick` and `Input::right_stick`, each axis from -1 to 1, and zero where they are not its or without focus: each stick's push, from when it leaves the middle until it returns there: the right stick's when, as it leaves the middle, no panel is carried, the right wrist's transcript does not show and the ray is on something of the environment's or on nothing of Tomori's, not on a panel, which the push scrolls if it has more than it shows and otherwise leaves alone, nor on a card or a worker; and the left stick's when, as it leaves the middle, the space's environment allows no travel on this headset, because it declares none or travel is turned off (see `locomotion.md`), and the ray is likewise on nothing of Tomori's, such as a panel carried. The desktop's keys stand in for them as for the rest of the frame step (see `desktop.md`).

The environment uses back only to back out of what it shows, so that B keeps no hidden destructive meaning (see `interaction.md`). What the participant does reaches only the client side of the joined space, on their own device; the server side learns of it only through the client side's intents.

A client side never runs on the server, and the spectator runs none: it draws an environment's scenery, as Tomori's own spectator draws the farmyard's yard, without what a client side shows, such as its chickens.

How this maps onto #76's plan: the kept state is #76's snapshot on join, here the whole state rather than its collections, values and series, which an environment encodes in its own payload; events are its transient events; intents are its intents, refused quietly for now rather than answered with a reason, since the first environment's are ambient; a newer state replacing an unsent one is its coalescing, without a lane of its own yet. Not yet: deltas with revisions and repair by snapshot, interest, a shared clock estimated from keepalive (an environment that needs one carries its own clock in its payload), per-space limits on the rate of a side's updates, and persistence across restarts. Each can be added beside these messages, as further optional fields and variants, without changing them. The GitHub environment's cards (see `github.md`) predate the channel: its `WatchCards`, `Cards` and `PlaceCard` could become interest, a state and intents of the GitHub environment's own side. Until they do, the card board, its messages and the scene's cards are the one environment-shaped part of the core, with GitHub's issues, pull requests, checks and labels in `tomori-protocol`'s `Card`. Moving them into the GitHub environment's crates is a follow-up, and needs what the channel does not have yet: state that reaches participants only, since visitors see no cards, as a repository may be private; placements kept with the space across restarts, as its record keeps them now; pointing at any of up to 200 cards, each described to the agent, where a side describes at most 32 objects; and letting participants pick up and place what an environment's client side (above) draws, which the farmyard's chickens did not need, so its interface does not have it yet.

Arrival, outside any space, uses the Minimal grid as its waiting area (see `arrival.md`).

An environment may allow travel beyond the room, declaring a locomotion profile with walkable surfaces (see `locomotion.md`). Until environments have server sides (#75), a headset build declares it beside the environment's scenery; Sky and the Minimal grid declare none, and the farmyard declares teleport about its yard (see `farmyard.md`).

An environment may say, in its registration, where Tomori's own projection wall stands in it, its `stage` anchor, with `Environment::with_stage`, the middle of its curved row of slots, which otherwise stands below the swarm, and declare projection walls of its own, with `Environment::with_walls`, general hooks that name no particular environment; the farmyard declares one, its noticeboard, and Sky and the grid neither. The Tomori wall and what is on it belong to the space and move with it; an environment's walls and the panels left floating in it are kept for the space and that environment, hidden while the space is in another (see `projection.md`).

**Anchors for the agent and the workers.** An environment may also say, in its registration, where Tomori's coordinator stands in it, its `agent` anchor, with `Environment::with_agent`, and where the arrangement of the space's delegated workers stands, its `workers` anchor, with `Environment::with_workers`, each a pose in the space's coordinates, as `stage` is (the next anchors of #79). The server sends those given in the space's state, `SpaceState::anchors`, while it offers the space's environment, and none otherwise: an optional field that an older client ignores and an older server never sends, so that either reads as the default layout. Each is used only when it is finite, within 20 m of the space's middle on each axis, as walls are, and has an orientation, and is made upright, turned only about the vertical, as a wall is; one that is not is left out, by the server and again by a client, which then uses the default. The server bounds an environment's `stage` the same way, leaving out one that is not finite, beyond 20 m or without an orientation, and making it upright; before, it used any `stage` as given, so a `stage` beyond 20 m or without an orientation is now ignored, as walls are. Without them, the layout is exactly today's: the swarm centred 1.4 m up and 2.3 m straight ahead of home, facing home, and the workers on their arc about home. Sky, the grid, the farmyard and the GitHub prototype declare neither. Anchors, like an environment's walls and its placement (below), come from the code an operator compiles into their server and clients, trusted as the rest of it is, and are bounded as above; nothing keeps the swarm, a worker or a sign clear of a participant's head (see `security.md`), which moves with travel and differs for each participant, so an environment that stands them where people stand puts them in someone's face, an accepted limit of this step.

- **The agent anchor** is where the swarm's middle stands, its eye facing along the anchor's +Z, in a space in that environment, for everyone in it, whether or not their client draws the environment, as the Tomori wall stands at `stage` for everyone. The anchor changes at once, and the swarm follows it at its usual bounded speed, at most 0.85 m/s, from where it was, as it moves between its shapes, and back to its default place on leaving the space, so that it never jumps (see `arrival.md`). What hangs on the swarm moves with it: its rings, the halo behind it as it faces and the ring on the floor beneath it, on the room's floor, or, for a swarm raised above its usual 1.4 m, on the floor it would stand that high over; the cubes workers fly out from and back to; and the agent's voice, which comes from the swarm (see `spatial-audio.md`); and the Tomori wall, which by default stands below the swarm, stands below it there, moved and turned as the swarm is, never lower than 0.3 m above the room's floor nor beyond 20 m, unless the environment gives `stage` too (see `projection.md`). The status pill, arrival's objects and home do not move; nor do the spectator's neutral view and its voice's fallback (see `spectator.md`).
- **The workers anchor** is the origin of the workers' arrangement: by default the arc about home, carried to the anchor and turned with it, its front along the anchor's −Z. Workers still fly out from the swarm, wherever it stands, to their places, and back to it.
- **Which way they face:** the agent anchor faces along +Z, the workers anchor looks along −Z. A wall, and so the swarm, faces along its pose's +Z towards whoever reads it, while a participant at home looks along −Z, so the workers anchor reads as where someone stands to see the workers ahead of them, and the agent anchor as something facing them.
- **Where workers stand is the client's.** An environment's client crate may register how its workers are placed, a `tomori-scene` `WorkerPlacement`, beside its scenery, with `Sceneries::set_worker_placement` (see `builders.md`). It applies only in a space bound to that environment while the build draws it, at the version the space names; elsewhere, for a space in an environment drawn at another version or not at all, on the grid, and in a build that registers none, the default arc stands at the workers anchor. Unlike a client side, which waits for the scenery to grow in, it applies from the moment the space is joined, as its scenery grows, so that workers arrive at their places rather than at the arc's and then move. A placement is asked where a worker stands as it arrives, given the arrangement's origin, the worker's identity, the worker that delegated to it, its state, its remembered slot and where the workers already standing stand, in the order of their slots; where what it gives is not finite or not within 90 m of the space's middle on each axis, or it panics, the worker stands where the default arc would put it. It is the build's own code, run on the frame step's thread, at most once for each of at most 64 live workers in a frame, so it must be quick. Whatever a placement does, the default's guarantees hold: a live worker's place never moves when the workers' titles, states, order or membership change, only when the arrangement changes, as when the space changes environment, when each live worker is placed again, in the order of their slots, its place changing at once and its flock following at the particles' usual bounded speed, at most 6 m/s; each identity's slot is remembered as before; the ray points at workers where they stand; and the spectator, given the same sceneries, places them as the headset does (see `spectator.md`). A placement may stand workers together; nothing parts them. A placement that panics is never called again in that client, which says so once in its log, and its workers stand on the arc from then on. Tomori's own environments register no placement.
- **A worker's sign stands above it**, wherever it is placed, as it does on the default arc, and moves with it when the arrangement changes: the signs of every worker that moved are placed again together, so that none is pushed aside by where a neighbour's stood before, and a small turn or shift of the arrangement leaves each above its worker. Where another sign is already within 0.5 m above or below and 1 m across of that place, as for workers placed together, it stands at the first place clear of every other sign, row by row 0.55 m above it, at most ten rows, and column by column beside it along the arc about home, a sign's width apart, within a quarter turn of the worker's bearing from home, so never behind a participant at home; where every such place is taken, as for very many workers at one spot, it stands above its worker, overlapping another, rather than further off. A sign moved off its own place, above or beside its worker, has a post down to it. The default arc's signs, whose rows and columns are further apart, each stand above their own worker as before.

An environment may contribute a layer of the instructions Tomori gives a space's agent, about what it presents and which tools and data sources to use (see `spaces.md`), given with the environment when it is offered. Sky and the Minimal grid contribute none yet; an environment the server no longer offers contributes none. A space keeps only its environment's identifier, not its layer: the server looks the layer up in the environments it offers whenever it shows the space's instructions or gives them to the agent, so that a space restored after a restart is given the same layer as one just created or changed to that environment, whatever order the server was configured in.

Long-term direction, not yet requirements:

- An environment is much more than scenery. It can be dynamic and data-backed, with its own interaction, such as Fantail Observe, a separate project that shows a running system's topology and telemetry spatially. Environments are expected to be built on the server-owned scene graph and modules in `scene-modules.md`.
- The space's agent is aware of its environment: the information and data it presents, and what each participant is pointing at or has selected in it. Pointing and selection identify concrete resources, with their identity and context such as the time window, not only positions or pixels.
- A participant can refer to what they are pointing at in speech, such as "Tomori, can you investigate why this server is overloaded?". The agent receives the identified resource with the request, and uses the tools available in that space, such as its MCP servers, to investigate and answer.

## Rationale

The user intends to build specific environments for different kinds of work, so a space represents much more than a cosmetic place: it pulls in the information and interaction that work needs. Tying the environment to the space keeps every participant looking at the same thing, which shared pointing and the agent's awareness of the environment depend on. Stated by the user, speaking from the headset, in November 2026, with Fantail Observe as the example to connect eventually.

In November 2026 the user decided, from the headset, that a space's environment can be changed after it is created, from the Space section of the hand menu: by owners only, for everyone in the space, and kept in the space's record (issue #74). Since the space moves as a whole, everyone keeps looking at the same thing. In November 2026, as environments came to agree versions with clients (issue #75), the user decided that a change is never refused because someone in the space cannot present the new environment: a participant or visitor who cannot present it falls back to the grid with a warning, as when joining such a space. So nobody's client, and no visitor, can keep owners from changing their space.

In November 2026 the user decided that environments are compiled into both the server and the clients, and that client and server agree on each environment through a protocol version (issue #75, the environment framework proposal in #90, section 1). Offering a client only the environments it presents keeps whoever creates a space, or moves one, from choosing an environment they would see only as the grid themselves, and keeps a client side from reading state it does not understand; the fallback remains for spaces someone else created, and for servers that no longer offer an environment. Clients and servers from before versions keep working with each other and with newer ones, since every addition is optional. The GitHub environment's prototype is listed by every client built on `tomori-scene`, because its cards are drawn by the shared scene rather than by a scenery, so that agreeing on versions does not take it from Tomori's own headset. Bounding the list a client sends keeps what the server holds for a connection small.

In November 2026 the maintainer agreed that the core is a clean slate that environments register themselves against: the builders register nothing by default, Tomori's own programs register Tomori's own environments as another project's would, and each environment's crates own its identity, in a common crate, with server and client crates beside it. Before, the core knew Sky and the GitHub prototype, and their identities were in `tomori-protocol`, so an environment offered by the core made the server library depend on it while its client half depended on rendering crates whose tests depend on the server, a package cycle; keeping environments out of the core removes it, and lets an environment be added without changing the core.

In November 2026 the user decided that an environment's server side is a full program in the server, not only a producer of scenery: it runs where the server's reach and credentials are, and clients never hold them (issue #75, the environment framework proposal in #90). It runs on a thread of its own, as the GitHub environment's source already reads GitHub, so that a failing or slow side cannot harm the hub or another space, and each binding runs it once so that a restored space is treated as a new one. A downstream project's environment, such as one that shows a running system's telemetry, is built on it. The state it shares with clients, its intents and its client side are separate steps of the same framework (#75, #76).

In November 2026, to give a new environment's animated objects a home whose server side owns them, the maintainer asked for a first generic state channel rather than messages for one environment's objects: an envelope naming the environment and its version around an opaque, bounded payload that the environment's own crate encodes, with intents that the server side validates, additive and gated, as a deliberately small first step towards #76. The payload is JSON, as the control messages are, which answers #76's question of encoding for now. A kept state and announced events rather than deltas keep the first step small: a state is replaced whole, so a gap is repaired by the next one. Only clients that say they read the channel and present the environment at its version are sent it, since an older client would refuse a message it does not know. Objects are described by the side and kept by the server, rather than asked of the side as an utterance begins, so that resolving attention never waits for a side's thread or runs its code under the hub's lock.

In November 2026, building the farmyard as a downstream environment would build one, with the principle that a dedicated environment customises everything about itself, its chickens needed a client side to present them: a general hook, `ClientSide`, in `tomori-scene` beside the frame step that drives it, registered beside a scenery and drawing through `Scenery::animate`, so that no crate but the environment's own knows what it shows. The value it shows is opaque to the renderer, rather than a list of model instances, so that an environment can draw anything with its scenery; its sounds are ambient sounds, rather than cues, since they mark nothing.

In November 2026 a downstream project's environment needed participants to choose what they point at, go back and turn a view, and could only select by dwelling on a target for 0.9 s, since a client side was told nothing of the trigger, B or the sticks. The maintainer asked for them as an additive part of `Input`, through the pointing machinery the hand menu and the projection panels use, giving each control to an environment only where it would otherwise do nothing, or, for B, only while the environment is what the participant points at and nothing else wants it, so that no control gains a hidden meaning and holding B still leaves. Selection is opt-in for each object, so that a pull on the farmyard's chickens still attracts the swarm.

In November 2026 the maintainer decided that whatever the participant points at gets the input, Tomori's own interface first: the environment gets the trigger, B and the sticks only when the ray is on something of the environment's, or on nothing of Tomori's. Giving the environment each control where it would otherwise do nothing had made the right stick the environment's while pointing at a panel, which scrolling a panel pointed at then needed back, and left later uses of the grip, B and A on walls and checklists to undo it again; each control now has one order of rungs (see `interaction.md`), with the environment's after Tomori's own.
In November 2026, as the next step of #79 towards a downstream environment that shows a globe of regions and pods, the maintainer asked that an environment say where the coordinator and its workers stand, and that its client crate position the workers by its own algorithm, such as ringing the pod a participant selected, rather than on the fixed arc. The anchors follow `stage`: poses in the environment's registration, sent to everyone with the space, so that every participant sees the coordinator in the same place and the Tomori wall still stands below it. Where each worker stands stays the client's, as it always was, since a worker's place is presentation and changes with every arrival; so the placement is a client-side hook registered beside the scenery, applied only where the environment is drawn, and the scene keeps the guarantees that make workers easy to find and point at whatever the placement does, by asking it only as a worker arrives or the arrangement changes. The swarm glides to its anchor rather than jumping, as it never jumps between arrival's steps. Defaults that reproduce today's layout keep Sky, the grid, the farmyard and the GitHub prototype exactly as they were. The anchors are poses rather than the volumes #79 proposes for the workers, since a pose with a placement covers the cases asked for; `presentation` and `arrival` anchors, and the coordinator's light turning towards a resource, are later steps.

## Scope

The space's shared state and its creation and change requests in `crates/protocol` and the server, the environment state channel (`crates/protocol`'s `channel.rs`, the server's `channel.rs` and the hub's handling of it, `tomori-environment`'s `Space`, and `tomori-scene`'s `client_side.rs` with the frame step's use of it, `channel.rs` and the conversation's environment updates and intents), the environments and versions clients list in `Hello` and the server offers in `Welcome`, the server sides of environments and the interface `crates/environment` defines for them, the environments' own crates (`crates/environment-*`) and their registration by Tomori's own programs (`crates/server-app`, and the `app` features of `crates/client-quest` and `crates/client-spectator`), the dependency rule's test in `bake/tests/dependencies.rs`, the clients' environment selection and the hand menu's change of it, the agent and workers anchors (`tomori-protocol`'s `Anchors`, `tomori_server::Environment::with_agent` and `with_workers`, `tomori-scene`'s `anchors.rs`, the swarm, `delegation.rs`'s placement of workers, the renderer's swarm rings and worker signs, and the spectator's use of them), and, long term, the scene module host and how participant pointing reaches the agent.

Open questions, not yet decided:

- Whether an environment is a scene module, a set of modules, or something that hosts them.
- How participant pointing and selection are delivered to the agent, and how that relaxes `scene-modules.md`'s current separation of the scene graph from agent interactions.
- How an environment's data sources, such as a telemetry service, relate to the tools available to the space's agent.
- Whether the trigger pulled while pointing at nothing an environment shows, which attracts the swarm, should also reach its client side, and how a hand-tracking pinch, which does not act as the trigger yet, selects; and whether selecting should tick as choosing does (see `feedback.md`), which it does not yet, so that an environment can decide what a selection means first.
- Which object a worker is working on: the protocol's workers carry no resource, so a placement cannot yet float a worker near what it investigates; associating one, and how it reaches the client, is a later step.
- Whether the workers anchor becomes a volume, as #79 proposes, and whether a placement moves to the environment's server side, so that a participant whose client cannot draw the environment sees workers where the others do.
- How far a client side's interface grows beyond what the farmyard needed, presenting replicated state, picking, intents and ambient sounds (above): for instance, whether a client side contributes panels, tools or locomotion of its own, and whether it should run anywhere but on the headset, as in the spectator.
