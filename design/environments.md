# Environments

This describes how a space's environment relates to the space. The first part is a current requirement; the rest is long-term direction, and the initial design must not prevent it.

## Requirement

Each space is bound to exactly one environment at a time. The environment is chosen when the space is created, is part of the space's shared state, and is the same for everyone in it, participants and visitors alike. A participant does not switch a space's environment on their own device; the per-device environment choice, such as squeezing the grip to switch between Sky and Minimal, does not apply inside a space.

**Changing it.** An owner may change a space's environment after it is created, to another the server offers, from the hand menu's Space section (see `hand-menu.md`), with `set_environment`. The change applies to the whole space at once: the server checks that the requester is an owner and that it offers the environment, keeps the new environment in the space's record, so that a restart keeps it (see `spaces.md`), and sends the space's state to everyone in it, participants and visitors alike, who switch to it, the new scenery growing out of the space as it does on joining. Someone joining later arrives in it, and the lobby lists the space in it. A collaborator or visitor is refused, and their menu does not offer the change; an environment the server does not offer is refused, naming those it does; and a closed space keeps the environment it had. The conversation, queue, workers and settings are unaffected, except that the agent is given its instructions again, since the environment's layer changes with it. A server says in the space state that it changes environments, and a client offers the change only to such a server, so older servers and clients work as before; an older client sees the new environment only when it next joins. The server offers the environments a space can use, as it offers backends and directories; today Sky (`crates/environment-sky`), first, so that it is the default for a space whose creator names none, and the Minimal grid, labelled Grid; and, only when it is started with `--github-repository`, the GitHub environment's prototype, whose spaces show a repository's open issues and pull requests as cards (see `github.md`). A server another project builds may offer more, registered after these, or in place of one with the same identifier, through `tomori-server`'s builder (see `builders.md`). A space kept across a restart in an environment the server no longer offers stays in it. A client that doesn't know a space's environment shows the Minimal grid and says which environment it lacks, rather than substituting another environment silently.

**A server side.** An environment may have a server side: a program in the server process, registered with the environment through `tomori-server`'s builder (see `builders.md`), that can reach whatever the server can, such as data sources and APIs, and whose credentials, endpoints and configuration stay in the server. It is trusted like the rest of the server, since it is compiled in. An environment without one, such as Sky and the Minimal grid, behaves as it always has.

- **It runs while a space is bound to its environment.** The server starts it for a space when the space is bound to the environment, whether it is created in it, an owner changes it to it, or it is bound to its session again after a restart in it, and stops it when the space is bound to another environment, when the space's session closes, and when the server stops. It is started once for each binding, so that a space restored after a restart is started as one just created, whichever order the server offers its environments and lists its kept spaces in. A space restored after a restart runs none until it is bound to its session again, which resolves its directory within the workspace roots again (see `spaces.md`), so a side is never given a directory the server no longer allows; one that cannot be bound again never runs one. A space whose environment the server no longer offers has no server side running, and a space that is closed has none.
- **It is given its space.** Starting it gives it the space's identifier, title and directory, and a cancellation that is cancelled when it is to stop; it has no other access to the space, the hub or the conversation. What it returns as an error is a `tomori-environment` `Error`, a message for the space, rather than a bare string, so that the interface can grow without breaking sides. Its own state, intents and anything it presents are described when they are introduced (see the long-term direction below).
- **It never harms the space.** It runs on a thread of its own, as a blocking program that may use whatever it needs, and never blocks the hub, other spaces or the conversation. When it returns an error, panics or cannot be started, the space shows the error in its error line, beside its other errors, and keeps its environment and its conversation; the failure raises no attention in the lobby, which only the problems `spaces.md` lists do. The side is not started again for that binding, and the error ends when the space is bound to another environment. What a side returns as its error is shown to everyone in the space, visitors included, cut to the bound on error text, so it must hold nothing that should stay in the server. Stopping is bounded: the server cancels the side and does not wait for it, except when it stops itself, when once the spaces have closed it waits for the sides it has cancelled for at most the time it allows connections to drain (see `server.md`), and then stops regardless. A side that ignores its cancellation is abandoned. A side is run only once the server is serving, and an environment offered again with another side, or none, stops the side it ran and runs the new one.
- **The environment's instructions are unchanged.** The layer a server side's environment contributes to the agent's instructions is given as for any environment, whether or not a side runs or has failed.

Arrival, outside any space, uses the Minimal grid as its waiting area (see `arrival.md`).

An environment may allow travel beyond the room, declaring a locomotion profile with walkable surfaces (see `locomotion.md`). Until environments have server sides (#75), a headset build declares it beside the environment's scenery; Sky and the Minimal grid declare none.

An environment may contribute a layer of the instructions Tomori gives a space's agent, about what it presents and which tools and data sources to use (see `spaces.md`), given with the environment when it is offered. Sky and the Minimal grid contribute none yet; an environment the server no longer offers contributes none. A space keeps only its environment's identifier, not its layer: the server looks the layer up in the environments it offers whenever it shows the space's instructions or gives them to the agent, so that a space restored after a restart is given the same layer as one just created or changed to that environment, whatever order the server was configured in.

Long-term direction, not yet requirements:

- An environment is much more than scenery. It can be dynamic and data-backed, with its own interaction, such as Fantail Observe, a separate project that shows a running system's topology and telemetry spatially. Environments are expected to be built on the server-owned scene graph and modules in `scene-modules.md`.
- The space's agent is aware of its environment: the information and data it presents, and what each participant is pointing at or has selected in it. Pointing and selection identify concrete resources, with their identity and context such as the time window, not only positions or pixels.
- A participant can refer to what they are pointing at in speech, such as "Tomori, can you investigate why this server is overloaded?". The agent receives the identified resource with the request, and uses the tools available in that space, such as its MCP servers, to investigate and answer.

## Rationale

The user intends to build specific environments for different kinds of work, so a space represents much more than a cosmetic place: it pulls in the information and interaction that work needs. Tying the environment to the space keeps every participant looking at the same thing, which shared pointing and the agent's awareness of the environment depend on. Stated by the user, speaking from the headset, in November 2026, with Fantail Observe as the example to connect eventually.

In November 2026 the user decided, from the headset, that a space's environment can be changed after it is created, from the Space section of the hand menu: by owners only, for everyone in the space, and kept in the space's record (issue #74). Since the space moves as a whole, everyone keeps looking at the same thing. When environments agree versions with clients (issue #75), a change is also to be refused, saying who cannot follow, when someone in the space cannot present the new environment.

In November 2026 the user decided that an environment's server side is a full program in the server, not only a producer of scenery: it runs where the server's reach and credentials are, and clients never hold them (issue #75, the environment framework proposal in #90). It runs on a thread of its own, as the GitHub environment's source already reads GitHub, so that a failing or slow side cannot harm the hub or another space, and each binding runs it once so that a restored space is treated as a new one. A downstream project's environment, such as one that shows a running system's telemetry, is built on it. The state it shares with clients, its intents and its client side are separate steps of the same framework (#75, #76).

## Scope

The space's shared state and its creation and change requests in `crates/protocol` and the server, the server sides of environments and the interface `crates/environment` defines for them, the clients' environment selection and the hand menu's change of it, and, long term, the scene module host and how participant pointing reaches the agent.

## Validation

- Create a space and confirm that its state names its environment, that a second participant sees the same environment, and that squeezing the grip inside the space doesn't change it.
- Test, with a server offering two environments, that an owner's change reaches everyone in the space, participants and visitors, the lobby listing and someone joining later; that the agent is given its instructions again; that a collaborator's or visitor's change, an unknown environment and a change to a closed space are refused without effect; and that the changed environment survives a restart. Test that the hand menu offers the server's environments only to an owner on a server that changes them, marking the current one, while anyone else reads the environment; and that the headset's scenery, the desktop window's and the spectator's follow the space's state when it changes.
- Test that the server offers Sky first and the Minimal grid, and binds a space whose creator names no environment to Sky.
- Test that an environment registered through the builder is offered, and, against a fake backend's recorded instruction entries, that the agent is given the `tomori-environment` entry of a space's environment: when the space is created in it, when an owner changes to it, removed when an owner changes to one with no layer, and when the space is bound again after a restart, with the environments offered before or after the kept spaces are listed again; for Tomori's own identifiers given a layer and for another project's environment alike.
- Confirm that the creation choices offer only the environments the server lists.
- Test, with an environment registered through the builder with a server side that records what it is given, that the side is started once with the space's identifier, title and directory when a space is created in the environment, when an owner changes a space to it, and when a kept space in it is bound to its session again after a restart, but not before, nor when it cannot be bound again, whichever order the server offers the environments and lists the kept spaces in; and that its cancellation is cancelled exactly once when the space is changed to another environment, its session closes, and the server stops. Test that Sky, the Minimal grid and an environment without a side start nothing.
- Test that a server side that returns an error, panics or cannot be started leaves its space with its environment and conversation, shows the error in the space until the space is bound to another environment, is not started again for that binding, and does not delay or stop other spaces, the hub or a conversation; and that a side that ignores its cancellation does not stop the server stopping.
- Test that a space's environment layer of the instructions is the same with a server side, one that failed, and none.
- Join a space whose environment the client doesn't know, for example with a test server that names an unknown one, and confirm that the client shows the grid and names the missing environment.

Open questions, not yet decided:

- Whether an environment is a scene module, a set of modules, or something that hosts them.
- How participant pointing and selection are delivered to the agent, and how that relaxes `scene-modules.md`'s current separation of the scene graph from agent interactions.
- How an environment's data sources, such as a telemetry service, relate to the tools available to the space's agent.
