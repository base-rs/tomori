# Environments

This describes how a space's environment relates to the space. The first part is a current requirement; the rest is long-term direction, and the initial design must not prevent it.

## Requirement

Each space is bound to exactly one environment at a time. The environment is chosen when the space is created, is part of the space's shared state, and is the same for everyone in it, participants and visitors alike. A participant does not switch a space's environment on their own device; the per-device environment choice, such as squeezing the grip to switch between Sky and Minimal, does not apply inside a space.

**Changing it.** An owner may change a space's environment after it is created, to another the server offers, from the hand menu's Space section (see `hand-menu.md`), with `set_environment`. The change applies to the whole space at once: the server checks that the requester is an owner and that it offers the environment to the requester's client (see below), keeps the new environment in the space's record, so that a restart keeps it (see `spaces.md`), and sends the space's state to everyone in it, participants and visitors alike, who switch to it, the new scenery growing out of the space as it does on joining, or, if their client cannot present it, the grid with a warning saying what it lacks. Someone joining later arrives in it, and the lobby lists the space in it. A collaborator or visitor is refused, and their menu does not offer the change; an environment the server does not offer that client is refused, naming those it does; and a closed space keeps the environment it had. The conversation, queue, workers and settings are unaffected, except that the agent is given its instructions again, since the environment's layer changes with it. A server says in the space state that it changes environments, and a client offers the change only to such a server, so older servers and clients work as before; an older client sees the new environment only when it next joins. The server offers the environments a space can use, as it offers backends and directories: those its program registers (see Registering environments, below). Tomori's own server, `tomori-server`, offers Sky (`crates/environment-sky`), first, so that it is the default for a space whose creator names none, the Minimal grid, labelled Grid, and the farmyard (`crates/environment-farmyard`, see `farmyard.md`); and, only when it is started with `--github-repository`, the GitHub environment's prototype, whose spaces show a repository's open issues and pull requests as cards (see `github.md`). A server another project builds offers those it registers through `tomori-server`'s builder, in the order it registers them, a later one with the same identifier in place of the earlier, by the same rule as an option that changes one on the configured server with `Server::with_environment` (see `builders.md`). A space kept across a restart in an environment the server no longer offers stays in it. A client that cannot present a space's environment shows the Minimal grid and says which environment, and which version, it lacks, rather than substituting another environment silently (see below).

**Agreeing on the environment.** Client and server agree on each environment through its protocol version, an integer, 1 unless the environment is registered with another (see `builders.md`). A change to what the server and a client side exchange that an older client side can ignore, such as a new optional field with a default or a new variant read as unknown, keeps the version; any other change raises it.

**Registering environments.** The core, the framework crates that the server and clients are built from, knows no environment but the Minimal grid, which every client draws built in, as its waiting area and its fallback, at the identifier and version in `tomori-protocol`, `GRID` and `GRID_VERSION`. Every other environment, Tomori's own included, is registered by an application, Tomori's own programs or another project's, through the same builder calls: `tomori-server`'s builder and `tomori-client-quest`'s start with no environments and register nothing by default. Tomori's own server program, `tomori-server` in the `tomori-server-app` package, registers Sky, the grid and the farmyard, and the GitHub prototype's `--github-repository` option from its server crate; Tomori's own app, the `tomori` executable and APK, behind `tomori-client-quest`'s default `app` feature, and Tomori's own spectator, `tomori-spectator`, behind `tomori-client-spectator`'s, register Sky's, the farmyard's and the GitHub prototype's client halves. The core keeps what an environment's crates build on: the server's card board, which the GitHub prototype's server half fills through a `CardSource` and offers with `Server::with_cards`, and the scene's cards, which a client presents over the grid for any environment whose spaces show them, as the protocol's card messages do, until the state channel (below) replaces them. So no core crate depends on an environment's crate, and an environment's crates may build on the core, and on each other, without a cycle.

**An environment owns its identity.** Each environment's identifier and protocol version are defined once, in its own common crate, such as `tomori-environment-sky`'s `ID` and `VERSION`, which its server half registers it with and its client half presents it at, so the two cannot disagree. To bump one, raise its version there, change its server and client halves together, and say so in the pull request's title, which becomes its release note, and in a `Breaking:` paragraph of its description, since clients of the earlier version then show the grid in its spaces. The GitHub prototype's is `tomori-environment-github`'s. A test in the apps keeps the two sides agreeing: `tomori-server-app`'s runs the `tomori-server` executable, offering the GitHub prototype too, and requires that Tomori's own app and spectator are each offered exactly what a client listing nothing is, and present exactly that, at the same identifiers and versions.

**Making an environment.** An environment is up to three crates, named for it after `tomori-environment-`:

- **Common**, `tomori-environment-NAME`: what both halves share, its identity, `ID`, `VERSION` and `LABEL`, and, as it grows, its message formats and shared simulation. It builds no renderer or GPU stack, such as `tomori-render` or wgpu, so that a server builds it.
- **Server**, `tomori-environment-NAME-server`: what runs only in the server, such as its server side (`tomori-environment`'s `ServerSide`), its data sources and its credentials, which never reach a client or the common crate, and the command-line options that configure it, which it adds to a server's builder. It builds no renderer either. The GitHub prototype's server crate holds its GitHub client and token and adds `--github-repository`.
- **Client**, `tomori-environment-NAME-client`: how a client presents it, such as its scenery (`tomori-render`'s `Scenery`), with a `register` function that registers it on a client's `Sceneries` at the common crate's identity. It may depend on the renderer.

An environment with nothing for one half has no crate for it: Sky has no server half, so a server offers it by registering its common crate's identity with `tomori_server::Environment`. An application registers each environment it offers or presents, the server's with `Builder::environment` and a client's with `tomori::Builder::register` or `Sceneries`, as Tomori's own programs register Sky. A test in the `tomori-bake` package reads `cargo metadata` and `cargo tree` and fails when an environment's common or server crate builds the renderer or GPU stack; when its common or client crate builds an environment's server crate, which holds what stays in the server, or its common crate a client crate; when a core crate depends on an environment's crate other than through its `app` feature, which is Tomori's own app in the package that also builds it, or on Tomori's server program, in any kind of dependency; or when a core crate builds an environment's crate at all with every feature but its `app`, as through another core crate's `app`.

- **A client says what it presents.** A client lists in `Hello` the environments it can present, each with its version: the grid, the environments it registers sceneries for, at the versions it registers them with, and those it presents over the grid, as the GitHub prototype's cards are presented by the shared scene (see `github.md` and `builders.md`). Tomori's own headset, desktop window, console and spectator list the Minimal grid, Sky and the farmyard, at version 1, and the GitHub environment's prototype, at version 1; a build that registers nothing lists the grid alone. A client that lists nothing, as one from before versions, is offered every environment, as before.
- **The server offers each client what it presents.** The server offers each environment in `Welcome` with its version, and offers a client that lists environments only those it lists with the same identifier and version, in the server's order. The first of those is what a `CreateSpace` from that client naming no environment is bound to; a `CreateSpace` naming none from a client offered nothing is refused, saying that the server offers no environment it can present. A `CreateSpace` or `set_environment` from it naming an environment the server offers, but not to it, is refused, saying that this client cannot present that environment at the server's version and naming those offered to it, or saying there are none; one the server does not offer at all is refused as unknown, naming those offered to it. A refusal names only the server's own identifiers and versions, never the request's text. The server skips an entry of a client's list that it cannot read, or whose identifier is empty or longer than the server takes (1024 bytes), keeps at most the first 64 of the rest, and reads a list that is not a list as none at all; an older server sends no versions, and a client reads each environment it offers as version 1.
- **A change reaches everyone.** An owner's change of a space's environment, to one offered to the owner's client, applies to the whole space at once, and is never refused because someone else in it, participant, visitor or spectator, cannot present the new environment: their client falls back to the Minimal grid and says what it lacks, as when joining such a space (below), as soon as the space's state reaches it. Only the requester's own list decides what they may choose.
- **The lobby lists every space.** The lobby lists each space whatever environment it is bound to, whether or not the client can present it, and anyone may join one in an environment they cannot present.
- **A client that cannot present it falls back.** A space's state names its environment's version when the server offers the environment, and names none from an older server or when the server no longer offers it. A client joining a space whose environment it lacks, or presents at another version than the state names, shows the Minimal grid and the space's state, and names the environment and the version the space needs; it never draws its own, other version of the environment instead. A state that names no version, as from an older server, is drawn by identifier, as before, and a client that lacks the environment then names it alone. On the headset, the hand menu's Space section names what it lacks in place of the environment's name. The Minimal grid is built in, at its own version, whatever version a scenery drawn with it is registered at (see `builders.md`).

**A server side.** An environment may have a server side: a program in the server process, registered with the environment through `tomori-server`'s builder (see `builders.md`), that can reach whatever the server can, such as data sources and APIs, and whose credentials, endpoints and configuration stay in the server. It is trusted like the rest of the server, since it is compiled in. An environment without one, such as Sky and the Minimal grid, behaves as it always has. An environment's server side is in its server crate, if it has one (see Making an environment, above); one that holds nothing that must stay in the server, such as the farmyard's, which runs a simulation its clients replay, may be in its common crate, which builds `tomori-environment` but not `tomori-server`.

- **It runs while a space is bound to its environment.** The server starts it for a space when the space is bound to the environment, whether it is created in it, an owner changes it to it, or it is bound to its session again after a restart in it, and stops it when the space is bound to another environment, when the space's session closes, and when the server stops. It is started once for each binding, so that a space restored after a restart is started as one just created, whichever order the server offers its environments and lists its kept spaces in. A space restored after a restart runs none until it is bound to its session again, which resolves its directory within the workspace roots again (see `spaces.md`), so a side is never given a directory the server no longer allows; one that cannot be bound again never runs one. A space whose environment the server no longer offers has no server side running, and a space that is closed has none.
- **It is given its space.** Starting it gives it the space's identifier, title and directory, and a cancellation that is cancelled when it is to stop; it has no other access to the space, the hub or the conversation. What it returns as an error is a `tomori-environment` `Error`, a message for the space, rather than a bare string, so that the interface can grow without breaking sides. Its own state, intents and anything it presents are described when they are introduced (see the long-term direction below).
- **It never harms the space.** It runs on a thread of its own, as a blocking program that may use whatever it needs, and never blocks the hub, other spaces or the conversation. When it returns an error, panics or cannot be started, the space shows the error in its error line, beside its other errors, and keeps its environment and its conversation; the failure raises no attention in the lobby, which only the problems `spaces.md` lists do. The side is not started again for that binding, and the error ends when the space is bound to another environment. What a side returns as its error is shown to everyone in the space, visitors included, cut to the bound on error text, so it must hold nothing that should stay in the server. Stopping is bounded: the server cancels the side and does not wait for it, except when it stops itself, when once the spaces have closed it waits for the sides it has cancelled for at most the time it allows connections to drain (see `server.md`), and then stops regardless. A side that ignores its cancellation is abandoned. A side is run only once the server is serving, and an environment offered again with another side, or none, stops the side it ran and runs the new one.
- **The environment's instructions are unchanged.** The layer a server side's environment contributes to the agent's instructions is given as for any environment, whether or not a side runs or has failed.

**The state channel.** A server side shares what its environment presents with the clients in its space through a channel of envelopes, each naming the environment and its version around a payload that only the environment's own crates read: any JSON value, which the server carries without reading it. It is the first, small step of state synchronization (#76).

- **State, for whoever joins.** A side keeps a state for its space with `Space::share`, at most 64 KiB of JSON (`tomori_environment::STATE_LIMIT`, equal to `tomori_protocol::STATE_LIMIT`), which replaces the one kept before and is sent at once, as `EnvironmentState`, to everyone in the space whom the channel reaches (below), and to whoever joins later, after the space's own state. A state still waiting to be sent on a slow connection is replaced by the newer one, sent after the events queued meanwhile, so that nothing is applied twice.
- **Events, for whoever is there.** A side sends an event with `Space::announce`, at most 4 KiB (`tomori_environment::EVENT_LIMIT`, equal to `tomori_protocol::MESSAGE_LIMIT`), as `EnvironmentEvent`, to everyone the channel reaches in the space now, together with the state it leaves, which is kept for whoever joins later, at once, so that nobody misses an event or sees it twice. A client ignores an event until it has a state, so a binding's first update, if it is an event, is sent to those in the space as the state it leaves instead. A client forgets what it kept when the space moves to another environment or version, so that it waits for the new binding's state.
- **Intents, validated by the side.** A participant's client asks the side for something with `EnvironmentIntent`, at most 4 KiB, only once the server has sent it the environment's state in the space, so that it never asks a server that runs no side or an older one. The server checks that the sender takes part in the space, refusing a visitor as for any action, and drops an intent quietly, since intents are ambient, when the space is not in the environment and version it names, when it is too large, or when the participant has sent more than 8 at once or 4 a second after that, across their connections, so that reconnecting does not refill the burst. It hands the rest on to the side, at most 64 waiting, with the number the server gives the participant, which everyone in the space knows them by; the side validates them against its own state and acts on those it takes. **A choice of a row** of a list panel the side published, which a participant makes with A or the trigger, reaches the side in the same inbox as an intent only the server makes, `Intent::choice`, whose `Intent::chosen` names the side's own panel and the row by their ids, and whose payload is empty; a client's intent is never one, whatever its payload says (see `panel-actions.md`). **An action the agent takes** on what the side describes reaches it in the same inbox, `Intent::action`, likewise made only by the server (see `environment-actions.md`). **Who is present**: a side reads who takes part in its space now, by their numbers, with `Space::present`, which the server says as it sweeps, about once a second, its participants whose connections are open, never its visitors, and `None` until it has said, so that a side can let go of what someone who has left held, or tidy up once nobody is there, as the farmyard's campsite does. **Where each is**: a side reads where each participant in its space is, `Space::presence`, a `Presence` of each, their head and each controller's grip pose where their presence says it, carried into the environment's own coordinates, turned and all, with when the server said it: as their client reports it, at most 20 times a second for each (`tomori_environment::PRESENCE_INTERVAL`), participants only, never visitors, and only while they are present; so that a side can check that what someone asks for is within their reach, and know where their hand holds what they hold, as the farmyard's beach does (see `physics.md`).
- **Who it reaches.** The state and events are sent to everyone in the space, participants and visitors alike, whose `Hello` set `environment_state`, saying it reads them, and listed the environment at the version the side runs for, so that a client from before the channel, which would refuse a message it does not know, and one that presents another version are never sent them. Tomori's own clients set it, and keep the joined space's state and events until the environment's client side takes them; a client without one ignores them.
- **Where participants are: zones.** A side may declare **proximity zones** with `Space::declare_zones(Vec<Zone>)`, replacing those declared before, as when a console's terminal changes: each named as an object's reference is (`valid_reference`, `ZONE_NAME_BYTES`), a sphere, `Zone::sphere(name, around, radius)`, or a vertical cylinder, `Zone::cylinder(name, around, radius, below, above)`, a radius across the floor and a band from `below` beneath its point to `above` over it, about a point in the environment's own coordinates, `Around::point`, or an anchor it declares or placed, `Around::anchor(name)`, or an object it describes with a position, `Around::object(id)`, wherever it stands as the zone is looked at, nobody being within one whose anchor or object is not there. The server refuses, saying why, and keeps none of it, a declaration `check_zones` refuses, which a side's tests may call: more than 16 zones (`ZONE_LIMIT`), a name refused or given twice, a radius outside 0.3 to 20 m (`LEAST_ZONE_RADIUS`, `MOST_ZONE_RADIUS`), a band of no height or reaching more than 20 m (`MOST_ZONE_HEIGHT`) below or above, a margin outside 0 to 5 m (`MOST_ZONE_MARGIN`), a dwell over a minute (`MOST_ZONE_DWELL`), a point not finite or beyond 30 m of home once carried, or an anchor's or object's name of no bytes or more than `IDENTITY_LIMIT`. As the hub sweeps, about once a second, the server takes each participant whose client reports where they are, by their head, as it was last reported, in the space's coordinates, against each zone carried there (`tomori-server`'s `zones.rs`): they enter it at its radius and band and stay within it until they are its **margin** beyond them, 0.5 m unless it says (`ZONE_MARGIN`, `Zone::leaving_beyond`), the hysteresis an anchor's `notify_within` keeps, so that the agent's proximity and the environment's agree; nobody whose report is 5 seconds old or more (`PRESENCE_STALE`, the server's own `presence::STALE`), as a headset asleep, counts, nor anyone whose client says they are away (`Engagement::Away`), as a headset lifted off says at once, and so a zone they were in empties; nor a visitor, nor the spectator, which report no presence; nor anyone who has left the space. It tells the side each zone's **occupancy**, how many are within it, as an intent only the server makes, `Intent::zone(Occupancy)`, whose `Intent::occupancy` names the zone and its count and whose participant is 0, in the same inbox as choices and actions: every zone at the first sweep after it is declared, whatever its count, so that a side declaring again learns where each stands, a zone declared again under the same name keeping who was within it, so that someone within its margin but not its radius stays within it; then each change of the count, one between nobody and somebody only once it has lasted the zone's **dwell**, none unless it says (`Zone::dwelling`), so that someone passing by, or stepping out a moment, is not told, and any other at once. The server takes a side's declaration at most once every 0.9 s (`ZONE_INTERVAL`), as it makes an anchor's changes: one sooner waits, the latest replacing the one before, and is taken at the hub's next sweep once it may be. A client's intent is never one, whatever its payload says. An occupancy the side's inbox has no room for is told at a later sweep, so that the side's count is never left wrong. The side is told only of its own zones: those of its binding, in its space, forgotten with the binding as everything it keeps is. Looking costs at most the zones times the participants, 16 by 64, distance checks a sweep, made into room the server keeps with the zones, so that the checks allocate nothing, beside one list of heads gathered for each space with zones; presence reports themselves, many a second, do no more than before. Who is within a zone the side is not told (see `security.md`).
- **Where participants are: engagement and staleness.** `Space::presence` (above) is the pull interface a side reads where participants are by: no stream is pushed to it, and what it holds is bounded by the participants present, each told at most 20 times a second. Each `Presence` also carries the engagement their client last reported, `Presence::engagement`, `tomori_protocol::Engagement`, or none where it has said nothing, which the server tells the side at once as it changes, whatever holds their reports back (`Inbox::set_engagement`), since a headset lifted off says it is away and then reports nothing more, and its `at` says how stale it is: a side judges a report `PRESENCE_STALE`, 5 seconds, old or more as a headset that has stopped, as zones do.
- **It belongs to a binding.** What a side keeps belongs to the binding it runs for: when the space is bound to another environment, closes or is bound again, what it kept is forgotten, and a side of an earlier binding keeps and sends nothing more. A side's state, events and descriptions that the server refuses, as text that is not JSON or too large, are refused with a message the side may show as its error.
- **What participants point at.** A side may describe what a participant can point at in its environment, with `Space::describe`: up to 1,024 objects (`tomori_environment::OBJECT_LIMIT`), every one of which the server keeps and finds for pointing, `inspect` and `act`, whatever order the side describes them in and however many there are, each an identity of at most 128 bytes (`IDENTITY_LIMIT`) and a description the server cleans onto one line, as it cleans everything in the context block, and cuts to 200 characters (`DESCRIPTION_LIMIT`). A client attends to one as `{"kind": "object", "object": "…"}` (`Resource::object`), and the server resolves it as the words begin, from all that the side last described, never only the agent's ambient list of them (below), only while the space is in that environment, telling the agent its description, as `Ada: [Pointing at a lantern glowing by the gate] why is it lit?` (see `spaces.md`). One the side has not described, or an identity longer than any it takes, is dropped and the words kept.
- **Ids for the agent to inspect.** An object a side describes may carry a **reference**, `Object::with_reference`: a short, stable name for it, opaque to Tomori, unique among the objects the side describes and the same for as long as the object is, such as `hen/marigold` or `panel/checkout-error-rate`; it is separate from the object's identity, which clients name it by and the agent is not told. The server keeps a reference only of 1 to 64 bytes (`tomori_environment::REFERENCE_BYTES`) of ASCII letters, digits, `-`, `_`, `.` and `/` (`tomori_environment::valid_reference`), so that it can neither end the context block nor read as anything but a name, and only the first object's of two with the same; it describes an object whose reference it refuses without one. The agent is told the object's **id**, its reference after the identifier of the environment it belongs to, so that ids of different environments never collide, in parentheses after its description, as `Ada: [Pointing at Marigold, a hen in the farmyard, wandering by the coop (id farmyard:hen/marigold)] what's she up to?`; an object without a reference is described as before, with nothing added. The environment's identifier is cleaned and cut to 64 characters, and a reference has no `:`, so the last `:` of an id ends the environment's identifier; the block's bound, 1,000 characters, is unchanged, and a description and id together, at most 200 and about 130 characters, always leave room for more.
- **Where an object stands.** An object a side describes may say where it stands, `Object::at(position)`, in the environment's own coordinates, as the side knows it now, such as a rack's middle or a hen where she pecks: a side whose object moves describes it again where it is. The server carries it into the space's coordinates as it does anchors, and describes an object whose position is not finite, or beyond 30 m of home on any axis once carried, without one. With it, the agent goes to it when asked, with `move_agent object ID`, and stands a worker by it, with `place_worker` (see `mcp.md`); without it, only an anchor by it gives either a place. The farmyard describes each hen where she stands. It may also say how far it reaches from there, `Object::with_extent(radius)`, from 5 cm to 3 m (`EXTENT_LIMITS`), or else is taken as 15 cm (`DEFAULT_EXTENT`), which a diagram's line to it rings it with (see `diagrams.md`); the farmyard gives its bonfire and sticks theirs.
- **The agent's ambient list.** The objects a side describes do three jobs, kept apart: every one is reached, pointed at, inspected and acted on by its id, as above and below; what someone points at, or anything else the note before their words names, is described to the agent from all of them; and only the agent's ambient awareness of them is cut short, for what it costs in the agent's context. `presence` lists at most 32 (`tomori_server`'s `ambient::AMBIENT_LIMIT`), about 2,000 tokens at the longest descriptions, as `objects`, each with its description, its id where it has a reference and its position where the side gives one, with `total`, how many the side describes, and, where that is more, a note that the rest are reached by their ids all the same (see `mcp.md`). They are ranked by how much they matter to whoever the turn is for, the speaker as every tool's form that names nobody finds them (`mcp.md`), by what that one participant pointed at and where that same participant's head is, never by what someone else pointed at meanwhile: first what they pointed at as they began their latest words for the agent, in the order their client named it, taken once those words are queued, so that words begun and cancelled, or never transcribed, change nothing, and kept for each participant, the latest 16 to speak; then the one their head faces most nearly, within 10° and 30 m, or, of those within 1° of the nearest, the one nearer their head; then those within 3 m of their head or in view, within 45° of where it faces and 30 m, nearer first; then the 8 pointed at, inspected or acted on most lately in the space, the latest first, which is the space's, shared by everyone in it, whoever pointed, inspected or acted; then the rest, in the order the side described them, which breaks every tie, so that a side never orders what it describes for the agent's sake. An object the side gives no position is ranked only by being pointed at, noted lately or its order. **Stable through a turn:** the list is ranked once in each turn of the agent's, the first time it is asked for, and stays the same objects, by identity, in the same order, for the rest of the turn, each described as the side describes it now, those the side no longer describes left out and none added, however what it lists moves or whoever speaks meanwhile; a list ranked when the side described nothing is ranked again once it does. **Cheap:** ranking is one pass over what the side describes, one key of 8 bytes for each, and a partial sort of the first 32, done at most once a turn; the identities and references are indexed as the side describes them, outside the hub's lock, so that finding one is never a search, and those replaced are freed after the lock is released. What the server keeps is bounded: 1,024 objects, each at most an identity of 128 bytes, a description of 800, a reference of 64 and 8 offers of 32, about 2 KB with its index, so about 2 MB a binding at the worst, with up to 4 objects pointed at for each of 16 participants and the 8 noted lately, by identity.
- **Inspecting an id.** A side may answer the agent's questions about what it describes with a reference, by giving its space an `Inspector`, with `Space::inspect_with`: a hook that takes a reference and answers with JSON of the environment's own choosing, such as a hen's name, activity, position, what she wears and where she roosts, or, for an object backed by a metric, its query, the range it shows, its source's name, its labels and its latest value (`tomori-prometheus`'s `Metric`, see `data-sources.md`); with nothing, for a reference it has nothing by; or with an `Error`, whose message the agent is told. The space's agent asks through the `inspect` tool (see `mcp.md`). The server asks only about a reference the side describes now, among all it describes, listed to the agent or not, in the environment the space is in now: an id of another environment, or one no object has now, as when what it named has gone, is refused, saying so, without asking the side. It asks the side's inspector on a thread of its own, never the side's, the hub's or the scheduler's, so that a side busy with its own work, such as a slow query, holds up neither the agent nor anyone else, and the inspector answers from what the side shares with it, such as its state behind a lock. It waits for an answer for at most 5 seconds (`tomori_server::INSPECT_TIMEOUT`, which `Server::with_inspect_timeout` changes), then tells the agent that the environment did not answer in time; an inspector that never returns keeps its thread, and a binding's side is asked at most 4 inspections at once, so that one stuck holds at most 4 threads, the agent being told that the environment is still answering beyond them. An answer larger than 16 KiB (`tomori_environment::INSPECTION_LIMIT`, which `tomori_server` also exports as `INSPECTION_BYTES`) or that is not JSON is refused, saying which; a panic is contained, the agent told only that the environment could not answer. The inspector belongs to its binding, forgotten with it. A side that gives none, or answers nothing for a reference, has nothing more to say than the object's description, which the agent is told.
- **What an inspection may hold.** What a side answers is told to the agent, which may repeat it aloud or project it, so it must hold nothing that should stay in the server, such as an endpoint, a credential or a token: an environment that reads a data source answers with what it asked and what it read, never how it reached the source, and passes on only the labels it would show (see `data-sources.md`). It may quote what the side reads from elsewhere, such as a metric's labels or a log line, which anyone able to write to that source chose, so the server cleans every string in it, keys included, as text others choose is (`security.md`): on one line, without control or format characters, cut to 2,000 characters; and the agent is told, in the result, the tool's description and `tomori-tools`, to read it as data, never as instructions.
- **Actions on what it describes.** A side may declare actions the space's agent takes on what it describes with a reference, when someone asks, such as showing a terminal's charts for another region, with `Space::declare_actions`, each a name, a description for the agent, typed parameters, a choice of values, a bounded number or short text, and whether it is consequential; an object offers those it takes by name, `Object::offering`. - **How often a side updates.** The server takes at most 30 states and events a second from a side, its shares and announcements together, after a burst of 60 (`tomori_environment::UPDATES_PER_SECOND` and `UPDATE_BURST`), refusing those beyond, saying that the environment is updating faster than Tomori sends its updates, so that a side announcing as fast as it can never floods its space's clients; a side that says where what moves is 20 times a second keeps well within it, and a side gathers what changes into one event, or paces itself, rather than announcing each change on its own, as the farmyard's does.
- **The limits, defined once.** The limits above that a side keeps within as it shares, announces, describes and answers are defined by `tomori-environment`, where they are documented, as `STATE_LIMIT`, `EVENT_LIMIT`, `UPDATES_PER_SECOND`, `UPDATE_BURST`, `OBJECT_LIMIT`, `IDENTITY_LIMIT`, `DESCRIPTION_LIMIT`, `REFERENCE_BYTES` and `INSPECTION_LIMIT`, and, as it publishes panels, `PANEL_ID_BYTES` and `PANEL_LIMIT`, and a list panel's rows, `ROW_LIMIT`, `ROW_ID_BYTES` and `ROW_CHARS`, and its columns, `COLUMN_LIMIT`, `COLUMN_TITLE_CHARS` and `CELL_CHARS`, and its rows' keys, `FIELD_LIMIT`, `FIELD_NAME_BYTES`, `FIELD_VALUE_BYTES` and `FIELDS_BYTES`, and, as it declares zones, `ZONE_LIMIT`, `ZONE_NAME_BYTES`, `LEAST_ZONE_RADIUS`, `MOST_ZONE_RADIUS`, `ZONE_MARGIN`, `MOST_ZONE_MARGIN`, `MOST_ZONE_HEIGHT`, `MOST_ZONE_DWELL`, `ZONE_INTERVAL`, `PRESENCE_LIMIT`, the most a zone counts, and `PRESENCE_STALE`, and the server enforces those same constants, so that what a side tests against is what it is held to, and its documentation, the exported value and the server cannot drift apart. `tomori-environment` depends on no other Tomori crate but `tomori-protocol`, for the chart spec it re-exports, which cannot depend on it in turn, so `tomori-protocol` keeps its own `STATE_LIMIT` and `MESSAGE_LIMIT` for what it carries, and the server's tests check that they equal `STATE_LIMIT` and `EVENT_LIMIT`; `tomori_server::INSPECTION_BYTES` is `INSPECTION_LIMIT`. **Its ambience.** An environment's client crate may declare what it sounds beneath the conversation, a `tomori-scene` `ambience::Ambience` (`tomori-client`'s, re-exported), and register it beside its scenery with `Sceneries::set_ambience`: its **beds** (`Bed`), stereo loops heard alike everywhere, such as wind; its **loops** (`Loop::at` a point or `Loop::along` a line of up to 16 points, with a `radius`), mono loops placed where they are, such as a river or a waterfall; and its **calls** (`Call`), mono sounds heard now and then, each one of its variants, `every` so often, from `around` its points within a `spread`, at a `pitch` and `gain` within their ranges, such as a bird's song, or, with a `run` (`Run::weighted` by how likely each length is, with its `gap`, `vary` and `order`), several times in a row from one place, as a ruru calls; each at a `gain` in decibels, in the environment's own coordinates. Each sound is a named `Slot`, `Slot::new(name, load)`, whose `load` gives its file's bytes, Ogg Vorbis, or `Slot::missing(name)`, which is silent, so that an environment declares its slots before it has their sounds and a slot plays once its file is added. How this maps onto #76's plan: the kept state is #76's snapshot on join, here the whole state rather than its collections, values and series, which an environment encodes in its own payload; events are its transient events; intents are its intents, refused quietly for now rather than answered with a reason, since the first environment's are ambient; a newer state replacing an unsent one is its coalescing, without a lane of its own yet. Not yet: deltas with revisions and repair by snapshot, interest, a shared clock estimated from keepalive (an environment that needs one carries its own clock in its payload), and persistence across restarts. Each can be added beside these messages, as further optional fields and variants, without changing them. **Loose objects.** An environment whose participants pick things up, carry, throw and stack them declares them as bodies of `tomori-physics`, an optional crate its common crate builds on, which builds no renderer, nothing in the core depending on it: simulated by its server side, with Rapier, behind the crate's `simulation` feature, which only a server builds, and mirrored by its client side without it, so that a client never simulates. - **One facing convention.** Every anchor faces along its pose's +Z, the way it looks: the participants arriving look along it, the agent's eye looks along it, the Tomori wall's and every wall's face looks along it, and the workers' arrangement faces along it, towards whoever watches it, as the agent does. `tomori_protocol::Pose::at(spot).facing_towards(target)` makes such a pose, so that an environment never turns one backwards: `Pose::at(balcony).facing_towards(arrival)` faces the arrival, and `Pose::at(arrival).facing_towards(balcony)` arrives looking at the balcony. - **Home stays at the space's origin, facing −Z.** A space's coordinates, which presence, placement, the agent's tools and every client use, always have home, where participants arrive, at their origin, facing −Z, as they always have. An environment's own coordinates are carried into them: the server carries every anchor and wall the environment registers, and a client that draws the environment carries its scenery, its walkable surfaces and its client side, by the carriage that takes the arrival to home, `tomori_protocol::Pose::carriage`. For an arrival whose orientation is exactly home's, `Pose::HOME`'s, the carriage is unturned exactly (one made with `facing_towards` to face −Z rounds differently, and is turned by the difference of their yaws as any other), so that for the default arrival it is exactly the identity, bit for bit on every platform, and the default layout is exactly as it was. The server sends the arrival, in the environment's own coordinates, in the space's state, `SpaceState::anchors.arrival`, only where it is not the default, and the agent, workers anchors carried; a client draws the scenery with the carriage, turns its declared walkable surfaces with it (`Locomotion::carried`), and gives its client side the ray and head in the environment's own coordinates and plays its sounds where they are in the space, so that an environment's crates work wholly in their own coordinates and never see the space's. The grid, drawn for an environment a build lacks, is never carried. Leaving a space, the environment shrinking away is drawn with its carriage as the participant last saw it, in their room, until it has gone (see `arrival.md`). The server uses an arrival that is finite, within 1 km of the environment's origin and has an orientation, made upright; and each anchor and wall, carried, as walls are bounded: finite, within 30 m of home on each axis, with an orientation, made upright; one that is not is left out, by the server and again by a client, which then uses the default. An environment whose arrival moves where its content stands relative to home raises its version, so that a client of the earlier version, which knows no carriage, shows the grid rather than its content in the wrong place; the farmyard did, to version 2.
- **Arrival.** Participants arrive at home, at the space's origin facing −Z: the rig, which travel moves, goes back home on joining, on leaving, on a change of environment and wherever the profile is none, as before (see `locomotion.md`), so it now goes to the environment's arrival. Travel from there is as free as the environment's locomotion profile allows. The status pill, the hand menu and the wrist stay with the participant.
- **The status wall's home: beneath the agent, by default.** Where the environment names no status wall, the space's own, the Tomori wall, stands beneath the agent's home, by one rule the server and every client share, `tomori_protocol::entourage`: the middle of its row 0.88 m (`entourage::BENEATH`) directly below the swarm's middle, facing the way the agent faces, towards the arrival, and curving about the point 2.3 m before it, so that the swarm stands above it with a clear gap of 0.23 m between the swarm's lowest reach and the top of its row; and never lower than 0.52 m above the floor where participants arrive, its row's bottom edge then 0.39 m above it (`entourage::wall_beneath`). In the default layout, that is 2.3 m ahead of home at 0.52 m, where the wall has always stood. An environment that names a status wall, one of its own or one it stands (`Environment::with_status_wall`, see `projection.md`), needs no agent home 1.4 m up; otherwise it keeps its agent's home at least 1.4 m above the floor, so that the wall stands beneath it with the gap. The status wall never travels: it stays at its home whatever the agent does, following, called or asked to go. An environment gives the boxes of its scenery that walls and the agent stay clear of, its solids, with `Environment::with_solids`; the farmyard gives the same ones its sightline tests check. The edits to the Tomori wall that a space keeps, its grid, shape, tilt and lock (#242, #245, #262), stand over its home wherever it is the space's own (see `projection.md`); its pose is never kept, so it stands at the home of whichever environment the space is in.
- **The agent's home.** The agent's home is the environment's `agent` carried into the space, or else the default. The agent, the swarm or whatever avatar shows it (see `avatars.md`), appears there as the space opens, and again, at the new environment's home, when the space changes environment: it is carried there at once, in the shape it has, rather than gliding across the scene, as the scenery grows in about it; only the swarm's cubes, for the participant joining, fly in from the lobby as it does, a flight of their client's alone (`arrival.md`). It stays there until it goes to someone, as it follows the speaker or is called or asked to go (below), and goes back there. What hangs on it moves with it: its rings, the halo behind it as it faces, the cubes workers fly out from and back to, and its voice, which comes from where it stands, from whatever avatar shows it, as do the points workers fly from and back to (see `spatial-audio.md`). **The ring on the floor is its home ring**, and never moves with it: it stays at home, in every movement mode, as the agent follows, is called or is asked to go, on the space's floor beneath the agent's home, however high the home stands, 1.5 cm up (`FLOOR_LIFT`), as the floor's other markings stand, or, where the environment's `home` anchor asks for it with `Anchor::with_ring(cluster::RingAt::UnderHome)`, under the home, 1.4 m beneath the point it stands about (`cluster::RING_BELOW`, the swarm's usual height, so that it lies at the swarm's foot, as it lay beneath a swarm before there were homes), never below the space's floor, the floor where participants arrive (the client does not look for other surfaces or solids beneath the home, so an environment floating its home over a lower level or a raised object keeps its point at least 1.4 m above it), 1.25 m about it (`anchors::FLOOR_RING`), or, where the home's workers stand in a ring (below), on their ring, about the same point within a millimetre, as much of it as they take, its cubes evenly either side of the way the ring faces, so that the side it leaves open is centred straight behind that; drawn at full brightness while the agent is within half its radius of home, it dims only to 0.85 of that by one radius further out (`HOME_RING_AWAY`), so that it plainly marks home, where the workers stand, while the agent is away, and brightens as it comes back. The roaming agent has nothing beneath it: the satellites already say where it is and what it carries. It moves to a new home at once, whatever avatar shows, as the space opens or changes environment, and stays where the participant saw it, with the environment, while a space being left shrinks away (`arrival.md`). The frame step gives the renderer the ring, `anchors::HomeRing`, with `Renderer::set_home_ring`, and the spectator draws it alike; a renderer given none, as one an older frame step drives, draws it beneath the swarm, and an older client still draws it beneath the agent wherever it goes.
- **Following the speaker.** In a space whose owner chose **Follow the speaker** (below), the agent comes to whoever it is talking with, its partner, as a person would, and the server decides where, from what it already has, sending everyone where it stands as `SpaceState::summoned`. As a participant presses X for words to the agent, not an answer, a name or a title, it begins turning to face them at once, gently (below), sent as `SpaceState::facing`, a yaw and not a move; a press let go within 0.4 s, a tap, moves nothing more, even once its words are given. Held 0.4 s, it commits, from where their head was as the words began. It stays where it is, only turning, when it already stands within 3 m of their eyes (`follow::NEAR`; 4 m is the alternative the maintainer named), whichever way they face, and even where it stands in their way or behind something: **distance alone moves it**. Someone it stands in the way of asks it to move, and, since coming to them again would only bring it along the same line, it asks where they would like it (see `mcp.md`). Otherwise it comes **straight towards them** from where it is, to their **conversation spot**: on the straight line from their eyes to where it is, **2 m** from their eyes horizontally (`follow::CONVERSATION`, the maintainer's choice, comfortably within 3 m so that it never stands at the edge of moving again; 2.5 m is the alternative to try), whichever way they face or what they look at, behind them if that is where it comes from, its middle 0.1 m above their eyes, never lower than 1.1 m nor higher than 2.4 m above the floor, facing them (`tomori-server`'s `follow.rs`). An environment may declare a **follow height** instead, with `Environment::with_follow_height(metres)`, 1 to 10 m (`FOLLOW_HEIGHTS`; one beyond them, or not finite, is left out with a warning): the agent's middle then hovers that high above the space's floor, the floor where participants arrive, but never more than 3.5 m above their eyes (`follow::HIGHEST_ABOVE`) nor less than 0.1 m above them; where nothing at that height is clear, as beneath a ceiling the environment declares a solid, it stands 0.1 m above their eyes instead, as by default but unbounded by the floor's heights. It is above the space's floor rather than theirs, so that the agent hovers at one height over the scene, above its side walls, for people on the main floor or a low bridge alike, as the environment that asked for it wants; the cap keeps it within talking distance of anyone on a lower level, such as a basement, where it would otherwise hover far above them, in or above its ceiling, and 3.5 m is what 5.1 m leaves above eyes 1.6 m up on the main floor, about 60° up from 2 m away, above them and never in front of their face; and nobody on a deck higher than it has it below their eyes. With a follow height, its nearness, the 3 m within which it only turns, is measured across the floor, horizontally, since the agent hovers well above whoever it comes to and their eyes are never 3 m from it in space: within 3 m across the floor it only turns, however high it hovers. It applies alike for a huddle and for **Call Tomori here**, which share the spot; beside an object it stands 0.5 m above the object (`follow::ABOVE_OBJECT`), but never lower than 0.1 m above the asker's eyes, so that it stands by what it is beside rather than high over it. A client's own summons, held and let go to an older server that keeps summons, stands it before the summoner as `entourage::summoned` does: such a server knows no follow height, and a client is never sent one. It chooses no side and keeps off no line of sight: someone who turns as it sets off finds it coming straight to them, not to what was their left. A spot is refused where the swarm's box, its reach (half of `entourage::SWARM` each way) and 0.1 m more on every side, meets the environment's solids, a wall shown, its slots 5 cm thicker, or a panel floating within 3 m of them, or comes within 0.8 m of anyone's head, or where anything of those stands between their eyes and its middle; then it swings round them at the same distance, 10° at a time, one way and then the other, by the least that is clear, to half a turn, and with none clear it only turns. Its way there goes by a waypoint where the straight way passes through a solid or near a head, as ever. While the agent answers someone else, with their words queued, being given or answered, a question or approval waiting, or another participant speaking, a new speaker's press only glances at them for 2 s, and the agent goes to them as their words are given, in queue order, which is when it begins answering them; so does a pinned agent glance. Once it arrives somewhere it stays at least 10 s before going for another partner, only turning, unless the new one stands more than 6 m from it or cannot see it. Two or more who spoke to it within the last minute, standing within 4 m of the speaker, are a **huddle**, served from one spot: on the straight line from the middle of their heads to where it is, about 2 m from the nearest of them, at their eyes' height on average, facing that middle, clear and seen by each, swung round them as for one where it is not; else from the speaker's own spot. Visitors never turn or move it. Words that come to nothing, cancelled, with no speech in them or failing to transcribe, stop a move begun for them where it has reached, facing them from there, or where it was, if it had barely begun; coming straight towards them, it already faces them, within the 5° it turns to someone by, and does not turn at all. Every move is logged at info with whom it followed and why.
- **On the environment's ground.** Where an environment gives its walkable ground, `Environment::with_navmesh`, the navmesh its clients land participants on, derived alike on the server from the description its crate shares (`tomori-server`'s `follow/ground.rs`), the agent's heights are measured from the floor beneath it rather than the space's floor: its middle stands as high above the floor beneath its spot as the person's eyes stand above theirs, 0.1 m more, within 1.1 to 2.4 m above that floor, so that it is never below someone on a deck or terrace. Their floor is the highest at least 0.3 m beneath their eyes, or, where none is or one within 1 m of them stands more than 1 m higher, as standing in their room just beyond a terrace's edge, that one. A spot over only other levels, more than 1 m from theirs, or over no floor within 1 m of one, as over the yard below a terrace's edge or the gap its rock cuts there, or over no floor at all where theirs is a raised level, more than 1 m above the space's floor, as beyond the farmyard's upper terrace, is refused and it swings round them as for a solid; over no floor near another level on the space's floor's own level, as over a meadow beside a path, it stands as over theirs; only where nowhere about them is on their level does it stand over whatever is there, clear of it, at their eyes' height. Its middle keeps 0.5 m from every floor, above or below, there and 0.3 m about it, never inside a raised level, beneath a floor with none under it, nor with a floor between it and their eyes. It is never near enough, however near, below their floor by less than 0.5 m or stuck in a floor, nor serves a huddle so, and those more than 1.5 m apart up and down are no huddle. An environment that gives no ground is unchanged.
- **Keeping with them through the exchange.** While the agent's partner speaks to it, holding X past a tap or being transcribed, while it thinks about their words, and while it replies, until its turn has ended and its speech has played, held speech included, it keeps with them. Its voice, not its text turn, ends its reply: what it has queued to say counts from as it is queued, through the seconds synthesis takes after its turn has ended, before its voice begins, until the last of it has been sent, at the rate it plays, and played, so that it keeps with them for as long as they hear it. That is the server's own measure of playback, alike for every listener, visitors and desktops too, each frame counted 0.7 s past its end for its lead and the client's buffer (`SPOKEN`), rather than each headset's report of its own playback, which stays on the headset for the swarm's look (see `speech.md`) and is absent where nobody listens; and speech of which nothing is queued, sent or finished for a minute (`STALLED`), as when synthesis hangs, counts no more, so that its reply always ends. It turns to face them as they move, sent as `SpaceState::facing`, once they stand more than 5° from the way it faces, so that it turns with them smoothly without turning at each sway of their head, unless it is on its way somewhere, and the swarm draws in about where they stand now. Once they have moved more than 0.25 m or turned more than 15°, it waits until they have stood still, within those, for 0.75 s (`hub/following.rs`'s `SETTLE`, `STILL` and `STILL_TURN`), so that it never chases each step nor moves while they travel, as by a teleport or flying, only once they arrive, or, where they never stand still so long, as walking about or looking around, 3 s after they began moving (`RESTLESS`), so that it is never left far behind; then, more than 3 m from them, it follows them on, straight towards where they stand now from wherever it has reached, by the same glide, waypoint and stream. Its 10 s dwell is for going to someone else, never for keeping with the partner it went to. Where they stand in a huddle, with others who spoke to it lately within 4 m of them, it stays while it stands within 4 m of the middle of the huddle's heads, however they move within it, and otherwise follows the huddle, served from one spot as ever, or them alone if they have left it. It keeps with nobody while pinned, where it moves only when asked or is kept home, for a tap, once their words come to nothing, after it was sent somewhere or called, and once its reply is over, until their next words or its next reply aloud. **A reply to a note about someone is an exchange with them**: where Tomori's notes alone began its turn (`timers.md`) and one of them is about a participant still in the space, as someone coming near an anchor is (below), it goes to them as its speech is first queued for synthesis, from where they stand now, and keeps with them through its reply as above, by the same trigger, settle, dwell and huddle; a turn with no speech in it moves nothing. Told of several people at once, it goes to whoever the latest such note is about, since the queue keeps notes in the order they came, a note coalescing going to the back. A timer's note, or a worker's (`events.md`), names no participant, even where its text mentions one, since it is about the workers, not someone arriving; nor do notes that ride on someone's words, whose turn is theirs. **A reply aloud to nobody's words is an exchange with whom it talks with**: where nothing about anyone it would go to began its turn, as a sub-agent's report, a message typed into its session outside Tomori, a timer's or a worker's note or a space event, it goes to its partner as its speech is first queued, and keeps with them through its reply, by the same rules, where they are still in the space, have reported where they are, and were last in conversation with it within 10 minutes (`hub/following.rs`'s `TALKED`): they spoke to it, it went to them for their words, a note about them or a walk, they called it or it went to them by its own `move_agent`, or its reply to them sounded. Such a reply is no conversation of theirs, so the 10 minutes still count from their last; with no such partner, as when several are in the space and none spoke to it lately, it speaks from where it is. It does not where it is pinned, moves only when asked or walks with someone, who it keeps with already. Its partner, and when they last talked, outlast its going home. Where its panels go in such a reply follows the same partner (see `projection.md`). Speech queued for the turn that the notes began, and not frames of an earlier reply still playing, starts it, since a note waits a quiet moment after the agent's turn. Visitors are never kept with. Each move is logged as following is, with its reason, such as that they moved while it answered them, how far it stood from them, where it goes, and how, gliding, by a waypoint or streaming, and how far that is from them; a move it gives up, with nowhere beside them clear, is logged as only turning to them, and the end of keeping with them is logged once.
- **Walking with someone.** Asked to walk with someone, it keeps with them throughout, as with a partner through an exchange, whether or not either speaks: once they settle more than 3 m away it comes straight to 2 m from them, facing them, and turns to keep facing them, by the same settle, restless and turning rules, its dwell not applying to them; it does not go home, its return delay counting again from the walk's end. Someone else speaking to it meanwhile is answered from where it is, as while it is busy with another: it glances at them for 2 s (`GLANCE`) as they begin, and stays with whoever it walks with, as a person walking with a friend answers a passer-by without leaving them; a reply to a note about someone else moves it nowhere. A participant starts one by voice, "walk with me" or "come along", which the agent answers with `move_agent with NAME`, gated by `requested_by` as its moves asked for are (see `mcp.md`), so that only a participant's words start one, for themselves, or, asked by an owner, for another participant who has reported where they are; or with **Tomori: walk with me** in the hand menu, `ClientMessage::WalkAgent { walking: true }` (see `hand-menu.md`). A walk unpins it, and is offered and taken in either mode where it may move, never where it stays home, nor by or for a visitor. It ends as they ask it to stay, follow again or go home, by voice through `move_agent stay`, `follow`, also where it moves only when asked, leaving it where it stands, or `home`, or from the hand menu with **Tomori: stay here**, **Tomori: follow again**, **Send Tomori home** or **Tomori: stop walking with me**, `WalkAgent { walking: false }`; as it is called or sent anywhere else; as they leave the space; as the space keeps it home; or after half an hour with nothing between them, neither of them speaking nor they moving (`hub/following.rs`'s `WALK_IDLE`), each logged with its reason. The server sets `SpaceState::walks`, and `walking`, the number of whoever it walks with, which a client reads to offer the walk or its end; `presence`'s `mode` is `walking with Ada#23`. Like following, it is for the run only.
- **How it goes.** Clients glide the agent's place, its rings, halo and voice with it, its ring on the floor staying home, to where the space's state stands it, as a hovering creature moves (`tomori-scene`'s `glide.rs`): a lead sets off along the way at once, at up to 1.06 m/s, slowing to 0.6 of that within 0.6 m of a waypoint, so that it slows round it no harder than it sets off, and the place follows it on a critically damped spring, at 6.25 a second, integrated exactly in steps of at most 1/240 s, so that it eases in, reaching nine tenths of its speed in about 0.6 s, at most at 2.4 m/s², cruises no faster than its lead, settles without overshooting, and moves alike at any frame rate; a new place to go, given on its way, carries on from how it moves, its velocity and acceleration never jumping, turning round smoothly when sent back. Its orientation, a quaternion, follows a lead that turns along the shortest arc at up to 90° a second, on a spring at 6 a second, so that every turn eases in and out, never faster than 90° a second before anyone's face, and a turn of 5°, as it keeps facing someone who moves, is a slight, eased lag of about 0.8 s rather than a twitch. Going further than 0.8 m, it turns towards where it goes as it sets off, never for a way straight up or down, and back to face whoever it faces, or the way it is to face there, as it arrives, blending over its last 1.6 m, so that it never glides sideways or backwards across a room; within 0.8 m it sidesteps, facing them. Each client glides from where it last stood towards where the server stands it, never from sampled positions, so every client converges on the server's place; the swarm's agents fly a quarter faster than it moves, so that they keep up, flocking as before. The participant is never moved, so this is an object moving in the scene, not travel, and `locomotion.md`'s rules for moving the rig do not apply. The server checks the straight way against everyone's heads, kept 0.8 m from it, and the solids and walls shown; where it is blocked, it gives one waypoint, `SpaceState::via`, raised a metre above the tallest head along the way or a metre to either side, which clients glide through; with none clear, or beyond 5 m, the agent **streams**, `SpaceState::stream`, at up to 6 m/s, as a worker's flock flies, its agents regathering at the spot. On the environment's ground, the way keeps above it as well, sampled every 0.2 m, through no floor and 0.5 m from every floor, as the spot is; where the straight way passes below it, as up onto a terrace or down from one, the waypoint is lifted over it: above where it sets off, so that it rises first, above where it goes, so that it travels out then descends, or above the middle, at the higher end's height and then 0.5 m higher each time, up to 6 m. A stream goes by such a waypoint, `SpaceState::via` with `stream`, through the air above the ground to a terrace reached only by teleport, never through a floor nor up from beneath one; and so does the agent's glide home.
- **Going home.** A following agent goes home once the conversation has been quiet for the space's delay, 90 s by default: nobody recording or transcribed for it, nothing queued, no question or approval waiting, its session idle, and no agent speech playing, held or caught up on for anyone, nor still to come from synthesis, checked each second while it is away or turned. Any words begun, and the agent's own speech, as from a worker's report, start the quiet again; a running worker does not hold it. Once its partner has left the space or gone away, the delay is 15 s at most. It goes home as it went, silently, its pin and turn ended, facing as its home faces.
- **Calling it and pinning it.** The trigger no longer summons the agent: a participant calls it by voice, "come here", which following answers, or, without speech, with **Call Tomori here** in the hand menu, `ClientMessage::CallAgent` (see `hand-menu.md`), which stands it at their conversation spot, in either mode, or, with nowhere clear there, 2.3 m in front of them as the summons did, and **pins** it there, for everyone, `SpaceState::pinned`. The agent pins itself with `move_agent stay` (see `mcp.md`), and a participant pins it where it stands with **Tomori: stay here**, `ClientMessage::PinAgent { pinned: true }`, where it follows the speaker. Pinned, it follows nobody and does not go home on its own, though it still turns to whoever speaks, and glances at them while busy, whether it follows the speaker or moves only when asked; unpinned where it moves only when asked, a press neither turns nor moves it; the pin ends when it is sent home, by the agent's `move_agent home` or a participant's **Send Tomori home**, `ClientMessage::PlaceAgent` without a place, as it is let follow again, by the agent's `move_agent follow` or a participant's **Tomori: follow again**, `PinAgent { pinned: false }`, only where it follows the speaker, as the space changes environment, as the server restarts, or after 30 minutes with nobody in the space. Following again, it goes home once the conversation is quiet, and to whoever's words it is answering, if they held X for them. **A participant always wins**: their call, stay, follow again or send home overrides the agent's own stay or follow at once, while a pin a participant made, by calling it or asking it to stay, stays theirs as the agent pins itself again, and the agent's own `follow`, or a move of its own from there, is refused but where `requested_by` names whoever's words asked. A server that takes `PinAgent` sets `SpaceState::pins`; a client offers stay and follow again only to such a server. Visitors call, pin and send home nothing.
- **Asked to go.** The agent goes where someone asks with `move_agent` (see `mcp.md`): to someone's conversation spot, `near` or `beside` them, as following would choose it, straight towards them from where it is, or, with nowhere clear there, in front of them; 2.3 m in front of them, `front`; beside an object its side gives a position, `object ID`, off the line of sight to it from whoever asked, at the conversation distance from where they stand, or, further from it than 2 m, from where they would stand 2 m before it, or at the anchor standing by it; or at an anchor. The mode is unchanged: a following agent is moved on by the next words that need it, and `stay` pins it there. Of its own accord, a move somewhere it does not already stand, but home, is limited to one every 20 s and six in ten minutes, beyond which it is refused and told to stay where it is; one asked for, which `requested_by` names and the server checks as for the gated tools, is not. Going home, staying and following again are never limited. Each move is logged at info with its reason, and who asked.
- **How the agent moves, a space setting.** An owner chooses, in the hand menu's Space section, how the agent moves, kept with the space, `SpaceState::movement`: **Follow the speaker**, all of the above; **Only when asked**, the default, in which it moves only when someone asks, by voice through `move_agent` or with **Call Tomori here**, and stays where it goes until sent home; or **Stay home**, in which it never leaves home, refusing `move_agent` but for home and **Call Tomori here**, and goes home as it is chosen. Following, the owner also chooses how long it waits, quiet, before going home: 30 s, 1, 1½, 2, 5 or 10 minutes, or never. A setting this server does not know, as a newer server kept, leaves the default.
- **Nothing travels with the agent.** Its status wall and its workers stay at home in every mode, as it follows, is called or goes where it was asked, and the server sends no `summoner`, which a client from this build reads, with `movement` sent, as workers at home. It sends `SpaceState::partner` instead, the eyes of whoever the agent went to, while it is away, near whom the swarm draws in (see `avatars.md`).
- **Older clients and servers.** A server no longer sets `SpaceState::summons`, so an older client's pull sends nothing and only draws its own swarm while held; one that sends `PlaceAgent` with a place anyway is dropped, logged at debug. An older client glides to `summoned` as before, so it sees the agent follow, but without the turn, the waypoint or streaming; it gathers its workers about the agent while it follows, a known limit, and lacks **Call Tomori here** and **Send Tomori home**, though anyone can say "come here" or "go home". A client sends `CallAgent` and `SetAgentMovement` only to a server that sends `movement`, and `PlaceAgent` without a place to one that sends it or `summons`; it no longer summons with the trigger from any server.
- **The agent's form.** The agent shows as the avatar its backend names, the swarm by default, unless the space's environment names one, which overrides it, with `Environment::with_avatar` (see `avatars.md`). Whatever its form, it stands, appears, follows, is called and goes home as above.
- **The workers' arrangement.** The workers stay at home (above), as an older server's, which sends `summoner`, still gathers them about whoever it summoned the agent to. Long-term direction, not yet requirements:

- An environment is much more than scenery. It can be dynamic and data-backed, with its own interaction, such as Fantail Observe, a separate project that shows a running system's topology and telemetry spatially. Environments are expected to be built on the server-owned scene graph and modules in `scene-modules.md`.
- The space's agent is aware of its environment: the information and data it presents, and what each participant is pointing at or has selected in it. Pointing and selection identify concrete resources, with their identity and context such as the time window, not only positions or pixels.
- A participant can refer to what they are pointing at in speech, such as "Tomori, can you investigate why this server is overloaded?". The agent receives the identified resource with the request, and uses the tools available in that space, such as its MCP servers, to investigate and answer.

## Rationale

The user intends to build specific environments for different kinds of work, so a space represents much more than a cosmetic place: it pulls in the information and interaction that work needs. Tying the environment to the space keeps every participant looking at the same thing, which shared pointing and the agent's awareness of the environment depend on. Stated by the user, speaking from the headset, in November 2026, with Fantail Observe as the example to connect eventually.

In November 2026 the user decided, from the headset, that a space's environment can be changed after it is created, from the Space section of the hand menu: by owners only, for everyone in the space, and kept in the space's record (issue #74). Since the space moves as a whole, everyone keeps looking at the same thing. In November 2026, as environments came to agree versions with clients (issue #75), the user decided that a change is never refused because someone in the space cannot present the new environment: a participant or visitor who cannot present it falls back to the grid with a warning, as when joining such a space. So nobody's client, and no visitor, can keep owners from changing their space.

In November 2026 the user decided that environments are compiled into both the server and the clients, and that client and server agree on each environment through a protocol version (issue #75, the environment framework proposal in #90, section 1). Offering a client only the environments it presents keeps whoever creates a space, or moves one, from choosing an environment they would see only as the grid themselves, and keeps a client side from reading state it does not understand; the fallback remains for spaces someone else created, and for servers that no longer offer an environment. Clients and servers from before versions keep working with each other and with newer ones, since every addition is optional. The GitHub environment's prototype is listed by every client built on `tomori-scene`, because its cards are drawn by the shared scene rather than by a scenery, so that agreeing on versions does not take it from Tomori's own headset. Bounding the list a client sends keeps what the server holds for a connection small.

In November 2026 the maintainer agreed that the core is a clean slate that environments register themselves against: the builders register nothing by default, Tomori's own programs register Tomori's own environments as another project's would, and each environment's crates own its identity, in a common crate, with server and client crates beside it. Before, the core knew Sky and the GitHub prototype, and their identities were in `tomori-protocol`, so an environment offered by the core made the server library depend on it while its client half depended on rendering crates whose tests depend on the server, a package cycle; keeping environments out of the core removes it, and lets an environment be added without changing the core.

In November 2026 the user decided that an environment's server side is a full program in the server, not only a producer of scenery: it runs where the server's reach and credentials are, and clients never hold them (issue #75, the environment framework proposal in #90). It runs on a thread of its own, as the GitHub environment's source already reads GitHub, so that a failing or slow side cannot harm the hub or another space, and each binding runs it once so that a restored space is treated as a new one. A downstream project's environment, such as one that shows a running system's telemetry, is built on it. The state it shares with clients, its intents and its client side are separate steps of the same framework (#75, #76).

In November 2026, to give a new environment's animated objects a home whose server side owns them, the maintainer asked for a first generic state channel rather than messages for one environment's objects: an envelope naming the environment and its version around an opaque, bounded payload that the environment's own crate encodes, with intents that the server side validates, additive and gated, as a deliberately small first step towards #76. The payload is JSON, as the control messages are, which answers #76's question of encoding for now. A kept state and announced events rather than deltas keep the first step small: a state is replaced whole, so a gap is repaired by the next one. Open questions, not yet decided:

- Whether an environment is a scene module, a set of modules, or something that hosts them.
- How participant pointing and selection are delivered to the agent, and how that relaxes `scene-modules.md`'s current separation of the scene graph from agent interactions.
- How an environment's data sources, such as a telemetry service, relate to the tools available to the space's agent.
- Whether the trigger pulled while pointing at nothing an environment shows, which in a space no longer draws the swarm, should reach its client side, what the freed trigger selects beyond objects marked selectable, such as workers and list items, and how a hand-tracking pinch, which does not act as the trigger yet, selects; and whether selecting, by the trigger or by A, should tick as choosing does (see `feedback.md`), which it does not yet, so that an environment can decide what a selection means first.
- Whether a worker should be placed where the words that started it pointed, when that is an object an anchor stands by, rather than by the agent alone, and whether one sent home by a removed anchor should return if it comes back soon; and whether participants carrying workers (#259) keeps placements by pose as well as by anchor.
- How a space's edits to the Tomori wall's pose, once wall editing keeps them, are shown against its home, and whether a participant can send the wall home as they send the agent home.
- Whether a pin should be kept across a restart.
- Whether a placement moves to the environment's server side, so that a participant whose client cannot draw the environment sees workers where the others do.
- How far a client side's interface grows beyond what the farmyard needed, presenting replicated state, picking, intents and ambient sounds (above): for instance, whether a client side contributes panels, tools or locomotion of its own, and whether it should run anywhere but on the headset, as in the spectator.
