# Environments

This describes how a space's environment works: what an environment is made of, how the server and clients agree on it, and the hooks with which it shapes a space. Where the agent and its workers stand and how the agent moves are described in `agent-movement.md`.

## Requirement

**One environment per space.** Each space is bound to exactly one environment at a time, chosen as it is created, kept in its record across restarts (see `spaces.md`) and the same for everyone in it, participants and visitors alike; no device switches it on its own. An owner may change it, from the hand menu's Space section (see `hand-menu.md`) or with `set_environment`, to one the server offers the owner's client. The change applies to the whole space at once, the new scenery growing out of the space as it does on joining, and is never refused because someone else in it cannot present the new environment; collaborators and visitors are refused. Arrival, outside any space, uses the Minimal grid (see `arrival.md`).

**Agreeing on it.** Each environment has an identifier and a protocol version, an integer, 1 unless it is registered with another. A change to what its server and client sides exchange that an older client side can ignore keeps the version; any other raises it.

- A client lists in `Hello` the environments it presents, with their versions. The server offers each environment in `Welcome` with its version, and offers a client that lists environments only those it lists at the same identifier and version, in the server's order; the first is what a `CreateSpace` naming none is bound to. A client that lists nothing is offered every environment.
- A `CreateSpace` or `set_environment` naming an environment not offered to the requester's client is refused, naming only the server's own identifiers and versions, never the request's text.
- The lobby lists every space, whatever its environment, and anyone may join one.
- A client joining a space whose environment it lacks, or presents at another version than the space's state names, shows the Minimal grid and the space's state, and names the environment and version it lacks; it never draws its own, other version instead.

**The core knows only the grid.** The framework crates that the server and clients are built from know no environment but the Minimal grid, which every client draws built in at `tomori-protocol`'s `GRID` and `GRID_VERSION`. Every other environment, Tomori's own included, is registered by an application through the same builder calls, which register nothing by default: the server's with `tomori-server`'s `Builder::environment`, a client's with `tomori::Builder::register` or `tomori-render`'s `Sceneries` (see `builders.md`). Tomori's own server program, `tomori-server` in `tomori-server-app`, registers Sky, the grid and the farmyard, and the GitHub prototype with `--github-repository`; Tomori's own app and spectator, behind their `app` features, present the same.

**An environment is up to three crates**, named for it after `tomori-environment-`:

- **Common**, `tomori-environment-NAME`: its identity, `ID`, `VERSION` and `LABEL`, defined once so that its halves cannot disagree, and what both halves share, such as its message formats and shared simulation. It builds no renderer or GPU stack, so that a server builds it.
- **Server**, `tomori-environment-NAME-server`: what runs only in the server, such as its server side, data sources and credentials, which never reach a client, and the command-line options it adds to a server's builder. It builds no renderer either.
- **Client**, `tomori-environment-NAME-client`: how a client presents it, its scenery and client side, with a `register` function for a client's `Sceneries`. It may depend on the renderer.

An environment with nothing for a half has no crate for it: Sky has a common and a client crate; the farmyard keeps its server side in its common crate, as it holds nothing that must stay in the server; the GitHub prototype has all three. A test in `bake/tests/dependencies.rs` fails when an environment's common or server crate builds the renderer or GPU stack, its common or client crate builds a server crate, its common crate a client crate, or a core crate depends on an environment's crate other than through its `app` feature. To bump a version, raise it in the common crate, change both halves together and say so in a `Breaking:` paragraph, since clients of the earlier version then show the grid in its spaces; `tomori-server-app`'s test requires that Tomori's own server program offers Tomori's own app and spectator exactly what each presents.

**A server side.** An environment's server registration may carry a server side, `tomori-environment`'s `ServerSide`, given with `Environment::with_server_side`: a program in the server process, trusted as the rest of the server is, since it is compiled in, that reaches whatever the server can, its credentials and configuration staying there. An environment without one, such as Sky or the grid, needs none of what follows.

- **It runs for a binding.** The server runs it on a thread of its own once for each binding of a space to the environment: as a space is created in it, changed to it, or bound to its session again after a restart, so that a restored space is never given a directory the server no longer allows. It is given a `Space`, with the space's identifier, title and directory and a cancellation, and no other access to the space, the hub or the conversation. The binding ends, and the side is cancelled, when the space is bound to another environment, its session closes or the server stops; the server does not wait for it, but bounds how long it waits as it stops itself. What a side keeps belongs to its binding and is forgotten with it.
- **It never harms the space.** It never blocks the hub, other spaces or the conversation. An error it returns, a `tomori-environment` `Error`, a panic or failing to start shows in the space's error line, to everyone in it, until the binding ends, and the space keeps its environment and conversation; the side is not started again for that binding, and the failure raises no attention in the lobby.

**The state channel.** A side shares what its environment presents with the clients in its space through envelopes naming the environment and its version around JSON that only the environment's own crates read:

- **State**, `Space::share`, at most `STATE_LIMIT` (64 KiB), replacing the one kept before, sent at once to everyone the channel reaches and to whoever joins later, a newer replacing one not yet sent on a slow connection.
- **Events**, `Space::announce`, at most `EVENT_LIMIT` (4 KiB), sent to everyone the channel reaches now together with the state it leaves, which is kept for whoever joins, so that nobody misses an event or sees it twice.
- **Intents**, `EnvironmentIntent`, at most 4 KiB, sent by a participant's client only once it has the environment's state in the space. The server refuses a visitor's, drops quietly, as intents are ambient, one for a space not in the environment and version it names, one too large, and one past a participant's 8 at once and 4 a second, across their connections, and hands the rest to the side, at most 64 waiting, with the number the server gives the participant. The side validates them against its own state.
- **Who it reaches.** Everyone in the space, participants and visitors alike, whose `Hello` set `environment_state` and listed the environment at the side's version.
- **How often.** The server takes at most `UPDATES_PER_SECOND` (30) states and events a second from a side, after a burst of `UPDATE_BURST` (60), refusing those beyond with a message the side may show; a side gathers what changes into one event rather than announcing each change.

Every limit a side keeps within, here and below, is defined and documented once, in `tomori-environment`, and the server refuses, saying why, what exceeds one.

**What participants point at, inspect and act on.** A side describes what can be pointed at in its environment with `Space::describe`: up to `OBJECT_LIMIT` (1,024) `Object`s, each an identity of at most `IDENTITY_LIMIT` bytes, which clients name it by, and a description the server cleans onto one line and cuts to `DESCRIPTION_LIMIT` characters.

- A client attends to one as `Resource::object`, which the server resolves as the words begin, from everything the side describes, and describes to the agent.
- An object may carry a **reference**, `Object::with_reference`, of 1 to `REFERENCE_BYTES` of `tomori_environment::valid_reference`'s characters, unique among the side's objects; the agent is told its **id**, the environment's identifier and the reference, as `farmyard:hen/marigold`, which it may `inspect`. A side answers inspection through an `Inspector`, given with `Space::inspect_with`, with JSON of its own choosing, which the server cleans as text others choose, since the agent reads it as data (see `security.md`); it holds nothing that should stay in the server.
- An object may say where it stands, `Object::at`, and how far it reaches, `Object::with_extent`, so that the agent and its workers can go to it, and the actions it offers, `Object::offering`, declared with `Space::declare_actions` and taken by the agent with `act` (see `environment-actions.md`).
- The agent's `presence` tool lists at most `AMBIENT_LIMIT` (32) of them, ranked by how much they matter to whoever the turn is for, saying how many the side describes, all of them reached by their ids all the same (see `mcp.md`).

**Where participants are.** A side reads each participant's presence with `Space::presence`, carrying the engagement their client last reported and how old it is, a report `PRESENCE_STALE` (5 s) old or more being a headset that has stopped. It may declare proximity zones with `Space::declare_zones`, `Zone::sphere` or `Zone::cylinder` about a point, an anchor or an object, at most `ZONE_LIMIT` (16), each left at a margin beyond it; as the hub sweeps, about once a second, the server tells the side each zone's occupancy, how many participants are within it, as an intent only the server makes, `Intent::zone`.

**Panels on its own walls, and their context.** A side publishes panels, `tomori_environment::Panel`, text, lists, tables and charts, onto the walls its environment declares, with `Space::publish` and `Space::retract`, at most `PANEL_LIMIT` (128) in a space, bounded and paced as `projection.md` describes; a participant may choose a list's choosable rows, each choice reaching the side as an intent (see `panel-actions.md`). It may declare the parameters its panels depend on, with `Space::set_context`, which a wall or a panel may fix, shown as chips and told back to the side for each panel (see `panel-context.md`).

**A client side.** What a client presents of an environment beyond its scenery, from what its server side shares, is a `tomori-scene` `ClientSide`, registered beside its scenery with `Sceneries::set_client_side` (see `builders.md`).

- The frame step makes one for the joined space once its scenery has grown in, only while the environment drawn is the one it is registered for, at the version drawn, and drops it on leaving and on a change of environment, so that each space's begins anew. Each frame it is given the space's updates in order, what each ray is on and where the head is, and it returns what it shows, which the renderer hands to its scenery through `Scenery::animate`, `submit` and `cull` (see `rendering.md`); its intents; and its sounds.
- Through `pick` and `pick_by` it names what each ray meets first, with its identity, a short label and its distance, which the ray ends on where nothing of Tomori's is nearer. What it marks selectable, `Picked::selectable`, takes the trigger, as a select, and B, to back out of what it shows; what it marks with `Picked::handles` takes either stick or either grip, `ClientSide::within_reach` and `within_reach_of` saying what is within reach of a hand. Each reaches it only after every rung of Tomori's own interface declines it, in the orders `interaction.md` gives.
- A client side never runs on the server. The spectator runs one as a watcher, drawing what it shows while telling it nothing a participant does (see `spectator.md`).

**Its ambience.** A client crate may declare what its environment sounds beneath the conversation, an `ambience::Ambience` of beds, placed loops and calls, registered with `Sceneries::set_ambience` (see `spatial-audio.md`).

**Loose objects.** An environment whose participants pick things up, carry, throw and stack them declares them as bodies of `tomori-physics`, which builds no renderer and on which no core crate depends: each a `Body::convex` of the points it is drawn from, dynamic or `kinematic()`, the static colliders it rests on, `Static::heights`, `mesh`, `convex` and `cuboid`, and its water, `Water::below`. Its server side simulates them, on Rapier behind the crate's `simulation` feature, which only a server builds, and its client side mirrors what the side sends, so that a client never simulates. Every body is taken, passed from hand to hand and let go by the same intents, checked against presence (see `physics.md`).

**Travel.** An environment may allow travel beyond the room with a locomotion profile, teleport or fly, of walkable surfaces, outlines or ground derived from what it draws with `tomori_environment::navmesh::Navmesh::derive`, teleport pads and teleport targets, registered beside its scenery with `Sceneries::set_locomotion` (see `locomotion.md`). Sky and the grid declare none; the farmyard declares teleport (see `farmyard.md`).

**Homes.** An environment's server registration says where its homes are, each a pose in its own coordinates facing along its +Z, the way it looks, as every anchor faces (`tomori_protocol::Pose::at(spot).facing_towards(target)`): where participants arrive, `Environment::with_arrival`; where the agent lives, `with_agent`; and, only where it must stand elsewhere than beneath the agent, which wall is the space's status wall, `with_status_wall` (see `projection.md`).

- A space's coordinates, which presence, placement, the agent's tools and every client use, always have home, where participants arrive, at their origin facing −Z. The server carries every anchor and wall the environment registers into them, and a client its scenery, surfaces and client side, by the carriage that takes the arrival to home, `Pose::carriage`, exactly the identity for the default arrival.
- Without them, participants arrive at the environment's origin facing −Z, the agent's home is 1.4 m up and 2.3 m straight ahead of them, facing them, and the status wall, the Tomori wall, stands beneath the agent's home by the rule the server and every client share, `tomori_protocol::entourage`. Sky, the grid and the GitHub prototype stand so; the farmyard gives an arrival, the agent's home and its notice board as its status wall.
- It may also name the agent's avatar, `with_avatar` (see `avatars.md`); the boxes of its scenery that walls and the agent keep clear of, `with_solids`; its walkable ground, `with_navmesh`, which the agent's height is measured above; and a follow height, `with_follow_height`. How the agent and its workers stand and move from these homes is described in `agent-movement.md`.

**Spawn points.** An environment may declare where people arrive as they join a space, spread out rather than on top of one another, with `Environment::with_spawn`: each a `tomori_protocol::spawn::Spawn`, the floor beneath the middle of the arriving room and the way it faces, with tags saying whom it suits; the server uses at most `SPAWN_LIMIT` (32), each with at most `TAG_LIMIT` (8) slugs, carried and bounded as anchors are, and sends them in `SpaceState::anchors.spawns`. An environment that declares none behaves as before: everyone arrives at home.

- **Whom each suits.** The tags are the roles, `owner`, `collaborator` and `visitor`, a pairing or unknown role taken as a visitor's, and `spectator`; other tags are open slugs that suit nobody yet. Someone arrives among the points tagged for them, or else among the untagged, or else at home.
- **Spreading out.** Of those, at the point fewest occupy now, a head within `spawn::OCCUPIED` (1 m) of it across the floor and within `OCCUPIED_HEIGHTS` of its height; of those alike, the one fewest have arrived at in the space; and then the first declared.
- **The server chooses.** It chooses by `spawn::choose`, as someone joins the space, joins it again after leaving it or being in another, or creates it, and for everyone in it as it changes environment, keeping who arrived where for this run only (`tomori-server`'s `spawns.rs`); never otherwise, so that nobody is moved later. A reconnect is not an arrival: it is told the point it arrived at, counting nothing. It tells that client alone, `ServerMessage::Spawn`, where its `Hello` set `spawns`, and the client sets its rig so that the middle of the participant's room stands on the point, facing the way it faces (`locomotion::Rig::arriving`), once for each arrival.
- **The spectator chooses for itself**, by the same rule, among the points tagged `spectator`, or else the untagged, without occupancy: the first.

**Anchors.** Besides its homes, an environment declares named places, cluster anchors, `tomori_protocol::cluster::Anchor`, with `Environment::with_anchor`: a name, a pose, an extent, a kind, a label and the reference of an object it stands by. `home` is where its workers stand, on an arc, the default, or a ring, as `Anchor::with_formation` says; `with_workers` declares a `home` without an extent.

- Its server side places, moves and removes anchors as its state changes, `Space::place_anchor` and `Space::remove_anchor`, within `ANCHOR_LIMIT` (64) anchors in a binding and the pace `tomori-environment` exports; what it places belongs to its binding. Anchors reach clients carried into the space's coordinates in `SpaceState::anchors.clusters`, and the agent through `presence`, which places workers at them with `place_worker` (see `mcp.md` and `agent-movement.md`).
- An anchor may tell the agent when a participant comes near it, `Anchor::notify_within`, 0.3 to 10 m across the floor: once, as a note of Tomori's through the space's event queue (see `timers.md`), until they go 0.5 m beyond it, and again only after 2 minutes (`tomori-server`'s `proximity.rs`). Arriving says nothing, and visitors are never told of.
- A client crate may register how its workers are placed, `Sceneries::set_worker_placement`, applied only in a space bound to that environment while the build draws it, at the version the space names.
- Anchors, like an environment's walls and placement, are the operator's code, trusted as the rest of it is, and bounded as above.

**Its own walls.** An environment declares projection walls of its own with `Environment::with_walls`, each a pose or a `tomori_server::EnvironmentWall` with its grid, the size and shape of its slots, whether it curves and tilts, and its name, by which the agent places panels on it; at most `tomori_protocol::DECLARED_WALLS` (64), the server ignoring any after. They are part of the place, and its scenery is expected to draw what each stands on, such as a notice board on posts or a console, so that it reads as belonging there; the farmyard lays out its notice board and its wall from the same constants, so that the two cannot drift apart. They are locked until an owner unlocks one, to move or reshape it for the space and put it back where the environment has it. The status wall's panels belong to the space and move with it; an environment's walls and the panels left floating in it are kept for the space and that environment, hidden while the space is in another (see `projection.md`). Each environment's tests check, with `tomori_environment::sightlines`, that its status wall can be read from its arrival, `readable`, and that its own walls are noticed, `noticed`.

**Instructions.** An environment may contribute a layer of the instructions Tomori gives a space's agent, about what it presents and which tools and data sources to use, with `Environment::with_instructions` (see `spaces.md`). The server looks the layer up in the environments it offers whenever it shows or gives the instructions, so that a restored space is given the same layer, whether or not a side runs or has failed; an environment the server no longer offers contributes none.

Long-term direction, not yet requirements:

- An environment is much more than scenery. It can be dynamic and data-backed, with its own interaction, such as Fantail Observe, a separate project that shows a running system's topology and telemetry spatially. Environments are expected to be built on the server-owned scene graph and modules in `scene-modules.md`.
- The space's agent is aware of its environment: the information and data it presents, and what each participant is pointing at or has selected in it. Pointing and selection identify concrete resources, with their identity and context such as the time window, not only positions or pixels.
- A participant can refer to what they are pointing at in speech, such as "Tomori, can you investigate why this server is overloaded?". The agent receives the identified resource with the request, and uses the tools available in that space, such as its MCP servers, to investigate and answer.

## Rationale

The user intends to build specific environments for different kinds of work, so a space represents much more than a cosmetic place: it pulls in the information and interaction that work needs, and tying the environment to the space keeps every participant looking at the same thing, which shared pointing and the agent's awareness of the environment depend on. In November 2026 the user and the maintainer decided, mostly from the headset, that environments are compiled into both the server and the clients, which agree on each by its version, so that a client never draws a mismatched one; that the core is a clean slate every environment registers itself against, owning its identity in its own crates; that a server side is a full, trusted program in the server, its credentials staying there; that it shares state through one generic channel whose payload only the environment reads; that what is pointed at carries an id the agent can inspect and act on; that whatever the participant points at gets the input, Tomori's own interface first; that the agent, its status wall and participants' arrival have fixed homes the environment sets; and that people arriving are spread across the spawn points that suit them. The narrative of each decision is kept in Git's history of this document; `agent-movement.md` keeps the agent's.

## Scope

The space's environment in `tomori-protocol` and the server: its creation and change, the versions clients list in `Hello` and the server offers in `Welcome`, and the clients' fallback to the grid; `tomori-environment`, its `Space`, `ServerSide`, objects, inspection, actions, zones, panels, context, anchors, `navmesh` and `sightlines`; the server's sides, channel and inspection (`server_sides.rs`, `channel.rs`, `hub/agent_inspect.rs`, `ambient.rs`, `zones.rs`, `proximity.rs`, `spawns.rs` and the hub's `spawning.rs`) and its `Environment` registration and carriage of homes, anchors, walls and spawn points (`environments.rs`); `tomori-protocol`'s `Pose`, `entourage`, `cluster` and `spawn`; `tomori-scene`'s `client_side.rs`, `ambience` and the frame step's use of them, as a participant's and as a watcher's; `tomori-render`'s `Sceneries`; `tomori-physics`; the environments' own crates (`crates/environment-*`) and their registration by Tomori's own programs (`crates/server-app` and the `app` features of `crates/client-quest` and `crates/client-spectator`); and the dependency rule's test in `bake/tests/dependencies.rs`. The panels a side publishes are also `projection.md`'s, its actions `environment-actions.md`'s, its bodies `physics.md`'s and its travel `locomotion.md`'s.

## Validation

- Create a space and confirm that its state names its environment, that a second participant sees the same environment, and that squeezing the grip inside the space doesn't change it. Join a space whose environment the client doesn't know, as with a test server naming an unknown one, and confirm that the client shows the grid and names what it lacks.
- Test, with a server offering environments at different versions, that `Welcome` offers each with its version and a client listing environments only those it lists at the same version, in the server's order; that `CreateSpace` naming none binds the first offered and one not offered is refused, naming only the server's identifiers; that an owner's change reaches everyone in the space, participants and visitors, the lobby listing and someone joining later, even those who cannot present it, while a collaborator's or visitor's is refused; that the lobby lists every space; and, against the protocol, that an older client's `Hello` and an older server's `Welcome` and state, without versions, are read as before.
- Test that `tomori-server`'s builder, `tomori::Builder` and `tomori-render`'s `Sceneries` register nothing but the grid by default; that Tomori's own headset, desktop window, console and spectator list what they register; and, in `tomori-server-app`, that Tomori's own server program offers Tomori's own app and spectator exactly what each presents. `bake/tests/dependencies.rs` checks the crate rule with `cargo metadata` and `cargo tree`.
- Test, with an environment whose server side records what it is given, that it is started once for each binding, with the space's identifier, title and directory, and stopped as the binding ends; that one that returns an error, panics or cannot be started leaves its space with its environment and conversation, showing the error until the binding ends, and is not started again for it; and that the environment's layer of the instructions is the same with a side, one that failed, and none.
- Test, with a side that shares a state, describes objects and announces an event for each intent it takes, that a client that reads the channel and presents the environment at its version, participant or visitor, is sent the state and then the events, whoever joins later the state, and nobody else anything; that intents beyond their bounds and pace are dropped; that each limit `tomori-environment` exports is the value stated, and a side beyond one is refused. `crates/server/tests/mcp_inspect.rs` checks objects' ids, inspection and its cleaning, and the server's `ambient.rs` the agent's ambient list.
- Test, in `tomori-environment`'s `zone.rs` and `tomori-server`'s `zones/tests.rs`, that zones are bounded, told as declared and as someone enters at their radius and leaves beyond their margin; in `tomori-server`'s `proximity/tests.rs`, that coming near an anchor that notifies is told once, held until 0.5 m beyond it and again only after the cooldown, and arriving within it is not; and, in `crates/server/src/hub_tests.rs`, that a side's panels reach everyone on its own walls, paced and bounded as `projection.md` says.
- Tests of the frame step check, with a client side of their own, that it is made once for the joined space once its scenery has grown in and dropped as the space or its environment changes; that it is given the updates the server side sent and what each ray points at; and that the trigger, B, the sticks (`scene/tests/scroll.rs`) and the grips (`scene/tests/grab.rs`) reach it only after Tomori's own interface declines them. Test, in `tomori-render` and `tomori-scene`, that ambiences are registered by identifier and handed to the feedback model once for the joined space.
- Test, in `tomori-protocol`, that `Pose::facing_towards` turns a pose's +Z towards its target, home faces −Z and `Pose::carriage` is exactly the identity for the default arrival; and, in `tomori-server`, that an environment's homes, anchors and walls are carried into the space's coordinates, those not finite or beyond reach ignored. Test spawn points in `tomori-protocol`'s `spawn.rs`, that someone arrives among the points tagged for their role, or else the untagged, spread to the least occupied, then the fewest arrived at, then the first; and, in `tomori-server`'s `environments.rs` and its hub, that they are carried and bounded, chosen as someone arrives and as the space changes environment, never on a reconnect, and told only to a client that set `spawns`.
- Each environment's tests check its status wall with `tomori_environment::sightlines`.

Open questions, not yet decided:

- Whether an environment is a scene module, a set of modules, or something that hosts them.
- How participant pointing and selection are delivered to the agent, and how that relaxes `scene-modules.md`'s current separation of the scene graph from agent interactions.
- How an environment's data sources, such as a telemetry service, relate to the tools available to the space's agent.
- Whether the trigger pulled while pointing at nothing an environment shows, which in a space no longer draws the swarm, should reach its client side, what the freed trigger selects beyond objects marked selectable, such as workers and list items, and how a hand-tracking pinch, which does not act as the trigger yet, selects; and whether selecting, by the trigger or by A, should tick as choosing does (see `feedback.md`), which it does not yet, so that an environment can decide what a selection means first.
- How a space's edits to the Tomori wall's pose, once wall editing keeps them, are shown against its home, and whether a participant can send the wall home as they send the agent home.
- Which tags beyond the roles spawn points match, such as a presenter the space names, and whether someone arriving where every point suiting them is occupied should be offset from whoever stands there.
- How far a client side's interface grows beyond what the farmyard needed, presenting replicated state, picking, intents and ambient sounds (above): for instance, whether a client side contributes panels, tools or locomotion of its own, and whether it should run anywhere but on participants' clients and, as a watcher, the spectator.
