# Avatars

This describes how a client shows the agent, Tomori's coordinator, in a space: the avatar its backend names by default, or its environment names in its place, the avatars a client's build registers, and the swarm, which is the default. Avatars are an extension point: another project's backend names an avatar, and its client crate draws it, without changing Tomori.

## Requirement

**The backend names the default avatar; an environment may override it.** A `tomori-backend` `Backend` names the avatar that represents its agent with `Backend::avatar`, an identifier, or none, the default, for the swarm. An environment may name one for its spaces in its place, with `tomori_server::Environment::with_avatar`, such as a character that suits its scene, which overrides the backend's. The server sends the backend's, while it offers the backend, in the backend's `BackendInfo::avatar`, offered to owners in `Welcome`, and in the space's state, `SpaceState::avatar`, the environment's where it names one clients read and the backend's otherwise, to everyone in the space, participants, visitors and spectators alike. Both are optional fields that an older client ignores and an older server never sends, so the protocol's version is unchanged. An identifier is at most 128 bytes (`tomori_protocol::AVATAR_BYTES`), not empty, and without control characters, bidirectional controls (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069) or invisible formatting characters (U+200B to U+200D, U+2060, U+FEFF), so that it reads as it is where a client names it (`valid_avatar`); the server sends one that is not as none, and a client reads one that is not as none. The server reads `Backend::avatar` each time it sends a space's state and each `Welcome`, so a change reaches clients with the next of those, as does a change of the space's environment. A space whose backend the server no longer offers names the environment's, if any, or none.

**Trusted as the build is.** The identifier comes from the backend or environment code the operator compiles into their server, trusted as an environment's anchors are (see `environments.md`), and only selects among the avatars already in a client's build; a client shows it as it is, once validated, in its notice. An avatar's code is a build's own, compiled in: its `Avatar`, its factory and its scenery run in the client with the client's reach.

**A client chooses from the space's state.** The avatar shown in a space is the one its state names, when this client's build registers an avatar by that identifier, and otherwise the swarm. The swarm is built in, as `swarm` (`tomori_scene::avatar::SWARM`), and is always available: a state that names `swarm`, or none, shows it, and so does every client outside a space, in arrival and the lobby, where the swarm behaves as `arrival.md` describes. A client whose build lacks the avatar a space's state names shows the default swarm. It says so only to an owner, as a diagnostic, `Unknown avatar: ID`, in the hand menu's Space section, on a row of its own beneath what the space runs, keeping its words whole within the menu's width and cutting only the identifier, with "…", where it is too long to fit (see `hand-menu.md`); everyone else, a collaborator or a visitor, who can do nothing about it, sees the default swarm and is told nothing, and no panel or status line names it. It never shows another avatar in its place.

**A build registers avatars by identifier.** An avatar is a `tomori-scene` `Avatar`, what it does each frame, with a `tomori-render` `Scenery` that draws it, registered together under an identifier beside the build's sceneries, with `Sceneries::set_avatar` or `tomori::Builder::avatar` (see `builders.md`). Registering an identifier again replaces it. Registering `swarm` shows that avatar in a space whose state names `swarm`; outside a space, and in a space that names none, the built-in swarm still shows. A build registers none by default, and Tomori's own app and spectator register none. An avatar lives in the crate of the project that brings it, as an environment's client side does, and draws with `tomori-assets` or anything else; nothing in Tomori knows what it draws.

**Made for a space.** The frame step makes the chosen avatar for the joined space, given the space's identifier, from the moment the space is joined, and drops it on leaving, when the space's state names another avatar, and in another space, so that each space's avatar begins anew. The renderer makes the avatar's scenery when the avatar first shows, and makes it anew whenever the avatar is made anew, for another space, so that nothing one space's avatar showed draws in the next; it drops it, with what it holds on the GPU, when the swarm or another avatar shows, so no avatar's scenery is made, nor its assets loaded, unless it shows. The built-in swarm is never dropped: it keeps moving underneath, unseen and not attracted by the trigger, following where the agent stands, appearing at a new home and gliding to where it is summoned, while another avatar shows, so that when that avatar is dropped the swarm shows again where it is, and moves on from there (see `arrival.md`). An avatar's code is run on the frame step's thread once a frame, so it must be quick.

**A panicking avatar falls back to the swarm.** An avatar that panics as it is made, or in any of its methods, is dropped for the space, the swarm shows in its place, the client logs one warning, and it never makes that avatar again while it runs. A scenery that panics as it is made or given what its avatar shows is dropped by the renderer and never made again, and the renderer reports it through the failures it shares with the conversation (`avatar::Failures`, from `Sceneries::avatar_failures`), so that from the next frame the avatar falls back to the swarm in the same way: the swarm, which kept moving underneath, shows and is heard, workers fly from it, one warning is logged, and the avatar is never made again. A scenery's drawing in each eye's pass is not guarded, as an environment's scenery's is not: a panic there is fatal to the client, so a scenery must not panic as it draws. The guards catch only panics that unwind: a build compiled with `panic = "abort"` ends the process on any of these panics, as it does on a panic in an environment's server side (see `tomori-environment`'s `ServerSide`).

**What an avatar is given.** Each frame, an avatar is given, as `avatar::Input`: the agent's state, the `Visual` the swarm is given, before the swarm smooths its audio level: its turn's mode, audio level, whether it works and the time; whether agent speech is playing here; where the agent stands and faces: where it went or was called, facing whoever it turned to, or else its home, the agent anchor (see `environments.md`), which the coordinator glides there, by the waypoint the server gives or streaming far away, so that every avatar's place eases in, keeps to its speed and settles rather than jumping (`glide.rs`), with the waypoint and whether it streams, and whether it appears there at once, as a space opens or changes environment, rather than moving there; the participant's head, to face them, where known; how far it stands from whoever it went to, about the vertical, while it is away, from the eyes the space's state gives, `SpaceState::partner`, or else those it turned to (`Input::near`); the point the trigger pulls towards, while it attracts; an attention point, something the agent acts on or a participant points at, which the frame step gives none of yet (see the open questions); and the time since the last frame. Each avatar decides what to do with them: the swarm is attracted to the trigger's point, as it is today (see `interaction.md`), and a model may turn towards it instead.

**What an avatar provides.** Everything else in a client that depends on where the agent is asks the avatar shown:

- **Its drawing:** its scenery is drawn in each eye's pass, prepared for each eye, given once a frame, through `Scenery::animate`, what the avatar shows (`Avatar::drawn`), a value only its own scenery reads, drawn before the scene and translucently after it, as an environment's scenery is, wherever it stands; it is never cut off by the sphere a space's scenery grows within. The swarm is drawn by the renderer itself, as now. The ring on the floor beneath the agent anchor stays for every avatar, moving to a new anchor at once, as it does for the swarm, rather than gliding with it.
- **Its voice:** the points the agent's voice comes from; agent speech sounds from their middle (see `spatial-audio.md`). A point that is not finite or is more than 90 m from the space's middle on an axis is left out; with none left, the agent sounds from the agent anchor.
- **Where workers fly from and return to:** the points a worker's flock departs from as it arrives and returns to as it leaves (see `environments.md`), left out and falling back to the agent anchor as voice points are.
- **Its bounds:** a sphere it stands within. Nothing uses it yet; it is for keeping the Tomori wall clear of the agent and pointing at the agent (see the open questions).

**An accepted limit: the first frame.** The avatar's factory runs in the frame step, before the first frame that shows the avatar, and its scenery is made on the render thread as that frame is drawn, synchronously, so an avatar whose models are slow to make, such as a glTF read and uploaded then, stalls that frame. A build should make its avatar's models cheap to create, or read them ahead of time, such as through the shared `tomori-assets` library, which reads each once.

**Drawing in up close.** Within 2 m of whoever it went to (`avatar::NEAR`), an avatar draws in, so that it never fills their view, and spreads out again beyond it and at home: the swarm eases, over about a second, to about half its size (`avatar::DRAWN`, 0.52), about 0.7 m across where it reaches 1.35 m, every shape and its flock alike, as a flock gathering to listen. Every client draws it so, from the same state, so everyone sees one size. An older client, which ignores `partner`, draws it at its full size.

**An accepted limit: the status wall.** The status wall stands at its own home, which the environment sets, and never travels with the agent (see `projection.md`), and the server does not know a client's avatar; an environment whose agent's home is near its wall's makes room for the avatars it expects.

**The swarm is the default avatar, unchanged.** The swarm is `SwarmAvatar`, the built-in `Avatar`, whose behaviour is exactly the swarm's: its 128 agents' simulation, its shapes, its rings and halo, its colours, its appearing at its home and gliding to where it is summoned, its drawing in near whoever it went to, its attraction to the trigger's point; its voice is the middle of its agents, its workers fly from and to its agents, and its bounds are the 1.2 m sphere about the agent anchor that its rings and halo stand within. Without an avatar named, or registered, every client draws and sounds exactly as before.

**Every client follows the same rule.** The headset and the desktop participant choose, make and draw an avatar through the frame step. The spectator chooses the avatar by the same rule, from the avatars registered with the sceneries it is given, makes it for the space it watches, animates it from the space's observed activity as it animates the swarm, and draws it with the same scenery; given none, it shows the swarm, as Tomori's own spectator does. The spectator has no panel, so it names a missing avatar in no notice. A panicking avatar falls back to the swarm in the spectator too. The server-less desktop window, which is never in a space, draws the swarm as it always has.

## Rationale

In November 2026 a downstream project asked for its agent to be represented by an animated 3D character rather than the swarm: standing at the environment's agent anchor, moved by the agent's state as it idles, listens, thinks and speaks, speaking from its mouth and turning towards what it acts on. Environments and backends differ, so the maintainer decided that the backend says which avatar represents its agent by an identifier, a client's build registers avatars by identifier, and a client that lacks the avatar named shows the swarm, which stays the default and behaves exactly as before. An avatar is the backend's, rather than an environment's, because it represents the agent, which the backend runs, in whatever environment its space is in.

`Welcome` lists backends only to owners, who create spaces, so a client could not map a space's backend to an avatar for a collaborator, a visitor or a spectator from it; the space's state reaches everyone in the space, as its environment and anchors do, so it carries the avatar too. `BackendInfo` carries it as well, so that an owner's client knows each backend's avatar before a space exists. A space whose backend is no longer offered has no agent running, which the swarm shows as it always has.

Everything that depended on the swarm, its drawing, the agent's voice, the workers' flights and the trigger's attraction, asks the avatar instead, so that an avatar can replace the swarm without the rest of the client knowing which it is; the swarm implements the same interface, which keeps the default exactly as it was. An avatar's drawing is a `Scenery`, the hook environments already draw with in each eye's pass, given what the avatar shows as an opaque value, as a client side's scenery is, so that a downstream crate draws anything with `tomori-assets`' animator and skinned models. Keeping the swarm running underneath costs one simulation a frame, as now, and is the simplest way never to make it jump.

In November 2026 the maintainer decided that the backend sets the default avatar and an environment may override it, so that a scene can bring a fitting character, while a backend's choice still holds everywhere else; and that "Unknown avatar" is shown only to owners, in the hand menu's Space section, as a diagnostic, since everyone else sees the default swarm and a permanent row on everyone's status panel was noise. The maintainer also decided that the agent has a fixed home the environment sets, where it appears as a space opens, and that a participant summons it with the trigger and sends it home when asked (see `environments.md`); an avatar is given where the agent stands and whether it appears there at once, so that any form it later takes, an animal, a bird, a humanoid or a robot, possibly of the agent's own choosing, stands, appears and is summoned as the swarm is.

## Scope

`tomori-backend`'s `Backend::avatar`; `tomori_server::Environment::with_avatar`; `tomori-protocol`'s `BackendInfo::avatar`, `SpaceState::avatar`, `AVATAR_BYTES` and `valid_avatar`; the server's backends and space state; `tomori-scene`'s `avatar.rs` (`Avatar`, `Input`, `SwarmAvatar`, `Coordinator`), the conversation's choice of avatar and its notice, and the frame step's use of it; `tomori-render`'s `Sceneries::set_avatar` and the renderer's drawing of an avatar's scenery; `tomori::Builder::avatar`, the desktop participant, the headset and the spectator.

## Validation

- Test against the protocol that a `BackendInfo` and a space state without an avatar, as from an older server, read as none, and that none is written when there is none; and that `valid_avatar` takes an identifier of 1 to 128 bytes and refuses an empty one, a longer one and one with a control character, a bidirectional control or an invisible formatting character.
- Test, in `tomori-server`, that a backend that names an avatar is offered with it in `Welcome` and that the state of a space bound to it names it to everyone in the space, a visitor included; that an environment that names one overrides it, and one clients cannot read does not; that a backend that names none, or an invalid identifier, gives none; and that the default `Backend::avatar` is none.
- Test, in `tomori-scene`, that the swarm draws in to `DRAWN` of its size, ready, speaking and flocking, and spreads out again, never below a tenth (`swarm.rs`); that `SwarmAvatar` draws in within `NEAR` of whoever it went to, and not beyond it nor at home (`avatar.rs`); and that the conversation takes how far that is from `partner`, or else whoever it turned to, only while it is away, ignoring nonsense, and none once sent home (`conversation.rs`).
- Test, in `tomori-scene`, that `SwarmAvatar` is the swarm exactly: given the same frames as a `Swarm`, its agents, visual and anchor are the same, its voice points and worker samples are its agents' positions, it follows the anchor and is attracted to the trigger's point; that existing tests of the swarm, the frame step, spatial audio and delegation pass unchanged; that the conversation chooses an avatar only in a space whose state names one this build registered, `swarm` too when registered, and none otherwise, reading an identifier `valid_avatar` refuses as none, and says which it lacks only to an owner, in the hand menu's Space section, laid out within the menu's width with only the identifier cut, never on the panel, and to a collaborator or visitor not at all; that the frame step makes the avatar once for the joined space, from the first frame, gives it the agent's state, where it stands and whether it appears there, the participant's head, the trigger's point and the time, takes the agent's voice and the workers' departures from it, draws no swarm while it shows, and drops it on leaving, the swarm, unattracted meanwhile, then standing at the anchor; that voice and departure points out of reach are left out, falling back to the agent anchor; and that an avatar that panics as it is made or in any method, or whose scenery the renderer reports failed, falls back to the swarm and is never made again.
- Test, in `tomori-render`, that avatars are registered by identifier, replacing one before, and none by default; that a renderer makes an avatar's scenery only when it shows, anew for another space, drawing nothing of the last one's, draws only the one shown, giving it what the avatar shows, and none for the swarm, never cuts it off, resizes it, and never makes again a scenery that panicked as it was made or given what its avatar shows; and, with the frame step, that a scenery that panics as it is made or given what its avatar shows leaves the swarm drawn and heard from the next frame.
- Test, with a test avatar of its own, built in code as a `tomori-assets` model and animated by a trivial controller from the agent's state, registered through `Sceneries` as a downstream crate would, that a space whose state names it draws it at the agent anchor and not the swarm, without changing Tomori.
- Test that the spectator shows a registered avatar for a space whose state names it, takes the agent's voice and the workers' departures from it, and shows the swarm otherwise.
- On the headset: confirm that the swarm looks, moves and sounds as before; and, with a build that registers an avatar for a backend that names it, that it stands at the agent anchor, its voice comes from it, workers fly from and back to it, and a build without it shows the swarm and names the missing avatar.

Open questions, not yet decided:

- Where the attention point comes from: what the agent acts on, such as the resource a tool call touches, or what a participant points at, and how either reaches every client alike.
- Whether the status wall's default place should follow an avatar's bounds, which the server does not know (see the accepted limit above).
- Whether participants can point at the agent itself, using its bounds.
- Whether an avatar's assets are delivered by the server, as environments' are to be (see `assets.md`), so that a client whose build lacks an avatar can still show it.
