# Panel Actions

This describes list panels an environment's server side publishes whose rows it names: rows it highlights by id, rows the agent inspects one at a time, and rows a participant chooses with A or the trigger, the choice reaching the environment's server side; rows drawn as rows, with the highlight on a bar, each row's tone and its value; and the side told when a participant moves one of its panels to another wall or throws it away; and rows laid out in columns, as a table under a header, each figure read down its column; and rows backed by keys, which the server keeps and hands back with a choice, so that the side resolves a row exactly. Increments 1 to 6 are requirements, built; the rest is a proposal, each its own decision for the maintainer.

## Requirement

**List panels.** An environment's server side may publish a list panel, `tomori_environment::Panel::list(id, title, rows)`, beside its text and chart panels (see `environments.md` and `projection.md`): a panel whose body is a list of rows, each a `tomori_environment::Row`, `Row::new(id, text)`, with an id the environment chooses and its text, a line of Markdown-lite, drawn as text and never as HTML, and optionally `Row::with_reference`, a reference the agent may inspect the row by, as an object's (`environments.md`). It is published, updated in place, retracted, placed, carried, pointed at, scrolled and thrown away as any panel an environment publishes, and every limit on those applies to it unchanged: it is one of the environment's 32, its changes are held to the same rates, and it rests as theirs do.

- **Its body.** The server writes the body from the rows, one Markdown list item a line, `- TEXT`, in their order, so that every client draws it, older ones, the spectator and the console included, as a text panel's list, scrolling it where it has more rows than its face shows (see Scrolling in `projection.md`). Each row's text is cleaned onto one line as a title is, without control or format characters, and cut after its first 80 characters (`tomori_environment::ROW_CHARS`), followed by "…" where it is cut, as a title is; a row whose text is empty once cleaned shows its id. **A row is never a checklist item:** a text that begins with a checkbox, `[ ]`, `[x]` or `[X]` followed by a space or nothing, has its brackets written as parentheses, `( )`, `(x)` or `(X)`, so that no client offers to tick it with A, which the server would refuse, as it refuses every tick of an environment's panel. A body holds at most 30 lines and 1,200 characters (`projection.md`), so rows that would take it past either are left out whole, the last first, never cut part way through.
- **Rows' ids.** A row's id is 1 to 64 bytes (`tomori_environment::ROW_ID_BYTES`) of ASCII letters, digits, `-`, `_`, `.` and `/` (`tomori_environment::valid_row_id`), so that it can be told to the agent and named in a message as it is, and unique among the panel's rows. A list has at most 30 rows (`tomori_environment::ROW_LIMIT`), as many as a body has lines. The server refuses, saying why, a list with more rows, a row id it does not take, and two rows with the same id. A row's reference is taken as an object's is: one `valid_reference` refuses is left out, and the row kept without it; of two rows with the same reference, only the first keeps it.
- **Highlighting a row.** A list panel may highlight one of its rows, `Panel::highlighting(row)`, by the row's id, such as the queue entry the environment's inspector shows: the server writes that row as `- **▸** TEXT`, the bold pointer before its text, so that every client draws it, and an older one, without any change. Publishing the panel again with another row highlighted, or none, moves or clears it, as any update does; highlighting is the environment's, the same for everyone in the space, as everything a panel shows is. A highlight naming no row of the panel, or given to a panel that is not a list, is refused, saying so, and one naming a row left out of the body, as past its bound, highlights nothing.
- **Pointing at a row.** A participant pointing at a row as they speak attends to it as to any list item of a text panel (`Resource::panel_at`, `projection.md`), and the server describes the row from its own copy, never from the client: its number of how many rows, whether it is highlighted, its id to inspect it by, where it has a reference, and its text, in double quotes, cleaned as an item's is, in place of the item, as `Ada: [Pointing at panel "Queue" (on a wall, published 3 minutes ago; the observe environment's, id observe:panel/queue; row 3 of 12, highlighted, id observe:pod/112: "pod112 · 41 waiting")] why is this one backed up?`. A list item of a list panel is always a row, since each row is a line of the body. **Named by its id:** a client that is sent the list's rows (`Panel::rows`, below) names the row it points at by its id too, `{"kind": "panel", "panel": "panel-3", "line": 1, "row": "pod112"}` (`Resource::panel_row`), and the server describes that row wherever it now stands on the list, or, where it has gone, says `a row since gone from the list`, rather than whatever row is on that line now, so that a queue reordering between what the participant saw and what they said never tells the agent of another row. An id longer than any row's is dropped, and the line taken alone; an older client, which names no row, is described by its line, as before, and an older server ignores `row`.
- **Inspecting a row.** `inspect` takes a row's id as it takes a panel's or an object's: the server asks the side's inspector about a reference that a row of a list panel it publishes now has, in the environment the space is in now, and refuses one no object, panel or row has now, without asking the side (`environments.md`), describing it to the agent as the panel's title and the row's text. Of an object, a panel and a row with the same reference, the object is asked about first, then the panel, then the row.
- **The agent's `panels`.** For a list panel, even one of no rows, `panels` gives its `rows`, each with its `id`, the environment's, its `inspect_id`, or null where it has no reference, whether it is `highlighted` and whether it is `choosable`, so that the agent can inspect a row nobody points at (see `mcp.md`).

A list panel is a text panel to every client that does not read its rows, and its references stay in the server.

### Choosing a row (increment 2)

- **Choosable rows.** A row the environment marks with `Row::choosable` may be chosen by a participant; a row without it is only read and pointed at, so a list may mix them, as a queue's summary rows and its entries. A projection's `Panel` gains `rows`, `tomori_protocol::ListRow`s, sent for every list panel an environment publishes, each row's id and whether it is `choosable`, in body order, at most 30 ids of at most 64 bytes, about 2.5 KiB at most, part of what the panel's version covers; a client uses it to name the row it points at and the row it chooses, and an older client ignores it, drawing the body as any list.
- **Choosing with A.** A participant pointing at a choosable row, not carrying the panel, presses **A**, Enter in the desktop window, to choose it, for its environment: the client sends `ClientMessage::ChoosePanelRow { panel, row, revision }`, the panel's identity, the row's id and the panel's version it last saw, only to a server whose `SpaceState::choices` says it takes it, with the choosing cue. It is among the last of the conversation's meanings of A (`interaction.md`, `precedence::A`'s `Conversation` rung), after everything that decides something, so that a press meant for a prompt never acts on the world beyond Tomori, as a teleport pad is last so that a prompt is never answered by teleporting (`locomotion.md`): after the hand menu, the right wrist's transcript, the list, a request's 0.6 seconds, a checklist item, saying to turn the right wrist, a request to decide, a decision on its way and a queued entry to cancel or keep; then the row; then a teleport pad, the last; then anything else of Tomori's and an environment's selectable object. While a request, an approval or a question, waits, A on a choosable row chooses nothing, saying `Answer the request before choosing.`, as the press is likelier meant for the request. A checklist item and a choosable row are never the same thing: an environment's list is never ticked, its rows' text never a box (above), and a client offers no tick on a panel with rows, so their order between them decides nothing, and the tick keeps the place it had. A press of A is one choice: `Buttons::a` is set once a press, however many frames the headset skips while A is held, and holding A chooses nothing more.
- **Choosing with the trigger.** A pull of the trigger begun on a choosable row, for a participant, chooses it, once pressed as far as choosing an arrival object takes while the ray is still on that row, as a pull selects an environment's object, with the choosing cue; it is the trigger's rung `Row`, after the hand menu, the right wrist's transcript and a wall carried, and before the rest of Tomori's (`precedence::Trigger`). The trigger decides no request, a question or a queued entry, those being A's, the wrist's and the stick's, and the rungs before `Row` are the only ones that could take a pull meant for something modal; so a pull on a row pre-empts nothing that decides, and with a request waiting it chooses the row, the request still waiting, since the trigger never decides one. **One select at a time:** a pull on a row, or on a teleport pad, that begins while A holds a select of the environment's object is nobody's until it is let go, choosing nothing, and A pressed on the environment's object while such a pull holds selects nothing, as the environment's own selector already kept between its trigger and A; a press of A on a row or a pad, one event that chooses at once and holds no select, still chooses while the trigger holds the environment's select, as A on a pad does (`locomotion.md`). Anywhere else on a panel, on a row not marked choosable, and for a visitor, a pull is Tomori's, which in a space does nothing, since the agent is called from the hand menu rather than the trigger (`environments.md`). This is sound because the trigger has no meaning on a panel in a space, carrying is the grip's, and throwing away is B's: choosing a row takes nothing from any of them; and the rung's place, after a wall carried and before the rest of Tomori's, is unchanged by the trigger no longer summoning, since it only ever came before the rungs that did. The maintainer's reason for ticking with A rather than the trigger was that the trigger keeps one meaning on Tomori's panels and stays the environment's selecting control; a choosable row is the environment's content, published for it to be selected, so the trigger selecting it keeps the trigger the environment's, as a downstream environment that selects everything with the trigger needs.
- **The ray's label.** On a choosable row, the label on the ray ends `A  choose`, `Enter  choose` in the desktop window, for a participant, in place of the tick's hint; a visitor's offers nothing, and their A is refused, saying they only watch. Just chosen, for 0.8 seconds (`tomori_scene::conversation::CHOSEN_SHOWN`), it ends `✓  chosen`, in the highlight colour, the brief confirmation, beside the choosing cue's click and buzz, that the choice was sent; a refusal from the server, which names the panel, takes the mark away at once and is cued as a refused tick is. The protocol has no acknowledgement, so the mark means sent and not refused: a choice the server drops quietly, past the participant's rate or with its side not running or not keeping up, as it drops intents, still shows it, and what tells the participant that the environment acted is what the environment then shows, such as its highlight moving; the row itself is highlighted only by its environment, which decides what a choice does, so that what every participant sees of the list stays the environment's.
- **What the server checks.** It takes a choice only from a participant in the space, refusing a visitor as for any action; refuses, saying why, a panel id longer than an identifier and a row id `valid_row_id` refuses, before looking anything up; refuses, naming the panel in its `ServerMessage::Error` so that the client cues it, a panel not shown in the space's current environment now, as one kept on a wall the environment no longer declares, one that is not a list its environment published, such as the agent's panel or a text or chart panel, a row the list does not have now, and a row its environment did not mark choosable; and holds the rest to the participant's rate of environment intents, sharing their allowance, 8 at once and 4 a second across their connections, dropping those past it quietly, as intents are, and logging a choice only once it is taken, so that a flood fills no log. A choice changes nothing in the projection: no revision, no version.
- **Stale versions, resolved by id.** The row is named by its id, never by its place in the list, so a choice made as the list changed names the row the participant saw, or is refused where that row has gone: it is never applied to another row. Where the panel's version differs from the one the participant saw, the choice is still handed on, and the side is told it was made against an earlier version (`Chosen::current` false), so that an environment that wants to may ignore it; one whose client said no version is taken at its word. The version compared is the one the participant's client was sent, which it says: since an environment's changes are sent at most four times a second (`projection.md`), a client may show a list up to a quarter of a second behind the space's, and a choice made against what it shows is handed on by id, as not current, or refused where that row has gone, and is current again once the paced send has arrived. A panel whose new version the client has not yet laid out, waiting its turn among the panels that changed together (`rendering.md`), shows its old face and points at no item, so that no row of it is named or chosen until its face is the panel as it is.
- **What the side is told.** The server hands a choice to the side as an `Intent` in the same inbox, in order with the client side's intents, at most 64 waiting, made with `Intent::choice`, whose `Intent::chosen()` is a `tomori_environment::Chosen`, with `panel()`, the side's own id for the panel, `row()`, the row's id, and `current()`, and whose payload is empty; `Intent::participant` is who chose. A client side's intent's `chosen()` is always `None`, whatever its payload says, so a client can never forge a choice, nor a choice be read as the client side's JSON; and since a published panel is shown only while the side running now publishes it, and is chosen only in the environment the space is in now, a side is only ever handed choices of its own panels. A side that knows nothing of choices parses the empty payload as it would any malformed intent, and ignores it. What the side does with it is its own, validated against its own state, such as opening that pod in its inspector and publishing the panel again with that row highlighted.
- **The desktop, hands and the spectator.** The desktop window runs the same frame step, so Enter chooses the row the mouse points at, as A does, and a click of the left button, the trigger, chooses it too (`desktop.md`). Hand tracking has no A, and a pinch does not act as the trigger yet (`environments.md`), so a row is not chosen by hand. The spectator draws no panels yet (`projection.md`), and chooses nothing, as it takes no input. A visitor sees highlights and points at rows as they speak, and chooses nothing.
- **Older clients and servers.** A new client offers choosing only to a server whose `SpaceState::choices` is set, so it never sends an older server `ChoosePanelRow`, which that server would refuse as unknown; an older client never sends it, and ignores `Panel::rows` and a refusal's `panel`. An older server sends no `rows`, so a new client neither names rows by id nor offers choosing there, and an older server ignores `Resource::Panel`'s `row`. Nothing changes for a client or server that knows nothing of choices, and no environment's protocol version changes, since panels are Tomori's.

### Rows drawn as rows (increment 4)

The maintainer asked that a published list feel like the attention list it replaced, "a nice scrolling indicator and you could highlight individual rows". A client that reads a list's rows (`Panel::rows`) draws them as rows; one that does not draws the body's list, as before.

- **A row's tone and value.** A row may say how it reads, `Row::with_tone(tone)`, a `tomori_environment::chart::Tone`, `Neutral`, the default, `Good`, `Warn` or `Bad`, named for what it means rather than a colour, as a chart's notes are, and a value against its limit, `Row::with_value(fraction)`, from 0 for none to 1 for all, such as 9 waiting of 20, 0.45: held within 0 to 1, and left out, the row without a value, where it is not finite, as a division by a limit of zero is. The server keeps both with the row, the value to the nearest thousandth, and adds neither to the body, so that the body is the list every client drew before, within the same 80 characters a row and 30 lines and 1,200 characters a body; a row's text should therefore say what matters, as `pod9 · 9 waiting of 20`.
- **What a client is sent.** Each `ListRow` gains `highlighted`, whether it is the row the list highlights, `tone` and `value`, each sent only where it says something, absent from an older server's and ignored by an older client, part of what the panel's version covers. A tone the client does not know reads as neutral, and a value it is sent is drawn within 0 to 1, or not at all where it is not finite (`ListRow::fraction`). At 30 rows of the longest ids, each choosable, in a tone, with a value of three decimals and one highlighted, a list's rows are within 4 KiB as sent, so that 32 lists add at most 128 KiB to a projection, which the frame's bounds already allow for (`projection.md`).
- **How a row is drawn.** Its text is the body's line, wrapped, scrolled and pointed at as a list item is, and around it: the highlighted row on a solid bar across the face, in the highlight colour, with an accent at its right end, without the body's `▸`, which the bar says; a row in a tone with a strip at its start and, in place of its bullet, a mark, `✓` good, `!` a warning, `✕` bad, bold, in its tone's colour from the chart's palette, so that it reads without telling colours apart, a neutral row keeping its bullet and no strip; and a row with a value with a bar 2.5 font pixels thick, a fifth of a line, at the foot of its last line, from after its mark to the face's right edge, its track very faint, so that it never reads as an underline, and its fill as far along as its value, in its tone, or the list's blue for a neutral row.
- **Pointed at and chosen.** The choosable row this participant's ray points at, as A or the trigger would choose it, is outlined, without a fill, so that it is never taken for the highlight, from the frame after it is pointed at; entering it ticks very lightly, as entering any target does, under the same rules, once until the ray leaves it, while leaving it for a row not choosable or the rest of the same panel ticks nothing; and the row they just chose, for as long as the label says `✓  chosen`, has a brighter, thicker outline in its place, which leaves its text, on the highlight's bar or not, as legible as it was. The marks are found among the rows of the list as it is drawn, so that one waiting its turn to be laid out again, reordered, marks the row named where it stands in what is drawn, never another. Only this participant sees either, and a visitor, who chooses nothing, sees neither, while the highlight is the environment's, the same for everyone.
- **Where a long list is.** A list longer than its face says which of its rows show after its title, as `rows 4–9 of 30 · …`, before the rest of its metadata, beside the scroll bar every long body has, counting a wrapped row once; a list that shows whole says nothing. Scrolling is a text panel's, each participant's own (`projection.md`), unchanged.
- **Kept by id.** A row keeps its marks, pointed at and chosen, by its id wherever a reordered list puts it, and is marked nowhere once gone. A list laid out again as it changed, scrolled down, is scrolled so that the row that stood at the top of its face, by its id, stands there still, as far into it as it was; one scrolled to its top stays at its top, so that a queue's newest is seen, and one whose top row has gone stays where it was. Rows move to their new places at once, without animation.
- **Its cost.** A face draws at most six shapes a row it shows, the highlight's bar and accent, an outline, its strip and its value's track and fill, beside its scroll bar, kept with the face and drawn again only when its scroll, its marks or its frame change; a list is laid out with its marks and tones once a version, and a version that changes only its rows' tones and values keeps its lines, their marks changed in place, and is drawn again rather than laid out, and the panels laid out together are paced as any panel is (`rendering.md`), 32 of the largest lists, every row in a tone with a value, arriving eight a frame and changing together two a frame.
- **Told to the agent.** `panels` gives each row's `tone`, in a word, `neutral`, `good`, `warning` or `bad`, and its `value`, from 0 to 1, or null (`mcp.md`); and a row pointed at is described with its tone and value in words, after whether it is highlighted, as `row 2 of 5, highlighted, tone bad, at 82% of its limit, id …`, nothing being said of a neutral row's tone or of a row without a value.
- **Older clients and servers.** An older client draws the body's list and its `▸`, and shows nothing of tones and values; an older server sends none, so a new client draws the body's `▸` as text and every row neutral. The desktop window runs the same frame step and draws rows as the headset does; the spectator draws no panels. No protocol version changes, since every field is optional.

### Rows in columns (increment 5)

The maintainer, reading a downstream environment's lists of observers and queues in the headset, liked choosing rows and their value bars, but found each row's figures, as `GRPC · 100% busy · wait 0ms`, where its own text put them, so that "1% busy, 0% busy, 10% busy" were read along each line rather than down a column, and asked for them as tables: aligned columns under a header, rows still chosen, toned and with their bars.

- **Columns and cells.** A list panel may be laid out as a table, `Panel::with_columns`, of `tomori_environment::Column`s, each with a title, which may be empty, a list whose every title is empty showing no header, its cells' alignment, a `tomori_environment::CellAlign`, left, the default, right, as `Column::number` makes it, so that a column of figures lines up by its digits, every character taking one cell of a panel, or centred, and, for at most one column, `Column::with_value`, its rows' values drawn under its cells rather than under the whole row; and each row given its cells, `Row::with_cells`, one for each column, in their order. A list whose rows have cells but which declares no columns is a table of as many untitled columns as its widest row. Cells are only shown: a row is still named, highlighted, chosen and inspected by its id and its reference, never by what its cells say.
- **Its bounds.** At most 8 columns (`tomori_environment::COLUMN_LIMIT`, `tomori_protocol::LIST_COLUMNS`), each title cleaned onto one line and cut to 24 characters (`COLUMN_TITLE_CHARS`), the last a `…` where it is cut; each cell cleaned onto one line and cut to 32 (`CELL_CHARS`, `LIST_CELL_CHARS`), a row's cells together at most 80, as its text, those past that cut or left empty, and a table's cells together at most a body's 1,200 characters, rows past that left out whole, as rows past the body are, so that a table adds to what is sent and read no more than its body does. A row whose cells are all empty shows its id in its first; a row of a table given text but no cells shows its text there. A client lays out a row whose cells are all empty, as from another server, one line tall, as it does a text panel's table's, so that its row can still be pointed at and chosen. The server refuses, saying why, more than 8 columns, a row of more than 8 cells, a row of more cells than its list declares columns, two columns with values, and columns on a panel that is not a list.
- **Its body.** The body every client draws is the list it was, a line a row: the row's text, where its side gave one, and otherwise its cells that say something, joined by ` · `, as `GRPC · 100% · 0 ms`, without their titles, so that thirty such rows fit in a body's characters.
- **What a client is sent.** A projection's `Panel` gains `columns`, `tomori_protocol::ListColumn`s, each its `title`, its `align`, a `CellAlign`, sent only where it is not left, an alignment a client does not know reading as left, and `value` where it is set; and each `ListRow` its `cells`, each sent only for a table and absent from an older server's, part of what the panel's version covers, so that a change of a cell or a column lays the list out again. A client lays out at most the first 8 columns, each row's cells of those, each its first 32 characters, whatever it is sent. A table's rows, at most 30 of the longest ids, each in a tone with a value and cells as many characters as a body holds, are within 8 KiB as sent, so that 32 tables add at most 256 KiB to a projection, which the frame's fit counts for each list panel by its rows and columns as it does by its text.
- **How a table is drawn.** As a text panel's Markdown table is (`tomori-scene`'s `table.rs`, `projection.md`), from the same layout code: a grid where its columns fit the face, each column as wide as its widest cell, title included, where the table fits, and otherwise each keeping at least 10 cells, or its widest where narrower, wrapping its cells within it at words, never cut with `…`; its header bold on a tinted bar with a rule below it, a faint line between columns and every other row striped; or, on a face too narrow for its columns at 10 cells, a card for each row, a `Title: cell` line for each of its cells that says something, a rule between cards. Each line stands two cells in, the first of a row's first line holding its tone's mark, `✓`, `!` or `✕`, bold in its tone's colour, a neutral row's empty. Everything a row is drawn with around it stays: the highlight's bar across the face and over every line of a row that wraps, the outline of the row pointed at and of the row just chosen, the tone's strip, kept by id across a reorder, and a value's thin bar under its last line, under its whole row, from after its mark, or, in a grid, under the cell of the column with values, from after the line before that column to the space before the next. Scrolled into a table's body, its header and rule stay at the top as a text panel's table's do, and the rows' marks, bars and where the list is, `rows 11–22 of 30`, follow the rows shown below them, the header saying nothing of where it is. A floating table grows wider, to 60 cells, as a text panel's table does.
- **Pointed at and chosen.** A row's lines are its row's, by its place among the rows, as a list item's are, whether in a grid or a card, so that the ray names the row it meets, A and the trigger choose it by its id, and the server describes it, as before; the header, its rule and the rules between cards name no row. **Told to the agent:** a row of a table pointed at is described by its cells, each that says something after its column's title, in place of its text, as `row 1 of 3, tone bad, at 100% of its limit, id observe:observer/grpc: "Name: GRPC · Busy: 100% · Wait: 0 ms"`, within as many characters as its cells and titles take, so that nothing is cut; and `panels`, reading a table whole, gives its `columns`, each with its `title`, `align`, `left`, `right` or `centre`, and `value`, and each row's `cells` in place of its `text`, which says them again only for the clients that draw no tables (`mcp.md`).
- **Its cost.** A table is laid out once a version, as a list is, its column widths found once from its content for the face's width; a version that changes only its rows' tones and values keeps its lines, their marks changed in place, and is drawn again rather than laid out, while one that changes a cell or a column is laid out again. A face draws the same few shapes a row as a list's, with its scroll bar, kept with the face; finding a column's cells for a value's bar reads the one line it is under. Its glyphs are a panel's, from the same atlas.
- **Older clients and servers.** An older client draws the body's list, each row's text, and ignores `columns` and `cells`; an older server sends none, so a new client draws its list as before. No protocol version changes, since every field is optional.

### Rows backed by keys (increment 6)

A downstream environment had to parse what a row stood for back out of its id, as `queue/<instance>/<node>`, and match others by name, which made choosing a row flaky; the maintainer asked that rows be backed by metadata the environment resolves exactly, as a proper mechanism.

- **A row's key.** A row may carry a key, `Row::with_field(name, value)`, called once for each field: what it stands for in the side's own terms, such as `{instance, region, node}` of a pod, or one opaque field naming an entry of the side's own table. Names are 1 to 32 bytes of lowercase ASCII letters, digits and `_`, beginning with a letter (`tomori_environment::valid_field_name`), each once; values text on one line, without control or format characters, of at most 256 bytes (`FIELD_VALUE_BYTES`); at most 8 fields a row (`FIELD_LIMIT`), and a list's keys at most 8 KiB of names and values together (`FIELDS_BYTES`). The server refuses, saying why, a list past any of them. A key is separate from the row's id, which still names it to clients and in a choice, from its reference, which the agent inspects it by, and from its text and cells, which are only shown.
- **Kept with the server.** The server keeps each row's key, verbatim, in its order, with the list as published, and never sends it to a client, so that no client can read, forge or change one: a client only names a row by its id. In its place, every row of a list any of whose rows has a key is sent the revision of its key, `ListRow::key`, a number the server gives the key: the stage's tick at which the row was first published with that key, kept for as long as the row with that id is published again with the same key, and new whenever its key changes, so that, within the server's run, one revision names one key of one row of one list, and two keys a client was shown never share one. A list without keys sends none. The revision is part of what the panel's version covers. Publishing a list again whose rows differ only in revisions the server would give them changes nothing, and one whose rows change only their text, cells, tones or values keeps each row's revision, so that a choice of a key seen before is still handed on. Revisions are compared, not keys: a key that changes and then changes back is given a new revision, so that a choice made while it was first so is refused as stale and the participant chooses again, which keeps the server from remembering past keys.
- **Handed back with a choice.** A client chooses a row as before, by its id with the panel's version it saw, and says the revision of the row's key it saw, `ChoosePanelRow`'s `key`. The server resolves the row it published by id, as before, refusing a panel or row it does not have, or one not choosable, and then, for a list with keys, **hands the side the row's key only where it is the key the participant saw, and otherwise refuses the choice as stale**, `That row changed as you chose it; look again.`, naming the panel so that the client cues it, the side told nothing: a choice that says a revision is taken where it is the row's now, whatever else of the list changed, and is otherwise stale, a revision the row never had, as a forged one, included; one from a client that says none, as an older one, is taken where the panel is the version it saw, or where it says no version at all, taken at its word as before, and is otherwise stale. So a row republished with another key between the participant's look and their choice's arrival never hands the side the new key as if chosen, nor a guess; a row whose key is unchanged is handed on even as the list reorders around it, `Chosen::current` saying whether the list was as seen. The side reads the key with `Chosen::fields`, in the order it gave them, or one with `Chosen::field(name)`; a row without a key, or of a list without keys, gives none, whatever a client says. A refusal is one more of those a choice already had, before the participant's rate is counted.
- **Told to the agent, as data.** A row pointed at is described with its key after its id, each value cleaned as all text others choose is, so that none ends the context block, cut to its first 48 characters, followed by `…`, and quoted as JSON quotes it, so that none ends its quotation, a row's key adding at most about 700 characters, as `row 2 of 3, id observe:pod/7, key {instance: "10.0.0.7:9100", region: "us-east", node: "n-3"}: "pod7 · 3 waiting"`; `panels`, reading a list whole, gives each row's `key` as an object of its fields, within the 32 KiB a panel read whole is held to: where its rows' keys whole would take it past that, each value is cut to its first 64 characters, then 16, followed by `…`, and then the keys are left out, the panel saying so as `keys_cut`; and `inspect` of a row's reference adds the row's `key`, where no object or panel has that reference (`mcp.md`). Each is data, never instructions, as everything an environment says is. **No agent action takes a row**: the agent inspects a row by the id it was told, and any action on rows to come names a row by its id or its key, never by its label.
- **Older clients and servers.** An older client never sends a key's revision, and is held to the panel's version, as above; an older server sends none, and a new client then says none. An older side, which reads no key, is unchanged. No protocol version changes, since every field is optional.

### Told of a move or a dismissal (increment 3)

- **Moved.** Whenever the wall a panel an environment published is on changes, the server hands its side an `Intent` whose `Intent::moved()` is a `tomori_environment::Moved`: the side's own id for the panel, `Moved::panel`, and where it is now, `Moved::place`, a `PanelPlace`: `Wall { wall, slot }`, one of the environment's own walls by its place in the order it declares them, as `Panel::on_wall` names it, and the slot; `OtherWall`, a wall it does not declare, as one a participant added; or `Floating`. Whatever made the change is told: a participant putting it onto another wall, off its wall or onto one; **every panel one action moves**, as the panel already in a slot a participant drops another into, which, on a full wall, swaps to where the dropped one came from; a wall an owner removes, or whose grid shrinks, floating what it held; the agent's `move_panel` and the anchors' moves; and a panel **put back**, as its side publishes it, somewhere other than the wall it asks for, as where it rested before its side started again, or floating as a full wall's newcomer would, so that a side started again, which knows nothing of where its panels were, learns where each is as it publishes it. A move between the slots of one wall, a floating panel moved on, and a move put back where it was tell nothing.
- **Dismissed.** When a panel an environment published goes and stays away, thrown away by a participant or given up by the layout, as the floating bound gives up the panel floating longest when one more floats (`projection.md`), the server hands its side an `Intent` whose `Intent::moved()` says `PanelPlace::Dismissed`; the panel stays away, its updates ignored, until the side retracts it and publishes it again, so a side that has no more use for it retracts it. A retraction by the side itself, and a run ending, which rests its panels, tell nothing.
- **Moves and pins.** A participant pulling a panel off its wall to float pins it when it depends on a parameter its side declares that it does not fix itself (`panel-context.md`): Tomori makes the copy, an instance under an id it mints, which floats where it was pulled, and the panel itself stays in its slot. The panel is then not moved, so its side is handed no `Intent::moved()` for it, and a side that pins a panel dragged off its wall on the moved intent, as a downstream console's System wall does, does not fire; it is told the copy instead, as an `Intent::context()` naming the panel it is of and what it is fixed to, as the participant's, and is told the copy's own moves and its dismissal by the copy's id. A panel that depends on nothing, or fixes all it depends on, is moved as before and told as a move; so is one put on another wall, which takes that wall's context. A side that wants the generic pin declares its parameters and depends on them; one that keeps its own pin on the moved intent leaves them undeclared.
- **By whom.** `Intent::participant` is the participant whose message made the change, or `0`, the number the server gives nobody, for one the layout, the agent or the side's own publishing made. The server compares where the environment's panels are with where its side was last told they were (`HubState::tell_places`), once each participant's message is taken, as that participant's, and at each other change of what the space projects, and as the hub sweeps, as nobody's; a side bound anew, as one started again, has been told nothing.
- **Within the participant's rate.** A participant's moves are told within their rate of intents, which they share with their choices, one intent for each message that moves any of an environment's panels, however many it moves, so that a client cannot flood the side's inbox of 64; moves past it are not dropped but held back, and told, as that participant's, with the next telling, as the hub sweeps if nothing else changes first, only where each panel is then. Moves past the inbox's 64 are dropped, as any intent, and logged at debug, as every move is.
- **Only the server's.** A move is made only by the server, never from a client's intent, whatever its payload says. A side that knows nothing of moves reads its empty payload as it reads any intent it cannot, and ignores it.

## Rationale

A row's key is kept by the server and handed back with a choice, rather than sent to clients and echoed, so that what reaches the side is what it published, which no client can forge, and so that a key may carry the side's own terms without their being shown. Of the two ways a republished row could resolve, to the row as shown or refused as stale, the server takes the first where it can tell that the key shown is the key now, by its revision, and the second otherwise, so that the side is never handed a key the participant did not see, and a busy list reordering under the ray, its keys unchanged, still has its choices taken. A revision rather than a hash of the key is sent, so that nothing of the key reaches a client, and the stage's tick rather than a count for each list, so that a side started again, its list published anew, never gives a key a revision a client may still hold for another.

Columns are laid out by the client from cells the server sends, rather than written into the body as a Markdown table, so that an older client's list is still a line a row that it scrolls, points at and names by its line, and so that a row's lines stay its row's for pointing and choosing, which a Markdown table's lines, items of no list, are not. The layout is the text panel's table's, the same widths, wrapping and cards, so that a list and a table read alike and the rules the maintainer settled for tables (`projection.md`) hold for both. Its cells' characters are held to a body's, as a list's text is, so that a table costs a frame, a listing and the agent no more than a list.

In November 2026 the maintainer asked, of a downstream environment publishing a queue to its walls, for "dynamic panels … the same awesome scrolling queue attention panel with the ability to highlight specific entries": a list whose rows are scrolled with the stick, pointed at, highlighted and chosen, the choice reaching the environment, as choosing a queue row opens that pod in the environment's inspector. A gap analysis found that published text panels already scroll for each participant, and a list item pointed at is already described to the agent, but that rows had no identity the environment or the agent could use, that nothing highlights a row but the environment rewriting its own Markdown, that A on an environment's panel ticks nothing and reaches nothing, that the ray takes a panel before the environment's client side, so that a client side cannot pick a row, and that a side is not told when its panel is thrown away.

Rows are written into the body by the server, rather than sent as a list face of their own, so that the first increment changes no protocol and no client: every client already draws a list, scrolls it and names the item pointed at, and the highlight as a bold pointer is legible to all of them, the spectator and older clients included. The server keeps the rows, so that what the agent is told of a row, and the row a choice names, come from its own copy, never from a client.

A row is named by an id rather than by its line or number, so that a highlight, an inspection and, later, a choice still name the row meant when the environment reorders its list between a participant's look and their press, as a queue does all the time; the tick, which names its item by line, needed a version check for exactly that race (`interaction.md`), which an id makes unnecessary. A row's id is separate from its reference, as an object's identity is from its reference, so that an environment may let a row be chosen without letting the agent inspect it, and the other way round.

Choosing is A's, the button that chooses and confirms, at the tick's rung, because a panel is Tomori's and comes before the environment's client side for every control (`interaction.md`): a client side cannot pick a row behind its panel, so Tomori must take the press and hand it on. Handing it on as an intent in the inbox the side already reads keeps one stream, in order, and the server-attested `chosen()`, apart from the payload, keeps a client from forging one, since the payload is whatever the client side wrote.

In November 2026 the maintainer asked for increment 2 for a downstream environment's queue, whose rows open their pod in its inspector, noting that the environment selects everything with the trigger. The first proposal left the trigger out, since ticking had been given to A to keep the trigger's one meaning on Tomori's panels. Reading the trigger's order showed its only meaning on a panel was attracting the swarm, which never summoned from a panel, and since the agent came to be called from the hand menu it has none in a space, while carrying is the grip's and throwing away is B's; so a rung for a choosable row, before the rest of a panel, takes nothing from any of them, and keeps the trigger the environment's selecting control on what the environment published to be selected. A row the environment does not mark, and a visitor's pull, do as before.

The choice names the row by its id and says the version seen, as the maintainer asked, so that the pointing race the review of the first increment found cannot apply a choice, or a description, to another row: by id, a reordered list still names the row seen, and a removed one is refused; the version only tells the side whether the participant saw the list as it is, since refusing every choice made as a busy queue updates, as a tick is refused, would refuse most of them. Pointing names the row by its id in the same change, since the protocol change carries it for free.

The confirmation is the label's `✓  chosen` and the choosing cue, rather than drawing the row highlighted on the participant's device at once, as a tick is shown, because what a choice does is the environment's: it may highlight that row, another, or nothing, and a highlight shown until the server said otherwise would show everyone's list wrong on one device. The fourth increment outlines the row just chosen brightly only for as long as the label says `✓  chosen`, on that participant's device alone, as the press's confirmation rather than a highlight.

A list's rows are drawn around the body's own lines, rather than as a list face of their own, so that a row wraps, scrolls, is pointed at and is named by its line exactly as before, and an older client's list is the body unchanged; a value is a thin bar under its row's text, one shape a row, rather than a chart's series, so that it needs no bounds of its own. Tones are the chart's, named for what they mean, and each has a mark as well as a colour, for readers who do not tell colours apart. The marks for what this participant points at and chose are kept by the row's id, as the choice itself is, so that a queue reordering under the ray never marks another row.

In November 2026 a downstream environment's maintainer asked, on its bridge in the headset, that a panel dragged off its wall of the system navigated to become an instance of that system, kept updating for it, while the wall shows the next one. The side could not tell where its panels were, nor that one had been thrown away, so the proposed dismissal was built with the move beside it: one intent, made by the server as a choice is, saying where the panel is now, rather than an event for each kind of move or a place the side polls, so that a side learns what a participant did with its panel in the stream it reads already. It is told only as the wall changes, so that rearranging a wall's slots, which a participant does freely, costs a side nothing. A review of the first version found that it told only the panel a participant dragged, so that one swapped out of its slot, floated by a wall removed or shrunk, or given up by the floating bound changed place unknown to its side; so the server now compares where every one of an environment's panels is with what its side was last told, after each change whatever made it, rather than watching each kind of change, and a side started again is told where its panels were put back.

## Open questions

- Whether the server should acknowledge a choice it hands on, so that `✓  chosen` shows only once it is taken, rather than shown, as now, on a choice it drops quietly, since the protocol has no acknowledgement.
- Whether a choice should be confirmed to the participant beyond the label's `✓  chosen`, which says only that the press was taken: by the environment, as by its highlight moving, or by Tomori, as by a cue when the side takes it, which would need the side to answer.
- Whether a row should be choosable by several participants at once, each told, or whether the environment decides one choice for the space, as by highlighting it; today the side is told each choice and decides.
- Whether a list longer than 30 rows should page, and whether its scroll should then be shared, as a queue's position might be, or stay each participant's, as panels' scrolls are.
- Whether a row should have right-aligned trailing text, such as a count or an age kept apart from its text, which would need a column of its own in the row's layout and in the older client's body.
- Whether an older client should be shown a row's tone or value as a compact suffix of its text, such as `(82%)`, within the 80 characters a row has, rather than nothing, as now.
- Whether rows should move to their new places with an animation as a list reorders, rather than at once, as now.
