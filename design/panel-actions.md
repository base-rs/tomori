# Panel Actions

This describes list panels an environment's server side publishes whose rows it names: rows it highlights by id, rows the agent inspects one at a time, and, in later increments, rows a participant chooses with A, the choice reaching the environment's server side, and the side told when its panel is thrown away. The first increment is a requirement, built; the rest is a proposal, in increments, each its own decision for the maintainer.

## Requirement

**List panels.** An environment's server side may publish a list panel, `tomori_environment::Panel::list(id, title, rows)`, beside its text and chart panels (see `environments.md` and `projection.md`): a panel whose body is a list of rows, each a `tomori_environment::Row`, `Row::new(id, text)`, with an id the environment chooses and its text, a line of Markdown-lite, drawn as text and never as HTML, and optionally `Row::with_reference`, a reference the agent may inspect the row by, as an object's (`environments.md`). It is published, updated in place, retracted, placed, carried, pointed at, scrolled and thrown away as any panel an environment publishes, and every limit on those applies to it unchanged: it is one of the environment's 8, its changes are held to the same rates, and it rests as theirs do.

- **Its body.** The server writes the body from the rows, one Markdown list item a line, `- TEXT`, in their order, so that every client draws it, older ones, the spectator and the console included, as a text panel's list, scrolling it where it has more rows than its face shows (see Scrolling in `projection.md`). Each row's text is cleaned onto one line as a title is, without control or format characters, and cut after its first 80 characters (`tomori_environment::ROW_CHARS`), followed by "…" where it is cut, as a title is; a row whose text is empty once cleaned shows its id. **A row is never a checklist item:** a text that begins with a checkbox, `[ ]`, `[x]` or `[X]` followed by a space or nothing, has its brackets written as parentheses, `( )`, `(x)` or `(X)`, so that no client offers to tick it with A, which the server would refuse, as it refuses every tick of an environment's panel. A body holds at most 30 lines and 1,200 characters (`projection.md`), so rows that would take it past either are left out whole, the last first, never cut part way through.
- **Rows' ids.** A row's id is 1 to 64 bytes (`tomori_environment::ROW_ID_BYTES`) of ASCII letters, digits, `-`, `_`, `.` and `/` (`tomori_environment::valid_row_id`), so that it can be told to the agent and named in a message as it is, and unique among the panel's rows. A list has at most 30 rows (`tomori_environment::ROW_LIMIT`), as many as a body has lines. The server refuses, saying why, a list with more rows, a row id it does not take, and two rows with the same id. A row's reference is taken as an object's is: one `valid_reference` refuses is left out, and the row kept without it; of two rows with the same reference, only the first keeps it.
- **Highlighting a row.** A list panel may highlight one of its rows, `Panel::highlighting(row)`, by the row's id, such as the queue entry the environment's inspector shows: the server writes that row as `- **▸** TEXT`, the bold pointer before its text, so that every client draws it, and an older one, without any change. Publishing the panel again with another row highlighted, or none, moves or clears it, as any update does; highlighting is the environment's, the same for everyone in the space, as everything a panel shows is. A highlight naming no row of the panel, or given to a panel that is not a list, is refused, saying so, and one naming a row left out of the body, as past its bound, highlights nothing.
- **Pointing at a row.** A participant pointing at a row as they speak attends to it as to any list item of a text panel (`Resource::panel_at`, `projection.md`), and the server describes the row from its own copy, never from the client: its number of how many rows, whether it is highlighted, its id to inspect it by, where it has a reference, and its text, in double quotes, cleaned as an item's is, in place of the item, as `Ada: [Pointing at panel "Queue" (on a wall, published 3 minutes ago; the observe environment's, id observe:panel/queue; row 3 of 12, highlighted, id observe:pod/112: "pod112 · 41 waiting")] why is this one backed up?`. A list item of a list panel is always a row: the row on the line pointed at, since each row is a line of the body. **The race this leaves:** the client names the row by its line, as it names any item, and the server describes the row on that line of the list as it is when the words begin, so that where the environment reorders or replaces its rows between what the participant saw and what they said, as a queue may within a second, the agent is told of the row now on that line, not the one they saw. The agent's description names the row's text and id, so that it can tell when what it was told does not match what was said; naming the row by id, or saying the panel's version it saw, as a tick does, needs `Resource::panel_at` to carry it, a protocol change left for the second increment, whose choices name their row by id.
- **Inspecting a row.** `inspect` takes a row's id as it takes a panel's or an object's: the server asks the side's inspector about a reference that a row of a list panel it publishes now has, in the environment the space is in now, and refuses one no object, panel or row has now, without asking the side (`environments.md`), describing it to the agent as the panel's title and the row's text. Of an object, a panel and a row with the same reference, the object is asked about first, then the panel, then the row.
- **The agent's `panels`.** For a list panel, even one of no rows, `panels` gives its `rows`, each with its `id`, the environment's, its `inspect_id`, or null where it has no reference, and whether it is `highlighted`, so that the agent can inspect a row nobody points at (see `mcp.md`).

Nothing in this increment reaches a client that it did not already read: a list panel is a text panel to every client, and its rows, ids and references stay in the server.

## Proposal: the later increments

### Increment 2: choosing a row with A

- **Selectable rows.** A list panel may declare its rows selectable, `Panel::selectable()`. A projection's `Panel` gains `rows`, sent only for a selectable list panel, the id of each row in body order, of at most 30 ids of at most 64 bytes, about 2 KiB at most, so that a client can say which row it chose by id; an older client ignores it, and draws the panel as before.
- **Choosing.** A participant pointing at a selectable row, not carrying the panel, presses **A**, Enter in the desktop window, to choose it, for the environment: the client sends `ClientMessage::ChoosePanelRow { panel, row }`, the panel's identity and the row's id, only to a server whose `SpaceState::panel_rows` says it takes it, and cues the choosing as a tick does. The label on the ray says `A  choose`, `Enter  choose` in the desktop window, for a participant; a visitor's label offers nothing, and their A is refused, saying they only watch.
- **A's order.** Choosing a row is the checklist tick's rung of A's order (`interaction.md`, `precedence::A`'s `Conversation`): after the hand menu, the right wrist's transcript, the list and a request's 0.6 seconds, and before saying to turn the right wrist, a teleport pad and an environment's selectable object. The two never compete: an environment's panel takes no tick, which the server refuses today (`projection.md`), so A on a row of an environment's list panel chooses, and A on an item of the agent's checklist ticks. A row carries no checkbox meaning: a row whose text begins `[ ]` is drawn with a box but still chosen, never ticked.
- **The trigger.** A pull of the trigger on a panel attracts the swarm and never summons, as now, and chooses nothing: the maintainer chose A rather than the trigger for ticking so that the trigger keeps one meaning on Tomori's panels (`interaction.md`), and the same holds for rows. Choosing with the trigger too is an open question.
- **What the server checks.** It takes a choice only from a participant in the space, refusing a visitor as for any action; of a panel shown in the space's current environment that the environment's side running now published as a selectable list; of a row id the panel has now, by id, so that a choice racing an update that reordered the rows still names the row chosen, and one whose row has gone is cued as not done and changes nothing. It holds choices to the environment intents' rate, sharing their allowance, 8 at once and 4 a second for each participant across their connections, dropping the rest quietly, and checks the panel and row ids' lengths before looking anything up. A choice changes nothing in the projection: no revision, no version.
- **What the side is told.** The server hands a choice to the side as an `Intent` in the same inbox, in order with the client side's intents, at most 64 waiting, whose `Intent::chosen()` is `Some(Chosen { panel, row })`, the environment's id for the panel and the row's id, and whose payload is empty; a client side's intent's `chosen()` is always `None`, whatever its payload says, so a client can never forge a choice, nor a choice be read as the client side's JSON. A side that knows nothing of choices parses the empty payload as it would any malformed intent, and ignores it. What the side does with it is its own, validated against its own state, such as opening that pod in its inspector and publishing the panel again with that row highlighted: a choice can make nothing happen but an intent to the environment whose panel it is.

### Increment 3: told of a dismissal

- **Dismissed.** When a participant throws away a panel an environment published, or the layout gives it up, as a full wall for the agent's newcomer or the floating bound does (`projection.md`), the server hands its side an `Intent` whose `Intent::dismissed()` names the environment's id for the panel, with the participant who threw it away, or with no participant, `0`, the number the server gives nobody, for one the layout gave up; the side may then stop updating it, retract it or publish it elsewhere. A retraction by the side itself, and a run ending, tell nothing. Dismissals share the inbox and its 64, but not participants' rate, since one panel is dismissed at most once until it is published again.

### Increment 4: richer rows

- **A highlight drawn as a bar, and rows' colours.** A projection's `Panel` gains, for a list panel, which row is highlighted and each row's tone, from the chart's palette, and clients draw the highlighted row on a bar of its own and each row's tone as a stripe at its start, while an older client still draws the body's pointer and text. A row's value as a bar along its row, as a queue's depth, is a further step, needing a list face of its own and the bounds a chart has, in vertices and values.

### Later, each the maintainer's call

- Choosing with the trigger as well as A; choosing by hand tracking, once a pinch is the trigger (`environments.md`); the environment told which row a participant points at, for hover; a row that is a panel's own link to an environment's object, which pointing at highlights in the scenery; and lists longer than a body's 30 lines, sent by pages, scrolled shared or each participant's own.

### The desktop, hands and the spectator

The desktop window runs the same frame step, so Enter chooses the row the mouse points at, as it ticks an item, and its left button, the trigger, chooses nothing (`desktop.md`). Hand tracking has no A, so a row is not chosen by hand until a pinch acts as the trigger and choosing takes the trigger, both later. The spectator draws a list panel, its highlight included, as the body every client draws, and chooses nothing, as it takes no input. A visitor sees highlights and points at rows as they speak, and chooses nothing.

## Rationale

In November 2026 the maintainer asked, of a downstream environment publishing a queue to its walls, for "dynamic panels … the same awesome scrolling queue attention panel with the ability to highlight specific entries": a list whose rows are scrolled with the stick, pointed at, highlighted and chosen, the choice reaching the environment, as choosing a queue row opens that pod in the environment's inspector. A gap analysis found that published text panels already scroll for each participant, and a list item pointed at is already described to the agent, but that rows had no identity the environment or the agent could use, that nothing highlights a row but the environment rewriting its own Markdown, that A on an environment's panel ticks nothing and reaches nothing, that the ray takes a panel before the environment's client side, so that a client side cannot pick a row, and that a side is not told when its panel is thrown away.

Rows are written into the body by the server, rather than sent as a list face of their own, so that the first increment changes no protocol and no client: every client already draws a list, scrolls it and names the item pointed at, and the highlight as a bold pointer is legible to all of them, the spectator and older clients included. The server keeps the rows, so that what the agent is told of a row, and the row a choice names, come from its own copy, never from a client.

A row is named by an id rather than by its line or number, so that a highlight, an inspection and, later, a choice still name the row meant when the environment reorders its list between a participant's look and their press, as a queue does all the time; the tick, which names its item by line, needed a version check for exactly that race (`interaction.md`), which an id makes unnecessary. A row's id is separate from its reference, as an object's identity is from its reference, so that an environment may let a row be chosen without letting the agent inspect it, and the other way round.

Choosing is proposed for A, the button that chooses and confirms, at the tick's rung, because a panel is Tomori's and comes before the environment's client side for every control (`interaction.md`): a client side cannot pick a row behind its panel, so Tomori must take the press and hand it on. Handing it on as an intent in the inbox the side already reads keeps one stream, in order, and the server-attested `chosen()`, apart from the payload, keeps a client from forging one, since the payload is whatever the client side wrote.

## Scope

For the first increment: `tomori-environment`'s `panel.rs` (`Row`, `Panel::list`, `Panel::highlighting`, `ROW_LIMIT`, `ROW_ID_BYTES`, `ROW_CHARS` and `valid_row_id`); `tomori-server`'s `stage/published.rs`, which writes and keeps a list's rows and finds a row by its reference for `inspect` (`Stage::referenced`, which `hub/agent_inspect.rs` already asks, unchanged), `stage.rs`'s description of what a participant points at and `hub/agent_panels.rs`'s `panels`; with the text of `environments.md`, `projection.md` and `mcp.md` that describes them. The protocol, the clients, the spectator and the renderer are untouched. The later increments would cover `tomori-protocol`'s `Panel`, `ClientMessage` and `SpaceState`, `tomori-environment`'s `Intent`, the server's handling of choices and dismissals, and `tomori-scene`'s A order and label.

## Validation

For the first increment:

- Tests of `panel.rs` check that a list panel and its rows, each row's id, text and reference, and an empty list's rows are what they were given, that a row id is a short name of safe characters, and that the limits are those this document states.
- Tests of `stage/published.rs` check that a list's body is a list item a row, in order, its text cleaned and cut, an empty one showing its id, a leading checkbox written as parentheses so that no row is a checklist item, an empty list still a list of no rows, rows past the body's bound left out whole, and the highlighted row written with its pointer; that more than 30 rows, a row id refused or repeated, a highlight naming no row, and a highlight on a panel that is not a list are refused, saying why; that a reference refused or repeated is left out; that moving the highlight, or a row's reference alone, updates the panel in place and the same again changes nothing; that the rows are found by reference, a panel's before a row's, and none once gone; and that pointing at a row describes it by its number, whether it is highlighted, its id and its text, a row without a reference without an id, and a line past the rows the panel alone.
- `tomori-server`'s `tests/environment_panels.rs`, through the whole server, with an example side publishing a queue, checks that a client is sent the list with its highlighted row, that `panels` gives its rows, and that `inspect` asks the side about a row's reference.
- Region coverage of everything added or changed is complete (`testing.md`).

## Open questions

- Whether the trigger should choose a row too, as it selects an environment's object, or stay the swarm's on every panel, as now.
- Whether a choice should be confirmed to the participant by the environment, as by its highlight moving, or by Tomori, as by a cue when the side takes it, which would need the side to answer.
- Whether a row should be choosable by several participants at once, each told, or whether the environment decides one choice for the space, as by highlighting it; today the proposal tells the side each choice and leaves it to decide.
- Whether a dismissal by the layout, rather than a participant, should be told at all, or only a participant's decision.
- Whether a list longer than 30 rows should page, and whether its scroll should then be shared, as a queue's position might be, or stay each participant's, as panels' scrolls are.
- Whether rows' tones and a highlight bar (increment 4) belong in a list face of their own or as spans of the text panel's body, as code panels' are.
