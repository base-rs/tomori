# Arrival

This describes how someone gets from putting the headset on to being in a space, as a participant or a visitor (see `security.md`): choosing a server, choosing or creating a space, and binding an existing agent session. Parts of it are long-term; the open questions at the end are not yet decided.

## Requirement

Arrival takes place in the 3D scene, not on a heads-up display. Servers, spaces and the action that creates a space are objects placed in the world. Text that labels them is anchored to those objects, not to the participant's view. On a headset, the participant chooses an object by pointing a controller at it and pressing the trigger. Pointing gives visible feedback, such as a ray and a highlight, before anything is chosen. Stick and button shortcuts may remain alongside pointing, but pointing must work for every arrival step. Controllers are enough for now; hand-tracking gestures such as a pinch are a separate, later piece of work.

Servers appear in the scene as well, including when only one server is found. Each server is a small, slowly turning constellation of glowing points, made from the same kind of pieces as the swarm, not a solid shape or a flat list item. Brighter points orbit its centre, one for each of the server's spaces. The server advertises in its Bonjour TXT record, alongside the protocol version, how many spaces it has and how many participants are connected, whether in a space or in the lobby; visitors are not counted. It updates both when they change. The constellation shows the participant count as well as the space count: one small cube for each connected participant, in a colour distinct from the swarm's, so that people read differently from the agent. A server that doesn't advertise a count, such as the USB entry, which isn't discovered, shows nothing for it rather than a guessed number. A server's state shows in its constellation: an incompatible server is dim and grey, the remembered server is nearer and warmer, and the USB entry trails a faint thread towards the floor. Choosing a server pours its constellation into the swarm, and its orbiting points spread out to become the space objects. A server whose protocol is incompatible is shown with its version but can't be chosen, as it is today. The USB entry is always offered, as it is today, so the scene is never empty; choosing it when no server is listening fails visibly. Connecting automatically, to the remembered server or to one given at startup, still works. The scene shows that server as chosen, and the participant can go back to the servers to choose another.

Arrival shows what needs attention (see `spaces.md`) on every server it can see, so that a participant who uses several computers can go straight to what needs them:

- **Servers.** A server that advertises spaces needing attention shows it before it is connected: a glow of points around it in the colour of its most urgent level, amber for input, red for a problem and a soft white for a reply, and a label line saying what is waiting, such as "1 needs you, 2 replies". Input and problems pulse quickly; a reply pulses slowly and faintly, since it can wait. Servers keep their order, since arrival relies on where things are; the glow is the cue. A server that advertises no attention counts, such as one whose operator turned them off, shows none.
- **Jump.** Above such a server stands a small jump object, pointed at and chosen on its own. Choosing it connects to the server and, once the server lists its spaces, joins the space that most needs attention, all in one choice and with the usual transitions. The most urgent space is the one with the highest level, then the one that has needed it longest. If someone dealt with it meanwhile, the participant stays in the lobby and is told so; a space that has gone is reported as ended, as for any join. Choosing anything else before the listing arrives takes over from the jump. Choosing the server itself still goes to its lobby.
- **Leaving.** Jumping away from a space leaves it, so that returning to that server shows its lobby, with its attention, rather than rejoining the space. Today a jump starts only from the server row, which a participant reaches from a space only by leaving it. If the server rejoins the participant to a space on arrival, the jump moves on from it without clearing its attention, unless it is the most urgent, which the jump joins. Without a jump, the headset joins a space the server put the participant in, as their own choice, since they now see it.
- **Automatic connection.** The remembered server is connected automatically a moment, about one and a half seconds, after browsing finds it, so that servers found at about the same time are known. If another listed server then advertises attention and the remembered server does not, it is not connected automatically at all, so that the participant sees the other on the server row and nothing connects later while they reach for it. Otherwise it is connected as before.
- **Spaces.** In the lobby, spaces keep their places on the orbit and are marked with the colour of what they need, and their labels say it. The stick's selection starts on the most urgent space, so the stick and A reach it too, and the status names it, such as "Deploy needs you".

How urgent each level is, which space is most urgent and the colour of each level are decided in the render-free arrival model, so every client that presents arrival shows the same thing.

The agent swarm is present from the moment the app starts, through choosing a server and a space, and into the space. It moves continuously between states and never disappears or jumps. Before a server is chosen, the swarm is an amorphous cloud. Choosing a server materializes the swarm into its circular, eye-like shape. That shape is the same for every server. This is a change: today the swarm stays a cloud until a space is joined. In the lobby there is no agent, so the shape shows no agent state. Inside a space it shows the agent's state as it does today. The swarm's existing look, an amorphous cloud of cubes that forms into its circular, eye-like shape, is kept, and arrival builds on it rather than replacing it.

Choosing a space and creating one happen in one view. Once connected, the connected server sits at the centre of the view, and the participant sees every space on the server, alongside an object that creates a new one, arranged evenly in a ring around it, as its orbit. Only owners can create spaces (see `security.md`), so the create object is shown only to owners; a visitor or collaborator sees the spaces alone, and an empty view says that there are no spaces yet. When there are more spaces than fit comfortably in one ring, the ring widens or a further ring is added outside it. Choosing the connected server returns to the servers. When there are no spaces, the view shows an owner the create object directly. There is no separate creation page, and no instruction to press a button to reach one. Choosing the create object opens its choices in place, as rings of objects around it, one step at a time: the backend, then the directory, then optionally an existing session for backends that support attaching, in the session browser described below rather than a ring, and the environment when the server offers this client more than one, of those it can present (see `environments.md`). Each choice is pointed at and chosen like any other object, and the participant can step back to the previous ring.

Spaces are visually distinct from each other. Each space's object has its own appearance, at least a colour and a form, derived deterministically from the space's identifier. It therefore looks the same to every participant and on every visit, and different spaces very likely look different. It also shows the space's live status: its activity (idle, running, waiting or closed), what it needs, how many participants it has, and its title. The approach to explore next, not yet a requirement, is that each environment has a preview mode: a small version of itself that it can render, which becomes the space's object. Spaces would then be recognised by how they look, using visual memory, rather than by reading names. Spaces that share an environment would still differ by their deterministic colour and form, which also remain the fallback for an environment without a preview.

Moving between arrival's steps is animated, never a cut. Each transition eases in and out over roughly half a second to a second, can be interrupted by the next choice or by stepping back, and stepping back plays it in reverse:

- Choosing a server: the chosen server glides to the centre of the view, where it stays, while the other servers shrink and fade away. Its spaces spread outward from it to their places in the ring, with the create object appearing among them; nothing doubles back or crosses the server's path.
- The creation rings: each ring grows outward from the create object, and stepping back folds it back in.
- Entering a space: the chosen space's object comes towards the participant while the other spaces recede. The space's environment then grows out from that object and wraps around the participant, replacing the grid. Leaving the space plays this in reverse: the environment shrinks back into the space's object and the grid returns.

Arrival assumes no environment theme. Server objects, space objects and the swarm do not borrow the look of any one environment, such as the moonlit shrine in `crates/environment-sky-client`. Arrival takes place in the Minimal environment, the plain floor grid, which reads as a waiting area. Entering a space moves from the grid into that space's environment, which belongs to the space (see `environments.md`), and leaving a space returns to the grid.

In the headset, authentication steps are part of the scene too, never a heads-up panel or a form; the web sign-in page in `security.md` is for browsers. A device that is not an owner is offered pairing as an object beside the connected server, on its orbit; choosing it starts pairing, and the pairing code is shown on it until the pairing completes or fails (see `security.md`). Knocking on a space, and admitting or declining a knock, happen in the hand menu (see `hand-menu.md`). A notice that the server's identity has changed, or that the device is no longer admitted, is shown on the server's object and in the hand menu.

When creating a space bound to an existing agent session, the participant can tell the sessions apart without opening them. Each listed session shows, as far as its backend can report them:

- its title,
- its git branch, when its directory is a repository,
- when it was last active,
- a short excerpt, such as its first prompt or last message.

Sessions are listed with the most recently active first. A backend that cannot report a field omits it; it never makes one up. The server derives these facts from what the backend reports, consistent with `agent-backends.md`, and says how long ago each session was last active in seconds as it lists them, so that a client's clock does not matter. Sessions are listed for the folder already chosen and every directory beneath it, since an agent is usually started in a project within a workspace root. Only conversations a participant would pick up are listed: a subagent's child session is a delegated worker of its parent, shown with that parent's space, and is never offered for attachment, nor is an archived session. A session already bound to a space that has not closed cannot be bound again (see `spaces.md`): a client that asks for them, as the headset does, is sent them marked with that space, and offers to join it instead; an older client, which does not ask, is sent only those it can attach. A space bound to an existing session runs in the session's own directory, which the server checks against its roots as it does any directory (see `workspaces.md`). The listing is bounded: the OpenCode backend reads its sessions page by page, newest first, at most 4,096 top-level sessions across every directory, and returns at most 1,000 of them; the server leaves out a session whose identifier or directory is too long to bind, cuts a title to the longest space title, and then leaves out the least recently active until the list fits the snapshot budget (see `server.md`).

**The session browser.** The headset shows the listed sessions in a browser of two columns of rows, not a ring, so that hundreds of sessions stay legible and reachable:

- **Where it stands.** It stands below the connected server and its label, as the Tomori wall stands below the swarm (see `projection.md`), about 1.2 m from the eyes at home, its rows between about 13° and 42° below the eye line, starting 17° below it in the middle, and within about 32° either side of straight ahead, so that it is read by looking down a little, as a page is, without turning the head far. Each column is a flat panel of rows leaning back to face the eyes; two columns are hinged on the edge between them, as a folding screen is, so that they never overlap as seen from home. The create object, which steps back, stands to the left of the browser.
- **The index.** On the left, when the sessions are in more than one folder, an index of their folders, the most recently active first, after "All folders": each row names its folder, by its last component, with the path to it from the folder chosen, how many sessions it holds and how many are busy, and a mark in a colour derived from its directory. The folder the list shows is joined to the list by a bar in its colour. With the sessions all in one folder there is no index, and the list stands straight ahead.
- **The list.** On the right, "New session" first, always shown, which runs in the folder the index shows, or else the folder chosen; then the sessions of the folder the index shows, or of every folder, most recently active first. Each row shows the session's title, or its identifier when it has none, and beneath it whether the agent is busy in it, the space it is already in, by its title, its folder when the list shows more than one, and how long ago it was last active, such as "busy · apps/web · 3 h ago", as far as each is known. Its mark is in its folder's colour and turns quickly while the agent is busy in it, with a dot in the colour of running above it; a session already in a space has a cube below it in the participants' colour, as on a server's constellation, and choosing it joins that space.
- **Legible and pointed at.** Each row is about 2.7° tall, which a ray tells apart, and its text has an x-height of at least 0.45° wherever it is (see `text.md`); the list holds 34 characters a row and the index 20, and a longer line is cut, its full text shown beneath the heading while it is pointed at. A row is drawn within, and pointed at by, its rectangle, as the hand menu's rows are.
- **Scrolling.** Each column shows 9 rows. A column that holds more shows a pager at either end that has more beyond it, saying how many, such as "Older sessions, 143 more": choosing it scrolls a page, so that every session can be reached by pointing alone. The right stick scrolls the column the ray points at, the list unless it points at the index: a push scrolls a row at once, back towards the older end and forward towards the newest; held, it scrolls on after about a third of a second, from 4 to 20 rows a second the further it is pushed; and a flick, a full push let go within a quarter of a second, scrolls a page more. In the desktop window, Page Up and Page Down do so. A column never scrolls past showing its last entry in its last row. The left stick moves the selection, which each column scrolls to keep in view: up and down within a column, left to the index and right to the list; moving it in the index shows that folder's sessions at once, and A there moves to the list.
- **Bounded.** The browser shows whatever the server lists, at most 1,000 sessions, in at most as many folders, with nothing more to page beyond them; with none, it offers a new session alone, and says so.

The browser keeps what it shows when the listing is refreshed, as far as it still fits: the folder the index shows, while it still has sessions, and how far each column is scrolled.

**The world is shown before the microphone is asked for.** The headset asks Android for the microphone ahead of the first recording, so that the request does not interrupt it, but only once the scene has been shown in submitted frames, with the session focused, for a second, never as the session first gains focus, while the launch is still settling. Asking is a call that returns at once, and frames go on being submitted while the system's dialog is up, as they did before; what matters is when it is made. Android answers later, with no callback that a native activity receives, so the frame loop checks the answer between frames every half second, whether the session stays visible, loses focus or stops and begins again meanwhile. These checks decide only what the participant is told and what is logged, not whether the world is drawn. While the request is unanswered, "Waiting for microphone permission..." is shown: on the server list, as its status, unless there is an error; in the lobby, as its status once connected, unless an error or another notice is shown; in a space, on the status pill, unless something outranks it; and in the hand menu's notice, unless something else is already noted. It counts as answered once the microphone is allowed; once focus has been back for a second after the dialog took it without allowing it; or after ten seconds with focus never lost, as when Android shows no dialog because the participant told it not to ask again. Asked and not allowed, the first use of the microphone asks again; a recording made while the request is unanswered checks, and asks if Android has not been asked, through its own request, as before. Between the steps of starting XR, which can take seconds, the headset acknowledges the activity's lifecycle, which Android's `NativeActivity` waits for on its main thread, so that a pause as the launch settles is acknowledged promptly between steps, though not during one; it logs how long each step took, so that the device's log shows whether one is long enough for the pause to time out during it.

## Rationale

The user found the heads-up panel unintuitive for getting connected, and found the separate "no spaces, press Y" step to create a space a detour. They asked for servers and spaces to be shown in 3D, chosen by pointing with the controllers, with spaces visually distinct and eventually previewed. They asked that the swarm's cloud-to-eye formation be kept and carried through arrival, and that arrival not assume the shrine theme, because they intend to build different environments for different kinds of work. Picking up an existing session needs more context than its name. Stated by the user, speaking from the headset, in November 2026. After trying the first pointing build, the user asked for better transitions between choosing a server, choosing a space and entering it, and agreed the transitions described above, also in November 2026. After trying them, the user found that the server's path to the centre and then on to the side overlapped its spaces spreading out, and chose to keep the connected server at the centre with its spaces around it, which also matches its constellation's orbit. Using a work laptop and a personal desktop, the user asked for the server list to show which servers and spaces need them and to jump to them quickly, in November 2026. They agreed to publish the attention counts on the local network with a switch to turn just them off, chose that jumping away leaves the current space, and left telling a participant inside a space for a later stage. The connection rule and the server row follow `docs/proposals/attention.md`, which compares the alternatives.

In November 2026 the maintainer found an OpenCode session in a project beneath their workspace root missing from the headset's session ring, which showed one session for the whole root. OpenCode's `directory` filter matches one directory exactly, and Tomori read one page of it for the root alone, so every session started in a project beneath the root was missing. The listing now reads every page and keeps the sessions beneath the folder, since a root holds many projects' sessions.

In November 2026, speaking from the headset, the maintainer found one ring of eight with a pager too limiting, with so much free space around it, and asked why the sessions could not radiate outward in more rings, accepting an upper bound but asking for a better way to page. Rings, a ring of folders opening into an arc of their sessions, a scrolling list with an index, and saying what you want were prototyped and drawn from the headset's eye at 12, 40 and 150 sessions across 15 folders, distributed as the maintainer's own are, many folders with a few sessions each. Rings fail first on legibility: a session's title is wide and its label horizontal, so rings must cut titles to about ten characters to keep them apart, 39 of 41 labels at 40 sessions, and outer rings shrink below a readable size and reach past 50° to the side at 150. A ring of folders looks like arrival and scales by folder, but its labels are as cramped and an open folder's arc still needs paging. Rows in a list read in full, at the size the text-sharpness findings ask for, about 18 at once in two columns within a comfortable turn of the head, and an index of folders reaches any of hundreds of sessions in two choices, while a pager and the right stick make every row reachable by pointing or the stick. Standing below the connected server keeps the swarm and the server in view, and leans the browser back like a page; hinging its columns keeps them from overlapping as seen from the eyes, which tilting each to face the eyes from its own middle did at their inner lower corners, where a ray chose the wrong column. Listing a session already in a space, marked, rather than leaving it out, shows where it is and joins it, and saying how long ago each was active tells sessions with similar titles apart. Filtering by voice, such as "the base-scheduler one", reusing the speech path, would complement the index and is left for later.

In November 2026 the user, starting the headset after reinstalling, sometimes found "a totally black world", with the microphone request "a bit glitchy". The headset asked for the microphone as the session first gained focus, before it had submitted a single frame and while Horizon OS was still settling the launch, and it serviced the activity's lifecycle, including Android's pause requests, only in its frame loop, never while starting XR; the device's log showed the activity's pause and top-resumed state loss timing out at the start. The request itself never stopped drawing: it was, and is, a call that returns at once. So what changed is when it is made, after the world has been shown and the launch has settled, and that the lifecycle is serviced between the steps of starting XR; the half-second checks only drive the waiting notice and the log of the answer. Waiting until the world has been shown puts the dialog over a drawn scene, after the launch has settled, and still before the first recording, which was the reason to ask early. Neither OpenXR nor Meta asks an app to stop rendering while a system panel is up: a visible session's frames are still composited, and focus-aware apps are expected to keep running under overlays. The cause is inferred from the device's log, so the fix is confirmed on the headset, as Validation describes.

## Scope

The headset client's flow from launch to joining a space (`crates/scene`, drawn by `crates/client-quest`), including how it presents pairing, knocking and authentication notices, the swarm's arrival behaviour, the lobby and session-listing messages in `crates/protocol`, and the session facts each backend reports for attaching.
