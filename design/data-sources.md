# Data Sources

This describes how an environment's server side reads monitoring systems through Tomori's data sources. Only the generic Prometheus source is decided; the rest of #83 stays open, below.

## Requirement

A **data source** is a connection from the server to a monitoring system, with an endpoint and credentials that the application configures, Tomori's own program or another project's, and that never come from a client or the agent and never reach them; what a source answers reaches them only as a server side passes it on (see what errors and warnings quote, below). An environment's server side (see `environments.md`) reads it on its own thread.

**The Prometheus source.** `tomori-prometheus`, in `crates/prometheus`, is Tomori's generic source for the Prometheus HTTP API, and holds nothing specific to one deployment: an application supplies the endpoint, the token and the queries, such as a gateway's identity token from a command of its own. It is a leaf crate: it depends on no other Tomori crate, an environment's server crate, an application or a server builds on it, and no client builds it, which the dependency test in the `tomori-bake` package checks, since it holds credentials and reaches the network.

- **A blocking client.** `Client` blocks its caller until it has an answer or the request's time is up, as a server side may, and never needs an async runtime of the caller's. Each client runs its requests on a thread of its own, on a scheduler of its own, with Base's HTTP client, sending up to its concurrency of requests at once, 4 unless the application sets another, from any of its callers' threads; clones share them. A request takes a slot before it is sent, and a caller whose request finds every slot held waits for one, so that a slow request holds up others only once every slot is taken; while fewer than the concurrency are in flight, a fast request is never kept waiting behind a slow one. Its requests go over the connections that Base's HTTP client pools for one address, one request at a time on each, kept for the requests after; a failure retires only the connection it happened on, leaving the others' requests undisturbed, and the pool for the address kept never holds more than twice the concurrency of connections, counting those still closing; when the client moves to another address, the old pool's connections close as their requests end, so for a moment there may be more. Each request in flight may hold an answer of up to the client's limit, so answers may take about the concurrency times that limit of memory at once. To connect, it tries each address the host resolves to in turn, the one that last connected first, until an attempt fails: each attempt but the last may take its share of what is left of the request's time-out, at least a quarter of a second and at most 5 seconds, so that an address that never completes connecting, as one whose packets are lost, is passed over within the time-out, while one that connects but is slow to answer is waited for. One request at a time finds an address, until it has connected, so that requests sent together share it; the client keeps to that address, opening new connections to it as needed, until a new connection to it fails to connect: one that fails, or that takes longer than an attempt's share of the time when the host has other addresses, makes the request, having sent nothing, try the addresses again, that one last. A caller giving up while a new connection is being made gives up only that connection, keeping the address and the pool's other connections. A request whose caller stopped waiting before it was sent is skipped, without touching any connection.
- **Priorities.** A caller may mark a call as a background request, such as a slow read of a whole fleet: a background request never takes a slot while another request waits for one, and background requests together hold at most all but one of the client's slots, so that one is always left for other requests. With a concurrency of 1 a background request takes the only slot when no other request waits, and a request that comes after waits for it; the documentation says to give a client that sends background requests a concurrency of at least 2. Slots are otherwise not given out in any order among waiters.
- **The endpoint.** It is `https://HOST[:PORT][/PATH]`, checked against the web's public roots, or `http://` only to a loopback host, such as a test's, so that a token never crosses a network in clear; one with user information, a query or a fragment, an IPv6 address without brackets or with text after them, or a path with spaces, control or non-ASCII characters is refused. Requests go to `PATH`, then the API's prefix, `/api/v1` unless the application names another for a gateway that serves the API elsewhere, then the call. Redirects are not followed, so the token is never sent anywhere else.
- **Credentials.** The application gives the client a `TokenSource`, which makes a bearer token, such as from a command or a file, or a fixed `Token`; a client without one sends no `authorization` field. The client keeps the token it was given for the token's lifetime, 40 minutes unless the application sets another, and asks for a new one when that has passed. When the source refuses a request with HTTP 401, the client asks the source for a new token, unless another caller has already renewed the one it sent, and sends the request once more; it reports a second 401, or any 403, as an authentication failure. The crate uses the token only in the `authorization` field of the client's own requests: it is not in `Debug` output, has no `Display`, is never logged, since the crate logs nothing, and is replaced in the text that errors quote from the endpoint's answers (an error that a `TokenSource` itself returns is the source's, which must not contain a token). `Token::expose` is the one way to read a token, public so that another client of the application's, such as one for another API of the same gateway, can send the token its `TokenSource` makes, which it gets by calling the source's `token` itself, in its own `authorization` field, and remove it from its own errors; its documentation says so, and never to log, print or store it, and that it gets none of this client's care: a source may run a command each time it is asked, so such a client keeps the token for its lifetime and asks again only when it expires or the endpoint refuses it with HTTP 401, as this client does. Anything that can call it already holds the token source, or a `Token` from one, so it can already make or send that token: reading it gives such code nothing new. It cannot stop code that reads the token from leaking it, by logging it or sending it elsewhere; that is the reading code's responsibility, as the source's own is.
- **Queries.** An instant query (`/query`) evaluates at an explicit time, so that several queries can be evaluated at one instant and agree; a range query (`/query_range`) has an explicit start, end and step, at most 11,000 points as Prometheus allows. Queries are form-encoded in a `POST` by default, since a long expression would pass a gateway's limit on a URL's length, or in the URL of a `GET` when the application asks. An expression longer than the client's bound, 16 KiB unless the application sets another, is refused before anything is sent. `promql::batch` joins instant-vector expressions with `or`, each on a line of its own so that a comment cannot swallow the next, into as few queries as fit a bound; `promql::quote` and `promql::escape_regex` quote values for a selector, so that a label value read from elsewhere cannot change a query's meaning.
- **Bounds.** Each request waits for a slot within its time-out, and then, from when it has one until its answer is read, ends within its time-out again, so that waiting behind the client's own requests never eats into the time the source has to answer. Its time-out is the client's, 30 seconds unless the application sets another, or one the call gives for itself, so that one client can serve quick reads with short time-outs and slow ones with long; either is at most a day, and is sent as Prometheus's own evaluation `timeout`. The token source's time is not bounded by the client, and the request after a renewal has time-outs of its own, so a call can take four times its time-out and the token source's time. A request whose caller stopped waiting is abandoned, with its connection. An answer larger than the client's limit, 8 MiB unless the application sets another, is refused as soon as it is read past it. Dropping a client's last clone stops its thread and waits for it for at most a second, since its scheduler waits for any lookup stuck in the system's resolver, which nothing can interrupt; the thread is then left to stop on its own once the lookup ends.
- **Caching.** A client may be given a `Cache`, shared by its clones, for a server side whose consumers read the same expressions at different cadences, such as several walls on one region or a chart beside the summary it charts. Without one, every call sends its own request, as before. With one:
  - **Identical calls share a request.** A call identical to one in flight, the same expression at the same time, or over the same range and step, waits for that request's answer, success or failure, rather than send its own, if that request has the same priority and a time-out at least as long as its own, and otherwise sends its own, so that a foreground call never waits for a background request's turn for a slot, nor fails sooner than its own time-out would; it waits for at most its own time-out twice, as long as its own request could wait for a slot and then for its answer, failing as `Timeout` after; a leading call that ends without an answer, as when a token source panics, fails those waiting with a transport error rather than leave them waiting.
  - **Answers are kept while fresh.** An answer is kept for as long as it is fresh, which the cache says for every call, nothing unless the application sets it, and a call may say for itself (`Call::fresh`); a call for the same answer within that time is answered from the cache without a request. A call may give an instant query a bucket (`Call::bucket`), such as 15 seconds, so that it is evaluated at the start of the bucket that holds its time (`Timestamp::floor`), and its answer is fresh for the bucket unless it says otherwise, so that every consumer within a bucket asks the same and is answered by one request; a client without a cache rounds the time all the same. Freshness should be no longer than the data's resolution, such as half the source's scrape interval.
  - **Range queries ask only for the steps they lack.** A range query's points are kept under its expression, step and phase, the milliseconds its steps lie past a multiple of the step, so that ranges whose steps coincide share them. A later range of the same key whose start is within what is kept, or the step after it, asks only for the steps from the one after the last kept, less an overlap, a minute unless the application sets another, rounded up to whole steps, to the range's end, which replace any kept within those steps, for samples that reached the source late: a series in what is kept but not in that answer has no points in those steps. Every other range of the key, starting before what is kept or after a gap, asks for its whole window. A range is answered wholly from what is kept, without a request, only while it is fresh and has every step of the range. Only the range's own steps are returned, oldest first, series with none left out; what is kept for a key reaches back no further than the longest range asked of it in the current period of the cache's decay, 15 minutes unless the application sets another, or the one before, so that a window that moves keeps its size and one no longer asked for lets what is kept shrink. A range's newest steps are merged into what is kept in place, without copying the rest. Series a label filter leaves alike are matched across answers by their order among those alike, as the source sorts them. `Range::aligned` rounds a range's start and end down to its steps from the epoch, so that a query cache in front of the source, such as a query frontend's, sees the same steps from every caller. A range whose expression evaluates at the range's start or end, with the `@ start()` or `@ end()` modifier, depends on the range at every point, so it is read whole every time and never kept, as query frontends treat it; the modifiers are found as PromQL reads them, with any space between their parts and never in a string literal or a comment (`promql::anchored`).
  - **Points kept elsewhere.** An application that keeps a range's answer itself, such as across a restart, may give it back to the cache (`Client::remember`), its points outside the range left out, kept as though read but never fresh, and refused unless each series' points are in order and on the range's steps; points the cache read itself are newer and kept in place of those remembered for the same steps, which only add the steps before and after them, so that the next read of a range of the same key asks only for the steps after it, with the overlap, rather than the whole window; the cache itself lives only as long as the client.
  - **Partial answers are flagged and never kept.** A `Response` says it is `partial` when the source gave a warning other than PromQL's own annotations about the query, as a gateway does that could not reach one of its stores and answered with what it reached, leaving whole series out. Annotations, which begin `PromQL info:` or `PromQL warning:` among the warnings, Prometheus's `infos`, which the response's warnings hold too, and the client's own warning about native histograms it left out say nothing of data left out, so they do not make it partial, and an answer with them is kept, a range's merged as any other. A partial answer is returned, a range's with the points kept before the steps asked for, but never kept, and what was kept of its range is dropped, so that the next read asks for the whole window again; an error is never kept either.
  - **Bounds.** The cache keeps at most 1,024 answers and 64 MiB of them, by its own estimate of the memory their labels, points and text take, their allocations' capacity and its own bookkeeping included, what a window drops given back, unless the application sets other bounds, dropping answers no longer fresh and then the least recently used to keep a new one within them, each found without looking through every answer kept; an answer larger than the cache is never kept. `Client::cache_stats` says how many calls it answered (`hits`), answered with a request for only the steps lacking (`tails`), sent a request for all they asked (`misses`), waited for another's (`deduped`), were partial (`partial`), how many answers it dropped for its bounds (`evictions`), and how many answers and bytes it holds.
- **Failures.** Every failure is an `Error` of one kind: invalid configuration or arguments, transport, time-out, the source not answering, a wait for a slot that outlasted the time-out, `Queued`, kept apart from it so that a caller can tell its own requests crowding the client from the source not answering, an HTTP status, authentication, an answer that cannot be read, a limit, or a query that Prometheus refused, with the HTTP status, its `errorType` and its message. A 429 or 503 carries the `retry-after` the source gave, in seconds or as an HTTP date, whether its body is Prometheus's error or not; a wait longer than a day is taken as a day, and a date out of range or malformed as none, every field checked before any arithmetic, so that nothing a source sends can overflow it. A panic while handling a request, which would be a mistake of the crate's, fails that request with a transport error and leaves the thread serving; a client whose thread has stopped says so as a transport error, never by panicking. The client sends nothing again but the one request after a 401, so that a struggling source is never asked again in a tight loop: the caller polls at its own cadence. Requests refused with a 401 while in flight together renew the token once between them: each renews only the token it sent, and one already renewed by another is sent again as renewed. One caller at a time asks the token source, without holding up callers whose token is still good; others needing a token wait for it, and ask again themselves only if it fails. A request that meets a connection the source has just closed fails as a transport error, and the next call opens a new connection.
- **What errors and warnings quote.** An error's own words never name the token or the endpoint. Errors and Prometheus's warnings may quote the transport's or the source's own text, such as a TLS failure, Prometheus's message or up to 512 bytes of an error page: that text has the token replaced, and the endpoint's host and path wherever each stands whole, the host ignoring case and with any trailing dot and port, the path plain or percent-encoded, and is cut to 512 bytes. A host shorter than three characters is not replaced, since it would be found inside unrelated words, such as a metric's name, nor a path shorter than eight characters or made only of `api`, `v1`, `v2` and `v3` segments, such as `/api/v1`, since it would be found inside the API's own paths. The text is not filtered by the label filter, and may hold the query, label values or anything else the source wrote, so it is the one way what Prometheus answered can reach a client or the agent unfiltered: the crate cannot stop a server side from passing it on, and gives only this guidance. A server side's error is shown to everyone in its space, visitors included (see `environments.md`), so a server side should say what failed in its own words rather than pass an `Error`'s text on verbatim; an environment that reads Prometheus checks this in its own tests, as the first such environment's server crate will.
- **Results.** Answers are typed: a vector of samples, a matrix of series, a scalar or a string, each sample at its own explicit timestamp, to the millisecond, with its metric's labels. Values are read from Prometheus's strings, `NaN`, `+Inf` and `-Inf` included; a stale marker reads as `NaN`. Samples of native histograms, which the client does not read, are left out, keeping other series and a series' own float samples, and a warning says how many, suggesting `histogram_count()`, `histogram_sum()` or `histogram_quantile()` to read them as floats. Prometheus's warnings are returned beside the data. The result types are plain, exhaustive structures and enumerations, accepted while the crate is 0.x.
- **Describing a metric to the agent.** A server side that lets the space's agent inspect a metric it presents (see `environments.md`) describes it with `Metric`, made from the name the application gives its source, such as `production`, never its endpoint, the expression, and the instant or range it was evaluated at or over, with the series' labels, the latest value, its unit and a link if it has them; `Metric::to_json` gives `{"kind": "metric", "datasource", "query", "at", "range": {"start", "end", "step_seconds"}, "labels", "latest": {"value", "at"}, "unit", "link"}`, with times in UTC as RFC 3339 (`Timestamp::rfc3339`) and a value JSON has no number for written as Prometheus writes it, such as `NaN`. It has no field for the endpoint or the token, so that what a side tells the agent cannot carry them by accident; a link with user information, or that is not `http://` or `https://`, is refused without being quoted, since it could carry a credential; and its labels are those the side passes on, which should be those its client's label filter keeps.
- **Labels are filtered on the server.** A client may be given a `LabelFilter`, an allow-list of label names, which it applies to every answer before returning it, removing every other label, `__name__` included unless it is listed; without one it keeps every label. A server side that sends what it read from Prometheus to clients, or describes it to the agent, gives its client a filter of the labels it needs, since labels can carry URLs, user identifiers or secrets. Series whose remaining labels are the same are kept apart, not merged.

## Rationale

Environments need live data from monitoring systems, and fetching it in the headset would put credentials on devices ([#83](https://github.com/base-rs/tomori/issues/83)). Prometheus-compatible endpoints are the common case, and the data center environment proposed in `docs/proposals/data-center-environment.md` (#156) reads per-instance metrics and topology from them, filtering labels before anything reaches a client or the agent. In November 2026 the maintainer asked for the generic part of a downstream environment's Prometheus access to be in Tomori, built from the working client of the maintainer's own prototype, Fantail Observe, which keeps the token on its host, renews it after a 401, posts form-encoded queries because of a gateway's limits on a URL's length and a query's size, batches expressions within that limit, and evaluates a poll's queries at one instant. What is specific to a deployment, such as how its token is made, its queries and any calls beyond the standard API, stays in the project that uses it.

A server side already runs on a thread of its own and may block (see `environments.md`), so a blocking client is the simplest one to use there; a thread and scheduler of the client's own let it keep its connections between calls, which a TLS handshake for every query of every poll would make slow, without the caller running any. Base's HTTP client is what the GitHub environment's server crate already uses. Sending a request again only after a 401 follows the prototype and keeps a source under load from being asked more often than its caller polls; a request on a connection closed at that moment is not sent again either, since the caller's next poll comes soon and a rule with no exceptions is easier to rely on. Trying each address in turn, each but the last within a share of the time, keeps a host whose first address has no route, such as an IPv6 address on a network without IPv6, reachable, whether it refuses at once or never answers; trying the address that last connected first keeps the cost of a broken address to one attempt until something fails. Leaving native histograms out with a warning, rather than refusing the answer, keeps one histogram from failing a batch of other series while still saying what is missing, as #83 asks failures to be visible. Scrubbing the endpoint from quoted text, rather than dropping the text, keeps errors useful for diagnosis while a path or host that is itself sensitive stays in the server's configuration.

In November 2026 a downstream environment that sends the same gateway's identity token to an events endpoint, through an HTTP client of its own, could not read a `Token`, whose text only the crate could read, so it kept a second secret type and token source beside `TokenSource`, implementing each of its sources twice. A downstream can already get a `Token` from its own source, since `TokenSource::token` is public, so only reading it was missing. A public accessor named for what it does, `Token::expose`, as `secrecy`'s `ExposeSecret` is, was chosen: a caller needs the token's text both for its `authorization` field and to scrub its own errors, as the crate does with the same accessor, and any HTTP client takes text. A method giving a ready `Bearer` value was rejected, since its text holds the token just as readably, so it narrows nothing, while leaving a caller unable to scrub its errors without taking the prefix off again; a type building the field with a redacted `Debug` was rejected for the same reason, as its text must be read in the end to be sent, and it would add a type for no guarantee the accessor's name and documentation do not already give. Leaving the token unreadable keeps nothing from code that holds the source, which can make the token itself.

In November 2026 a downstream environment that polls Prometheus heavily, with a slow read of a whole fleet beside quick reads for each pod, found its pod reads timing out after 15 seconds only from waiting behind its own slow read, since the client sent one request at a time, and built several clients to get around it; the maintainer asked for one client to send several requests at once over Base's HTTP client's pool, which keeps several connections to an endpoint. Slots that callers take on their own threads, rather than the pool's own waiting, bound the requests in flight, since only they let a wait for a free connection be timed apart from the exchange and reported as its own error: Base's HTTP client times them together. Requests go through its direct `open` path, which returns once a connection has been made, so that connecting is told apart from a slow answer without watching the pool, and gives the connection back to the pool as soon as the answer is read, so that the next request reuses it. A time-out for each call lets one client serve pollers that need short and long ones. Reserving a slot from background requests was chosen over a share for each class of caller as the least that keeps slow reads from starving quick ones, with nothing to configure.

In November 2026 the downstream environment that polls Prometheus heavily read the same expressions many times over: pods in focus every 5 seconds and summaries every 5 seconds while someone is near, though its source scrapes every 30 seconds and its rates average over 5 minutes; several consumers reading the same expressions, such as two walls on one region; and its charts backfilling and refreshing whole windows to add a point. It had also learnt to read a comparison's window whole again after the gateway answered it partially, rather than keep the partial answer as read. The maintainer asked for more aggressive caching in Tomori where it is generic: shared requests in flight, answers kept for the data's resolution with instant queries rounded to a bucket so that consumers agree, range queries asking only for their missing steps aligned to the step, partial answers flagged and never kept, and bounded memory with statistics. A cache in the client, rather than in each consumer, lets consumers that know nothing of each other share requests. Keeping a range's points by expression, step and phase, rather than by the exact range, is what lets a moving window reuse them; refetching an overlap rather than trusting the newest points kept follows samples arriving after a scrape, and replacing those steps whole, rather than merging point by point, keeps a series the source no longer has from lingering. Following an identical request, rather than queuing behind any request for the same key, keeps the waiting simple and lets range queries over different windows of one key proceed together, each merging what it read. A review of the cache found that ranges anchored with `@ start()` or `@ end()` cannot be extended, as query frontends know, that PromQL's own annotations made every rate of a gauge look partial, that a foreground call could wait out a background request or a shorter time-out, and that a window kept grew with the longest range ever asked; so those ranges are read whole, partial means a warning other than an annotation, a call joins only a request of its priority and a time-out as long, and windows decay. Not joining across priorities was chosen over raising a background request's priority, which its slot, already taken, could not follow. Remembering points an application kept, rather than the cache writing them to disk itself, leaves where and whether to keep them to the application, which knows its state directory, and keeps the crate without a file system of its own. Freshness is the caller's to say, since only it knows the data's resolution; none by default keeps a client given a cache from serving answers older than it expects.

## Open questions

- How a chart an environment publishes (see `projection.md`) binds to a series a data source keeps, so that the server, rather than the side, updates it as new points arrive (#83), and whether `tomori-prometheus` gives a range query's result as a chart's series, a gap for each step with no sample.
- How data sources are configured in the server and its builder, and shared among environments (#83, #73).
- Live chart bindings, which keep a chart's query current only while someone is interested, sharing one poll among charts (#83, #76, #82); and any polling scheduler in Tomori rather than in each server side.
- Whether the cache should keep a range query's points across restarts itself, in the server's state directory, rather than each application keeping and remembering its own.
- Whether, and how, environments offer their data sources to the agent as tools (#158), with the same bounds and label filtering.
- The live process source, which pulls metrics straight from running processes (#157).
- Series, label and metadata queries, and reading native histograms.
- A shared HTTP client, or a client for other APIs of the same gateway, so that a downstream that sends the token elsewhere, such as to an events endpoint, need not build its own connection handling, renewal after a 401 and scrubbing.
