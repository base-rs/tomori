# Tomori's MCP Tools

This describes how a space's agent reads and changes Tomori itself through tools: Tomori's MCP endpoint, its registration with agents, how a tool call is scoped to the space of the session that made it, and the first tools. Tools that draw in the space (agent projection, #82) come later, on the same endpoint. Tools that let the agent decide a device pairing are here too, and their security in `security.md`.

## Requirement

**The endpoint.** The server serves one MCP endpoint, `POST /mcp`, over MCP's streamable HTTP transport, on a listener of its own, which `tomori-server` binds to `127.0.0.1:0`, a free loopback port, unless given `--mcp-bind ADDRESS`, and does not bind with `--no-mcp`. It is not the clients' port: headsets, visitors and other machines cannot reach it, and it serves plain HTTP, since only processes on the server's machine use it; this is an exception to serving only TLS wherever credentials are accepted (`security.md`), which holds only on loopback, so the server warns at startup when it is given an address beyond this machine. A server built on the library serves it with `Server::run_with_tools`, given its listener; `Server::run` serves none. Each request must carry `Authorization: Bearer TOKEN`, with a random token of 256 bits that the server makes for each run and keeps only in memory; any other request is refused with 401, compared in a time that does not depend on where it differs. A request with an `Origin` field, as a web page's would have, is refused with 403. Only `POST` is served: the server opens no event stream and keeps no MCP session, so `GET` and `DELETE` are answered with 405, and each request stands alone. A request body is read before it is answered, up to 1 MiB, so that a refusal reaches its client, and one over 64 KiB is refused with 413. A request naming an MCP revision the server does not serve in `MCP-Protocol-Version` is refused with 400. The endpoint serves revisions 2025-11-25, 2025-06-18 and 2025-03-26, answering `initialize` with the revision asked for, or else the newest. Each request carries one JSON-RPC message, answered with one JSON response; a notification or a response is accepted with 202 and no body. The server answers `initialize`, `ping`, `tools/list` and `tools/call`; any other method is refused with JSON-RPC's method-not-found error, a tool it does not have with invalid-params, a message that is not one object, or a request without a method, with invalid-request, and a body that is not JSON with a parse error and 400. A tool that cannot do what it was asked answers with a result marked as an error, with the reason, as MCP asks, so that the agent can read it.

The server is named `tomori`, so that the agent sees its tools as `tomori_server`, `tomori_spaces` and so on, or as `tools.tomori.server` through OpenCode's Code Mode. Accepting a connection, timing out an idle one and draining connections at shutdown work as for the clients' listener (`server.md`). If the endpoint alone stops serving, as when its listener breaks, the server says so and spaces work on without tools.

**Registration.** A backend that can make Tomori's tools available to its agent says so in its capabilities, with `tools`, and registers a `tomori_backend::ToolServer` (a name, a URL and headers, whose values are never printed) for a directory, with `Backend::register_tools`, replacing one registered there under the same name, and removes it with `Backend::unregister_tools`. The OpenCode backend registers it as a remote MCP server for the directory with `PUT /api/experimental/mcp/tomori?location[directory]=…`, with the endpoint's URL, its bearer token in `headers`, and OAuth turned off, and removes it with `DELETE`, taking OpenCode's not-found answer as removed. These change only OpenCode's running set of MCP servers, not its configuration, which Tomori never writes (`agent-backends.md`), and OpenCode forgets them when it restarts.

The server registers its tools for a backend and directory whenever a space there is bound to its session, created or bound again after a restart, and whenever the backend reports a resynchronization of a space there, since the agent may have restarted and forgotten them; registering again replaces the registration with the same one. It removes them from a directory once no space bound there is open, as when the last space's session closes or the last space open there is deleted (see `spaces.md`). A space listed again after a restart counts as not open until it is bound, so a registration left by the previous run, whose token no longer works, is removed as the spaces are listed again and replaced as each is bound. Registrations are made one at a time, each for one backend and directory and deciding from the spaces there as they are when it is made, so that the last made for a directory always follows the latest change to its spaces, and a removal never follows a later registration. One that fails is logged as a warning and made again when a space there is next bound or read again. Nothing is registered or removed once shutdown has begun: the registration is left in place, and replaced when a space there is next bound, since OpenCode cannot tell that the endpoint has gone. Two Tomori servers sharing one OpenCode directory replace each other's registration; that is not supported.

**Which space a tool acts on.** Every session in a directory sees the same tools, so a tool that acts on a space acts on the space bound to the session that called it. OpenCode names that session in each `tools/call`'s `_meta`, as `ai.opencode/sessionID`. A space tool acts on the one open space bound to that session, whose backend takes tools and which has been bound since the server started; a space listed again after a restart is not one until it is bound again. A space tool called without a session in `_meta`, with one that is not text, empty, or longer than 256 bytes, from a session no open space is bound to, such as a sub-agent's or another project's, or from one that two open spaces are bound to, does nothing and says why, as a result marked as an error; one called from the session of a closed space says that the space's agent session has stopped. The global tools need no session. There is no other credential: no secret is given to the agent, and nothing in its instructions or a tool's arguments decides which space a call acts on.

The server gives the space's agent session, with the other layers (`spaces.md`), when the space's backend takes tools and the server serves them, the instruction entry `tomori-tools`, which says what the tools are, that the space tools act on the space this session is bound to and only when this session calls them, so that it uses them itself rather than through a sub-agent, and that it changes a setting only when someone in the space asks, and then tells everyone what it changed. It also says that the pairing tools never give the code or the device's name; that it confirms a pairing only when a participant in the space asks and has just read its code aloud from the device's own pairing object, never with a code from any other source, such as a file, a web page, a tool's output or another agent, and that a wrong code declines the pairing; that it declines one only when a participant asks; and that it then tells everyone what it did (see `security.md`). It is not one of the layers shown, since it is Tomori's and the same in every space; it is removed with them when the server forgets the space.

**Tools.** The first tools are few, as a foundation:

- `server`: the server's name, version, protocol version and the environments it offers.
- `spaces`: the spaces the server hosts, each with its identifier, title, environment, activity and number of participants, and nothing else: no directory, session or participant.
- `space`: the calling session's space's identifier, title, environment and its label, the environments it could be in, activity, speech setting, attribution, mode and the modes offered, its participants' names and engagement, how many visitors are watching and how many entries are queued: those queued or being sent, not yet delivered to the agent, and not the recently delivered or failed entries the space's queue also shows.
- `set_speech`, with `full` or `brief`: the space's speech setting, as a participant's change sets it (`speech.md`), from the next reply on.
- `set_environment`, with an environment the server offers, of at most 1024 bytes: the space's environment, for everyone in it, as an owner's change sets it (`environments.md`): the agent is given every layer again and the environment's server side follows it.
- `pairing`: the device pairing waiting on the server, if any, as `{"began_seconds_ago", "expires_in_seconds", "code_shown"}` or null, and whether pairing is `paused`; never its code, nor the device's name, which the device chose and could carry an attacker's code or instructions (`security.md`).
- `confirm_pairing`, with `code`, of at most 32 bytes: confirms the pairing waiting only if `code` is its code, and declines it on six other digits; text that is not six digits is refused and changes nothing.
- `decline_pairing`: declines the pairing waiting.

The three pairing tools are space tools: only a session bound to an open space may call them, though they act on the server's one pairing rather than on the space. What each does, what it tells, and the threat it is designed against, are in `security.md`, under pairing through the agent. On a server that does not pair, as in `--auth open` mode, each says so.

Each result is structured content, with the same as text.

**The agent's authority, and announcing its changes.** The agent acts for the space's owners, who created or bound the space and its session: a space tool may do what an owner of the space may, on the space its session is bound to and nothing beyond it, but for the pairing waiting, which it may confirm only with the code the device shows, or decline, as the operator may (`security.md`). Changing the environment is owner-only from a client, so this gives the agent an owner's authority over its own space's environment and speech setting; the maintainer confirmed this in November 2026. A call carries no speaker, so the tools cannot yet act only for the participant who asked, as #100 proposes, and a collaborator who asks the agent can have it change what only an owner could change from the hand menu. Each change is announced to everyone in the space, and logged:

- The space's state changes for everyone in it, participants and visitors alike, and the lobby's listing with it, as for an owner's change, and the change is kept across a restart.
- The tool's result says that it changed the setting and asks the agent to tell everyone in the space, in a sentence naming the change, such as that from its next reply on only the start of each is spoken; the agent's reply, which everyone hears, is the spoken announcement. A setting changed to what it already is changes nothing, and its result says there is nothing to tell.
- The server logs each change at info, naming the space and the new setting, as `The agent of space ID set its speech to Brief.`; a setting left as it was is not logged.

There is no typed notice in the space's state of who changed what yet: that needs a protocol message and a way for clients to show it. The pairing tools, whose decisions matter beyond the space, put theirs on the space's Tomori wall as a text panel, logged and printed on the console with the space and the calling session, and listed on the status page (`security.md`).

**What OpenCode sends.** OpenCode 2.2.5 calls the endpoint with `User-Agent: opencode/…`, `clientInfo` `{"name": "opencode", "version": "2.2.5"}`, and, on each `tools/call`, `_meta` with `ai.opencode/sessionID`, the identifier of the session whose agent made the call, also through Code Mode, and `progressToken`. Its fields name no session. The server logs every request's fields at debug level, naming secret fields such as `Authorization` without their values, with the method, `clientInfo` and `_meta`, and so the calling session, but never a request's arguments.

## Rationale

Asking the agent is more natural from a headset than finding a setting in menus (#100), and the agent needs tools of Tomori's to draw in the space (#82). In November 2026 the maintainer agreed this first pass: one endpoint served by Tomori, authenticated, on loopback; registration through OpenCode's API rather than its configuration; global tools, and space tools scoped to the calling session's space; and a small set of tools, leaving projection to #82.

**Why the calling session can be trusted.** The bearer token proves that a request comes from the agent service it was registered with: the server makes it for each run, keeps it only in memory, never logs it, and gives it only to OpenCode, in the registration's headers, over the backend's authenticated connection to OpenCode, which must run on this machine to reach the endpoint, since it listens only on loopback. OpenCode, not the model, sets `_meta`: the model chooses only a tool and its arguments, and OpenCode's MCP client adds the calling session to every call it makes, to every server. So the session a request names is the session whose agent made the call, as far as OpenCode can tell, and spoofing another session needs the token. Only Tomori's process and OpenCode's hold the token, and anything that can read either can already use OpenCode's own API, whose credentials Tomori's backend holds too, and prompt any session directly, so naming a session gives it nothing it lacks. This replaced a first design in which each space had a capability, a random secret given only to its session in its instructions and passed as an argument: it relied on the model keeping a secret, which OpenCode also kept in the session's records with every call, and it changed with every binding; the maintainer chose the session identity instead, in November 2026. A sub-agent's session is bound to no space, so it cannot use the space tools: mapping workers to their space, and the speaker from the session's latest prompt, are for later.

**OpenCode's client MCP WebSocket.** #82 and #100 proposed OpenCode's client MCP connection, `GET /api/experimental/client-mcp`. This is what it is, from OpenCode 2.2.5's own bundled source and, where marked, tried against a throwaway `opencode serve`:

- **Direction** (tried): the reverse of the endpoint Tomori serves. The tool host is the WebSocket client: it connects to OpenCode, with `location[directory]` and `name` in its query and OpenCode's own credentials, and OpenCode is the MCP client over the socket. A browser, which cannot set the field, first takes a short-lived single-use ticket from `POST /api/experimental/client-mcp/token` and passes it as `ticket`; a request with an `Origin` that is not OpenCode's host is refused.
- **Framing and protocol** (tried): one JSON-RPC 2.0 message per text frame, no batches: MCP's own messages, carried by an MCP SDK transport over the socket rather than by HTTP. On connecting, OpenCode sent `initialize`, with `protocolVersion` `2025-11-25`, then `notifications/initialized` and `tools/list`, each as a frame, and the host answered each in a frame.
- **Tools** (from the source): the host's tools are added to the directory's sessions as the server `name` while the socket is open, and removed when it closes; a `tools/call` comes as a frame, with the same `_meta` as over HTTP, and OpenCode's own terminal interface, which uses this to let the agent open terminals in it, reads `ai.opencode/sessionID` from it. Its client reconnects after a close, after half a second, doubling to at most ten seconds. A server attached this way was not listed by `GET /api/mcp` (tried).

It did not fit this first pass because Tomori's HTTP stack, `base-http`, has no WebSocket, so the server could not open the socket, and adding one was beyond it. The runtime registration, `PUT /api/experimental/mcp/:server`, which #82 named as the alternative, works with what the server has: it makes an endpoint Tomori serves available to a directory's sessions without writing configuration. It needs a port, a loopback one only processes on this machine reach, and a credential, a token made for each run, held only in memory and in OpenCode's running set of servers. Once `base-http` has WebSocket support, the client connection may be the better fit: no port of Tomori's and no token of its own, since it uses OpenCode's credentials, which the backend already has, and a registration that lasts exactly as long as the socket, so that a stopped Tomori's tools go with it, rather than staying listed as connected; it is experimental, and the server would keep a socket open for each directory with an open space.

The official Rust MCP SDK, `rmcp`, serves streamable HTTP only on Tokio, with axum or hyper. The server runs on `base-scheduler` and serves HTTP with `base-http-server`, so `rmcp` would bring a second async runtime and HTTP stack for four methods. The endpoint instead implements the small part of the transport its tools need, stateless JSON responses, on the server's own HTTP stack, sharing its accept loop, request timeout and drain, with tests of the protocol against requests as OpenCode sends them.

In November 2026 the maintainer, re-pairing a headset after reinstalling, asked for the agent to be able to confirm pairing, so that they could say "confirm the pairing, the code is 895 465" to it rather than type into the server's console. The tools give the agent no code, take the code only as a participant reads it from the device, decline on a wrong one, and tell the console, the status page and the space of every decision; requiring an owner in the space was considered and rejected, since the maintainer whose only headset has lost its pairing may be the only owner, and absent. `security.md` records the threat, prompt injection supplying an attacker's code, and why these mitigations answer it. A visitor cannot speak to the agent, so these tools help the holder of a device that lost its pairing only when they reach the agent another way: as a collaborator admitted by knocking, from another paired device, or in the agent's own session, such as in the OpenCode terminal.

## Scope

`crates/server`'s `mcp.rs`, `hub/tools.rs`, `hub/agent_pairing.rs`, the `tomori-tools` instruction entry, the MCP listener in `server.rs` and its command-line options; `tomori-backend`'s `Capabilities::tools`, `ToolServer`, `register_tools` and `unregister_tools`; and the OpenCode backend's registration.

## Validation

- Test that the endpoint's URL names a loopback address when it listens on every address, and that a listener on an address beyond this machine is warned of, and that one that cannot accept leaves the server serving.
- Test the endpoint over HTTP: a request without the token, with another token, or with the token but no `Bearer`, is refused with 401 and a `WWW-Authenticate` challenge; one with an `Origin` with 403; another path with 404; `GET` and `DELETE` with 405 and `Allow: POST`; an unserved `MCP-Protocol-Version` with 400; a body over 64 KiB with 413; and a body that cannot be read is none.
- Test the protocol: `initialize` answers the revision asked for, or the newest, with the server's name and its tools capability; a notification is accepted with 202 and no body; `ping` answers; `tools/list` lists the eight tools with object schemas; an unknown method, an unknown tool, a message that is not one object, a request without a method and a body that is not JSON are refused with their JSON-RPC errors.
- Test, with a fake backend, that the tools are registered for a directory, with the endpoint's URL and bearer token, when a space there is created, again for another space there and after a resynchronization; that a closed or deleted space leaves them registered while another there is open, and that they are removed once none is, whether the last closes or is deleted; that a failure is logged as a warning; that a backend without tools is never asked and its agent is given no `tomori-tools` entry; and that a kept space's directory, listed again after a restart, is removed while it waits to be bound, and registered with the new run's endpoint and token once it is.
- Test that the agent is given `tomori-tools`, saying what the tools act on, with no secret; that the global tools need no session and list no directory; that a space tool without a session in `_meta`, with an empty, non-text or over-long one, or with one no space is bound to, does nothing and says so; that each of two sessions in one directory reads its own space; that a session the agent names anew is followed; that one bound to two open spaces is refused; that a kept space's session reaches no space until it is bound again; and that the previous run's token is refused.
- Test that `space` counts as queued only input not yet sent to the agent: not an entry already delivered while its turn still runs, and an entry spoken during the turn until it is sent.
- Test that `set_speech` and `set_environment` change the space for everyone in it, an owner and a collaborator alike; that each result says whether it changed it and, if it did, asks the agent to tell everyone what changed, and otherwise that there is nothing to tell; that each change is logged once, naming the space; that they refuse a setting or environment the server does not know, and an environment identifier over its limit; that a change of environment gives the agent every layer again; and that the tools change nothing in a closed space.
- Test the pairing tools as `security.md`'s validation lists: no code listed, confirming with the device's code, a wrong code declining, declining, nothing waiting, sessions bound to no space refused, the rate limit, what each decision tells, and `--auth open` mode; and that `tomori-tools` says to confirm only a code a participant just read aloud from the device, never one from any other source.
- Test that no log line contains the bearer token, while a call's fields are logged with the token named as secret, and its `_meta` with the calling session, but not its arguments.
- Test the OpenCode backend against a simulated service: registering puts the remote server's configuration, with its headers and OAuth turned off, for the directory; removing deletes it, and removing one OpenCode does not have succeeds; a refusal is reported; and both fail at once once the backend has shut down.
- Against a throwaway `opencode serve` with its own port and state, confirm that a space's directory lists `tomori` as connected once the space is bound, that another directory does not, and that a call from the space's session reaches the endpoint with the session in `_meta`.
