# Builders

This describes how other projects build their own Tomori server and headset from Tomori's crates.

## Requirement

Another project builds a server of its own on the `tomori-server` library, without forking Tomori or changing its source: it registers backends and environments through the library's builder, `tomori_server::Server::builder()`, which starts with Tomori's own. What it can register is what Tomori supports today:

- **Backends:** any implementation of `tomori-backend`'s `Backend`, from any crate, registered under the name `--backend` and clients name it by, which must be its `Backend::name`. The server treats it as it treats OpenCode's; nothing in the server names a concrete backend. Registering a name already registered replaces that backend.
- **Environments:** an identifier, a label, a protocol version, 1 unless given with `Environment::with_version`, or that of one of Tomori's own with `Environment::built_in`, and the environment's layer of a space's instructions (see `spaces.md`), offered to clients after those already registered unless it replaces one with the same identifier. The first offered is the default, as `environments.md` requires. An environment may also bring a server side, which the server runs for each space bound to it, as `environments.md` requires; registering an environment again replaces its server side with the new one's, or removes it when the new one has none.
- **Configuration:** hooks that change the configured server before it serves, through its public settings.

Environments' client sides and state synchronization (#75, #76), data sources (#83) and tools (#82) will be registered through the same builder once Tomori has them; until then the builder offers nothing for them.

A server built this way takes the same command line as `tomori-server`, including `auth`, and serves the same way: admission, TLS, pairing, advertising, speech, kept spaces and shutdown follow `server.md`, `security.md` and `spaces.md` unchanged. `--help` lists the backends registered.

The `tomori-server` executable is the default build of that builder, with only Tomori's own backends, `fake` and `opencode`, and environments, Sky and the Minimal grid. Its command line, output and behaviour are those it had before the builder existed.

An example downstream crate, `tomori-example-server` in `examples/server`, depends on the published crates as another project would, registers a placeholder backend and environment through the builder, and is built and run by the workspace's tests.

Another project likewise builds a headset of its own on the `tomori-client-quest` library, whose library is `tomori`, through `tomori::Builder`, which starts with Tomori's own build. What it can register is what Tomori supports today:

- **Sceneries:** what the headset draws for a space bound to an environment, by the environment's identifier and at the environment's protocol version: an implementation of `tomori-render`'s `Scenery`, drawn natively in each eye's pass as Sky is, made for the renderer's targets by a function it registers, with `Builder::scenery` at version 1 or `Builder::versioned_scenery` at another. Registering an identifier already registered replaces that scenery and its version. The grid, `minimal`, is built in, at its own version: a scenery registered for it is drawn with it, and the grid is still listed and compared at its own version, whatever version the scenery is registered at. The grid is also what a build shows, naming the environment and the version, for a space bound to one it has no scenery for or has at another version (see `environments.md`). Tomori's own build registers Sky at Sky's version. The identifiers and versions of Tomori's own environments, the grid, Sky and the GitHub prototype, are defined once in `tomori-protocol`'s `environments` module, which the server's defaults and Tomori's own build both use, so that bumping one there changes both sides (see `environments.md`). A build's `Hello` lists the grid, each environment it registers a scenery for, with its version, and the GitHub environment's prototype, which the shared scene presents, at its own version unless a scenery is registered for it at another, so that its server offers it only those.
- **Locomotion:** the profile of an environment, by its identifier: none, the default, teleport onto walkable surfaces, or fly, as `locomotion.md` describes, declared with `Builder::locomotion` or `Sceneries::set_locomotion` and applied in a space bound to that environment when the build draws its scenery. Declaring an identifier again replaces its profile. Tomori's own build declares none, so Sky and the grid have no artificial travel. This is provisional: once environments have server sides (#180), the profile is to move to the environment's server side, so that everyone in a space has the same one.

A scenery, its version and its locomotion profile are all of an environment's client side that a headset build registers until state synchronization (#76) gives a client side more to present; an interface for client sides is introduced then, through the same builder.

`Builder::run_android` runs the headset on the Quest, from a build's own `android_main`: the `tomori` library's own, which runs `Builder::default()`, is its default `app` feature, which a build of another project's turns off by depending on `tomori-client-quest` with `default-features = false`, so that its `android_main` is the only one. `run_xr` runs it on a desktop OpenXR runtime; `run_desktop` and `run_demo` run the desktop windows, through a shell: `tomori::Desktop`, the window system, or a test's, which shows the same contents on the shared test device; and `run_console` the console, which names the build's environments. `tomori::main(builder)` is the `tomori` executable's command line, whose `--xr`, `--desktop`, `--console` and server-less window run the builder's, and whose desktop window's **E** cycles through its sceneries. The `tomori` executable and APK are the default build, `Builder::default()`; their command line and behaviour are those they had before the builder existed. The spectator modes still draw only Tomori's own sceneries, whatever the build.

A headset build is packaged as an APK of its own without changing Tomori: its own application ID, APK name, label, launcher icon and assets, in a copy of `tomori-client-quest`'s `[package.metadata.android]`, which is the only one `cargo-apk` reads. `scripts/android.sh --package NAME` builds, installs and runs any such package, in the dev profile or, with `--release`, the release profile signed with a key it is given (`android-release.md` describes Tomori's own release APK), reading its application ID, APK name and OpenXR loader folder from its manifest, and `scripts/fetch-loader.sh` fetches the loader into the folder it names. The intent extras and the log tag are the framework's, the same for every build. `crates/client-quest/context/android.md` is the guide.

An example downstream crate, `tomori-example-headset` in `examples/headset`, registers a placeholder floor for the example server's placeholder environment, and is built and tested by the workspace's tests. It is packaged as its own APK, `com.example.tomori.headset`, with its own label, icon and asset, on every pull request.

## Rationale

Other projects, such as a private integration with environments of its own, need their own server and headset with their own environments, data sources and tools, without forking Tomori or adding their specifics to its source (#73, and the environment framework proposal in #90). Registering backends and environments is what the server can support now; the rest of the framework slots into the same builder as it lands, rather than ahead of its design. The live server and the people who run `tomori-server` depend on its command line, so the default build must not change. Planned in #73 in November 2026.

## Scope

The `tomori-server` library's builder and the registries it fills, the `tomori-server` executable, and the example in `examples/server`; the headset's builder, `tomori-render`'s sceneries, the `tomori` executable, Android packaging (`scripts/android.sh`, `scripts/fetch-loader.sh` and the manifests), and the example in `examples/headset`.

## Validation

- Test that a backend registered through the builder is offered by name, listed in `--help` after Tomori's, replaces one registered under the same name, and is refused when its own name differs from the one it was registered under or its constructor fails; and that environments registered are offered after Sky and the Minimal grid, or in place of one with the same identifier, with their instructions and versions.
- Test against a fake backend that a registered environment's layer reaches the agent as its `tomori-environment` instruction entry, for a space created in it, changed to it or from it, and restored after a restart, including when a hook offers the environments after the kept spaces are listed again (see `environments.md`).
- Test that the example's executable lists its placeholder backend in `--help`, offers it and the placeholder environment in `Welcome`, and creates a space with both, whose state shows the environment's layer of the instructions.
- Compare `tomori-server --help`, an unknown argument and `auth --help` between the builder's revision and the one before it, and the startup output with the live server's flags, `--backend opencode --name NAME --speech-root PATH --speech-backend offline --workspace-root PATH` with token authentication and TLS, on a loopback port, without advertising and with an unreachable `--opencode-url`: they must be identical apart from ports, paths, fingerprints and times.
- Inspect the examples: each depends only on published crates and uses only their public interfaces.
- Test that the headset builder's default draws the grid and Sky, at version 1, that a registered scenery is listed after them, with its version, or replaces one with the same identifier and its version, that a participant's `Hello` lists them, and that a conversation and renderer given its sceneries draw a space bound to its environment, where Tomori's own build shows the grid and names it.
- Test that the headset builder's window modes, as `tomori`'s command line runs them through a test's shell, create a registered scenery and draw it once **E** or a space reaches its environment, and that its participant draws the build's environments; and check that each test fails when the builder, the command line or the window passes Tomori's own sceneries instead, or leaves the build's environments out.
- Test that the headset example draws its floor for a space in the placeholder environment on the shared test device, and in the server-less window that `tomori`'s command line opens for its build once **E** reaches it, and that its executable takes `tomori`'s command line.
- Link the headset example's library for Android at the Quest's API level: it exports one `android_main`, its own, and with the `tomori` library's `app` feature left on, linking fails with a duplicate `android_main`.
- Package the headset example with `scripts/android.sh --package tomori-example-headset build`, in CI, and check its APK with `aapt`: its application ID, label and icon are its own, its assets hold its own file and Tomori's licence notices, and it holds its own library and the OpenXR loader, not `libtomori.so`. `scripts/android.sh build` still produces `tomori.apk`, `com.codeotaku.tomori`.
- Run `cargo publish --workspace --dry-run --locked`.
