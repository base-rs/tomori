# Builders

This describes how other projects build their own Tomori server and headset from Tomori's crates.

## Requirement

Another project builds a server of its own on the `tomori-server` library, without forking Tomori or changing its source: it registers backends and environments through the library's builder, `tomori_server::Server::builder()`, which starts with Tomori's own backends and no environments, since every environment, Tomori's own included, registers itself from its own crate (see `environments.md`). What it can register is what Tomori supports today:

- **Backends:** any implementation of `tomori-backend`'s `Backend`, from any crate, registered under the name `--backend` and clients name it by, which must be its `Backend::name`. The server treats it as it treats OpenCode's; nothing in the server names a concrete backend. Registering a name already registered replaces that backend. A backend may name the avatar that represents its agent, with `Backend::avatar`, which the server sends to clients (see `avatars.md`).
- **Environments:** an identifier, a label, a protocol version, 1 unless given with `Environment::with_version`, each from the environment's common crate for one of its own crates, such as Sky's, the environment's layer of a space's instructions (see `spaces.md`), and, optionally, its anchors, `with_stage`, `with_agent` and `with_workers`, and walls (see `environments.md` and `projection.md`), offered to clients in the order registered, a later one with the same identifier in place of the earlier. The first offered is the default, as `environments.md` requires; a builder that registers none offers none, so that every space creation is refused. `Builder::environments` lists those registered. An environment may also bring a server side, which the server runs for each space bound to it, as `environments.md` requires; registering an environment again replaces its server side with the new one's, or removes it when the new one has none.
- **Configuration:** hooks that change the configured server before it serves, through its public settings; and command-line options of its own, `tomori_server::CommandOption`, added with `Builder::option`, such as an environment's configuration: `--help` lists each after Tomori's own options, in the synopsis and among the options, the command line reads its value, refusing one it cannot read, and it changes the configured server, after speech synthesis is configured and before the hooks run, in the order the options were added, the last value given of each. An option's parse runs exactly once each time its flag is given, as the command line is read, and its apply is given the value that parse made for the last, never one parsed again, so that a parse that reads a file or checks a service does so once; parse may still run for a command line that is then refused, such as for a later argument it cannot read or a backend it cannot make, and then apply does not run and the value is kept only until the next command line is read or the builder is dropped, which a refused command line ends. Adding a flag already added replaces that option in its place. The GitHub prototype's `--github-repository` is such an option, which its server crate adds. An option or hook changes one registered environment, without knowing the others, with `Server::with_environment`, which offers it in place of the one with the same identifier, keeping that one's place in the order, and so the default, or else after the others, by the same rule as `Builder::environment`, its server side the new one's or none; `Server::environments` lists those offered, in order, so that it can adjust one, such as giving it a live server side, rather than make it again. A changed environment takes effect exactly as one offered with `Server::with_environments`, which replaces them all: for every space, kept or new, when it is next shown or given to the agent, and, once the server serves, a space bound to it whose server side is not the same one has that side stopped and the new one started.

An environment's server side and anchors are registered with it, as above, and its client side and worker placement through the headset builder, below; data sources (#83) and tools (#82) will be registered through the same builders once Tomori has them; until then the builders offer nothing for them, and an environment's server crate may read Prometheus with `tomori-prometheus`, configured by its own application (see `data-sources.md`).

A server built this way takes the same command line as `tomori-server`, including `auth`, and serves the same way: admission, TLS, pairing, advertising, speech, kept spaces and shutdown follow `server.md`, `security.md` and `spaces.md` unchanged. `--help`, and the error for an unknown argument, which shows the same usage, list the backends registered, and after the options the environments registered on the builder, in the order offered, each by its identifier with its label and version, each control character in them shown as `?` so that each keeps to its line, or say that there are none, so that every space creation is refused; an environment an option offers once the command line is read, such as the GitHub prototype, is described by its option instead. Its usage, `auth`'s and the advice to run `auth` when no owner token is issued name the program `tomori-server`, unless `Builder::program_name` names it otherwise, such as after a project's own executable; the synopsis lines up after the name, counted in characters. A program's name is a plain executable name: one that is empty or holds whitespace, a control character or a zero-width character is not used, the program keeps the name it had, and a warning is logged saying why. `--help` lists the speech options, in the synopsis and among the options, only in a server built with the library's `speech` feature: one built without it has none to offer, leaves them out without a note, and refuses each of them, `--speech-provider`, `--speech-backend`, `--speech-offline-model` and `--speech-segmentation` as it reads the command line and `--speech-root` as it starts, saying that it was built without the speech feature, rather than ignoring them.

A server built this way with speech links the sherpa-onnx libraries only from the archive that `scripts/fetch-sherpa-onnx.sh` verified against its pinned SHA-256: `tomori-speech` has no build script of its own and finds the archive only through `SHERPA_ONNX_ARCHIVE_DIR`, so nothing in it assumes a Tomori checkout, and a project of its own copies the script, unchanged, from the release whose crates it depends on, into its own `scripts/`, where it works in the directory above, which holds its Cargo manifest, with `curl` and `python3`, and sets the variable in its own `.cargo/config.toml`, as `crates/speech/readme.md` describes. The script remains the only place the digests are kept.

The `tomori-server` executable is Tomori's own program built on that builder, in a package of its own, `tomori-server-app` (`crates/server-app`), which depends on the library and on Sky's and the farmyard's common crates: `tomori_server_app::builder()` registers, through the same calls another project's server makes, Sky, then the Minimal grid, labelled Grid, then the farmyard, with its server side, beside Tomori's own backends, `fake` and `opencode`, and `tomori-environment-github-server`'s `register` adds `--github-repository`, which offers the GitHub prototype after them when given a repository. A package of its own, rather than a feature of the library's, keeps the library free of every environment's crate whatever its features, so that an environment's server crate can build on the library without a cycle. Its command line, output and behaviour are those it had before, apart from the environments its `--help` and its error for an unknown argument now list, a deliberate addition; it is built with `cargo build -p tomori-server-app`, run with `cargo run -p tomori-server-app --bin tomori-server`, and installed with `cargo install tomori-server-app`, whose features are the library's.

An example downstream crate, `tomori-example-server` in `examples/server`, depends on the published crates as another project would, registers Sky and the grid, as Tomori's own server does, and a placeholder backend and environment through the builder, and is built and run by the workspace's tests.

Another project likewise builds a headset of its own on the `tomori-client-quest` library, whose library is `tomori`, through `tomori::Builder`, which starts with nothing but the built-in grid. What it can register is what Tomori supports today:

- **Sceneries:** what the headset draws for a space bound to an environment, by the environment's identifier and at the environment's protocol version: an implementation of `tomori-render`'s `Scenery`, drawn natively in each eye's pass as Sky is, made for the renderer's targets by a function it registers, with `Builder::scenery` at version 1 or `Builder::versioned_scenery` at another. The targets, `Target`, made with `Target::new`, include the renderer's glyph atlas, from which a scenery draws text of its own (see `text.md`); and each eye's pass tells a scenery where that eye is in the scene, through `Scenery::prepare_eye`, which by default is `Scenery::prepare`, so that a scenery that ignores it, as Sky and the farmyard do, draws as before. Registering an identifier already registered replaces that scenery and its version. The grid, `minimal`, is built in, at its own version: a scenery registered for it is drawn with it, and the grid is still listed and compared at its own version, whatever version the scenery is registered at. The grid is also what a build shows, naming the environment and the version, for a space bound to one it has no scenery for or has at another version (see `environments.md`). Tomori's own build registers Sky from `tomori-environment-sky-client`, whose `register` registers its scenery at Sky's identity, and the farmyard from `tomori-environment-farmyard-client`, whose `register` registers its scenery and teleport profile at the farmyard's (see `farmyard.md`), with `Builder::register`, which hands a build's `Sceneries` to an environment's own registration. A build's `Hello` lists the grid, each environment it registers a scenery for, with its version, and each it presents over the grid, so that its server offers it only those.
- **Presentations over the grid:** an environment whose spaces a build presents with the grid and what the shared scene draws for it, without a scenery of its own, at the environment's version, with `Builder::present_over_grid` or `Sceneries::present_over_grid`, as Tomori's own build presents the GitHub prototype, whose cards the scene draws. Presenting an identifier again replaces its version; a scenery registered for the same identifier is drawn instead.
- **Locomotion:** the profile of an environment, by its identifier: none, the default, teleport onto walkable surfaces, or fly, as `locomotion.md` describes, declared with `Builder::locomotion` or `Sceneries::set_locomotion` and applied in a space bound to that environment when the build draws its scenery. Declaring an identifier again replaces its profile. Of Tomori's own environments, only the farmyard declares one, from its own crate, so Sky and the grid have no artificial travel. This is provisional: once environments have server sides (#180), the profile is to move to the environment's server side, so that everyone in a space has the same one.
- **Client sides:** what a build presents of an environment beyond its scenery, from what the environment's server side shares, by the environment's identifier: a `tomori-scene` `ClientSide`, registered with `Sceneries::set_client_side`, usually by the environment's own `register`, made for each space bound to the environment while the build draws its scenery, and told each frame what the participant points at in it and what they do with the trigger, B and the sticks where it may have them, as `environments.md` describes. Registering an identifier again replaces it. Of Tomori's own environments, only the farmyard registers one, for its chickens.
- **Worker placement:** where an environment's delegated workers stand, by the environment's identifier: a `tomori-scene` `WorkerPlacement`, registered with `Builder::worker_placement` or `Sceneries::set_worker_placement`, usually by the environment's own `register`, and applied in a space bound to the environment while the build draws it, at the workers anchor its server gives, as `environments.md` describes; without one, the default arc. Registering an identifier again replaces it. Tomori's own environments register none.
- **Licence notices:** what a registered environment bundles, such as its models, may need its licence shown with the build's own bundled assets'. An environment's registration adds each notice, a heading and its text, with `Sceneries::add_license`, and `tomori --licenses` shows them after Tomori's own, as it shows the farmyard's chicken.
- **Avatars:** how the agent is shown in a space whose backend names an avatar, by the avatar's identifier: a `tomori-scene` `Avatar`, made for each such space, with a `tomori-render` `Scenery` that draws it, registered together with `Builder::avatar` or `Sceneries::set_avatar`, from the crate of the project that brings it, as `avatars.md` describes. Registering an identifier again replaces it. The swarm is built in, as `swarm`; registering `swarm` shows that avatar only in a space whose state names `swarm`. A build that lacks the avatar a space names shows it and names the avatar it lacks. Tomori's own build registers none.

A headset build registers, for an environment, its scenery and version, its locomotion profile, its client side and its worker placement, as above, and the licence notices of what it bundles.

`Builder::run_android` runs the headset on the Quest, from a build's own `android_main`: the `tomori` library's own, which runs Tomori's own build, `tomori::app::builder()`, is its default `app` feature, which a build of another project's turns off by depending on `tomori-client-quest` with `default-features = false`, so that its `android_main` is the only one, and so that it builds none of Tomori's own environments' crates it does not register. The `app` feature is Tomori's own app in the package that also builds the library, rather than a package of its own, because the APK is built from this package, with its library, `libtomori.so`, and its manifest; it is the only way a core crate depends on an environment's crate. `run_xr` runs it on a desktop OpenXR runtime; `run_desktop` and `run_demo` run the desktop windows, through a shell: `tomori::Desktop`, the window system, or a test's, which shows the same contents on the shared test device; and `run_console` the console, which names the build's environments. `tomori::main(builder)` is the `tomori` executable's command line, whose `--xr`, `--desktop`, `--console`, server-less window and spectator modes run the builder's, whose desktop window's **E** cycles through its sceneries, and whose `--help` names them for `TOMORI_ENVIRONMENT` and names the program `tomori`, unless `Builder::program_name` names it otherwise, as the example's does. The `tomori` executable and APK are Tomori's own build, `tomori::app::builder()`, behind the `app` feature; their command line and behaviour are those they had before. The spectator draws the sceneries it is given: the `tomori` executable's spectator modes give it the build's, and the `tomori-spectator` executable gives it Tomori's own, `tomori_client_spectator::app::sceneries()`, behind that crate's default `app` feature, which `tomori-client-quest` turns off.

A headset build is packaged as an APK of its own without changing Tomori: its own application ID, APK name, label, launcher icon and assets, in a copy of `tomori-client-quest`'s `[package.metadata.android]`, which is the only one `cargo-apk` reads. `scripts/android.sh --package NAME` builds, installs and runs any such package, in the dev profile or, with `--release`, the release profile signed with a key it is given (`android-release.md` describes Tomori's own release APK), reading its application ID, APK name and OpenXR loader folder from its manifest, and `scripts/fetch-loader.sh` fetches the loader into the folder it names. The intent extras and the log tag are the framework's, the same for every build. The APK carries the licence notices of what `tomori-render` compiles in, which `tomori_render::LICENSE_NOTICES` lists by their paths beneath its assets, with their texts, from that package's own `assets`, so that a build can check its copies against the `tomori-render` it builds with. `crates/client-quest/context/android.md` is the guide.

An example downstream crate, `tomori-example-headset` in `examples/headset`, registers Sky from its crate, as Tomori's own build does, and a placeholder floor for the example server's placeholder environment, and is built and tested by the workspace's tests. It is packaged as its own APK, `com.example.tomori.headset`, with its own label, icon and asset, on every pull request, and links its licence notices to `tomori-render`'s, with a test of the check that a build which copies them runs against its copies.

## Rationale

Other projects, such as a private integration with environments of its own, need their own server and headset with their own environments, data sources and tools, without forking Tomori or adding their specifics to its source (#73, and the environment framework proposal in #90). Registering backends and environments is what the server can support now; the rest of the framework slots into the same builder as it lands, rather than ahead of its design. The live server and the people who run `tomori-server` depend on its command line, so the default build must not change, apart from deliberate additions such as the environments listing. In November 2026 the first downstream build on these crates found its `--help` naming `tomori-server` and `tomori`, listing speech options its build had not built in and leaving out its environments, its APK's licence notices copied by hand, and no route to the verified speech libraries outside Tomori's checkout; the program's name, the environments' listing, the speech options' and the licence notices' check answer them, and the server's `--help` gained the environments listing on purpose. Planned in #73 in November 2026. In November 2026 a downstream application's option, which swaps its environment's server side for a live one, had to offer every environment again, Sky and the grid included, since the configured server could only replace them all; replacing one by identity, as the builder does, lets an option change its own environment whatever else the application registered. In November 2026 the maintainer agreed that the builders start empty and Tomori's own programs register Tomori's own environments as another project's would (see `environments.md`); the server's program moved into `tomori-server-app` so that GitHub's server half can build on the library, which a feature of the library's own could not without a cycle.

## Scope

The `tomori-server` library's builder and the registries it fills, the `tomori-server` executable in `crates/server-app`, and the example in `examples/server`; the headset's builder, `tomori-render`'s sceneries, the `tomori` executable and the `app` features of `tomori-client-quest` and `tomori-client-spectator`, Android packaging (`scripts/android.sh`, `scripts/fetch-loader.sh` and the manifests), and the example in `examples/headset`.

## Validation

- Test that a backend registered through the builder is offered by name, listed in `--help` after Tomori's, replaces one registered under the same name, and is refused when its own name differs from the one it was registered under or its constructor fails; and that a builder offers no environment until one is registered, and then those registered, in order, or a later one in place of an earlier with the same identifier, with their instructions and versions.
- Test against a fake backend that a registered environment's layer reaches the agent as its `tomori-environment` instruction entry, for a space created in it, changed to it or from it, and restored after a restart, including when a hook offers the environments after the kept spaces are listed again (see `environments.md`).
- Test that the example's executable lists its placeholder backend in `--help`, offers it and the placeholder environment in `Welcome`, and creates a space with both, whose state shows the environment's layer of the instructions.
- Test that Tomori's own server program offers Sky, then the grid, labelled Grid, then the farmyard, at their crates' versions, and the GitHub prototype too when given a repository.
- Test that `--help` lists the environments registered, in the order offered, with their labels and versions, their control characters shown as `?` and an identifier longer than its column still followed by a space, or says there are none; that it, `auth`'s usage and the advice to run `auth` name the program a builder names, and `tomori-server` by default, with the synopsis lined up after it by characters, and a name that is not a plain executable name is not used, for the reason its warning gives; and that the speech options are listed only in a server built with speech, with nothing else changed, and that a server built without it refuses them.
- Test that an option a builder adds is listed in `--help` after Tomori's own, needs its value, refuses one it cannot read, is applied with the last value given, can fail the server's start, and is replaced by one added later with the same flag; and, counting its parses, that it is parsed once each time it is given and never again to be applied, that it is applied with the value its last parse made, and that a value it cannot parse is not applied.
- Test that `Server::with_environment` replaces the environment with its identifier in its place, the default staying first, whatever its label and version, appends one not offered, and gives it the new one's server side or none; that `Server::environments` lists those offered, in order; and that an option applied through the command line changes one registered environment and leaves the others as registered.
- Compare `tomori-server --help`, an unknown argument, `auth --help` and a malformed `--github-repository` between a revision that changes the builder or the program's package and the one before it, and the startup output with the live server's flags, `--backend opencode --name NAME --speech-root PATH --speech-backend offline --workspace-root PATH` with token authentication and TLS, on a loopback port, without advertising and with an unreachable `--opencode-url`: they must be identical apart from ports, paths, fingerprints and times, and apart from the environments listing, against a revision before it.
- Inspect the examples: each depends only on published crates and uses only their public interfaces.
- Test that the headset builder's default draws nothing but the grid, and Tomori's own build the grid, Sky and the farmyard, at version 1, with the farmyard's teleport profile alone, and presents the GitHub prototype over the grid; that a registered scenery is listed after them, with its version, or replaces one with the same identifier and its version, as does an environment presented over the grid; that a participant's `Hello` lists them; and that a conversation and renderer given its sceneries draw a space bound to its environment, where a build without it shows the grid and names it.
- Test that the renderer tells a scenery where each eye is in the scene, from the eye's view and projection, and the origin for a view without one, and that a scenery that does not ask is prepared as before.
- Test that a worker placement registered through the headset builder or `Sceneries` reaches the conversation by identifier, replacing one before, and that a build registers none by default.
- Test that an avatar registered through the headset builder or `Sceneries` reaches the conversation by identifier, replacing one before, that a build registers none by default, and that a renderer given the sceneries makes its scenery when it shows.
- Test that the headset builder's window modes, as `tomori`'s command line runs them through a test's shell, create a registered scenery and draw it once **E** or a space reaches its environment, and that its participant draws the build's environments; and check that each test fails when the builder, the command line or the window passes other sceneries instead, or leaves the build's environments out. Test that `--help` names the build's environments for `TOMORI_ENVIRONMENT` and the program a build names, `tomori` by default, and compare `tomori --help` with the revision before a change to the command line: it must be identical; and that the spectator lists and draws the sceneries it is given, and the grid alone until then.
- Test that the headset example draws its floor for a space in the placeholder environment on the shared test device, and in the server-less window that `tomori`'s command line opens for its build once **E** reaches it, and that its executable takes `tomori`'s command line.
- Test that `tomori_render::LICENSE_NOTICES` are that package's assets, every licence in its `assets/licenses` among them, and that the headset example's check of its assets finds each notice that differs from it or is missing, and each file in `licenses` that is no notice: the example links `tomori-render`'s files, so its own assets cannot drift, and its test proves the check against copies in a temporary folder, while a downstream with copies runs the same check against its copies.
- Copy `scripts/fetch-sherpa-onnx.sh` into a new Cargo project's `scripts/` and run it there: it verifies the archive into that project's `.tools/sherpa-onnx`.
- Link the headset example's library for Android at the Quest's API level: it exports one `android_main`, its own, and with the `tomori` library's `app` feature left on, linking fails with a duplicate `android_main`.
- Package the headset example with `scripts/android.sh --package tomori-example-headset build`, in CI, and check its APK with `aapt`: its application ID, label and icon are its own, its assets hold its own file and Tomori's licence notices, and it holds its own library and the OpenXR loader, not `libtomori.so`. `scripts/android.sh build` still produces `tomori.apk`, `com.codeotaku.tomori`.
- Run `cargo publish --workspace --dry-run --locked`.
