# Agent Backends

This describes the target design for the Rust server that replaces `bridge/`, and for the headset client, which uses it. The current Node bridge differs; changes to it are not reviewed against this document.

## Requirement

Each agent integration (currently OpenCode and Claude Code) is a separate workspace crate implementing a backend-neutral interface. Backends report structured facts: messages and their parts, text deltas, tool activity, permission requests, questions with structured fields, delegated workers and busy/idle state. A delegated worker names the worker that started it as its parent, or no parent when the session itself started it, so that a change of the agent's own session identifier cannot leave workers pointing at it. They do not produce headset UI text, prompts or voice-answer parsing; the server derives those from the structured facts.

The server is authoritative for a space's delegated workers: the workers it reports, and their states, match what the agent is actually doing, so every client can trust them, subject to the OpenCode initial-discovery limitation below. A worker is reported as running whenever the agent is running it, however it started, including when the agent resumes a worker that had finished, such as Claude Code continuing a subagent through `SendMessage`. When a backend attaches to a session that already has workers, such as after the server restarts, it reports them from the agent's own session records, with their last known states. A worker that was running in an agent process that has since ended, including one that ended with the server, is not reported as running. When a space's agent process exits, the workers it was running stop being reported as running.

OpenCode worker discovery is best-effort where its API cannot provide a consistent family-wide snapshot or replay missed events. The backend subscribes to lifecycle events and traverses the pages of child sessions, including nested children, while preserving observed events across initial discovery. A worker that moves between pages or appears and disappears while disconnected may be missed, and a worker deleted while the event stream is down stays listed until its space is attached again; the server does not claim that its list is exhaustive in those cases. This exception does not authorize inferring deletion from a list omission.

When a worker is explicitly deleted from the agent's session records, the backend updates the parent space's worker list so clients can animate its departure. It must not infer deletion merely from completion, a failed refresh, or a partial or malformed list. The OpenCode backend applies observed child lifecycle events to its remembered workers; a paginated list omission alone is not evidence of deletion. Worker updates travel on their own coalesced lane, so a burst of worker changes never displaces conversation events, and the latest known state is delivered without polling for a new snapshot. A deletion observed while a later snapshot is being read is not undone by that snapshot.

OpenCode session timestamps outlive the process that wrote them, so the OpenCode backend prefers the server's list of sessions its process is currently running over the record's timestamps. A discovered worker is reported as running only on positive evidence: a start event the backend observed, or that list; without it, the worker's state is reported as unknown rather than running. The space's own session falls back to its record's timestamps when the list does not answer, so that its queue is never left without a running state. The list is optional: it is requested alongside the session record under a short bound, so a slow or failing lookup cannot prevent the record from reconciling the space.

If a backend's bounded event channel overflows before a space has started consuming it, the initial snapshot is refused rather than opening the space without the lost events; after that, the overflow ends the session visibly instead of silently dropping events.

A backend that observes its sessions through one shared connection, such as OpenCode's single event stream, survives losing that connection, as when the agent's service restarts, without a Tomori restart. The OpenCode backend finds the service again before every connection attempt, from the same sources in the same order as at startup (the configured URL, `OPENCODE_URL`, then the `opencode serve --service` registration file), because a restarted service may record another port and password. A registration file that exists but cannot be read is read once more, since a restarting service may be rewriting it. Once the service has been found through `OPENCODE_URL` or its registration file, it is never assumed to be at the default address instead: a file missing or unreadable mid-run means the service has not recorded itself yet, and the attempt fails and is retried, rather than reaching whatever listens on the default port without credentials. It reconnects with a bounded backoff: 250 milliseconds after a loss, doubling after each failed attempt up to 10 seconds, and starting again from 250 milliseconds after a connection that stayed open for 10 seconds; a connection lost sooner counts as a failed attempt, so a service that keeps dropping its stream is not reconnected to in a tight loop. A command that arrives while the service is unreachable waits for the next attempt, which it brings forward but never to less than 250 milliseconds after the previous one, and fails as unavailable if that attempt fails. Once a connection opens, a waiting command whose caller has given up is dropped rather than performed. Every command's request to OpenCode runs isolated from the event stream, the sessions' reads and every other command, up to 32 at once, so that one slow or stalled request, waiting or live, holds up nothing else; commands beyond that limit wait their turn, up to 64, and further ones fail as unavailable. A request, once sent, is not cut short, since OpenCode may already be performing it. Closing a session never waits for a connection. Resolving the service's address and opening its event stream are each bounded to 5 seconds. When the server shuts down, it tells the backend, which at once fails every command waiting for a connection or for OpenCode's answer, and every later one; dropping the backend ends its connection thread promptly, even while it waits to retry.

OpenCode's event stream does not replay what it missed, so after a loss the OpenCode backend reports to each attached session that it is reconnecting, a typed fact distinct from an error, so the space knows its state may be stale. Once the stream reopens, it reads again each session whose state it had read, as for a snapshot: within the snapshot's time bound and a limit on concurrent reads, and isolated from the stream and from every other session. The read also lists the directory's agents and the session's current agent, as at attach, since a restarted service may offer others; an agent switch observed during the read is newer and is kept. The session's events during the read are held, then reported after the state read again, which is reported as a resynchronization: the session's conversation, running state, modes and pending permissions and questions as the agent now records them. Its modes, including a switch or agents listed for a participant's mode change during the read, are reported only with that resynchronization, never ahead of it. Events that arrive while no read is in flight, such as while a failed read waits to be retried, are not held: the next read starts after them and so reflects them. Conversation events that arrived before the read requested the session's messages are already in its listing, so a held message start, text or tool call of a listed message, a completion of a message listed as completed, and the end of a tool listed as finished are dropped rather than reported again. Workers are not taken from it; the read is merged into the remembered workers instead: a listed worker is added or updated, a deletion observed during the read is not undone, a state or title set by a lifecycle event observed during the read is kept over the listing's, and a known worker the listing omits is kept, since an omission is never evidence of deletion, but is no longer reported as running unless such an event shows it running, because the evidence that it was running predates the gap. A read that fails is retried no sooner than the reconciliation cadence later, so a service still starting or lost again cannot use up the attempts at once. A read during which more than 512 of the session's events arrive is abandoned as a failed attempt; the next read covers them. A session that cannot be read in three attempts, counted across connections, including one that no longer exists, is closed with the reason, which says when the session no longer exists, without affecting other sessions. So is a session whose connection is lost five more times before it can be read, so that a service that keeps dropping its stream cannot leave a space reconnecting forever, and a session whose event channel lacks room for the state and the events held for it. Whenever the backend closes a session with a reason, the reason reaches the session even if its event channel is full, though the events queued ahead of it may then be lost. A session whose state had not been read when the connection was lost is closed: the read its space was waiting for was abandoned, and reading it later would present events from before the gap as current. What happened during the gap is recovered only as the agent's records show it. Events that arrive while the listing is in flight are kept, because the listing may or may not have them, so text streamed during that round trip may be repeated, but none is lost.

Reasoning — an agent's thinking, before its answer — is reported as a part of the message it belongs to, and never as a text delta. The speech stream reads only the text the agent said out loud; reasoning is transcript material, not speech. A backend whose stream carries a reasoning or thinking delta drops it at the wire: collecting it into the message's parts is enough, and surfacing it would speak the agent's private stream aloud, back to back with its answer.

Session identities are opaque and namespaced by backend. Clients and the wire protocol do not depend on a backend's identifier format.

Backends observe their agents through persistent connections or processes, such as an event-stream subscription or a long-lived child process, not by periodically polling for snapshots. A snapshot operation may exist for resynchronization when a participant joins.

The one exception to observation without polling is the running state of a session. A backend's event stream reports busy and idle as they happen, but the stream can drop an event; a space's queue is gated on idle, so a missed idle event would leave it stuck. A backend that loses events on its stream therefore reconciles each attached session's running state against the agent's own session record on a loose cadence, and reports busy or idle only when the record disagrees with the state it last reported. The record is authoritative; the cadence only matters once a turn has ended, so it can be loose.

The Claude Code backend drives sessions itself: Tomori starts and owns the `claude` process for a space and communicates over its structured stream interface. Sharing a live session with an interactive terminal is not supported.

Tomori never approves a tool permission automatically and never changes an agent's model or project configuration. It changes a session's mode only as described below.

Sessions run under the user's own agent configuration. Tomori does not override permission rules, so a tool the user's configuration already allows runs without a Tomori approval.

Each session has a mode, chosen from the modes the agent's own interface lets its user switch between while a session runs: for Claude Code, the permission modes its terminal cycles through with Shift-Tab, such as default, accept edits, plan and auto; for OpenCode, the primary agents its terminal cycles through with Tab, such as build and plan. A backend reports the modes it offers for a session, each with its name and a short description, and the session's current mode, and changes the mode the way the agent's interface does, through the agent itself: for Claude Code, its stream interface's permission mode request; for OpenCode, switching the session's agent, which its later prompts go to. A backend offers only modes the agent would offer that user in its terminal, such as Claude Code's bypass mode only when the user's configuration enables it. The mode is shared space state: every participant sees it, and any participant can change it from any client, including the headset, where choosing the mode's control steps to the next mode in the agent's own order, as the terminal key does. Tomori never changes a session's mode except when a participant chooses one, or when it starts a session's agent process.

Claude Code sessions start in auto mode, in which the agent itself decides which tool uses need a permission request, so that a space works autonomously by default. This applies whenever Tomori starts the agent process, both for a new session and for one it attaches to. The server's operator can choose a different starting mode, and a mode the agent refuses at startup, such as auto mode where the user's account doesn't offer it, is reported to the space and the session starts in the agent's own default mode instead. OpenCode sessions start with the agent OpenCode would choose by default. Every permission request that does reach Tomori is presented to the space and resolved only by an explicit participant decision.

Tomori changes an agent's permissions only when a participant chooses a standing option, such as "don't ask again", that the agent's own interface offers for the same request. Tomori offers exactly the standing options that interface would offer, labelled with everything each grants and where it is kept, and nothing else. Choosing one has the same effect as choosing it in that interface: the same rules, directories and mode changes, written to the same destination (the session, the project's local or shared settings, or the user's settings) by the agent itself. Tomori never writes agent settings files, and never invents, widens, combines or edits a grant. An option whose grants cannot all be described in its label is not offered. For Claude Code, the standing option is the one standing row of the terminal permission dialog for that tool, such as "Yes, and don't ask again for …" or "Yes, and switch to accept edits for this session". It is built from the request's `permission_suggestions` as that dialog builds it, filtering them by type, destination, tool and size, and answered with exactly the updates the row displays as `updatedPermissions`. It is not offered when the terminal would show no such row, such as when the request sets `suppress_always_allow_rule`, or when the row is one the terminal computes or lets the user edit in ways Tomori cannot reproduce, except that a Bash command prefix row is offered with the single prefix Claude Code suggests.

## Rationale

Tomori must support multiple agent systems without coupling the protocol, server or headset to one of them. Streaming text from the backend is required to start speech before a reply completes; see `speech.md`. Agreed in the October 2026 design discussion.

Answering the same request repeatedly from a headset is tedious, so participants may grant standing permissions, but only in the way the agent's own interface does: a user who knows what "don't ask again" means in the terminal gets the same result in Tomori, and Tomori adds no permission path of its own to review. Agreed with the user in October 2026, on the condition that it works the same way as the terminal interface.

Participants watch workers to see what the agent is doing on their behalf. In November 2026 a subagent resumed after a server restart was running but not shown, and the user asked for the server to be authoritative about running subagents, so that the state is always accurate for clients.

OpenCode's current session listing has no atomic family-wide snapshot or event watermark. Initial discovery can therefore miss a worker that moves between pages or appears and disappears while disconnected. Directly observed deletion is authoritative, but the backend must not present an omitted list entry as proof of deletion. In November 2026 the user accepted this best-effort discovery limitation; a stronger guarantee would require an upstream snapshot/replay contract or an equivalent journal.

In November 2026 the OpenCode service restarted while Tomori was running. The backend's one connection closed, every space closed, and every later attempt to create a space failed until Tomori was restarted by hand. The user asked for the backend to survive a service restart or a dropped event stream, with new sessions working once OpenCode is reachable and existing spaces kept where that is sound. Reading each session again is the only conservative source for what the stream missed, since it has no replay; holding a session's events until that state is presented keeps them in order after the state they follow, as when a space opens. A space that cannot be read again closes visibly rather than presenting a state it cannot vouch for.

In November 2026, the user found that nearly every tool use in a Tomori space waited for an approval from the headset, which stopped the agent working while they were away. They asked for Claude Code sessions to start in auto mode, and for participants to switch modes from Tomori as Shift-Tab does in the terminal, generalised across backends.

## Scope

The backend interface crate, every backend crate, and the server code that consumes them. The standing option requirement also covers the protocol and clients that present approval options and send decisions.

## Validation

- Inspect the dependency graph: the protocol, client and headset crates do not depend on any backend crate, and backends do not depend on the server.
- Inspect backend outputs: no user-facing prompt strings or answer parsing in backend crates.
- Test each backend against a recorded or simulated agent stream, including permissions, questions, workers and a turn that streams text deltas.
- Test each backend's workers against recorded streams and session records: a worker resumed after finishing is reported as running again and then finishes; attaching to a session reports the workers its records show; a worker left running by an ended agent process, and the workers running when a space's agent process exits, are not reported as running. For Claude Code, record the stream of a `SendMessage` that resumes a subagent and its completion notification, and re-check when the supported Claude Code version changes.
- Test that an OpenCode worker without a start event or an active-session entry is not reported as running, that a slow or stalled active-session lookup does not delay an idle reconciliation, and that event overflow before the consumer starts refuses the initial snapshot.
- Test that an OpenCode child deletion updates only its known parent, that completion and resumption preserve membership, that an omitted list entry does not remove a known worker, and that stale queued worker events cannot undo an installed snapshot. Test retry after a full event channel and reject malformed paginated snapshots.
- Test the OpenCode backend against a simulated service that stops and starts again on another port with another password, recorded in a changed registration file. Every open space is told it is reconnecting, a session not yet read is closed, and a space closed meanwhile closes at once; creating a session fails promptly while the service is down and succeeds once it returns, and each run of the service sees only its own credentials. After reconnecting, a permission raised during the gap is reported in the session's resynchronization, a session deleted during the gap closes with the reason, and while one session's read stalls, another session's live events are delivered and the stalled session's held events follow its resynchronization.
- Test against a simulated service that a stalled prompt holds up neither a listing nor the session's live events; that among commands held while the event stream was slow to open, a listing is answered at once while a prompt stalls, the prompt is answered once OpenCode answers it, and a create whose caller gave up is not performed; that a shutdown fails a held command at once and later requests without waiting; and that requests beyond the held limit are refused.
- Test that a close reason reaches its session when the event channel is full; that an agent switch, and agents listed for a mode change, during a read are reported only with the resynchronization, the switch over the read's own; that held conversation events the listing already reflects are dropped while later ones are kept, both directly and against a simulated service whose session record is held so that events arrive before the messages are requested; that closing a session during its read cancels the read and its result is ignored; that events are held only during a read, more than the limit abandon only that read, and a loss discards them while keeping failures; and that five losses before a session is read close it with the reason. Test that once the registration file has been used, its absence makes resolution wait rather than fall back to the default address, and likewise for `OPENCODE_URL`.
- Test that reconnection attempts against a service that drops every connection back off (a handful in two seconds, not a tight loop), that a command fails as unavailable meanwhile, and that dropping the backend ends its thread within a second while it waits to retry. Test that the registration file is read again on each resolution and that `OPENCODE_URL` and an explicit URL take precedence over it.
- Test that a resynchronization merges workers without removing an omitted worker or restoring one deleted during the read, stops reporting an omitted worker as running, and keeps the state and title that lifecycle events during the read set over an older listing; that more held events than the limit, or too little room in the event channel, close only that session with the reason; that a lost connection after the stream reopened discards the events held from it; and that the reason a registration ended always reaches its session.
- Test against a simulated service that fails reads that each failed read of a session is retried a reconciliation cadence later, that a session read successfully on its third attempt is resynchronized, and that one failing every attempt is closed with the reason.
- Confirm that no backend issues periodic snapshot requests while a session is attached; the only periodic check is the running-state reconciliation against the session record, and it reports nothing while the record agrees with the state last reported.
- Test each backend's modes against recorded streams: the offered modes and their order match the agent's terminal for that configuration, a participant's choice reaches the agent through its own interface and the reported mode follows the agent's confirmation, and no mode change is sent without a participant's choice except the starting mode. Test that a Claude Code session starts in auto mode, that the operator's starting mode is used instead when set, and that a refused starting mode is reported and falls back to the agent's default. On the headset, confirm that the current mode is shown in a space and that choosing its control steps through the modes.
- Confirm that permission decisions only reach a backend in response to an explicit participant action.
- Inspect the server and backends: no code writes agent settings files, and a standing grant reaches the agent only as the agent's own answer to the request, such as Claude Code's `updatedPermissions`.
- Test each backend's standing options against recorded requests: the options offered and the grants they describe match what the agent's interface offers for that request, and choosing one sends exactly the corresponding answer. For Claude Code, compare with the installed CLI's permission dialog (for example by searching its bundled source for the dialog's rows) and probe in a scratch directory that the answer is applied and saved to the suggested destination. Re-check when the supported Claude Code version changes. Last compared with Claude Code 2.1.311 in October 2026. The comparison covered the Bash, edit, `Read`, `WebFetch` and generic dialogs in its bundled source. A scratch probe recorded the suggestions for Bash (single prefix, compound command and outside path), `Write` inside and outside the project, `Edit`, `Read` outside the project, `WebFetch` and `WebSearch`. It confirmed that granting a Bash prefix saved `Bash(npm run *)` to the scratch project's `.claude/settings.local.json` and stopped a later prompt, and that granting `Read` session rules and the `Write` mode and directories stopped later prompts.
- Test that the server refuses a grant naming an option the pending request does not offer, and that every offered option's label names each grant and its scope.
