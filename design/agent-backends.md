# Agent Backends

This describes the target design for the Rust server that replaces `bridge/`, and for the headset client, which uses it. The current Node bridge differs; changes to it are not reviewed against this document.

## Requirement

Each agent integration (currently OpenCode) is a separate workspace crate implementing a backend-neutral interface. A server another project builds on `tomori-server` may also offer a backend from a crate of its own, registered through the server's builder (see `builders.md`), which the server treats as it treats Tomori's. Claude models are used through OpenCode, so Tomori has no Claude Code backend. Backends report structured facts: messages and their parts, text deltas, tool activity, permission requests, questions with structured fields, delegated workers, busy/idle state and, where the agent has one, the session's own title, as read with the session and whenever it changes, which a space follows unless renamed (see `spaces.md`). The OpenCode backend reads the title from the session's record and its changes from `session.renamed` events naming the session; a rename of a worker's session changes that worker's title instead. A delegated worker names the worker that started it as its parent, or no parent when the session itself started it, so that a change of the agent's own session identifier cannot leave workers pointing at it. They do not produce headset UI text, prompts or voice-answer parsing; the server derives those from the structured facts.

The server is authoritative for a space's delegated workers: the workers it reports, and their states, match what the agent is actually doing, so every client can trust them, subject to the OpenCode initial-discovery limitation below. A worker is reported as running whenever the agent is running it, however it started, including when the agent resumes a worker that had finished. When a backend attaches to a session that already has workers, such as after the server restarts, it reports them from the agent's own session records, with their last known states. A worker that was running in an agent process that has since ended, including one that ended with the server, is not reported as running. When a space's agent process exits, the workers it was running stop being reported as running.

OpenCode worker discovery is best-effort where its API cannot provide a consistent family-wide snapshot or replay missed events. The backend subscribes to lifecycle events and traverses the pages of child sessions, including nested children, while preserving observed events across initial discovery. A worker that moves between pages or appears and disappears while disconnected may be missed, and a known worker deleted while the event stream is down stays listed until its session is read again and OpenCode confirms it no longer exists, as below; the server does not claim that its list is exhaustive in those cases. This exception does not authorize inferring deletion from a list omission.

A snapshot says when its workers may not be every worker the session has, and why, and a backend reports a change to such a list as incomplete too, so that the space keeps it non-authoritative (see `spaces.md`). The OpenCode backend lists a session's family for whatever remains of a read's time bound once its record, messages, pending permissions and questions have been read, listing at most eight parents' children at once. A family it cannot walk whole in that time, such as a chain of workers too deep to list in 5 seconds, is returned in part, said to be incomplete, and walked on in the background from where the read stopped. This applies to the initial snapshot and to a read again after reconnecting alike; the record, messages, permissions and questions are never returned in part, and a read that runs out of time for them fails as before. At most four sessions' families are walked in the background at once, each within the worker limit and the bound on the size of their records. A walk stops when OpenCode answers a listing with an error, or not within 5 seconds, and the workers are reported as incomplete, with the reason; it then goes on from where it stopped, listing again the parent whose listing failed, about 5 seconds, 30 seconds and 2 minutes after each failure in turn, and once that last attempt fails too, it gives up, leaving the workers reported as incomplete, with the reason, until the session is read again. A walk the session's closing, a read again or a lost connection stopped is not a failure, and its result is ignored. A worker identity beyond the supported size gives up at once, since the walk has already taken its record. A walk that fails during a read, before the space opens, still fails the read, as do the limits; in the background, the same failures leave the space open with its workers reported as incomplete, since its workers are all that is read there. Lifecycle events observed meanwhile are kept, as during initial discovery, for the workers the walk has not found yet: a worker deleted meanwhile is not restored by a page listed before its deletion, one created meanwhile under a parent found only later is added with it, once, and the state or title an event set is kept over the record's. The workers it finds are added oldest first, as at attach, a worker already known keeps its state, and none is ever removed for being missing from a page. Once the family has been walked whole, the workers are reported as every worker the session has. Closing the session, or losing the connection, stops the walk; after a reconnection, the session's read walks the family again.

When a worker is explicitly deleted from the agent's session records, the backend updates the parent space's worker list so clients can animate its departure. It must not infer deletion merely from completion, a failed refresh, or a partial or malformed list. The OpenCode backend applies observed child lifecycle events to its remembered workers; a paginated list omission alone is not evidence of deletion. Worker updates travel on their own coalesced lane, so a burst of worker changes never displaces conversation events, and the latest known state is delivered without polling for a new snapshot. A deletion observed while a later snapshot is being read is not undone by that snapshot.

Besides its workers' states, a backend that reports workers reports what each was last seen doing, as `Event::WorkerActivity`, from which the server judges whether it has failed, stalled or left a message unanswered; the OpenCode backend takes it from the events of the stream it already reads, keeping only those facts (see `events.md`).

OpenCode session timestamps outlive the process that wrote them, so the OpenCode backend prefers the server's list of sessions its process is currently running over the record's timestamps. A discovered worker is reported as running only on positive evidence: a start event the backend observed, or that list; without it, the worker's state is reported as unknown rather than running. The space's own session falls back to its record's timestamps when the list does not answer, so that its queue is never left without a running state. The list is optional: it is requested alongside the session record under a short bound, so a slow or failing lookup cannot prevent the record from reconciling the space.

A backend that supports attaching lists the sessions that can be attached in a directory and in every directory beneath it, most recently active first, each with its own directory and whether the agent is running a turn in it (see `arrival.md`). OpenCode's `directory` filter matches one directory exactly, so the OpenCode backend reads the top-level, unarchived sessions of every directory, page by page through its cursor, and keeps those whose `location.directory` is the directory or beneath it, compared component by component. It marks a session busy when the server's list of the sessions its process runs has it, read under the same short bound, or, when that list does not answer, by the session record's timestamps.

If a backend's bounded event channel overflows before a space has started consuming it, the initial snapshot is refused rather than opening the space without the lost events; after that, the overflow ends the session visibly instead of silently dropping events.

OpenCode's event stream keeps running while a space's initial snapshot is read, so some events that arrive meanwhile are already in it: a message that ended during the read is listed with its text. Until its initial snapshot has been read, the OpenCode backend holds a session's events and delivers them after the snapshot, as it does after a reconnection, except those the snapshot already shows: the start, text and completion of a message it lists as completed, a tool call it lists, and a tool's end it lists as finished. A message the snapshot lists still being written keeps its start, since every event after it was held, so the space follows it from its start, and speaks the text that follows. OpenCode records a message's text when the text ends, before the message completes, as when a tool follows it. So such a message's held text deltas are dropped too when their end was reported before the snapshot requested the messages and the snapshot records that text, part for part: that text is shown with the snapshot, and, like the conversation the snapshot lists, is not spoken. Text still streaming, which no record has yet, is delivered, and in any doubt the text is delivered, so a fragment may repeat but none is lost. The running state is that of the last held busy or idle event, or else the snapshot's, and the modes are the latest confirmed. More than 512 held events, counting a run of text deltas as one, refuse the snapshot, and so does an event channel without room for them; the events stay held, so a later snapshot through the same handle can still deliver them, though the server closes the handle instead. A session's events therefore reach its space only once its initial snapshot has been read, and its running state is reconciled only from then.

The OpenCode backend bounds what it holds of the event stream: an event is decoded once it is whole, so a character split between two reads is kept, and an unfinished event larger than 16 MiB, the bound on any response, is treated as a lost event stream. Dropping part of it could lose an event, so the backend reconnects and reads each session again instead.

A backend that observes its sessions through one shared connection, such as OpenCode's single event stream, survives losing that connection, as when the agent's service restarts, without a Tomori restart. The OpenCode backend finds the service again before every connection attempt, from the same sources in the same order as at startup (the configured URL, `OPENCODE_URL`, then the `opencode serve --service` registration file), because a restarted service may record another port and password. A registration file that exists but cannot be read is read once more, since a restarting service may be rewriting it. Once the service has been found through `OPENCODE_URL` or its registration file, it is never assumed to be at the default address instead: a file missing or unreadable mid-run means the service has not recorded itself yet, and the attempt fails and is retried, rather than reaching whatever listens on the default port without credentials. It reconnects with a bounded backoff: 250 milliseconds after a loss, doubling after each failed attempt up to 10 seconds, and starting again from 250 milliseconds after a connection that stayed open for 10 seconds; a connection lost sooner counts as a failed attempt, so a service that keeps dropping its stream is not reconnected to in a tight loop. A command that arrives while the service is unreachable waits for the next attempt, which it brings forward but never to less than 250 milliseconds after the previous one, and fails as unavailable if that attempt fails. Once a connection opens, the waiting commands are started in order, ahead of later ones, except one whose caller has given up, which is dropped rather than performed; further ones beyond 64 fail as unavailable at once. Commands are performed beside the event stream, snapshots, reads and one another, so that a request OpenCode is slow to answer delays neither another session's events, reads or commands, nor reconciliation, closing or shutdown. At most 16 requests are in flight at once. A session's own commands, including attaching it and removing its instruction entries, are performed one at a time in the order they arrived, so a stalled request holds up only that session's later commands; listing and creating sessions are not ordered. At most 256 commands wait to start, and further ones fail as unavailable at once. Snapshots and closing are taken as they arrive; closing a session, with or without a connection, fails at once its commands that have not started. When only the event stream drops, every session is told at once that the backend is reconnecting, and the reads in flight are abandoned, but a request in flight is not cut short: the backend reconnects once every request in flight has been answered, so a prompt OpenCode accepted is reported delivered, or after 5 seconds, when those still unanswered are abandoned and fail as unavailable, so that a request OpenCode never answers cannot keep every space from reconnecting. Meanwhile, commands that arrive wait for the next connection, as while none is open, and those not yet started wait ahead of them, even beyond the limit of 64. Closing a session never waits for a connection. Resolving the service's address and opening its event stream are each bounded to 5 seconds. When the server shuts down, it tells the backend, which at once fails every command waiting for a connection and every later one, and abandons a request in flight rather than wait for OpenCode's answer; dropping the backend ends its connection thread promptly, even while it waits to retry.

OpenCode's event stream does not replay what it missed, so after a loss the OpenCode backend reports to each attached session that it is reconnecting, a typed fact distinct from an error, so the space knows its state may be stale. Once the stream reopens, it reads again each session whose state it had read, as for a snapshot: within the snapshot's time bound and a limit on concurrent reads, and isolated from the stream and from every other session's read. Reads are isolated from commands too. The read also lists the directory's agents and the session's current agent, as at attach, since a restarted service may offer others; an agent switch observed during the read is newer and is kept. The session's events from the loss until a read succeeds are held, through failed reads and further losses, then reported after the state read again, which is reported as a resynchronization: the session's conversation, running state, modes and pending permissions and questions as the agent now records them. Its modes, including a switch or agents listed for a participant's mode change during the read, are reported only with that resynchronization, never ahead of it. No held event that carries content is dropped unless the read shows that content, because OpenCode does not keep streamed text in its records until the message ends: a listed message still being written has none of the text streamed so far. So a held text delta is dropped only when its message is listed as completed, as is that message's completion; a held message start is dropped when the message is listed, a tool call when its tool is listed, and a tool's end when the tool is listed as finished. Every other held event is delivered, so a fragment may be repeated but none is lost. Held permission and question events from before the read requested the session's messages are dropped, because the read lists the pending permissions and questions after that request, and delivering such an event afterwards could present a request already resolved. Consecutive text deltas of one message are held as one. Workers are not taken from it; the read is merged into the remembered workers instead: a listed worker is added or updated, a deletion observed during the read is not undone, a state or title set by a lifecycle event observed during the read is kept over the listing's, and a known worker the listing omits is kept, since an omission is never evidence of deletion, but is no longer reported as running unless such an event shows it running, because the evidence that it was running predates the gap. A worker deleted while the stream was down sent its deletion to no one, so each known worker the listing omits is then looked up by its identifier, at most eight at once, as part of the read, within a further bound as long as the snapshot's, during which the session's events are still held. It is removed only when OpenCode answers that it does not exist and no lifecycle event during the read showed it; a lookup that fails, finds it or does not finish in time keeps it, until the session is next read again, and none is removed once worker observation is incomplete. A read that fails is retried no sooner than the reconciliation cadence later, so a service still starting or lost again cannot use up the attempts at once. A session that has more than 512 events held, counting a run of text deltas as one, is closed with the reason rather than dropping any. A session that cannot be read in three attempts, counted across connections, including one that no longer exists, is closed with the reason, which says when the session no longer exists, without affecting other sessions. So is a session whose connection is lost five more times before it can be read, so that a service that keeps dropping its stream cannot leave a space reconnecting forever, and a session whose event channel lacks room for the state and the events held for it. Whenever the backend closes a session with a reason, the reason reaches the session even if its event channel is full, though the events queued ahead of it may then be lost. A session whose state had not been read when the connection was lost is closed: the read its space was waiting for was abandoned, and reading it later would present events from before the gap as current. What happened while the stream was down is recovered only as the agent's records show it. Text streamed during the gap itself is in no event, and in no record until its message ends, so each message the latest read listed still being written is read again, isolated and bounded like a read, when its end is reported, and the backend reports it as restored: the message as the agent recorded it, with all its text. The text may be recorded before the message is marked completed, so a recorded text is enough; a record with no text yet is read again at the reconciliation cadence, up to three times. A restore read lost with the connection is read again on the next one, and one returned while the session waits to be read again is held behind that read. A message whose end is never reported, as when the service restarted before recording it, keeps only the text its space received.

Reasoning — an agent's thinking, before its answer — is reported as a part of the message it belongs to, and never as a text delta. The speech stream reads only the text the agent said out loud; reasoning is transcript material, not speech. A backend whose stream carries a reasoning or thinking delta drops it at the wire: collecting it into the message's parts is enough, and surfacing it would speak the agent's private stream aloud, back to back with its answer.

Session identities are opaque and namespaced by backend. Clients and the wire protocol do not depend on a backend's identifier format.

A backend may name the avatar that represents its agent in a space, the default, which the space's environment may override (see `avatars.md`), with `Backend::avatar`, an identifier that clients' builds register avatars by; by default it names none, and clients show the swarm. The server sends it to clients, which show the swarm for one they lack, saying so (see `avatars.md`); it reads it each time it sends a space's state and each `Welcome`, so a change reaches clients with the next of those. Tomori's own backends name none.

Backends observe their agents through persistent connections or processes, such as an event-stream subscription or a long-lived child process, not by periodically polling for snapshots. A snapshot operation may exist for resynchronization when a participant joins.

The one exception to observation without polling is the running state of a session. A backend's event stream reports busy and idle as they happen, but the stream can drop an event; a space's queue is gated on idle, so a missed idle event would leave it stuck. A backend that loses events on its stream therefore reconciles each attached session's running state against the agent's own session record on a loose cadence, and reports busy or idle only when the record disagrees with the state it last reported. The record is authoritative; the cadence only matters once a turn has ended, so it can be loose.

Tomori never approves a tool permission automatically and never changes an agent's model or project configuration. It changes a session's mode only as described below.

A backend may support session instruction entries: named pieces of text the agent keeps with one session and gives its model alongside its own instructions, such as OpenCode's experimental session instruction entries. A backend that supports them says so in its capabilities, sets and removes an entry by key on a session it has bound, and removes entries by key from a session no space is bound to any more. Instruction entries are not agent configuration: they live in the session's own records, change no model, agent, permission or project setting, and are no settings or instructions file. Tomori never writes agent configuration, `AGENTS.md` or other instruction files, and uses instruction entries only for the layers `spaces.md` describes. The server sets its entries again whenever it binds a session and after a resynchronization, so a backend need not remember them across a reconnection. Failing to set or remove one never fails creating or binding a session; see `spaces.md`.

A backend may delete sessions. A backend that can says so in its capabilities, and deletes a session no space is bound to any more, as when an owner deletes a space with its session (see `spaces.md`), the way the agent's own interface deletes one, with its workers' sessions, stopping any turn it is running first. It refuses to delete a session it has bound again by then, which is another space's, and a session that no longer exists is not an error. The OpenCode backend stops the session's turn with its interrupt request, and then deletes it with `DELETE /api/session/{id}`, which OpenCode answers with no content and which deletes the session's child sessions too. Deleting is one of the session's own commands, performed in order after the space's handle is closed, and waits for a connection as they do. Tomori deletes a session only when an owner asks to, as `spaces.md` describes, or, for a worker, when the space's agent removes it (see `mcp.md`), and never otherwise.

A backend that reports workers and deletes sessions also deletes a worker of a session, with its own workers, when the space bound to that session removes it (see `mcp.md`). It checks the agent's own records as it does, never only what it reported: the worker must descend from the session through its chain of parents, and neither it nor any session on that chain below the session may be bound to a space; otherwise it is refused as invalid, and nothing is deleted. A worker, or one of its own workers, that the agent says is running is refused as busy, unless the removal is forced, when each is stopped first. A worker that no longer exists is not an error. Once deleted, the worker and its own workers leave the workers the session reports. The OpenCode backend reads the worker's record with `GET /api/session/{id}`, follows its `parentID` up to at most 32 sessions to the space's session, refusing one bound to another space on the way or one that no longer exists, takes whether the worker and its own workers known run from the states it observed, as it reports them, or, for a worker it never observed, from its record's busy and idle times, since a record's times outlive the process that wrote them, stops the worker, and with force each of its own workers known to run, with the interrupt request, and deletes it with `DELETE /api/session/{id}`, which deletes its child sessions too. It then stops observing the worker and its own workers known, as for a deletion it observed, and reports the workers left. A session attached is a space's own, and is refused as a worker at once.

A backend may make Tomori's own tools available to its agent: one that does says so in its capabilities, with `tools`, and registers Tomori's MCP server, a `ToolServer` naming the server, its URL and the headers its requests carry, for a directory, and removes it again. The OpenCode backend registers it in OpenCode's running set of MCP servers for the directory, through its experimental API, which is not configuration and is forgotten when OpenCode restarts, so the server registers it again whenever it binds a session there and after a resynchronization. The headers carry a credential, so a backend never prints them. See `mcp.md`.

Tomori does not hold back, reorder or rewrite what the agent's own service delivers to its session, such as OpenCode's report that a background sub-agent finished, which the service enqueues in the session's inbox and which starts a turn at once on an idle session. OpenCode's inbox delivers an item either to steer a running turn or queued behind it, and a client may cancel an item not yet delivered or switch it between those two, but no delivery holds an item, and whether an item the service enqueues starts a turn is the service's choice. Cancelling such an item and creating it again later would rewrite the agent's record of its own session, and race the service, which may deliver it first. So the server instead tells the agent which of its messages a participant's words answer when it said more while they spoke (see `interaction.md`), holds a reply that starts while a participant records for them (see `speech.md`), and tells the agent who is recording (see `mcp.md`).

Sessions run under the user's own agent configuration. Tomori does not override permission rules, so a tool the user's configuration already allows runs without a Tomori approval.

Each session has a mode, chosen from the modes the agent's own interface lets its user switch between while a session runs: for OpenCode, the primary agents its terminal cycles through with Tab, such as build and plan. A backend reports the modes it offers for a session, each with its name and a short description, and the session's current mode, and changes the mode the way the agent's interface does, through the agent itself: for OpenCode, switching the session's agent, which its later prompts go to. A backend offers only modes the agent would offer that user in its terminal. The mode is shared space state: every participant sees it, and any participant can change it from any client, including the headset, where choosing the mode's control steps to the next mode in the agent's own order, as the terminal key does. Tomori never changes a session's mode except when a participant chooses one.

OpenCode sessions start with the agent OpenCode would choose by default. Every permission request that does reach Tomori is presented to the space and resolved only by an explicit participant decision.

Tomori changes an agent's permissions only when a participant chooses a standing option, such as "don't ask again", that the agent's own interface offers for the same request. Tomori offers exactly the standing options that interface would offer, labelled with everything each grants and where it is kept, and nothing else. Choosing one has the same effect as choosing it in that interface: the same rules, directories and mode changes, written to the same destination (the session, the project's local or shared settings, or the user's settings) by the agent itself. Tomori never writes agent settings files, and never invents, widens, combines or edits a grant. An option whose grants cannot all be described in its label is not offered.

## Rationale

Tomori must support multiple agent systems without coupling the protocol, server or headset to one of them. Streaming text from the backend is required to start speech before a reply completes; see `speech.md`. Agreed in the October 2026 design discussion.

Answering the same request repeatedly from a headset is tedious, so participants may grant standing permissions, but only in the way the agent's own interface does: a user who knows what "don't ask again" means in the terminal gets the same result in Tomori, and Tomori adds no permission path of its own to review. Agreed with the user in October 2026, on the condition that it works the same way as the terminal interface.

Participants watch workers to see what the agent is doing on their behalf. In November 2026 a subagent resumed after a server restart was running but not shown, and the user asked for the server to be authoritative about running subagents, so that the state is always accurate for clients.

OpenCode's current session listing has no atomic family-wide snapshot or event watermark. Initial discovery can therefore miss a worker that moves between pages or appears and disappears while disconnected. Directly observed deletion is authoritative, but the backend must not present an omitted list entry as proof of deletion. In November 2026 the user accepted this best-effort discovery limitation; a stronger guarantee would require an upstream snapshot/replay contract or an equivalent journal.

A November 2026 review found that a space could open with a reply repeated, because events delivered while its initial snapshot was read were applied again on top of it (issue #36), and that the event stream was read into memory without a bound and decoded a read at a time (issue #43). Holding a session's events until its first state is read is the same conservative rule as after a reconnection, and a lost stream is the one recovery that never drops an event silently.

A November 2026 review found that the OpenCode backend performed every command inline on the loop that also read the event stream, so one request OpenCode was slow to answer stopped event dispatch, every other space's commands, snapshots and reconciliation (issue #35). Ordering only matters within a session, where a prompt, a decision or a mode change must reach the agent in the order the space sent them, so commands are ordered per session and otherwise run side by side, within bounds.

Once spaces survived a reconnection, a worker deleted while the stream was down would stay in its space for as long as the space lasted, since only an observed deletion removes one (issue #57). A not-found answer for that worker's own identifier is direct evidence from the agent, unlike an omission from a paginated listing, so it may remove the worker; anything less certain keeps it.

Listing children several parents at once made a wide family quick to read, but a deep one is still listed a level at a time, so a chain of workers, or a few hundred workers on a slow service, outlasted the snapshot's time bound on every retry, and its space could never open (issue #45). In November 2026 the user chose to open such a space with the workers found so far, marked incomplete as a trimmed list is, and to find the rest in the background, rather than wait longer or keep the limitation. Only the worker list is relaxed: it was already allowed to be incomplete, and is never taken as evidence of deletion. Since a walk that failed once would otherwise leave the list incomplete for as long as the space lasted, the coordinator decided that it is tried again a bounded number of times, with growing delays, so that a briefly slow service does not cost the space its departures and a failing one is not listed in a loop.

In November 2026 the OpenCode service restarted while Tomori was running. The backend's one connection closed, every space closed, and every later attempt to create a space failed until Tomori was restarted by hand. The user asked for the backend to survive a service restart or a dropped event stream, with new sessions working once OpenCode is reachable and existing spaces kept where that is sound. Reading each session again is the only conservative source for what the stream missed, since it has no replay; holding a session's events until that state is presented keeps them in order after the state they follow, as when a space opens. A space that cannot be read again closes visibly rather than presenting a state it cannot vouch for.

In November 2026, the user found that nearly every tool use in a Tomori space waited for an approval from the headset, which stopped the agent working while they were away. They asked for Claude Code sessions to start in auto mode, and for participants to switch modes from Tomori as Shift-Tab does in the terminal, generalised across backends.

In November 2026 the user decided that Tomori gives each session instructions of its own, in layers, so that the agent replies briefly and plainly and delegates non-trivial work in a spoken, shared space (issue #72). Session instruction entries carry them in the session itself, without touching the user's configuration or files, which stay off limits. OpenCode's endpoints for them are experimental, so a failure is visible but never stops a space.

In November 2026 the maintainer asked for a space's agent to remove its own finished workers through Tomori's tools rather than OpenCode's API, checked against the agent's own records, so that it can never delete a session beyond its space's family (see `mcp.md`).

In November 2026 the maintainer asked for owners to delete a space's agent session with the space, through OpenCode's own deletion, which deletes its sub-agents' sessions too, and only the session bound to that space (see `spaces.md`).

Later in November 2026 the user decided to drop the Claude Code backend: OpenCode serves Claude models too, it already restores a session's conversation and pending requests when a space is bound again after a restart, which the Claude Code backend did not, and keeping one agent integration keeps the server simpler. The backend-neutral interface stays, so that another agent can be added.

In November 2026, speaking from the headset, the maintainer found a spoken "yes" to one question delivered after a sub-agent's completion had prompted another (see `interaction.md`), and suggested not processing sub-agent completions while someone records. OpenCode's API, as of v2.2.5, lists a session's inbox (`GET /api/session/{id}/inbox`), cancels an item (`DELETE /api/session/{id}/inbox/{inboxID}`) and changes its delivery between `steer` and `queue` (`PATCH`), and a prompt or synthetic message may be admitted without starting a turn (`resume: false`), but only by whoever enqueues it, here the service itself; nothing holds an item already enqueued. A plugin could intercept the report, but plugins are agent configuration, which Tomori never writes. So the completion is left to the service, and Tomori addresses what the participant meant and heard instead.
In November 2026 a downstream project asked for its agent to be shown by a character of its own rather than the swarm; the maintainer decided that the backend names its avatar, since the avatar represents the agent the backend runs, and that clients register avatars by identifier (see `avatars.md`).

## Scope

The backend interface crate, every backend crate, and the server code that consumes them. The standing option requirement also covers the protocol and clients that present approval options and send decisions.

## Validation

- Inspect the dependency graph: the protocol, client and headset crates do not depend on any backend crate, and backends do not depend on the server.
- Inspect backend outputs: no user-facing prompt strings or answer parsing in backend crates.
- Test each backend against a recorded or simulated agent stream, including permissions, questions, workers and a turn that streams text deltas.
- Test each backend's workers against recorded streams and session records: a worker resumed after finishing is reported as running again and then finishes; attaching to a session reports the workers its records show; a worker left running by an ended agent process, and the workers running when a space's agent process exits, are not reported as running.
- Test against a simulated service that the text of a message that ended while a space's initial snapshot was read, or whose text ended before a tool, is not delivered again after it, while the text streamed for a message still being written is; that a session not yet read is not reconciled; that more held events than the limit refuse the snapshot; and that a channel without room for them refuses it and keeps them for a retry, which delivers them with the latest running state and modes.
- Test against a simulated service that a character split between two reads of the event stream arrives whole, and that an unfinished event larger than 16 MiB is treated as a lost stream, after which the session is read again.
- Test that an OpenCode worker without a start event or an active-session entry is not reported as running, that a slow or stalled active-session lookup does not delay an idle reconciliation, and that event overflow before the consumer starts refuses the initial snapshot.
- Test against a simulated service that deleting a worker refuses the space's own session, another space's session, a worker beneath another space's session, a session with no parent, one whose parent no longer exists and a chain longer than 32, deleting nothing; that a running worker, as observed or, never observed, as its record says, or one whose own worker is known to run, is refused as busy unless forced, while one observed not running is not refused for a busy record, and that forced, each is stopped before the worker is deleted; that a finished worker is stopped and deleted, and leaves the reported workers with its own; that one that no longer exists is already gone; that a record or interrupt that fails is reported, deleting nothing; and that a shut-down backend deletes nothing.
- Test that an OpenCode child deletion updates only its known parent, that completion and resumption preserve membership, that an omitted list entry does not remove a known worker, and that stale queued worker events cannot undo an installed snapshot. Test retry after a full event channel and reject malformed paginated snapshots.
- Test the OpenCode backend against a simulated service that stops and starts again on another port with another password, recorded in a changed registration file. Every open space is told it is reconnecting, a session not yet read is closed, and a space closed meanwhile closes at once; creating a session fails promptly while the service is down and succeeds once it returns, and each run of the service sees only its own credentials. After reconnecting, a permission raised during the gap is reported in the session's resynchronization, a session deleted during the gap closes with the reason, and while one session's read stalls, another session's live events are delivered and the stalled session's held events follow its resynchronization.
- Test against a simulated service that while a session's prompt stalls, another session's events, reads and commands, and creating a session, are not held up; that the stalled session's next prompt waits and follows in order; that closing it fails its waiting commands at once; that no more than 16 requests are in flight, any further command waiting; that commands beyond 256 waiting are refused; that two attachments of one session made at once bind it once; that commands arriving after the event stream is lost, while a request is in flight, wait for the next connection, while the sessions are told at once and a close is taken at once, failing that session's waiting commands; that a request still unanswered 5 seconds after the stream is lost is abandoned and the session is read again; and that closing a session while no connection is open fails its held commands at once.
- Test against a simulated service that a prompt in flight when only the event stream drops is reported delivered, and the loss noticed afterwards; that commands held while the event stream was slow to open are performed once it opens, except a create whose caller gave up; that a shutdown fails a held command at once and later requests without waiting, and abandons a request in flight within half a second; and that requests beyond the held limit are refused.
- Test that a close reason reaches its session when the event channel is full; that an agent switch, and agents listed for a mode change, during a read are reported only with the resynchronization, the switch over the read's own; that held events the read reflects are dropped while the text of a listed message still being written is delivered, both directly and against a simulated service whose listing has such a message with an empty text part, held so that events arrive before the messages are requested; that held permission and question events from before that request are dropped; that text deltas held through a retry gap are delivered and run together as one event; that more than the limit of held events closes only that session, with the reason; that closing a session during its read cancels the read and its result is ignored; that a loss keeps held events and failures; that a message the read listed still being written is restored with its recorded text once it ends, end to end against a simulated service, while a message it did not list is not read again, and that a restore returning after another loss is held until the session is read; and that five losses before a session is read close it with the reason. Test that once the registration file has been used, its absence makes resolution wait rather than fall back to the default address, and likewise for `OPENCODE_URL`.
- Test that reconnection attempts against a service that drops every connection back off (a handful in two seconds, not a tight loop), that a command fails as unavailable meanwhile, and that dropping the backend ends its thread within a second while it waits to retry. Test that the registration file is read again on each resolution and that `OPENCODE_URL` and an explicit URL take precedence over it.
- Test against a simulated service that a known worker deleted while the event stream was down, which the listing omits and OpenCode reports not found, is removed when its session is read again, while an omitted worker that still exists, or whose lookup fails or does not finish in time, is kept; and that a worker a lifecycle event during the read showed, or any worker once observation is incomplete, is not removed.
- Test against a simulated service whose child listings each take 80 milliseconds that a chain of 64 workers opens within the snapshot's bound with the workers found so far, said to be incomplete, and that every worker is then reported, oldest first, as complete. Test that while the rest are found, worker changes are reported as incomplete, and that once they are, a worker deleted meanwhile is not restored from an older page, one created meanwhile under a parent found later is added, a worker no page lists is kept, and a state observed meanwhile is kept; that a worker found in the background is reported running only when OpenCode lists it among the sessions it runs, not because its record looks busy; that a walk stops on a listing OpenCode does not answer within 5 seconds, reports the workers as incomplete, with the reason, and goes on after 5 seconds, listing that parent again, against a simulated service; that a walk whose listing failed lists it again when it goes on, and takes none of a page that fails; that, with time given rather than waited for, a failed walk goes on 5, 30 and 120 seconds after each failure and not before, keeps the lifecycle events observed meanwhile over the pages it lists later, and gives up after its last attempt, leaving the workers incomplete with the reason; that a read again, a lost connection or closing the session drops a retry, and a result of a walk stopped so is ignored, neither counted as a failure nor overwriting newer state; that a session whose record or messages are not read in time is still refused; that closing a session during a walk cancels it and its result, or that of a walk a later read replaced, is ignored; that a read again after reconnecting walks on the family it ran out of time for, both directly and against a simulated service, where a known worker the read did not reach is kept while OpenCode still has it, one deleted while the stream was down is removed, and every worker is then reported as complete; and that workers found in the background are held to the same limits as a snapshot's.
- Test that a resynchronization merges workers without removing an omitted worker or restoring one deleted during the read, stops reporting an omitted worker as running, and keeps the state and title that lifecycle events during the read set over an older listing; that more held events than the limit, or too little room in the event channel, close only that session with the reason; that a lost connection after the stream reopened discards the events held from it; and that the reason a registration ended always reaches its session.
- Test against a simulated service that fails reads that each failed read of a session is retried a reconciliation cadence later, that a session read successfully on its third attempt is resynchronized, and that one failing every attempt is closed with the reason.
- Confirm that no backend issues periodic snapshot requests while a session is attached; the only periodic check is the running-state reconciliation against the session record, and it reports nothing while the record agrees with the state last reported.
