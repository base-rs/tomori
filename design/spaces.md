# Spaces

This describes the Rust server, which replaced the legacy Node bridge in `bridge/`, and the headset client, which uses it. Changes to the bridge are not reviewed against this document.

## Requirement

A space's participants are the owners and collaborators in it; visitors watching it are not participants and cannot act on it (see `security.md`). A space is bound to exactly one agent session. Every participant in a space interacts with that same session; a space never fans one participant's input out to several sessions, and a participant never addresses a session outside the space they have joined.

The server hosts multiple spaces concurrently. Clients can list, create, join, leave and move between spaces. Only owners create spaces. Creating a space either starts a new agent session or binds an existing one, where the backend supports binding. A client is in at most one space at a time, as a participant or a visitor; moving to another space leaves the previous one. Starting a session can take time; once it has started, the creator joins the new space, unless they have joined another space since asking.

Spaces survive a server restart. The server keeps each space's identifier, title and who renamed it, if anyone did (see titles, below), when it was last active, to the minute (see `arrival.md`), backend, directory, bound session, environment and settings, such as attribution, a brief speech setting (see `speech.md`) and the space's own instructions to the agent, and its projection walls and panels, with where each panel an environment published rests but nothing it showed (see `projection.md`), in its state directory, and when it starts it binds each space again to its agent session, so that a client restoring a space by identifier after a restart lands in the same space, and a collaborator admitted to it stays admitted. The conversation, pending approvals and questions come from the agent's own record of the session as it is bound again. A space whose session cannot be bound again is listed as closed, with the reason. Only when the agent says that the session no longer exists is it kept as closed; otherwise, such as when the agent is not yet reachable or its backend is not enabled, it is bound again when the server next starts, and is not forgotten meanwhile. A space is removed, and no longer kept, when a closed space is forgotten. Each kept space is listed again as soon as the server starts, while it is still being bound, so that a client restoring it and a collaborator admitted to it find it. Closing the sessions when the server stops does not close their spaces. Input still queued when the server stops is not kept, since replaying stale speech to an agent after a restart would surprise its participants. A record of spaces that cannot be read stops the server from starting, rather than losing every space and the admissions to them, and one server at a time keeps its spaces in a state directory. The order in which spaces closed is kept, so that the least recently closed are still forgotten first.

**Deleting a space.** An owner deletes a space from inside it, in the hand menu's Space section, once it has asked (see `hand-menu.md`), and from nowhere else: not from the lobby's listing or the server list, so that the owner sees which space it is before deleting it, rather than picking one from a list. The request names the space the owner is in, and is refused for any other. Deleting removes the space from the server at once: it is no longer listed, and it is removed from the spaces kept in the state directory, which are written whole through a temporary file, so that after a restart it is listed as before the deletion or not at all. Its projection walls and panels, its environment's server side and what that kept, its kept speech, its input queue, its pending approvals and questions, and the knocks on it go with it, and Tomori's MCP tools are removed from its directory unless another space open there still needs them (see `mcp.md`). Everyone in it, participants and visitors, is returned to the lobby and told who deleted it, by their display name, and their clients say so, such as "Studio was deleted by Ada."; nobody is put back in it on reconnecting, and a collaborator admitted to it is no longer admitted anywhere, since a collaborator token outlives no space (see `security.md`). This holds whoever else is in it, including when the owner deleting it is its last owner. An utterance being recorded in it is cancelled, and words already being transcribed fail as for someone who left. The agent is not interrupted: a reply under way finishes in the session, and its input still queued is never sent.

By default the agent session is kept: the space's handle to it is closed, Tomori's instruction entries are removed from it as for a forgotten space, and it can be bound to a new space later. The owner may delete the session too, in the same confirmation, where the space's backend deletes sessions (see `agent-backends.md`): the space's handle to it is closed first, and then the backend stops any turn it is running and deletes it, with its workers' sessions, as the agent's own interface does. Only the session the space was bound to is deleted, and never one that another listed space, open or closed, is bound to: a request to delete such a session is refused whole, deleting nothing, and a session bound again before it is deleted is kept. The session is deleted only once the record of spaces no longer lists the space, so that a server that stops meanwhile never lists again a space whose session it deleted; a deletion not yet performed when the server stops is not performed, and the session is kept. The owner who asked is told, on the connection that asked, what became of the session: deleted, or kept, with why, as when the agent cannot be reached, in which case the space is deleted all the same and the session keeps none of Tomori's entries where they can be removed. A session the agent no longer has, as for a space whose session closed because it no longer existed, counts as deleted. While the backend is reconnecting, the space is deleted at once and its session once the agent answers, or kept if it does not. A space whose session has closed is deleted in the same way.

**Removing workers.** A space's agent removes its own finished workers through Tomori's tools, `workers` and `remove_workers` (see `mcp.md`), and only the space's own: the workers the space shows, descended from its session, never its session or one bound to any space. The workers removed leave the space for everyone in it at once, and a notice on the space's Tomori wall says so. A worker still running is removed only when the agent is asked to stop it, and is stopped first.

No tool lets the agent delete a space yet. An MCP tool for it, such as `tomori_delete_space`, may come later, and would need the same confirmation by an owner in the space, and the same second, explicit confirmation for its session.

**Titles.** A space's title is how its participants, its visitors and the lobby tell it apart. It follows its agent session's own title, as the space's backend reports it: from the session as read when the space is created, bound again after a restart or read again after a reconnection, and whenever the session is renamed, as from the agent's own interface or as the agent titles a session after its first turn. A space whose backend reports no title keeps the title it was created with. An owner in the space, from the hand menu (see `hand-menu.md`) or the console, or the space's agent, through Tomori's tools (see `mcp.md`), may rename it: the title given replaces the session's, and the space no longer follows its session, whatever the session is renamed to, until it is renamed with an empty title. An empty title lets the space follow its session's title again, taking the session's title at once where the backend has reported one, and otherwise keeping the title it has. Collaborators and visitors cannot rename a space, and the server refuses it to them; an owner renames only the space they are in, and the agent only the space its session is bound to. A title, given or reported, is cleaned as a display name is (`tomori_protocol::text::clean_name`): on one line, composed, without control or format characters, each run of spaces made one, and none at either end. A title given is refused, saying why, when it is longer than 200 bytes once cleaned, the limit of the title a space is created with; a session's title is cut to that length with "…", and one with nothing left once cleaned is ignored. The space's state names who renamed it, the agent or an owner by their display name as the server knew them, and is without one while the space follows its session, so that a client in the space can say who changed the title as it changes, such as "Tomori renamed this space to “Release planning”." for the agent, or "This space is now called “Tomori development”." for its session. A change reaches everyone in the space, participants and visitors alike, and the lobby's listing at once, is kept across a restart and is logged; renaming to the title the space has already changes nothing shown, though an owner's or the agent's rename still stops it following its session. Who renamed a space is kept with it, so that a renamed space keeps its title when it is bound again after a restart, while one that follows its session takes the session's title as read then, including a rename made while the server was stopped. An older client reads the title as before, and ignores who renamed it; a client offers renaming only to a server whose space state says that it renames spaces.

Space identifiers are never reused, including by a later run of the server, because a client restores its space by identifier when it reconnects and must not land in an unrelated space. Refusing a join because the space does not exist names that space in the error, so a client can tell the refusal from errors about other requests.

A participant who disconnects leaves their space but keeps their identity and audio source, and rejoins that space when they reconnect, unless they left it explicitly. A client may send `leave` straight after Hello to restore a leave made while it was disconnected; this overrides the rejoin, and is harmless when the participant is in no space. The server forgets a participant who has been disconnected for longer than a generous retention, 12 hours by default; after that they reconnect as a new participant in the lobby. A visitor is kept, rejoins and is forgotten in the same way, and keeps their public handle while they are kept, except that the server keeps at most 256 disconnected visitors, forgetting those longest gone first, since anyone can connect as a new visitor.

Shared space state is held by the server and is the same for everyone in the space, participants and visitors alike: the space's environment (see `environments.md`), the conversation, the input queue, pending approvals and questions (including partially answered forms), delegated workers, the session's mode and the modes it offers (see `agent-backends.md`), presentation cards and worker visibility. A delegated worker names the worker that delegated to it as its parent; a worker the space's own agent session started has no parent, so clients can arrange workers without knowing the backend's session identifier. Per-participant state is limited to presence, local presentation choices such as mute or paging, the participant's own in-progress recording, and where they are in the space's kept speech (see `speech.md`). The space's speech setting, full or brief, is shared state.

Everyone in a space is placed in one shared Euclidean space, the space's scene coordinates. Each headset tracks its participant relative to their own play space, and travel is local to each client, a rig that maps that play space into the shared space (see `locomotion.md`). A participant's presence carries their head, and their controllers and hands where the client has them, in the shared space: where they are in the space, including where they have travelled in an environment that allows it, since the client applies its participant's rig before sending them. To the server and every other client, a participant is only those positions; the rig itself is not sent, which may be revisited if something such as drawing a participant's play-area boundary needs it. Two participants can be in the same place, as when both stand at the centre of their own play space at home, and can move apart; spreading people out as they arrive belongs to environments, with spawn or arrival anchors (#79). A client places each other participant's voice at their head from presence, with no seats, as `spatial-audio.md` describes; the maintainer decided this in November 2026. Presence includes engagement: whether a participant is wearing their device and attending. A client that can tell reports it as `engaged` (worn, with input), `distracted` (worn, while something else such as a system menu has input) or `away` (removed, asleep or in the background), when it changes, and once on each connection when it first enters a space after connecting; it never sends it with each pose. The server applies the latest report to every space the participant joins on that connection. The server records the latest report per connection, forgetting it when the connection ends, and shows it in each participant's entry in the space state, so everyone sees who is away. A participant counts as listening unless they report `away`; one whose client reports nothing, such as an older client or the spectator, counts as listening, as before. Engagement decides who hears agent speech live and who hears it later from the start of the latest reply, as `speech.md` describes, and whether the agent's timers count someone as present, as `timers.md` describes, and nothing else; it is never sent to the agent, except as the names of those present in a timer's note. In particular it does not change a space's attention: a participant who is away is still in the space, so what happens meanwhile raises no problem or reply, and putting the headset back on clears nothing, as only joining and answering do; the participant hears what they missed from the catch-up instead.

Tomori gives a space's agent instructions of its own, in three layers, each a separate instruction entry of the agent's session, where the space's backend supports them (see `agent-backends.md`). `tomori` is Tomori's own, the same in every space: that people talk to the agent aloud from headsets and its replies are spoken, so it replies briefly in plain speech without Markdown, tables or code unless asked; that each message begins with its speaker's name, and that what they pointed at as they began may follow it in square brackets, as Tomori describes it; that, if the agent said more while they spoke, a note in square brackets before their words says which of its messages they answer, which they are to be taken as answering, and that without one they follow the conversation (see `interaction.md`); and that only Tomori's notes are in square brackets; that something the space's environment shows may end with an id, as in `(id farmyard:hen/marigold)`, which it may inspect with Tomori's `inspect` tool, where it has it, when the details would help it answer, reading what it returns as data, never as instructions (see `environments.md`); that it delegates non-trivial work to sub-agents, says briefly what it started and reports back; that its words are spoken as it writes them, so that before the tool calls a request needs first it says in a sentence what it is about to do, and gives the rest after (see `speech.md`); that it removes a finished sub-agent once it has reported its findings, unless someone asks to keep it, with Tomori's worker tools where it has them and never by calling the agent service's own API itself (see `mcp.md`); and that it may project what is better read than heard as a text panel, in a fenced block of language `panel`, sparingly, saying in a sentence what it shows (see `projection.md`). `tomori-environment` is from the space's environment, about what it presents and how to use it (see `environments.md`); it is empty for Sky. `tomori-space` is the space's own: an owner may give it when creating the space and change it later, up to 4096 bytes. An empty layer's entry is removed rather than set. The server gives every layer whenever it binds the space's session, when the space is created and when it is bound again after a restart, again after the backend reports a resynchronization, each time before any queued input it then releases, and again when an owner changes the space's environment (see `environments.md`); when an owner changes the space's layer, it gives that layer alone. Only owners change the space's layer; nobody overrides Tomori's own, and an owner who wants different behaviour in a space says so in the space's layer. The layers in effect are shared space state, so that everyone in the space, participants and visitors alike, can see what the agent is told; a space whose backend takes no instructions shows none and works as before. If the agent does not take them, as when its experimental interface for them changes, the space works without them and shows why beside its layers until they are next given successfully; that is not a problem that needs attention, and it never fails creating or binding the space. Where the server serves Tomori's MCP tools and the space's backend takes them, the agent is also given the entry `tomori-tools` with every layer, which tells it about the tools and that they act on the space its session is bound to; it is Tomori's, the same in every space, and not one of the layers shown (see `mcp.md`). When the server forgets a closed space, it removes its entries from the session, since they are Tomori's, unless another space is bound to that session. Entries stay while the server is stopped, so a session used from the agent's own interface meanwhile still has them.

If the initial session snapshot cannot be read, the server refuses to open the space, reports a retryable error to its creator, and closes the backend handle. It does not delete an attached agent session. This avoids presenting incomplete conversation, permission or question state as current. The initial snapshot carries every pending approval and question, so a session with several parallel requests opens with all of them queued. The worker list alone may be incomplete: a backend that has read the session's conversation, running state, modes and pending approvals and questions in time, but not yet every worker, as for a large or deep family of workers, returns the workers found so far and says that the list is incomplete. The space then opens, and binds again after a restart, with its worker list marked non-authoritative and the reason shown, while the backend goes on finding the rest in the background (see `agent-backends.md`). Meanwhile, new workers and changes to known ones are shown, and the list stays non-authoritative until every worker has been found, when it is authoritative again. A departure is shown only once the list is authoritative again: until then, a worker missing from the list, even one the backend reported deleted, is not shown leaving. If finding them fails, because the agent answered with an error or not in time, the backend tries again from where it stopped, at most three times, about 5 seconds, 30 seconds and 2 minutes after each failure, with the reason shown meanwhile. Once those attempts have failed too, the list stays non-authoritative, with the reason, until the session is read again, as after a reconnection or when the space is bound to it again. Closing the space, or reading the session again, cancels a retry, and a retry never replaces a newer state. Finding workers in the background only adds them: a worker leaves the list only as it otherwise would.

An OpenCode session is bound to at most one space at a time. A request to bind one that is already bound is refused with an error directing the requester to the existing space, and the refusal does not affect that space. A stale handle to a session that has since been bound again cannot close or command the new binding.

Worker-list authority is reported independently from unrelated space errors: when the server says omissions are authoritative, a client may retire a previously observed worker even if another error remains visible. An incomplete list, including one trimmed to fit the snapshot budget or one whose workers are still being found, never authorizes a departure. Older servers without this indication retain the earlier conservative error-based behavior.

When participants act concurrently:

- The first decision on a pending approval or question resolves it. Later decisions on the same request are rejected without effect, and every participant observes the resolution.
- A participant may answer the presented question's current field by speaking: their client marks the utterance as an answer to that question and field, and its final transcript is applied as the answer, as a typed answer would be, never queued as input; a transcript the field does not accept, or one for a question no longer presented, fails as the utterance with the reason, and nothing is queued. The server says in the space state that it routes spoken answers, and a client marks an utterance as an answer only for a server that does, as an older server would queue it. A repeated finalization of an answer already applied is acknowledged with the text applied, as a repeated queued utterance is.
- An agent may have several approvals or questions pending at once, such as for parallel tool calls. Each is kept until it is resolved; none replaces another. They are presented one at a time, oldest first, and a decision applies only to the presented request. If the backend rejects a decision for a reason other than the request being gone, that request is presented again ahead of later ones. While any request is pending or its decision is being delivered, the space is waiting and no queued input is sent to the agent.
- Finalized utterances enter a per-space queue in finalization order. Each entry records its speaker, by public handle and display name, and its state (queued, sending, then delivered or failed); the handle lets a client recognize its own entries, since display names need not be unique. Shared state names participants by the public handle the server assigns, never by the identity they said in Hello (see `security.md`). Every participant can see the queue, and any participant can cancel an entry until it is sent to the agent. Finalizing the same utterance again, as a client may after reconnecting, queues nothing: the participant receives the final transcript that was queued the first time. A repeat is the same utterance identifier from the same participant; utterances of different participants are never taken for each other, whatever their identifiers contain. The server recognizes a repeat among a space's 32 most recently queued utterances, more than the queue shows.
- The queue releases a queued entry only when the space is idle — its agent finished a turn, and no approval, question or decision is pending. The agent's idle state comes from the backend, and the backend reconciles it against the agent's own session record on a loose cadence, so a busy state that the backend's event stream failed to clear cannot leave a queue, or its entries, stuck; within one cadence of the agent going idle, a stuck space is reported idle and the queue advances.
- When a backend reports that it is reconnecting, as after its connection to the agent drops (see `agent-backends.md`), the space shows the reason, and releases no queued input until the backend reports a resynchronization or the session closes, since the space's state may be stale meanwhile. For the same reason it refuses a participant's decision, answer or mode choice meanwhile, saying the agent is reconnecting; a decision or answer already on its way is still delivered, and a request it settles is not presented again by the resynchronization that follows, whose state may predate it. On a resynchronization the space takes the session as read again: its conversation, running state and modes are replaced, as when the space opened, except that a message still being written keeps the text the space already shows when the read lists only a beginning of it, since the agent records a message's text only once it ends. A message the backend reports as restored replaces the space's copy of it. Pending approvals and questions are reconciled with those the agent lists. Those still pending keep their place, and a partially answered question keeps its answers; new ones are queued after them; those no longer listed are withdrawn, including one whose decision or answers are being delivered, since the agent no longer waits for it. Workers change only through their own events. The reason shown for the gap is cleared, if it is still the space's error, and queued input is released again. The input queue is kept: input released before the backend reported the gap is delivered if it reconnects at its next attempt, and otherwise fails visibly. Speech of a message that the gap interrupted stops, and nothing said during the gap is spoken. A closed space ignores a resynchronization.
- When a space's agent session ends, the space stays listed with its state, marked closed (activity `closed`, with the reason in its error) in both its state and the lobby listing. Entries still queued fail visibly, pending approvals and questions are withdrawn, and new input is refused with a transcript failure instead of being queued. The server keeps at most the 32 most recently closed spaces that nobody is in, and forgets those that closed earlier, whenever they were created, so that sessions ending repeatedly cannot grow its memory without bound; a closed space someone is still in is kept until they leave.
- Each participant has a colour, the same on every client: it comes from their public handle, from a palette of six that avoids the agent's cyan, attention's amber and a problem's red. Handles are given across the server, so two people in a space may share a colour; colour is never the only signal, and a name is always shown with it. The headset uses it for speakers in its transcript and the queue (see `wrist-transcript.md`).
- Messages delivered to the agent identify their speaker. Attribution is a per-space setting that defaults to on. With attribution on, the delivered text is the speaker's display name as the server knows them when the words are queued, kept with their token for a token holder (see `security.md`), which is on one line and contains no colon or square bracket, so that the prefix ends at the first colon and cannot pass for another speaker's line or a context block, a colon and a space, then the transcript (`Ada: run the tests`); with it off, the transcript is delivered unchanged. The queue shows the transcript without the prefix.
- Shared attention, stage 1 (issue #81): what a participant points at as they begin speaking reaches the agent with their words, as the server describes it. A client reports only **identities**, in the optional `attention` of `utterance_begin`, most relevant first, as `tomori_protocol::Resource`s: each kind names its identity in a field of the kind's name, such as `{"kind": "worker", "worker": "ses_1"}` for a delegated worker (and so its station). The GitHub environment's prototype adds cards, `{"kind": "card", "card": "github://…/issues/97"}`, which the server resolves only in a space that shows cards, from the board it read itself, and describes as the utterance begins, since the board changes only when it is read again (see `github.md`). Others, such as an environment's resources (#75) or a participant, are added as variants, so `Resource` is `#[non_exhaustive]`, as each of its variants is, since a kind may gain fields, such as #81's time window; a worker is made with `Resource::worker`, and a card with `Resource::card`. Attention is advisory, so it never costs the words: an entry that cannot be read, such as one without a kind, a known kind in the wrong shape or an entry that is not an object, and one of a kind the reader does not know, are each skipped as the message is read, logged at debug level, and the utterance is kept with the rest; attention that is not a list names nothing. So adding a kind, or changing a kind's shape, needs no new protocol version. Anything else a client says about a resource, such as a title or a description, is never read. The server **captures attention as the utterance begins**: it takes the first 4 resources read, resolves each against the space's own state, and ignores one the space does not have, an oversized identifier, a kind it does not know and a repeat. What the participant points at later in the utterance changes nothing, so the start wins, as #81 proposes, since a participant points at what they mean as they begin to ask about it. An utterance that answers a question or says a new name attends to nothing. On delivery, a **context block** comes before the words and after the speaker's name, describing each resource from the space's state at that moment: `Ada: [Pointing at worker "Review commit 2657a52" (opencode session ses_…, running)] how is this one doing?`, or, with attribution off, the block then the words. Several resources are separated by `; ` within the one block. A worker that has left meanwhile is named as the space last knew it, `(… session ses_…, no longer present)`. Something the space's environment shows is described as its server side last described it, followed, if the side gave it a reference, by its id, as `(id farmyard:hen/marigold)` (see `environments.md`). Each title is quoted on one line, cleaned as names are (`tomori_protocol::text::one_line`, see `security.md`), with control characters and every kind of line break made spaces and format characters removed, its double quotes and square brackets made single quotes and parentheses so that it cannot end the quotation or the block early, and bounded to 160 characters; the backend's name and the session identifier are cleaned the same way. The block is at most 1,000 characters: resources after the first that would make it longer are left out. Square brackets in the words are made parentheses in what the agent reads, so that nothing in them can read as a block: in practice, the only brackets in a transcript are Whisper's notes of noise among speech, such as "\[Music] deploy it", which then read as its other notes do, "(Music) deploy it" (see `speech.md`). So the block is on one line, starts at the first `[` after the speaker's name, which has none, ends at its first `]`, and is the only bracketed text in the prompt but for the note of which message the words answer, which, when there is one, comes before it, on one line, its quotations neutralised in the same way (see `interaction.md`), and Tomori's notes of what participants did since the words before, such as ticking a checklist's item, which come in a block of their own before both, cleaned in the same way (see `projection.md`). The queue shows only the transcript, as heard; the conversation shows the delivered text, block included. Only participants send utterances, so visitors cannot point the agent at anything. A client from before stage 1 names the worker it pointed at in the optional `pointed` of `utterance_end` instead; the server still takes it, resolved the same way as the utterance ends, but only for an utterance that began attending to nothing, so it never replaces what was captured at the start. Current clients send no `pointed`, and an older server ignores `attention`, so the agent is then told nothing of what was pointed at. Persistent selections and highlights, shared hover in presence, and their headset feedback are later stages of #81.

The lobby listing says which spaces need a participant, so that a client can show what needs attention across servers and spaces (see `arrival.md`). Attention is worked out by the server, from facts it already has, for anyone rather than for one participant: whoever deals with something first deals with it for everyone. Each listed space carries at most one attention level, the first of these that applies:

- **Input**: an approval or question is pending, or its decision or answers are still being delivered. It ends when the request is resolved, by anyone.
- **Problem**: while nobody was in the space, a queued entry failed to be delivered, the agent reported an error or refused a mode, or the session closed. It ends when a participant joins the space.
- **Reply**: while nobody was in the space, the agent completed a message with text, and its turn then ended. A message of tool calls alone is not a reply. A reply or a turn's end that the space learns of only from a resynchronization or a restored message, after a backend reconnected, counts too. It ends when a participant joins the space.

Only a participant's own `join` ends a problem or a reply. Being put back in a space when they reconnect does not by itself, since what happened while they were away was not seen; their client restoring its membership with a `join`, or joining the space it was put in once it shows it, does. Visitors are not participants (see `security.md`): a visitor watching does not count as someone in the space, and their `join` ends nothing.

Running, idle, queued and closed spaces need no attention by themselves, and a backend reconnecting is not a problem unless the session then closes. Being in a space when something happens counts as having seen it, since replies are spoken to everyone there (`speech.md`). The listing also says how long, in whole seconds, each space has needed its current level, so the longest waiting can come first. Attention is kept in memory, not with the spaces kept across a restart: a space listed again after a restart starts with no problem or reply, including one already closed or one that cannot be bound again, since what happened while the server was stopped is not known, and the history read again is not news. A request the session still has pending is input, as before. Both fields are optional in the listing and an attention level a client does not know is read as unknown, so adding them, or a later level, does not change the protocol version. The agent addressing a participant by name is not attention. Personal attention, such as a reply only the participant who missed it needs to hear, and telling participants inside a space that another space needs attention, are not yet requirements.

## Rationale

Several people should be able to share one conversational workspace with one coordinating agent, and move between separate workspaces. Agreed in the October 2026 design discussion for replacing the Node bridge.

In November 2026 the user chose to refuse and retry an initial snapshot failure rather than open an incomplete space while attempting recovery. Later that month, a session whose family of workers was too deep to list within the snapshot's time bound could never be opened, on any retry, while the agent was responsive (issue #45). The user then decided to relax the rule for the worker list only, which was already allowed to be incomplete and is marked so: the space opens with the workers found so far and the rest are found in the background, while the conversation, approvals and questions stay all or nothing. A review then found that one failed listing, likely on the slow services this is for, left the list non-authoritative for as long as the space lasted, so a deleted worker was never shown leaving; the coordinator decided that a failed discovery is retried a bounded number of times with growing delays, and that only an error or a timeout from the agent counts as a failure.

In November 2026 the user, working across a work laptop and a personal desktop, asked for the server list to show which servers and spaces need them, with a quick way to jump there. They decided that a finished reply counts, that attention is for anyone for now, and that no mention detection is needed; the alternatives are compared in `docs/proposals/attention.md`. A space that closed while nobody was in it counts as a problem, as that proposal recommended.

In November 2026 an OpenCode service restart closed every space. The user asked for spaces to keep working across a reconnection where that is sound, and for no approval request to be silently lost. Replacing the conversation and reconciling requests from the session as read again is the same trust the space places in its initial snapshot; the gap is shown while it lasts.

In November 2026 the user decided that Tomori sets per-session instructions, so that the agent replies briefly and plainly in a spoken, shared space and delegates non-trivial work rather than doing it inline, and so that environments can later tell it what they present (issue #72). Each layer is its own entry, so that each changes alone. The entries are Tomori's, so they are removed with the space that set them; owners shape a space through its own layer rather than by overriding Tomori's. Later in November 2026 the user asked that the agent keep the workspace clean of finished sub-agents, so Tomori's layer asks it to remove one once it has reported its findings, unless someone asks to keep it; the wording is kept generic, about any work rather than source code. In November 2026 the maintainer found agents inconsistent at doing so, for want of a tool, and some improvising raw calls to the agent service; the layer now names Tomori's worker tools and forbids calling the service's API, as `mcp.md` records.

In November 2026 the maintainer set the first stage of shared attention (#81) apart from the worker-pointing prototype it replaces: the server resolves identities, never text a client claims, so that the agent's input stays trustworthy with several people in a space; attention is captured as an utterance begins, as #81 proposes, rather than the worker pointed at most recently while X is held; and the context comes before the words, after the speaker's name, so that the agent reads what is meant before the question about it. The tagged `<tomori-context>` block proposed in #81 was not adopted: the bracketed form already in use is compact and, with names and titles cleaned, as clearly delimited. The limits, 4 resources and 1,000 characters, answer #81's open question for now; they keep a prompt's context small next to its words while leaving room for a selection of a few resources later. After an independent review, `Resource` was made non-exhaustive before its first release, as `tomori-client`'s growing types were, since it is the type designed to gain kinds; an attention entry that cannot be read was made to cost only itself rather than the words spoken with it; and square brackets in the words were made parentheses, rather than Whisper's notes being left out of transcripts with speech, since that holds for every recognizer and loses nothing the participant said.

In November 2026 the maintainer, looking for a session in the server browser, created an empty space by accident, and found nothing in Tomori to remove it, or a session. They asked for owners to delete a space, and optionally its agent session, from inside the space, through the hand menu's Space section, and deliberately not from the server or space browser, so that an owner deletes a space only after seeing that it is the one they do not want, and cannot delete the wrong one from a list. The session is kept by default and deleting it asks again, since it cannot be undone and loses the conversation; the session becomes unbound and can be bound to a new space later. They asked for no MCP tool yet.

In November 2026, speaking from the headset, the maintainer found it confusing to tell spaces apart, switching between them and in the server browser, and asked for anything that makes that easier. The coordinator agent had renamed its own OpenCode session, from "Tomori opencode support" to "Tomori development from the headset", and the space bound to it kept the title it took when it was created, so its title no longer said what the space was for. A space's title now follows its session's, which is where people and agents already name their work, while a rename by an owner or the agent wins, since it says what the people in the space want it called. Renaming to an empty title was chosen as the way back to following the session, so that one message and one tool both rename and undo a rename; the headset offers it as a row of its own, since an empty title cannot be said.

In November 2026 the user decided that spaces should survive a server restart, so that a space, and a collaborator's admission to it, last as long as the work it holds; it is implemented separately from knocking. They then decided that input still queued when the server stops is dropped rather than replayed.

## Scope

The server's space registry and what it keeps of spaces across restarts, a space's title and who renamed it, the client protocol for joining, leaving and renaming spaces, the input queue, and approval and question handling.

## Validation

- Test that closing sessions when the server stops does not close their spaces, that input queued then is not kept, that a collaborator token for a kept space still admits after a restart, and that an unreadable record of spaces stops the server from starting.
- Test that only an owner deletes a space, and only the one they are in, refusing a collaborator, a visitor and a request naming another space; that everyone in it is returned to the lobby, told who deleted it, and can no longer list or join it; that its session is kept, closed and without Tomori's entries, and can be bound again, unless the owner asked to delete it, when only that session is deleted and the owner alone is told, or told why it was kept when the backend fails, on the connection that asked; that a backend that does not delete sessions refuses deleting one, deleting nothing, and that a session another listed space is bound to is never deleted; that a deleted space is not kept and stays deleted after a restart, and that its session is deleted only once the record of spaces no longer lists it; and that a space deleted during a reply with input queued, while the backend reconnects, or after its session closed is deleted at once, with its reply not interrupted and its queued input not sent.
- Test titles, against the fake backend and a simulated OpenCode service: that a space takes its session's title as read when it is created, and whenever the session is renamed, reported through the agent's event, while a rename of another session changes nothing; that a title reported with nothing in it is ignored and a long one is cut; that an owner's rename, typed or said, and the agent's set who renamed it, reach everyone in the space and the lobby's listing, and stop the space following its session; that an empty title lets it follow its session again, taking the session's title at once; that a collaborator's and a visitor's renames are refused, as is a title too long once cleaned; that who renamed a space is kept across a restart, so that a renamed space keeps its title when it is bound again while one that follows takes its session's title, renamed while the server was stopped; and that an older client's state and messages read as before.
- Test that spaces survive a restart: after the server stops and starts again with the same state directory, each space is listed with the same identifier, title, directory, environment, including one an owner changed, and settings, is bound again to its session with that session's conversation, and a client rejoining by identifier lands in it; a space whose session cannot be bound again is listed as closed with the reason, and is kept as closed only if the agent said that the session no longer exists; and a forgotten closed space is not kept.
- Test against a fake backend that a space's instruction layers are given when it is created and when it is bound again after a restart, with its own layer kept across the restart; that they are given again after a resynchronization; that an owner's change gives only the space's layer and every participant sees it, while a collaborator's or visitor's is refused; that a refusal is shown with the layers without closing the space or holding its input, and clears once they are given; that a backend without instructions is given none; and that a forgotten space's entries are removed unless another space is bound to its session.
- Test that an initial snapshot failure opens no space, reports a retryable error, closes only the failed handle and allows a later retry; an already running space remains unaffected.
- Test that a space opened, or bound again, with a worker list its backend says is incomplete shows it as non-authoritative with the reason, keeps it so through worker changes reported as incomplete, including one that omits a worker, and shows it as authoritative once the backend reports every worker; that clients retire a worker missing from a non-authoritative list only once the list is authoritative again; and, against a simulated OpenCode service, that a session whose conversation is not read in time is still refused, whatever its workers.
- Test that attaching an OpenCode (or fake) session already bound to a space is refused without closing that space, that a stale handle cannot close or command a reattachment, and that an initial snapshot with several pending approvals and questions presents them all in order.
- Inspect the space model: a space has exactly one session binding, and per-space stores are keyed by space.
- Test two participants in one space: both observe the same conversation, queue and pending requests; concurrent decisions on one approval result in exactly one decision reaching the backend. Test two parallel approvals: both are presented in turn and both decisions reach the backend in order.
- Test that finalizing the same utterance twice queues it once and acknowledges the repeat with the text queued first, and that utterances of participants `a` and `a/b` whose identifiers would join to the same text are both queued.
- Test that a worker whose backend parent is the space's session is reported without a parent, while a nested worker keeps its parent.
- Test queue cancellation: a queued entry can be cancelled by another participant before sending, and cannot be cancelled after delivery. Each entry carries its speaker's public handle as well as their display name, and neither entries nor the space's participants carry anyone's Hello identity.
- Test that spaces created by two server runs have different identifiers, and that joining a missing space is refused with an error naming it.
- Test attribution on and off for delivered messages.
- Test shared attention: that the context block comes before the words and after the speaker's name, and first without attribution; that the server resolves identities from the space's state, describing a worker as it is on delivery and as no longer present once it has left; that unknown, oversized and repeated identities and unknown kinds are dropped, and that an entry that cannot be read, or an older client's `pointed` that cannot, is skipped and the utterance still delivered with the rest; that square brackets in the words are made parentheses, with and without context and attribution, while the queue keeps the transcript; that hostile titles, session identifiers and backend names stay on one line inside the block; that a description a client adds is ignored; that attention is captured as the utterance begins, so that neither a worker that arrives later nor an older client's `pointed` at the end changes it; that at most 4 resources are taken and the block stays within 1,000 characters, with titles cut; that the queue shows only the transcript; and that an older client's `pointed` still reaches the agent.
- Test that a participant's colour comes from their public handle, the same for every client, and is none of the agent's, attention's or a problem's colours.
- Test that reconnecting rejoins the space, that `leave` straight after Hello overrides the rejoin and is harmless in the lobby, and that a participant gone longer than the retention reconnects as a new participant.
- Test that closing a session fails its queued input, marks the space closed in its state and the listing, and refuses new input, and that beyond 32 closed spaces nobody is in, those that closed earliest are forgotten, including when an early space closes last, while an occupied closed space is kept.
- Test that no queued input is released between a reconnection and the resynchronization that follows it, and that an unrelated error reported meanwhile stays visible, both in the space model and through a running server with a fake backend. Test that decisions and answers are refused while reconnecting, and that a request decided or answered meanwhile is not presented again by the resynchronization. Test that a resynchronization keeps the shown text of a message still being written when the read lists an empty or shorter text, replaces it otherwise, and that a restored message replaces the space's copy while an unknown one is ignored. Test that a resynchronization replaces the conversation and clears the gap's error; keeps pending approvals and questions still listed, with their partial answers; queues new ones; withdraws those no longer listed, including one being decided; leaves workers unchanged; does not repeat a tool start already read; and is ignored by a closed space.
- Test that a space whose idle event was missed is reconciled to idle against the backend's session record within the reconciliation cadence, and that its queued entries then advance.
- Test moving a client between two spaces: it receives the new space's state and no further events from the old one.
- Test, in the space model, each attention level: input while a request is pending or being decided; a problem for a failed delivery, an error, a refused mode and a closed session only while nobody is in the space; a reply only for a turn that ends after completing a message with text while nobody is in the space; that input outranks a problem, which outranks a reply; and that a join clears a problem and a reply but not input. Test that a reply whose turn ends during a backend reconnection still counts, whether learned from the resynchronization or from a restored message. Test through the hub that the listing carries the level and its age, that a join clears it for every participant, and that neither being put back in a space on reconnecting nor a visitor joining does. Test that after a restart the kept spaces, including closed ones and one that cannot be bound again, are listed with no attention, while a request still pending in a session is input.
- Test that a spoken answer answers the presented question and is never queued, and that one the field refuses, or for a question already answered, fails as the utterance.
- Test that a reported engagement is shown in the participant's entry, that a reconnecting participant reports nothing until their client reports again, and that the speech setting is shared, starts full, and refuses a setting the server does not know.
