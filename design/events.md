# Space Events

This describes how a space's agent is told, without asking, that something it depends on has changed: that one of its workers has failed, has left a message unanswered, or has stopped making progress. Its first increment, for OpenCode's workers, is a requirement; what follows **Proposed** below is not, until the maintainer accepts it. Events share one per-space event queue with the agent's timers (`timers.md`), which owns the queue's mechanics; this document owns the events that feed it.

## Requirement

**What a backend reports.** A backend that reports workers reports, besides each worker's state, what it was last seen doing, as `tomori_backend::Event::WorkerActivity` with a `WorkerActivity`: when it last made progress, never zero, the message it has longest left unanswered, when that was sent and since when it has been the worker's to answer, the tool it is running and since when, how its last step ended, why it failed, and whether it is waiting for a permission or a question. Times are in milliseconds since the Unix epoch, by the backend's clock as it observed each event. It reports activity as it changes, and at least as often as progress moves on by 30 seconds while the worker is busy, but not with every streamed word, and without allocating for each streamed word. A backend reports facts, never conditions: the server alone judges them, so that the policy is the same for every backend.

**What the OpenCode backend observes.** It keeps using the one global event stream it reads (`GET /api/event`), and keeps, for each worker it knows, only those facts, never the events. Progress is a step beginning, streaming or ending, text, reasoning, a tool's input, a tool being called, progressing or ending, compaction, a shell command, or a retry being scheduled; a worker first seen, by any event, or beginning to run, has made progress no earlier than then, so that no worker is judged from nothing. A tool is running from `session.tool.called` until its `success` or `failed`, by the name `session.tool.input.started` gave it, and a call whose input is still being written is not running. How its last step ended is `session.step.ended`'s `finish`, such as `tool-calls`. Why it failed is the type and message of the error of `session.execution.failed`, or else of the last `session.step.failed`, kept until it runs again. It waits while any permission or form for it is pending, each kept by its id until replied to or cancelled, or until its run ends. At most 16 tool calls, queued messages and pending requests are kept for a worker, and its error, a tool's name and a step's finish are bounded. Activity is reported only once the session's workers have been read, and not while it is read again; activity that could not enter the session's event channel waits and is tried again. A worker's activity is forgotten when its session is deleted.

**When a message is answered.** A user message enqueued in a worker's inbox (`session.inbox.enqueued`) is only queued: no progress answers it, since the worker has not received it, and while a run it was queued behind is still going it is not yet the worker's to answer. It becomes the worker's to answer when the run ends, succeeding, failing or interrupted, without its having been delivered, or at once if the worker was known to have no run going when it was queued; whether a run is going is unknown until its events or records say, as for a worker first seen after a restart, and a message queued meanwhile waits for them. Delivered by an id the queue does not know, a delivery takes the oldest message queued, as the inbox delivers in order. Delivered (`session.inbox.delivered`), it is the worker's to answer from the delivery, and only progress after the delivery answers it, and not progress of a step that was already going when it arrived, which only that step ending, or a step beginning after it, makes an answer possible; a run that ends after the delivery without such progress leaves it unanswered. A message cancelled from the inbox is not waiting. The run ending does not answer a message, so that the order of a delivery and the run's end cannot hide one.

**After the stream is lost, and when first seen.** What happened while the stream was down, such as a tool or a run ending, is in no event that will arrive, so every worker's activity becomes unknown when the stream is lost, and the space is told it is reconnecting, as `agent-backends.md` describes, upon which the server judges none of its workers until they are reported again. A worker first seen other than by its creation, as after a restart, is unknown in the same way. Once the stream reopens and the session has been read again, or as soon as such a worker is first seen, the backend reads the records of the workers whose activity is unknown, after a gap at most 64, those last active first, forgetting the rest until they are active again: each one's latest 20 messages (`GET /api/session/{id}/message?limit=20&order=desc`, which OpenCode 2.2.5 lists newest first, as the backend takes them), its inbox (`GET /api/session/{id}/inbox`) and its pending permissions and forms (`GET /api/session/{id}/permission` and `/form`), each bounded like a snapshot, in turn. From them it establishes the same facts: the latest progress, from each assistant message's `time`; how its last step ended and why it failed, from its `finish` and `error`; the tools still `running` in a message not yet completed, which also says a run is going, as an `idle` record says none is; a user message after the last assistant message, as delivered and unanswered; the inbox's user messages as queued, the worker's to answer from their sending or the end of the last run, unless a run is still going; and the requests it waits on. The events that arrived about it meanwhile, held, at most 256, with a run of streamed progress kept as one, are then applied over what the records say, being newer; a worker that had more keeps what its events said, with the records' progress if later. One whose records could not be read keeps what its events said, or starts again from the time they were read. Only then is its activity reported.

**Failed, unanswered and stalled.** The server judges each worker of a space whose activity it has been told since it started, or since the backend last reconnected, and whose last progress is known, from its state and what it was last seen doing, each time the server looks at its clock, as it does for its timers (`timers.md`), and each time either changes:

- **Failed**, at once, when its backend reports it failed (`WorkerState::Error`).
- Otherwise, not while it is waiting for a permission or a question.
- **Unanswered**, when a message has been the worker's to answer, as above, for 5 minutes (`watch::UNANSWERED`), or for 30 minutes (`watch::STALLED_RUNNING_TOOL`) when a tool was already running when it became so, as for a worker in a long silent build; whatever its state, since a follow-up queued behind a run that then ended, or sent to a finished worker, can be left unanswered too.
- **Stalled**, when it has not finished and has made no progress for 10 minutes (`watch::STALLED`), or for 30 minutes while a tool is running (`watch::STALLED_RUNNING_TOOL`), so that a long build or test run is not taken for a hang; a message waiting on it, queued behind its run or not yet long unanswered, does not stop it stalling, so that a worker sent a follow-up that then hangs is still told, and the note says the message is waiting.

A worker leaves a condition as soon as it no longer holds, as when it makes progress, answers, finishes, runs again or is removed. Each episode of a worker's stalling or leaving a message unanswered that was told doubles its thresholds for the next, up to eight times, until it completes cleanly, with no message left to answer. The thresholds are constants; making them a space's setting is proposed below.

**Told once, together, paced, never mid-turn.** A worker entering a condition is told to the agent once, and again only after it has left that condition, or entered another: one episode, one note; while its activity is unknown, after the backend reconnected, what was told of it stays told. Notes go only through the space's event queue (`timers.md`), as `events::Source::Worker`, so they are never given in the middle of the agent's turn, ride on participants' words queued then, before them, or else wait for the queue's quiet moment and gap, and supersede the words given last as any prompt of notes alone does. They join the queue only at the moment the queue can tell them, when participants' words are queued or a prompt of notes alone may be given, and each worker is judged again then, so that one that recovered meanwhile is not told. Every worker newly in a condition is told in one note for that condition, naming at most 5 and counting the rest. A failure is told as soon as the queue can tell it, rare and urgent as it is, together with the other failures due then; notes about stalled or unanswered workers are told at most once every 2 minutes in a space (`watch::PACE`), those that fall due meanwhile waiting for the next. At most 48 deliveries of notes about workers are made in a space in a day (`watch::DAILY`), and 12 of them while nobody is in it (`watch::UNATTENDED`); on reaching either, the agent is told once that notes about workers are paused, and until when, the time the oldest delivery counted leaves the day, as `[Notes about workers are paused until Wed 14:05, having reached the most for a day, 48; look at the workers tool meanwhile]`, and what falls due meanwhile is neither told nor counted as told, nor doubles a worker's thresholds, but waits to be judged again once notes resume.

**Time.** Times are judged by the wall clock, which the backend's times share, but the server also watches the monotonic clock, which does not run while the computer sleeps: when the wall clock has moved more than a minute beyond it between two looks (`watch::JUMP`), as across a sleep or when the clock is set, every time the watch holds moves by as much, and so do the times of later reports observed before a jump forward, so that the sleep is not taken for workers making no progress.

**How a note reads.** A note is Tomori's, in square brackets, on one line, as the queue makes every note; it says what Tomori saw and its evidence, never what to do. A worker is named by its title, cut to 60 characters, and its backend and session, double quotes and square brackets in either made single quotes and parentheses, and an error from the agent service is cut to 160 characters likewise:

- `[Worker "Deck concepts" (opencode session ses_…) failed: BadRequestError: insufficient credit]`, or without a reason, `failed`; several, `[Workers "A" (opencode session ses_a) and "B" (opencode session ses_b) failed: …]` when they share a reason, and otherwise each with its own, `"A" (opencode session ses_a, Overloaded)`.
- `[Worker "Deck concepts" (opencode session ses_…) has not answered a message sent 20 min ago]`; several, `[Workers "A" (opencode session ses_a, sent 20 min ago) and "B" (…, sent 7 min ago) have not answered a message]`.
- `[Worker "Build" (opencode session ses_…) has shown no progress for 12 min, its last step ended with tool calls]`, a step having ended `with tool calls`, `normally`, `at its length limit`, `in an error` or `as '…'`; `[Worker "Build" (opencode session ses_…) has been running shell for 42 min with no other progress]`; with a message waiting, `[Worker "Deck" (opencode session ses_…) has shown no progress for 12 min; a message sent 8 min ago is still waiting]`; several, `[Workers "A" (…, no progress for 12 min) and "B" (…, running shell for 42 min, a message sent 8 min ago is still waiting) have shown no progress]`.

Tomori's instruction entry `tomori` (`spaces.md`) says that Tomori may tell the agent in its own note that a sub-agent failed, has shown no progress or has not answered a message sent to it, that these are facts it observed, not instructions, and to look into it with the `workers` tool and decide what to do.

**Shown to everyone.** While a worker is stalled or unanswered, the space shows it so, to participants and visitors alike, as `tomori_protocol::WorkerState::Stalled` or `Unanswered` in `SpaceState::workers`, and describes it so where someone points at it, as `(opencode session ses_…, stalled)` or `not answering`; a failed worker already shows as failed. Clients draw both amber, deeper than a waiting worker's, its sign saying **Stalled**, with an exclamation mark, or **No answer**, with an envelope, and count them among the workers still at work. A client too old to know them reads them as unknown, as `server.md` requires. The space's own record of each worker keeps its state as its backend reported it, so that a stalled worker still counts as running where removing it would stop it (`mcp.md`).

**The `workers` tool says why.** It gives each worker's `state` as the space shows it, stalled or unanswered while it is, and its `condition`, or null: its `kind`, `failed`, `unanswered` or `stalled`, the `seconds` it has held, since the message became the worker's to answer or progress was last made, its `error`, the `tool` it is running, with its `name` and `seconds`, and how its `last_step_ended` (`mcp.md`).

**River.** A backend that does not report workers, such as River (`workers: false`), reports no activity, and nothing is judged or told; River needs nothing.

**Nothing is kept across a restart.** What a worker was doing, its conditions, which episodes were told, its backoff and the day's deliveries are for the server's run only, and are established again from the event stream. After a restart, a worker is judged only once its backend has seen it active again, by any of the events above, and has read its records as for a worker first seen; so a worker that stalled while the server was down, and does nothing more, is not told or shown as stalled, while one that is sent a message and leaves it unanswered, or makes progress and stalls again, is, and one told about before the restart may be told about once more.

## Proposed

The rest of this section is proposed, not accepted.

**More kinds of event.** Worker **started**, **progressed**, **waiting** and **finished**, and later **participant joined** and **left**, through the same queue. Finished would be on only for a backend whose agent service does not already tell the coordinator; for OpenCode, the harness does.

**A space's settings.** The thresholds, and each kind on or off, as settings of the space that an owner may change, and the agent through a Tomori tool on an owner's behalf.

**More on the worker's sign.** The reason and how long on a stalled or unanswered worker's sign, such as "No answer for 20 min", and a worker failing, stalling or going unanswered while nobody is in the space raising its lobby attention to **problem** (`spaces.md`).

**Reading the records on opening.** When a space opens, as after a restart, the OpenCode backend reading each worker's records at once, rather than when it is first seen active, so that a worker that stalled while Tomori was not running is judged at once.

## Rationale

In November 2026 the maintainer's coordinating agent, an OpenCode session bound to a Tomori space, delegated to workers that stopped silently, twice. First their model provider refused requests when credit ran out; the harness reported those as errors to the coordinator, but nothing in the space said so. Then, after workers were resumed or sent follow-up messages while running, several sessions never processed them: each one's last message was the coordinator's, with no reply, for 30 to 90 minutes, and one ended with an assistant message finished as `tool-calls` and nothing after. Nobody was told. The maintainer asked for events such as "a worker seems to have gone idle" to reach the agent by default, so that it is told at once that a worker is idle or dead.

Before the first increment, Tomori could not notice any of this. At 9612c31, the OpenCode backend read the global event stream (`crates/backend-opencode/src/connection.rs:2007`), but for a worker it applies only lifecycle events, `session.created`, `deleted`, `renamed` and `session.execution.started`, `succeeded`, `failed` and `interrupted` (`connection.rs:3544-3560`), mapped to running, completed, failed and stopped (`connection.rs:3589-3592`); every other event is routed only to a session a space is bound to (`connection.rs:3457`), so a worker's steps, text, tool calls, inbox and permission requests are dropped. A worker read from the records is running only if its `time.busy` is later than its `time.idle`, and otherwise takes its state from its `outcome` (`crates/backend-opencode/src/wire.rs:414-433`), and is then demoted from running to unknown unless `GET /api/session/active` lists it (`connection.rs:2583-2591`). On the maintainer's service (OpenCode 2.2.5), a worker in the middle of a shell call had neither `time.busy` nor `time.idle` and was not in `/api/session/active`, so a worker the space did not see start is shown as unknown however busy it is. The backend never produces `waiting` or `idle` for a worker. `Worker` carries only its identity, parent, title and state (`crates/backend/src/lib.rs:262-282`), so a failure's reason never reaches the space; `execution_failed` reads it only for the bound session (`wire.rs:291-303`). The `workers` tool reports each worker's session, title, state, whether it finished and how long ago (`crates/server/src/mcp.rs:597-598`, `crates/server/src/hub/agent_workers.rs:175-215`), only when asked, and nothing in the server tells the agent about a worker unprompted. River reports no workers at all (`backend-river/src/lib.rs:18`, `316`, in `tomori-shopify`).

Each of the day's stalls had no event that marks it. A session that never picks up its message, or stops after a `tool-calls` step, emits no `session.execution.failed` or `interrupted`, keeps no `outcome` and writes no idle record, so the lifecycle events Tomori watches say nothing, and the state the space shows stays whatever it was. Observed on the maintainer's service while writing this: one worker's last assistant message held a shell call whose input was still `streaming` 39 minutes after it began, and another's last message was an assistant message finished as `tool-calls` 39 minutes earlier, neither with an outcome. What distinguishes a stall is the absence of progress over time, which needs a clock on the server and a record of the last progress for each worker; Tomori has neither today.

OpenCode 2.2.5 exposes what is needed. Its event stream offers, among others, `session.inbox.enqueued`, `delivered`, `cancelled` and `delivery.changed`, `session.execution.*`, `session.step.started`, `ended` and `failed`, `session.text.*`, `session.reasoning.*`, `session.tool.input.*`, `session.tool.called`, `progress`, `success` and `failed`, `session.retry.scheduled`, `session.shell.started` and `ended`, `permission.asked`, `form.created`, `session.status` and `session.idle` (the `types` of `GET /api/event` in its `/openapi.json`). Its records give each assistant message `finish` (`stop`, `length`, `tool-calls`, `content-filter`, `error` or `unknown`), `error` (a type, message and HTTP status), `retry` and `time` (`created`, `streamed`, `completed`), and each tool call a state of `streaming`, `running`, `completed` or `error` with `time.ran`; a session's inbox lists messages not yet delivered. So, with their latency:

- **A worker failed** is detectable at once from `session.execution.failed`, `session.step.failed` or a completed message with `finish: "error"` and its `error`, and after a reconnection from the record's `outcome: "failed"` or the last message's `error`. A retry being scheduled is progress, and its error is evidence for a later note.
- **A message not picked up** is detectable from `session.inbox.enqueued` or `delivered`, or the last message being the user's, followed by no progress; only a threshold separates it from a slow model, so its latency is the threshold. In the day's cases the inbox was empty and the message was in the history, so the history must be checked as well as the inbox.
- **No progress** is detectable as the time since the worker's last progress event, against the threshold. A running tool is visible, from `session.tool.called` without its end and from a tool in the `running` state, so a long foreground command can be told apart and given longer; a tool whose input is still `streaming` is the model's stream, and counts as no progress.
- **Finished normally** is `session.execution.succeeded` and an `outcome` of `succeeded`. The coordinator is told today by OpenCode's harness, which returns the worker's result to it, not by Tomori, so a Tomori note would repeat it.

The server, not the backend, decides the conditions, so that every backend's workers are judged alike. The backend reports only the few facts the conditions need, rather than forwarding the events, and reports progress at most every 30 seconds, so that a worker streaming text does not flood the space's channel, while thresholds of minutes stay accurate to within half a minute. Notes go through the same queue as timers so that the agent is interrupted by one mechanism with one set of rules for turn-taking, and so that a person's words are never made to wait behind Tomori's. They are data in Tomori's square brackets because the evidence includes text written by an agent service and by workers, which must not be able to pose as instructions or as a participant (`spaces.md`, `security.md`). Judging a worker again as its note is told, and telling each episode once, keeps the agent from acting on stale news or being nagged; the worker's colour keeps the condition visible for as long as it lasts. Coalescing keeps a storm, such as every worker failing as credit runs out, to a note, and the 2-minute pace, on top of the queue's 30-second gap, keeps stalls from nagging, while a failure, rare and urgent, is not held to it; the daily and unattended caps and the backoff bound what a worker that keeps stalling can cost, as the timers' limits do. In November 2026 the maintainer accepted the proposal's first increment, failed, unanswered and stalled for OpenCode, with the thresholds as constants, the pace, the amber and red stations and the `workers` tool's evidence, and no persistence. Its independent review then found that any progress answered a message, even before its delivery, so that a follow-up queued while a worker ran and never processed, this morning's very case, was never told; that a success missed while the stream was down left a worker's message or tool standing for good; that a worker first seen by a reply to a request was judged from the epoch; that a sleep counted as time without progress; that a single flag lost track of several pending requests; and that a failure waited behind the pace. Hence when a message is answered, the records read again after a gap, a known last progress, the monotonic clock, requests kept by id, failures told at once, and the caps and backoff above. Its confirmation found that a follow-up queued while a worker ran stopped it being judged at all until the run ended, so that a worker that then hung was never told; that a worker waiting on a permission across a gap looked stalled; that the agent was never told notes were paused at the cap; and that a worker first seen after a restart by a queued message was taken as idle. Hence a waiting message not stopping a stall, the requests read with the records, the note that notes are paused, and a worker first seen read as after a gap. Reading the records was checked against the maintainer's OpenCode 2.2.5 service: `limit=20&order=desc` answers the 20 latest, newest first, with a `cursor`, and the assistant, user and `idle` records and their tools have the fields above.

## Scope

`tomori-backend`'s `WorkerActivity`, `RunningTool` and `Event::WorkerActivity`; `tomori-backend-opencode`'s `activity.rs` and its use in `connection.rs`; `tomori-server`'s `watch.rs`, the space's watch in `space.rs`, the event queue's worker source in `events.rs`, the clock in `hub/agent_timers.rs`, the `workers` tool in `hub/agent_workers.rs` and `mcp.rs`, and the `tomori` instruction entry in `instructions.rs`; `tomori-protocol`'s `WorkerState::Stalled` and `Unanswered`; and their drawing in `tomori-scene`'s `delegation.rs` and `tomori-render`'s `workspace_graphics.rs`.

## Validation

- `crates/backend-opencode/src/activity/tests.rs` tests that a follow-up queued behind a run that streams on and ends without taking it up is unanswered from the run's end; that a message delivered and followed by the run's end, without progress, is unanswered from its delivery; that progress after a delivery answers it, but not progress of the step it arrived in; that cancelled, non-user and repeated messages are not waiting, and queued ones are bounded; that a worker first seen by a reply has progressed no earlier than then, and one first seen by a queued message is read before it is judged, the events held meanwhile applied over its records, too many keeping what they said; that a delivery by an unknown id takes the oldest queued; that the records say which requests a worker waits on; that it waits while any of its requests is pending; that the records say what a worker was doing; that after the stream is lost nothing is reported until the records are read again, a success missed in the gap leaving no tool running, a worker with events since keeping them, and one whose records could not be read starting again from then; that only the workers last active are read again; and that a tool runs from its call to its end by the name its input gave, a call never announced is a tool all the same, and a call whose input is being written is not running; that a step's finish is kept; that a failure says why, from the run's error or else the last step's, until the worker runs again; that calls are bounded; and that a worker is reported as it changes, and again only as its progress moves on by 30 seconds, waiting when refused and forgotten when unknown.
- `crates/backend-opencode/src/connection.rs` tests, with the events the stream sends, that a known worker's activity reaches its session after the session's workers are read and not while it is read again, that an event about an unknown session or saying nothing of activity changes nothing, and that a deleted worker is forgotten; and, against a simulated service whose stream is lost while a worker runs a tool, that the space is read again first, then the worker's records, so that the success missed in the gap leaves no tool running, the follow-up queued meanwhile is known, the permission raised meanwhile leaves it waiting, and the records, newest first, are read oldest first, a worker whose records do not answer in time starting again from when they were read. `api.rs` tests reading a worker's latest messages, inbox and pending requests. A worker first seen other than by its creation is read once.
- `crates/server/src/watch/tests.rs` tests the conditions with the time given: a failure told at once with its reason, and a worker never seen active since the server started not judged; a message unanswered at 5 minutes and not before, and not while waiting, or at 30 minutes when a tool was running, saying when it was sent, and a message still queued behind a run not unanswered, but not stopping a worker that hangs from stalling, at 10 minutes or 30 with a tool running, the note saying the message is waiting; a stall at 10 minutes, and not before 30 while a tool runs; a finished or waiting worker not stalling; recovery ending an episode and a new one told again, after twice as long, up to eight times, until the worker completes cleanly; a worker recovered before it is told not told; workers in one condition told in one note naming five and counting the rest; several conditions a note each; the 2-minute pace for stalls, a failure told at once; the daily and unattended caps, the agent told once that notes are paused and until when; a sleep or a jump of the clock not counted as time without progress; nothing judged while activity is unknown, or without a known last progress, and what was told staying told; and what a note says, bounded, with no square brackets.
- `crates/server/src/hub_tests/watching.rs` tests through the hub, with the fake backend's events: an unanswered worker shown so to everyone mid-turn, with nothing told until the turn ends and the queue's quiet moment passes, then told once alone, described so when pointed at, and shown running again once it answers; failures riding on participants' words, the second told at once, not held to the pace; a stalled worker running a tool shown so only after 30 minutes; and the `workers` tool's state and condition.
- `crates/scene/src/delegation.rs` and `crates/render/src/workspace_graphics.rs` test that stalled and unanswered map to their station states, amber and still at work, with signs and symbols of their own.

## Open questions

- Are 5 minutes unanswered, 10 minutes stalled and 30 minutes with a tool running the right defaults, and should the agent be reminded once more while a condition lasts, or is the amber worker reminder enough?
- Should Tomori ever tell the agent that a worker finished for OpenCode, for instance when the harness's own notice demonstrably did not arrive, and how would the server know that it did not?
- Should a note be delivered while nobody is in the space at all, within the unattended cap, which starts the agent's turn unattended, or held until a participant joins?
- Should a stalled or unanswered worker be offered, to an owner, a way to nudge, interrupt or remove it from its station?
- OpenCode's `/api/session/active` did not list a running worker on the maintainer's service, and the record had no `time.busy`: should the backend treat a worker's recent progress as its evidence of running, rather than demoting it to unknown?
